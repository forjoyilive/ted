# Apps run in detached hosts the Tasks module owns

An App (spec §9.6) is a long-running command from `repos[].apps` in `workflow.yaml`, such as a dev server. Only `packages/daemon/src/apps/apps.ts` starts, stops and reads Apps; the Tasks module creates it and is its only caller, so the human (`POST /tasks/:id/apps/start|stop|restart`, app-only except start), `ted run-app` (start, open to a Run of the same Task) and the Task’s lifecycle all go through one place.

- **Hosts.** Each App runs in its own detached host, `packages/daemon/src/apps/host.ts`, started through `nodeEntry` like a Run host. The host holds `host.lock`, starts `/bin/sh -c <run>` in a new process group in the repo’s worktree, writes `host.jsonl` (`start`, `exit` records) and the App’s output to `app.log`, and on SIGTERM, SIGHUP or the end of `TED_EXIT_WITH_PID` kills the whole group (SIGTERM, then SIGKILL after 5 s). When the App’s own process exits, the host kills what is left of its group. Everything lives in `TED_HOME/apps/<task id>/<repo>/<app>/`.
- **Survives the daemon.** A restarted daemon reads `instance.json` and `host.jsonl` and watches every App that hasn’t ended. A host that is gone without an `exit` record counts as a crash. The daemon signals a host only while it holds its lock, so a reused PID is never signalled.
- **Environment.** An App’s environment comes from `worktreeCommandEnv` (ADR 0071) with the repo’s `worktree.env`, the App’s own `env` (where `${PORT}` and `${TED_APP_<NAME>_…}` are filled in), every `TED_APP_<NAME>_PORT`/`_URL` of the Task, `PORT` and `TED_TASK`. No `TED_RUN`, `TED_HOME` or agent credential reaches it. The host is spawned with that environment plus the test markers, so nothing secret is written to disk. Outside Bypass the host runs the App inside the OS sandbox of ADR 0091-agent-started-checks-and-apps-run-sandboxed, with its own temp folder in the App’s folder.
- **Ports.** Ports are picked per App per Task and kept in `ports.json`, so a Run started before the App already knows `TED_APP_<NAME>_PORT`. A free port is one Ted can bind on `127.0.0.1` and that nothing answers on. A fixed `port:` that is taken fails the start with a clear message and a thread event; a picked port that became busy is replaced. Ted never binds a public interface; it only checks ports on loopback.
- **Ready.** A `web` App is running once its `url` answers with a status below 500 (probed on loopback only; certificate errors are ignored because nothing is sent). After 5 minutes without an answer Ted stops it and records the failure. `ready: start` and `command` Apps count as running once started. The `url` must be an `http(s)` address on `localhost`, `127.x.x.x` or `[::1]`; `workflow.yaml` validation refuses anything else, and the app opens only such a URL (or the pull request’s hosted preview) in the default browser.
- **Logs.** The host keeps the last 10 MB as two halves, `app.log` and `app.log.1`. The App log view reads the last 512 KB.
- **Lifecycle.** Apps don’t take working-Run slots. Starting one checks `store.newWorkHold()`. `finish` (Done, archive, delete, Factory removal) stops the Task’s Apps and deletes its App folder before teardown; removing a repo from the Task stops that repo’s Apps. The thread gets `v1.AppStarted` (also for restarts), `v1.AppStopped` (only the human’s), `v1.AppExited` (a crash) and `v1.AppStartFailed`.
- **Kinds.** `web`, `command` and `ios-simulator` share one runner. An `ios-simulator` App first gets a booted simulator from `apps/simulators.ts` (ADR 0085-ios-simulator-apps) and runs with `TED_SIMULATOR_UDID` instead of a port.

## Considered Options

- **Run Apps inside Run hosts.** Rejected: Apps outlive Runs and are shared by the human and every Run of the Task.
- **Keep App state in the store.** Rejected for now: a running App is a fact about a process, which the host files already record; the store only gets the thread events.
