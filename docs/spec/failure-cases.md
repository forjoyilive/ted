# Failure cases

A Failure case records one failure independently of factual Check runs and original Findings. It belongs to a Task, survives daemon restart and a fresh Task Lead Run, and keeps the source, bounded evidence, tested context, assessments, recommendations, human requests, resolutions and observed invalidations.

This foundation creates cases only through explicit API operations. Factory Checks, reviewer Findings, post-rebase Checks and GitHub CI retain their existing behavior until their consumers adopt the operations. A Task with no cases takes its existing advancement and merge paths without additional context capture or GitHub work.

## Operations and authorization

All paths start with `/tasks/:id`. DaemonClient exports matching typed operations.

| Method and suffix | Caller | Purpose |
| --- | --- | --- |
| GET /failures | App, file token, or own-Task Run | Read every case and its history |
| GET /validation-obligations | App, file token, or own-Task Run | Verify context, durably invalidate stale consent, return independent blockers |
| GET /failure-contexts/:contextId | App, file token, or own-Task Run | Inspect the referenced tested revision and hashes |
| POST /failure-contexts | Current Task Lead | Capture context before executing or observing the result |
| POST /failures | Current Task Lead | Record source, evidence and optional contextId |
| POST /failures/:caseId/evidence | Current Task Lead | Append evidence and optional new tested context |
| POST /failures/:caseId/assessments | Current Task Lead | Append regression, unrelated or uncertain assessment and recommendation |
| POST /failures/:caseId/decision | Current Task Lead | Ask the human about the latest assessment and its context |
| POST /failures/:caseId/resolve | App only | Resolve the linked requestId as accepted, fixed or no-longer-applicable |

App and file tokens cannot impersonate the Task Lead. A sub-agent, previous Task Lead or another Task’s Run cannot mutate a case. Resolution routes have neither runToken nor fileToken permission. The existing app-only `POST /comments/:id/answer` uses the same resolver with the exact choices **Accept this failure**, **Fixed**, and **No longer applicable**. Fixed and No longer applicable require a reason. A textual reply posts a human Comment, including line-comment drafts, and leaves the decision open.

A source identifies a Factory Check or post-rebase Check by checkRunId and zero-based position; a Finding by originating runId and original text; or GitHub CI by repo, pull request number, head and attempt. Check references must belong to this Task, identify failed or timed-out execution and match the trigger. The saved snapshot comes from the store. Finding and CI evidence is explicitly Task Lead reported, with recordedBy provenance; TED does not claim to have independently verified it. CheckRun.outcome, CheckResult.state and ValidateJudged are never changed by these operations.

Recording, assessment and human acceptance are separate writes. A decision requires an assessment, is linked atomically to one question Comment, and binds that exact case, assessment and context. Resolution and one CommentAnswered are committed together, with the human’s line-comment drafts. Duplicate, stale, withdrawn and already answered requests return 409. A newer assessment or evidence withdraws the previous question; withdrawal does not close the case. New acceptance following invalidation requires a fresh assessment and request. Fixed and No longer applicable close this case explicitly; a later failure is a new case.

## Tested context

Contexts are generated by the daemon, versioned and referenced by ID. They bind every active Task repo’s identity, HEAD, base tip, merge-base and complete scratch-index worktree tree, including tracked edits, deletions, binary files and nonignored untracked files. They use workingChanges and never trust the worktree’s index or diff output. Ignored dependencies, build artifacts and other normally ignored paths are outside this boundary. Git tree identity covers submodule references rather than files inside a submodule.

The context also hashes resolved Check definitions (commands, timeouts and repo selection) and applicable Check environment, including repo settings and the inherited command environment. Raw environment values and diffs are never persisted in context. Resolved Workflow settings come from the Library and Factory default branch, as usual; editing a worktree’s .ted files changes its tree identity before those settings become active. HEAD and base identities invalidate consent after rebases even when file content stays identical.

Where pull requests exist, the existing GitHub poller supplies the current head and every Check/status identity, attempt timestamps and state. Same-SHA reruns and pending replacement attempts change context. Missing identity, unavailable reads or truncated Check lists cannot establish current consent. Merged pull requests remain polled until Done where explicit cases need their context. Decision and merge boundaries refresh through watch.next; there is no second GitHub client or poller.

Callers capture context before execution and supply that ID with the result. A Check’s context cannot have been captured after execution began. This explicit capture is a caller’s assertion of which execution used the context; legacy Check runs have no independent execution-to-context attestation. Without a reliable capture, omit contextId. Unknown-context cases hold and cannot be accepted; the human may close them with a reason. Evidence additions may reference a new explicit capture, followed by a new assessment and decision. They do not change the original source or original Check snapshot.

Evidence, Findings, recommendations and reasons pass through redactSecrets and are bounded to 16,000 characters. Credential-bearing HTTP links and links containing credential query parameters are refused. Submit a concise redacted explanation and stable source reference, never full logs, credentials or environment dumps.

## Obligations and holds

validationObligations returns satisfied, cases (each with disposition and context state), blocker IDs, and factual checkRuns with their unchanged passed, failed or interrupted outcomes (an unfinished run has no outcome). The satisfied flag covers the explicitly recorded case obligations. Unresolved and invalidated cases block. Accepted means a human decision remains effective in current context; it never means passed. Fixed and No longer applicable are explicit closures. Consumers must continue to check factual execution and all existing Workflow and merge prerequisites.

An observed context mismatch or read failure appends a durable invalidation. Returning to a previously accepted fingerprint never revives consent. The poller observes changes while watching GitHub; decisions and movement verify again. Changes that occur and are reverted entirely between observations cannot be detected.

Tasks serializes mutations and decisions with movement, guards forward advancement, skip, Gate approval, move-anyway, no-Merge completion and Done, and checks again before each remote merge or enable-auto-merge action. Repair, discussion and send-back remain available. Each case resolves independently.

Opening a case or invalidating consent disables auto-merge that TED previously enabled. If GitHub refuses, the hold remains saved, the API reports the failure and polling retries. External merges remain factual and are never reverted. A human or GitHub can complete a remote merge already issued before a new failure arrived; TED cannot retract that race, but it still holds forward completion. Multi-repo merge rechecks obligations between repos and retains existing partly-merged behavior.

## Storage

Versioned FailureContextCaptured, FailureCaseRecorded, FailureEvidenceAdded, FailureAssessed, FailureDecisionRequested, FailureResolved and FailureAcceptanceInvalidated events materialize contexts and cases. Each case snapshot retains append-only history; request and resolution linkage is committed with its Comment event. The area’s routes parse requests, Tasks owns authorization and lifecycle, and only store/ imports LiveStore. Task removal deletes both materialized tables through the existing removal path. Store replay rebuilds the same decisions and holds.
