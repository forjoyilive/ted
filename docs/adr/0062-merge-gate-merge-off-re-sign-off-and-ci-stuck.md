# Merge Gate, Merge off, re-sign-off and CI stuck run in the merge watcher

The merge watcher from ADR 0056-ted-merges-pull-requests-at-the-merge-stage now runs for every Task at Merge, whatever the Merge settings, and in one of four modes worked out each cycle from the Workflow and the Task’s log (`mergeMode` in `packages/daemon/src/tasks/merge-watcher.ts`):

- **merge**: Merge on with no Merge Gate, or the Merge Gate approved this visit. Ted merges as before.
- **gate**: Merge Gate on and not yet approved. The cycle is the same up to the point of merging: CI failures, conflicts, rebases and changes after sign-off are handled as in merge mode, but auto-merge is never turned on. When every open pull request has passed CI and is mergeable (a missing GitHub review doesn’t hold it back), Ted posts the Merge sign-off itself, as a `signoff` Comment from Ted at Merge. Its `gate` carries one row per pull request (`MergeRow`: repo, number, title, check counts, mergeable, merge method, review missing) and, when the human approved an earlier sign-off, `changes` since then; with no earlier approval the card carries the brief instead. Approving it switches to merge mode, which merges at once. The Task Lead no longer posts the Merge Gate, and `ted outcome advance` is refused at Merge in every mode.
- **off**: `stages.merge.enabled: false`. A Task that would go to Done from a Stage before Merge goes to Merge instead, so it keeps its worktree, Task Lead and blockers. The watcher only reads the pull requests, shows Waiting for merge, records the merges it sees, and moves the Task to Done when none is left open. Done Tasks that still have an open pull request (from before this change) are watched the same way at daemon start, so the Tasks they block wake when GitHub reports the merge.
- **canceled**: the human sent a Comment while the merge was pending, or asked for changes at the Merge Gate. Ted neither merges nor posts another Merge sign-off in this visit; the watcher only keeps trying to turn GitHub auto-merge off, then stops.

**Merge pending and Send and cancel merge.** `v1.MergeStarted` is logged when Ted starts merging in a Merge visit, and `v1.MergeCanceled` (with the Comment) when the human cancels. The store shows the comment box as `merge-pending` while the last of these in the visit is a start and a pull request is still open. While it is pending, the plain Comment route refuses a human Comment; the app sends it to `POST /tasks/:id/cancel-merge` (app key only), which posts the Comment, logs the cancel, waits for any merge cycle in flight, turns off GitHub auto-merge on the Task’s pull requests (`gh pr merge --disable-auto`, recorded as `v1.PullRequestAutoMergeDisabled`), and tells the Task Lead. If GitHub won’t turn auto-merge off, the cancel fails closed: the route answers 502 saying GitHub may still merge, the activity line says auto-merge is still on, and the watcher retries every cycle until it is off. Each merge checks the mode again just before `gh pr merge`. The cancel counts as Request changes: `ted outcome advance` is refused until the Task Lead sends the Task back to Work or Design, and that send-back doesn’t count toward `max_back`.

**Re-sign-off.** When the Task Lead posts the sign-off whose approval leads to Merge, and the human approved an earlier one, the card’s `gate.changes` lists what changed since: `since` (the earlier approval), an optional one-line `summary` from `ted outcome advance --changes "…"`, and per repo the changed files with +/− counts. Only values Ted trusts go in: the approved commit per repo is the first `v1.PullRequestSignedOff` commit recorded after that approval (now kept in the Task log), and the new commit is the one Ted pushed (or the signed-off one at the Merge Gate), never the worktree’s head. `changesBetween` in `git.ts` diffs them; when the new commit isn’t a descendant (the Task Lead rebased), it replays the approved work onto the new commit’s base with `git merge-tree`, conflicts included, so what the base added doesn’t show. The base tip comes from a Ted-owned `fetchBranch` of the base branch, never the worktree’s `origin/*` refs, which the agent can move; if that fetch fails, it diffs the two commits directly, which shows more, never less. All of it runs in a temporary bare repo that borrows the clone’s objects, so no config, filter or diff driver from the worktree runs. A repo Ted couldn’t compare says so on the card, and the card then shows the full brief too. The approval still records a new signed-off commit, and Ted merges only that.

**CI stuck.** For a repo with CI, the watcher asks a `question` from Ted when no check has appeared 10 minutes after the last push (or rebase), or a relevant check is still queued or pending 60 minutes after it. The choices are **Send to Task Lead** (back to Work with what Ted saw, not counted toward `max_back`), **Keep waiting** (asks again 60 minutes after the answer) and **Merge anyway** (only when no required check is pending; CI counts as passed for that push). A free-text answer goes to the Task Lead and also waits another 60 minutes. The question doesn’t hold the watcher back, and Ted withdraws it (`ciReported`) once CI reports. A CI-stuck question is a Ted `question` at Merge whose choices include Keep waiting. The times come from `ciStuckMs` in `startDaemon`, for tests.

## Considered Options

- **Keeping the Task in Review under Merge off.** Rejected: the spec’s status table puts Waiting for merge at Merge, and a Task in Review looks like it still needs a sign-off. A disabled Stage that is current shows as current on the Stage track.
- **Diffing the approved commit straight against the new head.** Rejected: after a rebase it lists every file the base changed.
- **Holding the watcher while the CI-stuck question is open.** Rejected: CI often reports while the question waits, and Ted should then merge (or post the Merge sign-off) without making the human answer.

## Consequences

- Partly merged and merging several repos in order come with KRI-132.
- A free-text answer to the CI-stuck question resets the wait like Keep waiting.
- If GitHub merges through auto-merge between the cancel and `--disable-auto`, the Task stays at Merge with a merged pull request until the Task Lead sends it back.
- Posting a re-sign-off waits for the Task’s pull request queue and one fetch of the base branch per repo.
