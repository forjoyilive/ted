# Runs and Providers

Rules for Runs, their hosts, output and messages, and the Provider CLIs (`packages/daemon/src/runs/`, `agents/`, `health/`). They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- A human message to a working Run is held in the store and delivered only by `packages/daemon/src/runs/steering.ts`, at the agent’s next tool-call boundary or when the turn ends; never write it to the agent early, and never as a hook’s `additionalContext` (ADR 0052-steering-holds-queued-messages-in-the-daemon).
- Agent health lives in `packages/daemon/src/health/` and uses `cli-env.ts` and `terminal.ts` like GitHub and Git health; a fix command opens in the user’s own terminal, never Ted’s. A kind that isn’t Ready is paused in the store, and a Task Lead that can’t start is held and started again when the kind is Ready; what a CLI prints for its version, login and auth errors stays in its `agents/` module (ADR 0033). Tests set a stub’s health with `TED_HOME/stub-claude.json` or `stub-codex.json` (`{"signedIn": false}`, `{"version": "2.0.0"}`).
- Antigravity under Subscription billing starts only after the human has turned on the `antigravityPlanAccepted` machine setting from Settings → Providers, because Google’s terms treat using Antigravity through other software on a Google plan as a breach. `launchBilling` in `runs/run-manager.ts` refuses every such launch and Antigravity’s health check reports the notice as a problem; never add a launch path that skips `launchBilling`, and never set the setting from anything but the app (ADR 0125-antigravity-on-a-google-plan-waits-for-the-human).
- A usage limit, being offline or a Run using an API key under Subscription pauses an agent kind only through the agent health monitor, which composes every cause into the one reason `pauseAgent` stores; what a CLI’s output says about limits, retries, credentials, plan usage and cost stays in its `agents/` module. Billing is the `billing` machine setting; under Subscription the agent module removes the key variables. Tests never reach the network or a billing or usage API: `TED_ONLINE_FILE` (set in `vitest.config.ts`) or `startDaemon`’s `online` option decides online, and the stubs emit limit and usage lines (ADR 0057-usage-limits-offline-and-credentials-pause-an-agent-kind).
- To send a live Run a message, use `RunManager.send`, which appends to the Run’s `input.jsonl`; the host forwards it to the agent’s stdin (ADR 0019).
- An idle Task Lead, sub-agent, Coordinator chat or planning chat Run goes to sleep: after `sleepIdleRunsAfterMinutes` (machine setting, default 10, `null` for never; 2 minutes, or less if the setting is less, while `store.busyHold()` is set) `runs/idle-sleep.ts` has `RunManager.sleep` end its host and agent, and the Run stays `idle` with `asleep: true`, the same ID and session. Only `sleepKind` and `maySleep` in `runs/idle-sleep.ts` decide which Runs may sleep: Claude Code or Codex with nothing queued, and per kind the current Task Lead with no sub-agent that isn’t idle and `Tasks.midWork` false, a sub-agent whose parent and Task are live, or a chat its owner’s `mayRest` allows (`Coordinators`, `Plans`); anything new that a Task Lead waits for without a working turn adds its case to `Tasks.midWork`, and a new kind of Run may sleep only once it has a `sleepKind`, a `mayRest` and an environment source. The only record is `asleep.json` in the Run folder, which `RunManager` reads when it starts following a Run; there is no event, and the store’s flag is in memory (`setRunAsleep`). A sleeping Run is woken only inside `RunManager`, by `send`, `steer`, `dispatch` and `restart`, through the host replacement path (`prepareReplacement`: resumed session, `runPermissions`, `launchBilling`, a fresh launch authority), and a wake waits while `store.newWorkHold()` is set. A wake takes the Run’s environment from memory or, after a daemon restart, from the owner’s `runEnv` (`Tasks`, `Coordinators`, `Plans`) through `RunManager.envSource`, never from the Run folder’s `env.json`; a wake that keeps failing is retried and shown as the `run-wake-failed` banner from the `wakeFailed` and `woke` observers in `daemon.ts`. Never append to a Run’s `input.jsonl` another way, or a sleeping Run won’t see it. A sleep or a wake is never a Run ending: don’t route it through `recover`, `revive` or `store.reviveRun`, and don’t count it in `failureHistory`. Code that looks for a Run’s processes uses `currentHostPid` and skips Runs with `asleep`. Tests drive the clock with `startDaemon`’s `idleSleep.now` and a short `checkEveryMs` (ADR 0172-an-idle-task-leads-agent-is-ended-and-started-again-on-the-next-message, ADR 0187-idle-sub-agents-and-chats-sleep-too-and-sooner-while-the-computer-is-busy).
- A Run’s output lines live only in its `runs/<run-id>/host.log`; the store holds no lines. `store.recordRunOutput` commits `v3.RunOutputRead` (the read offset and the last output time) only together with another event the lines led to (a state, session, problem, retrying or ending change, auto mode unavailable, a permission Comment asked or withdrawn); a batch that leads to none commits nothing, the store holds its offset in memory and `RunManager` writes it to the Run’s `read-offset.json`, which it reads when it starts following the Run again, so read the offset and last output time only through `store.runReadOffset` and `store.lastOutputAt`, never from the `runs` row (ADR 0120-the-read-offset-is-an-event-only-with-another-change), and `v1`/`v2.RunOutputRead` materialize only the offset and time. Read a Conversation only through `RunManager.output` (`runs/run-output.ts`), which reads `host.log` up to the Run’s read offset: `entries`, or `last` and `findLast` when the newest lines are enough. Code that reads every line of a Run again and again (the Run chat, Run summaries, `inputAccepted`) goes through `parsedOutput` in `runs/parsed-output.ts` instead: it is an `output.fold`, a value kept beside the cached lines that is given only the lines added since the last call and is dropped whenever the cached lines are dropped or read again from the start, so it never holds anything the lines don’t. A finished Run’s tokens, credential and cost are remembered in `conversations.ts` under `output.stamp` (the file’s inode and size and the read offset), so pruned or cut output changes them. A missing `host.log` gives an empty Conversation and a cut one gives its tail, never an error; the Run chat then shows a “From Ted” row saying so (ADR 0097-run-output-lives-in-host-log).
- A Run’s start is `v5.RunStarted`, which holds its prompt as `promptParts`: its own text, `{ hash }` for a shared text in `promptTexts` (`v1.PromptTextSeen`, committed with the first start that uses it, kept for good) and `{ request }` for a sub-agent’s instructions, which `v2.SubAgentRequested` keeps in `subAgentInstructions` after the request row goes. `splitPrompt` in `store/prompt-parts.ts` builds the parts from the texts `RunManager.start` is told may be shared (`fixedPromptTexts` and `taskLeadSharedTexts` in `workflow/workflow.ts`) and keeps the prompt whole unless they join back to the same text. Read a Run’s prompt only through `store.runPrompt`, never `runs.prompt`; `Run.prompt` is filled only by `GET /runs/:id`, never in events or lists. Old `v4.RunStarted` events are not rewritten (ADR 0157-run-starts-store-shared-prompt-text-once).
- When a Run finishes, `conversations.ts` saves what it used as `v1.RunUsageRecorded` (tokens and the cost from the agent module’s `costOf`, whatever the billing), because the output it is read from is deleted later. `store.apiCost(days)` and `GET /agents/api-cost` sum those rows per agent, and Settings → Providers shows them as what the Runs would cost on an API key. Never work these totals out by reading old Run output. Codex’s cost comes from the price table in `agents/codex.ts`; keep its date and source comment current (ADR 0126-a-runs-use-is-saved-when-it-ends).
- What an agent CLI’s output lines mean for the Run chat lives in that agent’s `chatFrom` builder in `packages/daemon/src/agents/`, which takes one line at a time (`chat` runs it over a whole list); `runs/conversations.ts` builds the chat items from the Run’s row, messages and permission Comments on every call, so only the parsed lines are kept between calls. A `run-output` event carries `lines: true` when it is new agent output; the app’s chat hooks reload at most once a second for those and at once for every other event, and a message typed into a Run chat goes only through `Conversations.send`, never as a Comment. Files copied or ported from agent-orchestrator say so at the top and say what Ted changed (ADR 0043).
- Code that knows how a particular agent CLI starts or what its output means lives only in `packages/daemon/src/agents/` (ADR 0014). Codex runs as `codex app-server`, driven by `agents/codex-driver.ts` inside the host (ADR 0018). The host’s `launch.json` and `host.log` formats only ever gain fields, because a running host can outlive a daemon update (ADR 0013).
- Permission prompts come only from an agent module’s `permissionPromptFrom` and are answered only through `RunManager.answerPermission`, which tags the reply with the agent generation; never write a reply to `input.jsonl` another way, and never add a route that answers one with a Run token. Under `auto` the Claude Run’s `settings.json` allows only `Bash(ted *)`; don’t widen it (ADR 0047-permission-prompts-become-permission-comments). Under `auto` Codex gets `approvals_reviewer="auto_review"`, so its own reviewer decides requests for access outside the sandbox, such as a commit’s write to the clone’s git metadata; don’t make the clone’s `.git` a writable root instead (ADR 0121-codex-reviews-its-own-approvals-under-auto).
