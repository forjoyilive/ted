# An idle Task Lead’s agent is ended and started again on the next message

Every live Run keeps its whole process tree: the Run host (30 to 60 MB), the agent CLI (about 600 MB for Claude Code) and the MCP servers the CLI starts from the user’s config. On a 36 GB Mac with 11 live Runs, 9 of them idle for hours, that was about 9 GB held by Runs that were only waiting for the human, with swap nearly full.

**An idle Task Lead Run goes to sleep.** `runs/idle-sleep.ts` checks once a minute. `maySleep` there allows a Run only when all of this holds: it is the current Task Lead of a Task that is not archived, stopped, in Backlog or Done; its state is `idle` (so no turn is working and no permission prompt is open), with no `problem`; it has a session ID; its agent is Claude Code or Codex; it has had no output for `sleepIdleRunsAfterMinutes` (a machine setting, default 10, `null` for never, 1 to 1440); no sub-agent of it is live; no Run message is queued for it and its Task has no pending Task Lead messages; and `Tasks.midWork` says the Task is not in the middle of anything (`tasks/in-flight.ts` kinds other than `merging`, a Task Lead restart being applied, a working sub-agent, a queued sub-agent request, a loop check or a Check run). Nothing sleeps while `store.newWorkHold()` is set, because a Run that can’t be started again must not be ended.

**Sleeping ends the host and the agent.** `RunManager.sleep` checks again that nothing has been written to the Run’s `input.jsonl` since the idle time began, that no input is still unanswered and no delivery is in progress, writes `asleep.json` in the Run folder (the size of `input.jsonl` at that moment), and sends the host SIGTERM, the same way an outdated host is replaced (ADR 0078). The host ends its agent, which ends its MCP servers, and exits; if it still holds its lock after the stop grace period, Ted kills it. The Run’s row doesn’t change: it stays `idle`, with the same ID, session and Conversation. The exit record is not read as an ending, so no Run ending is recorded, `recover` never sees it and `failureHistory` doesn’t count it.

**No event.** Being asleep changes nothing the store has to remember: the only durable fact is `asleep.json`, which `RunManager` reads when it starts following a Run. With the file there and no host holding the lock, the Run is asleep and stays so across a daemon restart; with a host still holding the lock after the grace period, the file is stale and is removed. The store keeps the flag in memory (`setRunAsleep`) and puts `asleep: true` on the `Run`, so the app and `ted dev memory` can say so. The app shows nothing different for now.

**Any input wakes it.** `RunManager.send`, `steer` and `dispatch` are the only ways a message reaches a Run, and each wakes a sleeping one first, so no caller has to know. Waking is the host replacement path: `prepareReplacement` builds a new launch that resumes the session with an empty prompt, under the Run’s permission lock, with `runPermissions`, `launchBilling` and a fresh launch authority, and a new host starts. `send` and `steer` wait until the old host is gone, append their line and return; the new host reads `input.jsonl` from the size recorded in `asleep.json`, so the line is delivered once. `dispatch` waits for the new agent to start, because its lines are tagged with the agent generation. A wake waits while `store.newWorkHold()` is set, and `dispatch` is refused then. A wake that fails is logged and tried again, after the stop grace period at first and at most a minute apart. A Run that was just woken, or has input its agent hasn’t answered, doesn’t go back to sleep until the agent has produced output.

**A wake takes no slot.** It is the same Run resuming, it stays `idle` until its agent starts a turn, and `slotUse` counts working Runs by state as before. An agent kind that is paused can still be woken; whether a message is delivered to a paused kind is decided where it always was.

**Restarts.** `RunManager.restart` on a sleeping Run records the new model and effort and wakes it. `version-restarts.ts` skips sleeping Runs: the next wake starts the installed version anyway. Stopping a sleeping Run ends it as `stopped` without starting anything.

**Setting.** Settings → Limits has a switch, **End idle Task Lead agents to free memory**, and while it is on a stepper for the idle time in steps of 5 minutes. Turning the switch on sets the default.

**What a wake trusts.** A wake happens far more often than the host replacement it reuses, so it takes less from the Run folder on trust. `RunManager` keeps the environment each Run was started or revived with in memory and a wake uses that copy. After a daemon restart a wake asks the Tasks module for it again (`Tasks.leadRunEnv`, through `RunManager.envSource`: the recorded setup environment, the Task’s App variables and `TED_TASK`, as a revive builds it) and never reads `env.json`. A host replaced for another reason (a host protocol change after an update, which no Run can bring about) still reads the file, and drops every name a Workflow couldn’t set either (`isReservedEnvName`: `NODE_OPTIONS`, `PATH`, the loader and agent prefixes), keeping `TED_` names. A sleep marker counts at daemon start only for an idle Task Run with a session. The forced kill after a sleep reaches the agent’s PID only if it was the host’s child when the sleep began. A restart of a sleeping Run is refused before anything is recorded when the wake would be refused.

**A wake that fails.** When the new host can’t start, `RunManager` keeps trying, at most a minute apart, and the Run stays asleep; an agent that can’t start under a host that did start ends the Run, which goes through `recover` as usual. From the second failed try the daemon shows a warning banner (`run-wake-failed`, kept in memory, one per Run) that names the Task and says Ted keeps trying; it goes when the agent starts or the Run ends.

**Diagnostics.** `ted dev memory` and Settings → Developer find a Run’s processes from the host’s current PID file, not the first start record, and leave sleeping Runs out; `MemoryUse.asleepRuns` counts them.

## Consequences

- The first message after a long idle waits for the agent CLI to start and load the session, a few seconds.
- Anything the agent left running in its own process tree (a background shell command, a watcher) ends with it. Apps started with `ted run-app` are not affected: they run in their own hosts.
- If the CLI can’t resume the session at wake (for example Claude Code deleted an old transcript), the agent exits, the Run ends with `resumeFailed`, and `recover` starts a fresh Run from the Task brief, as for any failed resume.
- A sleeping Run still holds the daemon’s idle timer, as any live Run does.

## Considered Options

- **Keep the host and end only the agent.** The host would wait for a signal to start the agent again. Rejected: it needs a new host protocol version and a parked state in the host, keeps 30 to 60 MB per Run, and the replacement path already starts a new host for the same Run.
- **End the Run and revive it on the next message.** Rejected: a finished Task Lead Run goes through `recover`, shows as ended in the thread and counts toward the failure history, and every sender would have to know how to revive.
- **A `v1.RunSlept` event and a new Run state.** Rejected: nothing in the state database depends on it (ADR 0157), and a new state would touch every place that reads `idle`.
- **Sleep sub-agents, Coordinator, side-chat, planning and Automation Runs too.** Left out for now. The wake is in `RunManager`, so it would work for them, but each owner has its own rules about idle Runs (a reviewer whose report is being read, an Automation that ends when idle, a planning chat’s worktrees), and each needs its own conditions in `maySleep` and its own test.
- **Antigravity.** Left out: its driver refuses to resume when the CLI doesn’t advertise `sessionCapabilities.resume`, which is only known once it runs.
