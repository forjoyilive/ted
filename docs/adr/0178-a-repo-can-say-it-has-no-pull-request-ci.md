# A repo can say it has no pull request CI

When Ted thought a repo had CI but no check ever appeared on a Task’s pull request, every Task waited 10 minutes at Merge and then asked “CI hasn’t started” (ADR 0062-merge-gate-merge-off-re-sign-off-and-ci-stuck). A repo whose base branch gets checks only after a merge, such as a hosting provider’s production build on `main`, hit this on every Task, so running without pull request CI wasn’t a workable choice (TED-483).

**Detection at push looks at pull requests, not the base branch.** `detectCi` in `tasks/pull-requests.ts` keeps three signals. A workflow file counts only when `runsOnChanges` in `tasks/workflow-triggers.ts` finds a trigger that fires for this push: `push` filtered by `branches`/`branches-ignore` against the Task branch (a tags-only `push` doesn’t count), `pull_request` and `pull_request_target` filtered against the base, and `merge_group`. Patterns follow GitHub’s filter syntax; anything Ted can’t read counts. Required status checks on the base still count. The third signal is now `recent-pull-requests`: any check on the head commit of the last 10 open or merged pull requests into the base, other than this Task’s own. The old `recent-checks` value stays in `ciSignals` for pushes recorded before.

**A per-repo setting overrides it.** `repos[].pull_request_ci` in `.ted/workflow.yaml` is `auto` (the default, written as no key), `none` or `required`. It is applied when merge targets are built, by `expectsCi` in `tasks/merge.ts`, so a change reaches Tasks that have already pushed. `none` never skips a required status check: GitHub won’t merge without it, so Ted keeps waiting as before. Factory settings shows the field on each repo with the newest push’s result (`lastCiFound`, from the Tasks’ stored pushes; no GitHub call when the page opens).

**The question can save it.** “CI hasn’t started” (no check at all, no required check on the base) adds a fourth choice, “Merge, and don’t wait for CI on <repo> again”. It merges like Merge anyway, then saves `pull_request_ci: none` through `FactorySettings.setPullRequestCi`, a Save and merge of that one field, and Ted posts a note with the settings pull request and whether it merged. Only the human may choose it: Autopilot and the Coordinator get a 403, because it changes the Factory’s settings.

**The sign-off says so.** A sign-off after which Ted merges at once, and the Merge sign-off, list the repos Ted won’t wait on in `gate.noCi`: repos whose stored push `expectsCi` turns down, read when the request is posted. Since ADR 0187 nothing is pushed before Merge entry, so a first sign-off before Merge has no stored push and lists no repo; the list fills in on a re-sign-off after the Task came back from Merge, and on the Merge sign-off. The card shows “No CI on <repo>, so Ted merges without waiting” for each. With Merge off, or on a Stage sign-off that a Merge sign-off follows, the list is left out (TED-543).
