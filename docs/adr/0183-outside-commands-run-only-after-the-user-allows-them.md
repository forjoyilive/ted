# Outside commands run only after the user allows them

Status: accepted (TED-434). Builds on ADR 0182-an-agent-runs-named-commands-in-its-chats-copy, ADR 0180-a-chat-records-its-agent-and-ted-checks-its-powers, ADR 0181-the-coordinator-drafts-agents-the-user-creates, ADR 0054-the-app-holds-the-human-token-in-memory and ADR 0091-agent-started-checks-and-apps-run-sandboxed.

Everything an agent starts runs in Ted’s sandbox, so nothing an agent starts can push, publish, sign or read the keychain. A release needs all of that. TED-434 adds one narrow way out: commands the user lists for an Agent and allows, run by Ted on this Mac outside the sandbox.

**A new power, Run outside commands (`run_outside`), and an `outside_commands` map per Agent.** The map has the same shape as `commands` (a name to a command, or to `{ command, repo }`), at most 10 entries. A command must be plain words separated by spaces: each word matches `[A-Za-z0-9@%+=:,./_-]+`, so quotes, `$`, backticks, `;`, `&`, `|`, `<`, `>`, `(`, `)`, `*`, `?`, `~`, backslashes and newlines are refused. One word may be an argument slot, `<name>`, but not the first. `outsideCommandWords` in `packages/protocol/src/outside-command.ts` is the one check; `ted workflow check`, the settings parser and the settings editor all use it. The power is chat-only: `ted workflow check` refuses it on `planner`, and planning chats never run outside commands. It doesn’t need Read the code. The chat stores its Agent’s outside commands at its first commit, as `v1.ChatAgentOutsideCommandsRecorded`, beside `v1.ChatAgentCommandsRecorded`.

**The agent sends a name and at most one argument; Ted builds the process.** `ted agent run-outside <name> [argument]` posts `POST /chat-outside-commands` (open to Run tokens, and in the Coordinator Run allow list in `server.ts`). Ted finds the chat from the Run token, checks `run_outside` on the stored Agent, takes the command text from the stored Agent and checks that the Factory’s current Agent files still give the power and list the same text (`stillListed` in `coordinators/coordinators.ts`), so removing the power or changing the command stops chats that started earlier. The argument must match `[A-Za-z0-9._-]{1,100}` and not start with a dash. `outsideArgv` puts it in the slot’s place as one argument; a command with a slot needs one and a command without one refuses one. Ted spawns the first word with the rest as separate arguments and never through a shell.

**Where and how it runs.** Only `createOutsideCommands` in `chats/outside-commands.ts` runs outside commands. The folder is the real path of the local folder set for the command’s repo (`store.localFolder`, the primary repo when `repo` is left out); with none set, or a folder that isn’t there, Ted refuses and says to set it in Factory settings → Repos. The command gets the daemon’s login environment without Ted’s Run variables (`TED_RUN`, `TED_RUN_TOKEN`, `TED_RUN_CAPABILITY`, `TED_TASK`, `TED_PLAN`, `TED_CHAT`), at normal priority, outside the sandbox and outside `CheckSlots`, one at a time per Factory, for at most 2 hours, and not while `store.newWorkHold()` is set. Stop on the chat line (`POST /coordinator-chats/:id/outside-command/stop`), the chat’s Stop, archive, delete and daemon shutdown end its process group.

**The first run of each command waits for the user’s click.** Without an approval, Ted posts a chat request of the new kind `outside-command` (`v1.ChatOutsideCommandAsked` in the request’s commit), which shows as a card in the chat and the Inbox with the full command, the argument, the folder and the repo, **Run**, **Don’t run** and **Always allow this command**. Only the app’s `POST /coordinator-chats/:id/requests/:rid/outside-command` answers it; it sets neither `runToken` nor `fileToken`, so only a request signed with the app’s in-memory key runs or approves a command. The Coordinator’s `answer` action handles Task requests only, Autopilot never answers chat requests, and the generic chat answer route refuses this kind. Before running, Ted builds the plan again and refuses when the command text or folder differ from what the card showed.

**Always allow is stored on this Mac per Factory, Agent, command name, exact command text, repo and folder.** It is one `outsideCommandAllowances` row (`v1.OutsideCommandAllowed`, `v1.OutsideCommandAllowanceRemoved`), deleted with the Factory by `v1.FactoryRemoved`. A request whose Factory, Agent, name, text, repo and folder match runs at once, and its chat line says Always allowed. Any difference brings the card back and names what was allowed before. The argument isn’t part of the approval. The user sees and removes approvals in the Agent’s details pane and its Factory settings (`GET` and app-only `DELETE /factories/:id/outside-command-allowances…`).

**Output goes back as data, and the result reaches the chat as a message from Ted.** The CLI returns at once, saying the user was asked or the command is running. While it runs, the chat line shows the last output, read once a second. When it ends, Ted commits the run as `v1.ChatCommandRan` plus `v1.ChatOutsideCommandRan` (the shown command, folder and whether it was always allowed) with a redacted 4 KB tail, and queues a message from Ted to the chat’s Run with the last 32 KB through `redactSecrets` between fresh-nonce `COMMAND OUTPUT` fences. A refusal is a message too. Nothing is delivered to an archived chat.

**Drafts can’t add it.** The Manage Agents draft card writes only names, instructions and powers, and `planDraft` refuses a draft that gives `run_outside` unless the Agent already has it. Only the user adds the power or an outside command, in Agent settings.

**The Release recipe and this repo’s Release Agent.** New Agent… offers Blank and Release. The Release recipe fills in the four powers, instructions that build, ask the user and then publish or discard, and empty `build`, `publish` and `discard` outside commands for the user to fill in. This repo’s `.ted/agents.yaml` has a Release Agent with `pnpm release build <version>`, `pnpm release publish` and `pnpm release discard`. The stop between build and publish is a question in the Agent’s instructions; publish still needs its own Run unless the user allowed it always.

## Considered Options

- **Run outside commands through `$SHELL -lc` with the argument as `"$1"`.** Rejected: the listed text would still be shell code, so a later edit could add a pipe or a substitution that the plain-word rule now refuses.
- **Allow the agent any argument string.** Rejected: one plain word covers versions and names, and nothing in it can become a flag or a second command.
- **Key approvals by command text only.** Rejected after review: the same text in a different folder runs different code, so the repo and folder are part of the approval.
- **Let the Coordinator or Autopilot approve.** Rejected: the point of the card is that a person decides; Run tokens never reach the approval.

## Consequences

- A command the user allowed always runs whenever the Agent asks, with any plain argument. The card and the settings say so. A slot must therefore never be able to pick a different action: with `pnpm release <version>`, the argument `publish` would run `pnpm release publish` with no card once build was always allowed. This repo’s Release Agent uses `pnpm release build <version>`, which refuses anything but a version, and the Release recipe tells the user to write build commands the same way.
- An approval for a command that later leaves the Agent files stays listed until the user removes it, but no longer matches anything.
- Tests stub `pnpm` on `PATH`; real signing never runs in a test.
