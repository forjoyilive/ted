# Runs and Providers

Rules for Runs, their hosts, output and messages, and the Provider CLIs (`packages/daemon/src/runs/`, `agents/`, `health/`). They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- A human message to a working Run is held in the store and delivered only by `packages/daemon/src/runs/steering.ts`, at the agent’s next tool-call boundary or when the turn ends; never write it to the agent early, and never as a hook’s `additionalContext`.
- Agent health lives in `packages/daemon/src/health/` and uses `cli-env.ts` and `terminal.ts` like GitHub and Git health; a fix command opens in the user’s own terminal, never Ted’s. Pi has no sign-in: it is Ready once it lists a model. `piModels` in `agents/pi-models.ts` asks `pi --mode rpc --no-session` for `get_available_models`, which lists the same models as `pi --list-models` (only providers Pi can use); the Ready check and `GET /agents/:agent/models`, which fills the model picker, both use it, and the picker keeps the default option, the current and extra model names, and “Other…” when it returns nothing. A kind that isn’t Ready is paused in the store, and a Task Lead that can’t start is held and started again when the kind is Ready; what a CLI prints for its version, login and auth errors stays in its `agents/` module. Tests set a stub’s health with `TED_HOME/stub-claude.json` or `stub-codex.json` (`{"signedIn": false}`, `{"version": "2.0.0"}`).
- Antigravity under Subscription billing starts only after the human has turned on the `antigravityPlanAccepted` machine setting from Settings → Providers, because Google’s terms treat using Antigravity through other software on a Google plan as a breach. `launchBilling` in `runs/run-manager.ts` refuses every such launch and Antigravity’s health check reports the notice as a problem; never add a launch path that skips `launchBilling`, and never set the setting from anything but the app.
- A usage limit, being offline or a Run using an API key under Subscription pauses an agent kind only through the agent health monitor, which composes every cause into the one reason `pauseAgent` stores; what a CLI’s output says about limits, retries, credentials, plan usage and cost stays in its `agents/` module. Billing is the `billing` machine setting; under Subscription the agent module removes the key variables. Pi is never paused for being offline or for limits, because its models may be local, and has no `billing` entry (`BilledAgentKind`): it uses the keys in its own settings, and Ted records its tokens and the cost it reports. Tests never reach the network or a billing or usage API: `TED_ONLINE_FILE` (set in `vitest.config.ts`) or `startDaemon`’s `online` option decides online, and the stubs emit limit and usage lines.
- The guidance every Run’s prompt carries comes from `promptGuidance` in `packages/daemon/src/guidance.ts`, the only code that reads the `aiDisclosure` machine setting for prompts. It returns the writing guidance and the skills line (`workflow/defaults/writing.md`, `skills.md`), then the AI disclosure instruction (`disclosure.md`) while the setting is on; when it is off the user’s other instructions decide. Every prompt builder (Task Lead, sub-agent, Coordinator, planning, Automation and Scheduled Check Runs) takes that list in place of its own copies, so an instruction meant for every Run is added there. Side chats get none of it. The disclosure instruction comes last so `splitPrompt` in `runs/conversations.ts` still finds the preamble (`preambleText` and `subAgentPreamble` end with `baseGuidance`). `fixedPromptTexts` lists `guidanceTexts`. A Run keeps the instructions it started with.
- A message the human types into a Run chat, Coordinator chat or planning chat may carry uploaded files. The route resolves each with `attachments.find` (an unknown file is a 400) and `messageWithFiles` in `runs/message-files.ts` builds the text the agent gets: the message, then the same `Attached files:` block Task comments use, or only the block for a file-only message. The `runMessages` row keeps that delivered text, so delivery, bundling and chat matching compare it against the transcript unchanged; the files are stored by `v1.RunMessageFilesAttached` in the same commit, and the chat’s `human` item shows `shownText` (the text without the block) with `attachments`.
- To send a live Run a message, use `RunManager.send`, which appends to the Run’s `input.jsonl`; the host forwards it to the agent’s stdin.
- `RunManager.dispatch` gives every record an input permit, so Ted sees when the host forwards it; a record that isn’t revocable is marked `pickup` and is never revoked or counted by `consumedInputs`. Only the host’s pickup has a time limit (`inputAckMs`); after pickup, dispatch waits for the agent to repeat the message for as long as the Run lives, and sends it again to a new agent generation. A missed pickup (`InputNotPickedUp`) is retried 3 times, 3 seconds apart, before it fails. The tool-call boundary hook returns once the host has the message, because Claude Code reads stdin only after its hooks finish; never make the hook wait for the agent to repeat a message. A Coordinator chat whose Run ends during delivery carries on as Retry does, up to 3 times, before it shows Failed.
- An idle Task Lead, sub-agent, Coordinator chat or planning chat Run goes to sleep: after `sleepIdleRunsAfterMinutes` (machine setting, default 10, `null` for never; 2 minutes, or less if the setting is less, while `store.busyHold()` is set) `runs/idle-sleep.ts` has `RunManager.sleep` end its host and agent, and the Run stays `idle` with `asleep: true`, the same ID and session. Only `sleepKind` and `maySleep` in `runs/idle-sleep.ts` decide which Runs may sleep: Claude Code, Codex or Pi with nothing queued, and per kind the current Task Lead with no sub-agent that isn’t idle and `Tasks.midWork` false, a sub-agent whose parent and Task are live, or a chat its owner’s `mayRest` allows (`Coordinators`, `Plans`); anything new that a Task Lead waits for without a working turn adds its case to `Tasks.midWork`, and a new kind of Run may sleep only once it has a `sleepKind`, a `mayRest` and an environment source. The only record is `asleep.json` in the Run folder, which `RunManager` reads when it starts following a Run; there is no event, and the store’s flag is in memory (`setRunAsleep`). A sleeping Run is woken only inside `RunManager`, by `send`, `steer`, `dispatch` and `restart`, through the host replacement path (`prepareReplacement`: resumed session, `runPermissions`, `launchBilling`, a fresh launch authority), and a wake waits while `store.newWorkHold()` is set. A wake takes the Run’s environment from memory or, after a daemon restart, from the owner’s `runEnv` (`Tasks`, `Coordinators`, `Plans`) through `RunManager.envSource`, never from the Run folder’s `env.json`; a wake that keeps failing is retried and shown as the `run-wake-failed` banner from the `wakeFailed` and `woke` observers in `daemon.ts`. Never append to a Run’s `input.jsonl` another way, or a sleeping Run won’t see it. A sleep or a wake is never a Run ending: don’t route it through `recover`, `revive` or `store.reviveRun`, and don’t count it in `failureHistory`. Code that looks for a Run’s processes uses `currentHostPid` and skips Runs with `asleep`. Tests drive the clock with `startDaemon`’s `idleSleep.now` and a short `checkEveryMs`.
- A Run’s output lines live only in its `runs/<run-id>/host.log`; the store holds no lines. `store.recordRunOutput` commits `v3.RunOutputRead` (the read offset and the last output time) only together with another event the lines led to (a state, session, problem, retrying or ending change, auto mode unavailable, a permission Comment asked or withdrawn); a batch that leads to none commits nothing, the store holds its offset in memory and `RunManager` writes it to the Run’s `read-offset.json`, which it reads when it starts following the Run again, so read the offset and last output time only through `store.runReadOffset` and `store.lastOutputAt`, never from the `runs` row, and `v1`/`v2.RunOutputRead` materialize only the offset and time. Read a Conversation only through `RunManager.output` (`runs/run-output.ts`), which reads `host.log` up to the Run’s read offset: `entries`, or `last` and `findLast` when the newest lines are enough. Code that reads every line of a Run again and again (the Run chat, Run summaries, `inputAccepted`) goes through `parsedOutput` in `runs/parsed-output.ts` instead: it is an `output.fold`, a value kept beside the cached lines that is given only the lines added since the last call and is dropped whenever the cached lines are dropped or read again from the start, so it never holds anything the lines don’t. A finished Run’s tokens, credential and cost are remembered in `conversations.ts` under `output.stamp` (the file’s inode and size and the read offset), so pruned or cut output changes them. A missing `host.log` gives an empty Conversation and a cut one gives its tail, never an error; the Run chat then shows a “From Ted” row saying so.
- A Run’s start is `v5.RunStarted`, which holds its prompt as `promptParts`: its own text, `{ hash }` for a shared text in `promptTexts` (`v1.PromptTextSeen`, committed with the first start that uses it, kept for good) and `{ request }` for a sub-agent’s instructions, which `v2.SubAgentRequested` keeps in `subAgentInstructions` after the request row goes. `splitPrompt` in `store/prompt-parts.ts` builds the parts from the texts `RunManager.start` is told may be shared (`fixedPromptTexts` and `taskLeadSharedTexts` in `workflow/workflow.ts`) and keeps the prompt whole unless they join back to the same text. Read a Run’s prompt only through `store.runPrompt`, never `runs.prompt`; `Run.prompt` is filled only by `GET /runs/:id`, never in events or lists. Old `v4.RunStarted` events are not rewritten.
- When a Run finishes, `conversations.ts` saves what it used as `v1.RunUsageRecorded` (tokens and the cost from the agent module’s `costOf`, whatever the billing), because the output it is read from is deleted later. `store.apiCost(days)` and `GET /agents/api-cost` sum those rows per agent, and Settings → Providers shows them as what the Runs would cost on an API key. Never work these totals out by reading old Run output. Codex’s cost comes from the price table in `agents/codex.ts`; keep its date and source comment current.
- What an agent CLI’s output lines mean for the Run chat lives in that agent’s `chatFrom` builder in `packages/daemon/src/agents/`, which takes one line at a time (`chat` runs it over a whole list); `runs/conversations.ts` builds the chat items from the Run’s row, messages and permission Comments on every call, so only the parsed lines are kept between calls. A `run-output` event carries `lines: true` when it is new agent output; the app’s chat hooks reload at most once a second for those and at once for every other event, and a message typed into a Run chat goes only through `Conversations.send`, never as a Comment. Files copied or ported from agent-orchestrator say so at the top and say what Ted changed.
- Code that knows how a particular agent CLI starts or what its output means lives only in `packages/daemon/src/agents/`. Codex runs as `codex app-server`, driven by `agents/codex-driver.ts` inside the host. Pi runs as `pi --mode rpc`, driven by `agents/pi-driver.ts`: the host splits Pi’s output on LF only, because Node’s `readline` also breaks lines at U+2028 and U+2029; the driver answers every extension dialog as cancelled so a user extension can’t hold a Run; a turn that ends in a Pi error ends the Run through the host’s `fail`, with Pi’s message as an error line; and a Run resumes only from the session file in its `pi-sessions` folder, never a bare session ID. Pi reads the user’s `~/.pi/agent` (or `PI_CODING_AGENT_DIR`) and Ted never writes there. Before a new Pi Run starts, `agentStartHold` requires a model on the request or from `Agents.savedModel`, which reads `defaultModel` and optional `defaultProvider` from Pi’s `settings.json`; an existing Run is exempt from this model hold. Pi has no sandbox of its own and runs every command without asking, so outside Bypass the Run host wraps the `pi` process, and only it, in Ted’s OS sandbox at every agent start: `RunManager` puts a `sandbox` field (scope and Ted home, from `runs/pi-sandbox.ts`) in `launch.json`, and `host/main.ts` spawns the argv, environment and descriptors `createSandbox(...).wrap` returns; if the field is there and wrapping fails, the agent start fails and never falls back. The host and `pi-driver.ts` stay outside it. A Task Run writes its live worktrees, each one’s own git folder (`<clone>/.git/worktrees/<name>`), `<clone>/.git/objects` and the folder of its branch under `refs/heads` and `logs/refs/heads`, so a Pi Task Lead can commit, and its `pi-sessions` folder; it reads the Task folder, the clones, `TED_HOME/bin` and `TED_HOME/public`; its temp is the Run’s `tmp`, its cache the Task’s sandbox cache. Grant git metadata only through `worktreeGit` in `runs/pi-sandbox.ts`: the worktree’s plain `.git` file must point into a trusted clone’s plain `.git/worktrees/<name>` folder, and that folder’s `gitdir` must point back to the worktree. A Run can rewrite its `.git` file, so its pointer alone never authorizes a grant. `.git/config` and `.git/hooks` stay read-only, so a Run can’t plant a hook or config that runs later outside the sandbox; it can still move another Task’s branch in the same folder or add objects. A Run outside a Task writes its `pi-sessions`, its `pi-agent` copy and a worktree it owns, with temp and cache in its Run folder. Pi’s scope sets `ownTempOnly`, so on macOS it gets neither the `shared-tmp` access group’s `/private/tmp` nor the `ios-xcode` access group’s per-user temp and SwiftPM `ManifestLoading` grants, even if its scope names them, and `hideProtected`, so on Linux an empty `tmpfs` covers each protected folder that exists in `HOME`, as the macOS profile already denies them. A side chat, which always runs in Auto, follows its Factory: in a Bypass Factory it runs without the sandbox. Everything else in `TED_HOME`, `daemon.json` included, stays unreadable, and on macOS the user’s original Pi folder is outside the base read set; Pi uses the Run’s copy instead (a refreshed Pi sign-in isn’t saved). Pi takes lock files beside `settings.json` and `auth.json` even to read them, so `piSandboxScope` copies the user’s Pi folder, without `sessions`, to the Run’s writable `pi-agent` folder at every launch and `launch.json`’s `sandbox.env` points `PI_CODING_AGENT_DIR` at it. Resolve the source folder with `realpath` before copying, so a symlink at `~/.pi/agent` or `PI_CODING_AGENT_DIR` supplies its settings and sign-in too; exclude `sessions` under that resolved folder and leave the source unchanged. When `sandbox.problem()` gives a reason, `agentStartHold` holds Pi work outside Bypass with `piSandboxQuestion` until the human turns on the app-only `piUnsandboxedAllowed` machine setting in Settings → Providers, agent health raises the `pi-sandbox-unavailable` stops-work banner while Pi is enabled, and `launchSandbox` in `RunManager` refuses the same way, so no path starts Pi unsandboxed by mistake; with the setting on, Pi runs outside Bypass without a sandbox only while `sandbox.problem()` gives a reason. A working sandbox is used even with the setting on. The reason is kept in the store (`setPiSandboxProblem`), set at daemon start, at each Pi health check and at each launch, and shown as Pi’s `AgentHealth.sandboxProblem`. The host’s `launch.json` and `host.log` formats only ever gain fields, because a running host can outlive a daemon update. Host protocol 10 is the first that reads `sandbox`, so the daemon replaces older hosts before they could start Pi from a launch they don’t understand.
- Permission prompts come only from an agent module’s `permissionPromptFrom` and are answered only through `RunManager.answerPermission`, which tags the reply with the agent generation; never write a reply to `input.jsonl` another way, and never add a route that answers one with a Run token. Under `auto` the Claude Run’s `settings.json` allows only `Bash(ted *)`; don’t widen it. Under `auto` Codex gets `approvals_reviewer="auto_review"`, so its own reviewer decides requests for access outside the sandbox, such as a commit’s write to the clone’s git metadata; don’t make the clone’s `.git` a writable root instead. On macOS a Claude Run with tools gets Claude Code’s own `sandbox` with `protectedFolders` in `denyRead`, everything else open, `autoAllowBashIfSandboxed: false` and `allowUnsandboxedCommands: true`, `Read(~/<folder>/**)` deny rules, and the `claude-home-guard.ts` PreToolUse hook that refuses an unsandboxed Bash call naming the home folder or a personal folder; Codex under `auto` gets the `ted` permission profile in place of `sandbox_mode`. Never pass `sandbox_mode` beside the profile, which makes Codex ignore it.
- **What a Run token may do.** A Run acts only on its own Task, or, for an Automation or Planning Run, on what it creates. Routes with `runToken: true` are the full list; add one only for an action of this kind.
  - Allowed: post Comments and set the activity line; report the Stage outcome and, at Merge, title its own pull requests and write their merge commit message with `ted task pr` (the Task Lead only); start, message and stop its own sub-agents; start its own Task’s Apps, and stop them (the Task Lead only); edit its own Task’s Repos and blockers (a blocker may be any Task); create Tasks or propose them (a Task Lead’s `--child` Task queues under the conditions in `docs/agents/tasks.md`; its other Tasks enter Backlog and may start through automatic Backlog starts under the same doc’s rules); read Tasks, the brief and Checks; record, assess and verify its own Task’s failure cases and choose to fix one in its own Task (`ted failure fix`), never accept one; report its own tool-call boundary. The current Task Lead may also read peers and send plain, attributed notes to Tasks in its own Factory, which grants no control over them. A Run may register a test invocation and read test-lock measurements only for its own Task; the credential that returns can only report that invocation’s metadata. Only Ted associates an invocation with a Check run; see [the reporting contract](../contracts/test-lock-reporting.md).
  - Refused: answering or approving an Inbox item, except that the current Task Lead may answer an ordinary question on its own Task while effective Autopilot is on, through `answerAutopilot` with a recorded explanation (`docs/agents/tasks.md`); signing off, merging, archiving or deleting; editing a Task’s title or description, or any other Task; changing settings, Automations or `workflow.yaml` through the API. A Task may still change `.ted/` files on its branch, which go through review.
  - Run tokens prevent mistakes, not attacks: agents run as the same user and, without Ted’s OS sandbox, can read `daemon.json`, so every human decision needs the app’s in-memory key. A sandboxed Pi Run reads only `TED_HOME/public/daemon.json` for the daemon’s port, pid and version, never a token; `readDaemonInfoFor` in `packages/protocol/src/daemon-info.ts` prefers that file when a Run token is present and falls back to the private file for older daemons. Keep the public file free of credentials.
