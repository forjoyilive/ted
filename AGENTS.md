# TED

TED (“Totally Excellent Development”) is a desktop app for running software factories: agents carry development tasks through a configurable workflow, and the human steers through an inbox and comments. Vocabulary lives in `GLOSSARY.md`; use its terms.

## Code

For validation policy and Factory customization, read [Factory validation](docs/testing/factory-validation.md). The test-runner limits below belong to this repo’s development tooling.

pnpm workspace on Node 24: `packages/protocol` (paths, `daemon.json`, API types, `DaemonClient`), `packages/daemon`, `packages/cli`, `packages/app` (Electron, React renderer). Node and Electron run the `.ts` files directly. Only the renderer has a build step (Vite), and the preload stays plain `.cjs` because Electron’s sandboxed preload loader doesn’t strip types (ADR 0011).

- `pnpm install`, then `pnpm typecheck`, `pnpm lint` (Biome; `pnpm format` fixes), `pnpm test` (Vitest). Run all three locally before merging to `main`; GitHub CI runs typecheck and lint on every pull request and push to `main`; the full test suite runs only locally, never on GitHub. Agents never start GitHub workflows. Agents, TED’s own Runs included, run only the test files their change touches (`pnpm vitest run <files>`) and never `pnpm test` or `pnpm check`; the full suite runs only when the human or a merge runs `pnpm check`. A Run in this Factory runs test files only in Validate, as the Task Lead, once per visit; Work, the other Stages and sub-agents run none (`.ted/stages/work.md`, `.ted/stages/validate.md`). With `TED_RUN` set, `pnpm check` and any Vitest run of more than 3 test files (`runTestFiles`) are refused before they take a lock (`runRefusal` in `scripts/check.ts` and in `suite-lock.ts`). `pnpm check` runs typecheck, lint and two Vitest processes at once: the `electron` project (test files that use Playwright’s `_electron` or resolve the installed Electron executable, directly or through a relative import) with 3 workers and the `node` project with 6; any other run of 10 or more test files also gets 6 workers, because it runs alone, and a smaller run gets 3, so two small runs side by side don’t take every core (`workersFor` in `vitest.config.ts`). On a branch whose changes since `origin/main` are all in `packages/app/src`, `packages/app/test` or docs, `pnpm check` runs only the tests in `packages/app/test` (`onlyAppChanged` in `scripts/check.ts`) and records no passing commit; `pnpm check --all`, any run on `main` and `pnpm release` run every test. Nearly every daemon test starts the whole daemon, so a change to `packages/daemon` or `packages/protocol` always needs them all; it writes per-file times to `node_modules/.cache/ted-test-times.json` and prints the 10 slowest. The `electron` project retries a failed test once; `scripts/retry-reporter.ts` reports each test that failed and then passed, and `pnpm check` prints it as “passed on retry” and keeps it as `passedOnRetry` in `node_modules/.cache/ted-test-failures.json` without failing the run. Treat such a test as broken and fix its timing. Keep each Electron test file to about a dozen app launches so no one file sets the run’s length. The `electron` project retries a failed test once, because app tests time out at random when the whole suite runs; a test that fails twice fails the run. Test runs share the machine through `packages/daemon/test/support/suite-lock.ts`, across every checkout: the global setup gives a run of fewer than 10 test files one of 2 slots in `~/.cache/ted/test-slots/`, and a full run (10 or more files) takes `~/.cache/ted/test-suite.lock` and then every slot, so it runs alone; `pnpm check` holds them through dependency refresh and both of its Vitest processes. A run waits while live pids hold what it needs, says so, and takes over from a dead pid, so a test command can sit waiting before it starts; waiting runs hold tickets in `~/.cache/ted/test-slots/queue/`, named with the time asked, the pid and `small` or `full`: small runs get slots in the order they asked and don’t wait behind a waiting full run, full runs go in the order they asked, and a full run whose turn comes first lets the small runs that were already waiting go, for at most 5 minutes (`fullRunYieldMs`); it adds the time its turn came to its ticket, and small runs that ask at or after that time wait for it. A ticket without a kind is from a checkout with the older lock code: every run waits behind an earlier one, and no full run lets small runs go first while one waits. Every run that takes a slot or the suite lock appends a `start` and an `end` line to `~/.cache/ted/test-waits.jsonl` (time waited, time running, file count, folder), and `pnpm test-waits [days]` sums them by kind, day and folder; a small run that can’t write the slot folder runs without one. Every Vitest run, `pnpm check`’s two processes included, also appends to `~/.cache/ted/test-failures.jsonl` when it ends (`recordVitestRun` in `scripts/failure-log.ts`, called from the global setup’s teardown): one `run` line with the time, the checkout, `small` or `full` and the test files that finished, and one `test` line for each test that failed or passed on retry; a run that can’t write the file carries on, and lines older than 90 days are dropped about once a day. `pnpm test-failures [days]` ranks tests and files by how often they failed, with the rate over the runs that included the file, and leaves out runs with more than 10 failed tests (`brokenRunTests`). `TED_TEST_FAILURES_FILE` names another file or, as `off`, records nothing; `vitest.config.ts` sets `off` for every test file, so a Vitest run a test starts is never recorded. Resolve the native test executable with `resolveElectron` from `packages/app/test/support/electron-installation.ts`, never by requiring `electron`: its loader can install concurrently in workers. The native project’s preflight prepares it once before collection. Launch an app in a test with `firstWindow` from `packages/app/test/first-window.ts`, which waits 60 seconds for the window. Inside Codex’s sandbox (`CODEX_SANDBOX` set) the Electron test files are skipped with a warning, because Electron can’t start there. `pnpm release <version>` checks `main` is clean and pushed, runs all three locally unless `pnpm check` already passed on that exact commit (it records passing commits in `.git/ted-checked`), bumps the version, tags `v<version>`, pushes, builds the macOS app on this machine, signed with the first Developer ID or Apple Development identity in the keychain (or `TED_SIGN_IDENTITY`) so macOS keeps trusting it across releases, and installs it in `/Applications`; `pnpm release --install` installs the last build again. The GitHub release workflow runs only when started by hand.
- Code run from source is TED Dev; only the code `pnpm package` stages is the release. `edition` in `packages/protocol/src/edition.ts` says which, and `markRelease` in `packages/app/scripts/stage.ts` is the only thing that changes it. Anything machine-wide (home folder, app name and userData, keyring service, installed command, login item, update checks, simulator names) comes from `identity()` or checks `edition`, so the two never touch each other (ADR 0089-dev-and-release-run-side-by-side).
- `pnpm ted <args>` runs the `ted` CLI from source, against TED Dev’s home. It starts the daemon if needed.
- `pnpm app` builds the renderer and opens TED Dev from source. Like `ted`, it reuses a running daemon or starts one.
- `pnpm ted dev run start [--agent claude|codex] [--cwd <dir>] "<prompt>"` starts a Run in a detached host; `pnpm ted dev run show <run-id>` prints its state and Conversation. `pnpm ted dev slow` prints the daemon’s slow requests and event-loop stalls of the last minute and hour.
- The human adds a Factory from the app’s Add Factory form: `POST /factories/check-repo` checks each row and `POST /factories` adds it and clones in the background, with progress as `factory-updated` events. Queued Tasks of a Factory that is still cloning wait until `v1.FactoryCloned` (ADR 0034).
- `pnpm ted dev factory add <owner/repo | git URL> --key NB [--local-folder <dir>]` adds a one-repo Factory and clones it into `TED_HOME/repos/`; `pnpm ted dev factory local-folder NB <dir>` changes the folder `worktree.copy` reads from. Then `pnpm ted task create --factory NB "<title>"` and `pnpm ted task start NB-1` start a Claude Code Task Lead in the Task’s worktree. `pnpm ted help` lists every command.
- Set `TED_HOME` to use a folder other than the default: `~/.ted-dev` for TED Dev, `~/.ted` for the release. Tests always set it to a temp folder. `TED_IDLE_EXIT_MS`, `TED_CLAUDE_BIN` and `TED_CODEX_BIN` are TED Dev overrides only; release finds `claude` and `codex` through the login-shell `PATH`. Read runtime `TED_*` inputs through `tedEnv` in `packages/protocol/src/env.ts`, which classifies them and ignores test-only and unknown names in release; use `filterTedEnv` when forwarding an environment to TED processes. Classify new inputs there, with a reason for each retained release input. See `docs/environment.md` for the policy and inventory.
- Write erasable TypeScript only, and name the `.ts` file in relative imports (ADR 0008).
- Only `packages/daemon/src/store/` imports LiveStore. Events are named `v<N>.<PastTense>` and never edited once shipped; a change is a new versioned event (ADR 0010). The one exception is `store/compact.ts`, which `data.ts` runs once per home with the store closed: after a pre-update backup it drops the lines from old `v1.RunOutputRead` and `v2.RunOutputRead` events in a copy of the event log, verifies the copy against the original, renames it into place and records `outputCompaction` in `store/ted-store.json`. A second exception is `store/drop-output.ts`: when the state database is about to be rebuilt, or once per home when `outputDrop` in `store/ted-store.json` isn’t `done` and at least 1,000 events would go, and after a pre-update backup taken in that same open, `data.ts` drops every `RunOutputRead` event that a later one for the same Run replaces, renumbers the rest into one chain in a copy of the event log, verifies the copy against the original, removes every state file and renames it into place. Event sequence numbers, and the Task log and interval boundary IDs the state derives from them, can therefore change across a rebuild: use them only for ordering and never store one in an event. Don’t rewrite any other event (ADR 0099-old-run-output-events-are-compacted-once, ADR 0122-replaced-run-output-events-are-dropped-before-a-state-rebuild).
- A commit is in memory until LiveStore’s leader writes it to the event log; `server.ts` awaits `store.persisted()` after every non-`GET` route before answering. Code outside a route that must know a write is on disk awaits it too (ADR 0053-write-routes-answer-after-the-event-log-saves).
- Every daemon route sits behind the loopback guard in `packages/daemon/src/server.ts`. Each JSON request body has one hand-written parser beside its type in `packages/protocol/src/`, with an explicit request return type and a direct all-fields test; the CLI reuses these parsers. The machine `settingParsers` table stays in `routes/machine.ts`; attachment resolution and authorization stay in the daemon. A route, its token flags and its handler live in the area’s file in `packages/daemon/src/routes/` (`tasks.ts`, `factories.ts`, `machine.ts`, `integrations.ts`, `runs.ts`); routes that work before the store opens stay in `server.ts`. Clients call the daemon only through `DaemonClient` (ADR 0009). A route is closed to Run tokens unless it sets `runToken: true`, which only actions spec 2.3 allows may set (ADR 0015). Any route other than a `GET` is also closed to the token in `daemon.json` unless it sets `fileToken: true`; only requests signed with the app’s in-memory key may call it. Never mark a route that answers a request, passes a Gate, posts as the human, changes settings or credentials, adds or changes a Factory, or starts a Run outside a Task. Never write the app’s key to disk, send it in a request, or hand it to the daemon other than on its stdin (ADR 0054-the-app-holds-the-human-token-in-memory).
- The renderer reaches the daemon only through `window.ted`. A forwarded daemon call is added only to `forwardedRequests` in `packages/app/src/daemon-requests.ts`, with the same name, arguments and result as its `DaemonClient` method. Main-process actions and semantic adapters use `CustomRequests` in `custom-requests.ts` and explicit handlers in `main.ts` and `renderer/ted.ts`; the preload stays as it is (ADR 0011). The renderer imports only types from `@ted/protocol`; a value comes from its own sub-path (`@ted/protocol/run`, `@ted/protocol/task`, …), because the main entry also exports `DaemonClient` and the request parsers, which use Node modules. `packages/app/test/renderer-bundle.test.ts` fails when one gets in.
- Every renderer colour is a token in `packages/app/src/renderer/styles/tokens.css`, written as `light-dark(<light>, <dark>)` with Figma’s Theme variable name; components use a CSS Module and `var(--…)` only, and `packages/app/test/theme.test.ts` fails on any other colour. Reuse the shared components in `packages/app/src/renderer/components/` (ADR 0020).
- Keyboard shortcuts live in `packages/app/src/renderer/keymap.ts` and run through the one `keydown` listener in `App.tsx`; don’t add another window key listener for a shortcut. A new list or card view marks its focusable items `data-nav-item` so J/K reach them (ADR 0074-keyboard-shortcuts-one-keymap-one-listener).
- A Task’s status, markers and activity line are chosen only in `packages/daemon/src/tasks/status.ts` from `TaskFacts`; a new input is a new `TaskFacts` field, and the app only draws what the Task carries (ADR 0023).
- A new machine setting is a field and default in `packages/protocol/src/settings.ts` plus a parser in `settingParsers` in `packages/daemon/src/routes/machine.ts`; every change is one `v1.MachineSettingsChanged` event. A new App Settings page is a component in `packages/app/src/renderer/settings/`, listed in `settingsSections` in `sections.tsx` (ADR 0024).
- Text the daemon logs or puts in Copy report goes through `redactSecrets` in `packages/daemon/src/redact.ts`, which removes URL passwords and token-shaped strings (ADR 0024).
- A new kind of live update is a new `DaemonEvent` variant, emitted by `TedStore` after its commit (ADR 0012), by `packages/daemon/src/data.ts` for the store’s own status, by the Tasks module for `slots-changed` (ADR 0030), by `factory-setup.ts` for `factory-updated` (ADR 0034), or by `factory-settings.ts` for `factory-settings-changed` (ADR 0123-factory-settings-open-from-the-clone-and-refresh-in-the-background).
- A machine or Factory problem shows as a banner: call `banners.raise(…)` where you detect it and `banners.clear(…)` where it resolves, through `packages/daemon/src/banners.ts`; a button that does work in the daemon registers `banners.onAction(problem, handler)`; a button that first needs a folder sets `choose: 'folder'`, and the app sends the chosen path to the handler. A stops-work problem starting is the `banner-raised` event (ADR 0021).
- `packages/daemon/src/data.ts` opens the store, takes backups and restores them; a route that needs the store gets it through `data.services()`, so it waits while the store opens and answers `503` while a data screen is up. Only `/events`, `/data-status`, `/backups`, `/shutdown`, `/command-line`, `/app/open`, `/diagnostics/slow` and `/diagnostics/profile` work before the store opens (ADR 0026). `pnpm ted backup list` and `pnpm ted backup restore <name>` work on `TED_HOME/backups/`.
- The daemon times every route in `server.ts` and watches its own event loop in `packages/daemon/src/slow-moments.ts`: a request of 100 ms or more and a stall of 200 ms or more are counted for an hour in memory and logged, rate-limited, through `console`. A route is named only by `routePattern` (`routes/route.ts`), which works from the route’s regular expression and never from the request, so keep each capture a whole path segment and never log a URL, query string or body. A route that holds its response open on purpose (a stream, a long-poll, a wait for the app or another process) sets `waits: true` so it isn’t timed. `GET /diagnostics/slow` (`ted dev slow`) returns the figures as `SlowMoments`; a Run token can’t read it. `POST /diagnostics/profile` records a CPU profile through `cpu-profile.ts` with `node:inspector`’s in-process session, one at a time, 5 to 120 seconds, into `TED_HOME/logs/profiles/` (mode `0600`, plain folders only, newest five kept). It never sets `runToken` or `fileToken`: only the app’s key starts a profile, from Settings → Developer, and nothing opens an inspector port The daemon process also runs a watchdog worker thread (`watchStalls` in `cpu-profile.ts`): when the daemon’s thread has sent it no beat for 2 seconds it profiles that thread through `connectToMainThread` until the beats return, and a stall of 5 seconds or more is saved as `stall-<time>.cpuprofile` in the same folder (newest five kept) with a log line naming the file. Never keep the CPU profiler running outside a stall or a profile the app asked for, because it slows CPU-bound work several times over; only `main.ts` turns the watchdog on (`stallProfiles`), never a daemon started in a test, and the app’s own profile pauses it (ADR 0114-the-daemon-records-its-own-slow-moments, ADR 0124-the-daemon-saves-a-profile-of-a-long-stall).
- Anything that starts new work (a Run, App, simulator or Automation firing) checks `store.newWorkHold()` or goes through the queue, which starts nothing while the disk is full. Code that deletes files under `TED_HOME` checks the name and real path first and never follows links, like `retention.ts` and `storage.ts`. `TED_FREE_BYTES_FILE` names a file holding the free bytes TED should see; `vitest.config.ts` points every test at one with 500 GB, and `startDaemon`’s `disk` option overrides it (ADR 0039).
- Retention deletes a Run folder (`TED_HOME/runs/<id>/`) only through `pruneRunOutput` in `packages/daemon/src/retention.ts`, and only `runOutputEnd` there decides when: never while the Run is live, its Task is open (not Done, not archived), or a Coordinator, an Automation draft, or a plan that is unfinished or Failed owns it; otherwise `runOutputDays` days (machine setting, default 7) after the Task became Done or was archived, or after a Run without a Task ended. Anything new that reads a finished Run’s output or revives it adds its case to `runOutputEnd`. Tests drive the clock with `startDaemon`’s `retention.now` and a short `checkEveryMs` (ADR 0098-run-output-stays-while-its-task-is-open).
- Only `packages/daemon/src/tasks/` starts Tasks or changes their Stage; it owns the order of git, commit and Run steps (ADR 0016). A route open to Runs acts only on the Run’s own Task, except the Factory-scoped peer reads and plain peer notes in `tasks/peers.ts`; only a current Task Lead uses those, and only the Task Lead reports outcomes. Peer notes persist with their recipient Comment in one commit and use its delivery receipt; they reach working Leads through steering and replacement Leads through the normal Task start. A Coordinator Run reaches only the `/coordinator/tasks` routes, for Tasks of its own Factory, and acts only through `Coordinators.act` in `packages/daemon/src/coordinators/coordinators.ts`: start, move, tell (`Tasks.coordinatorTell`), resume (`Tasks.coordinatorResume`) and answer (`Tasks.coordinatorAnswer`), which closes any open request on the Task the way the human’s answer would: a `question`, a Gate request or sign-off, a `round`, a `proposal`, a size check or a failure decision. `mayAnswer` there decides how each kind is answered. Its `ted coordinator` commands never read a file, and its message text and round answers are capped and go through `redactSecrets` in the route. It never answers a `permission` or `simulator` ask or the Linear team ask, and it changes a Stage only as the effect of an answer; what it posts starts with `coordinatorLine`, and a round it answers carries that line as the answer’s `text` (ADR 0094-coordinators-have-bounded-factory-authority).
- A Comment’s files are recorded with `v1.CommentAttachmentAdded` in the Comment’s own commit and point at bytes already in `TED_HOME/attachments`. The human’s come from `POST /attachments` (app only); a Run uploads through `POST /tasks/:id/attachments` and may attach only files it uploaded or its own Task already has. Code that deletes attachment files checks `store.filesInUse()` first (ADR 0073-attachments-in-comments).
- HTML that must run scripts (the design review’s prototype) loads from `ted-prototype://file/<hash>/<name>` in an `<iframe sandbox="allow-scripts">`, never `allow-same-origin`; the main process serves it with a CSP that blocks the network. Other HTML stays in the `srcdoc` frame with `sandbox=""`. **Open ↗** on the Figma row opens the link the main process reads from the Comment, not one the renderer passes (ADR 0081-design-reviews-carry-their-parts-and-prototypes-run-from-their-own-scheme).
- A request is a non-`note` Comment; it leaves the Inbox only through one `v1.CommentAnswered` event (answered, approved, changes requested or withdrawn). Gate requests are posted by `ted outcome advance`, never by `ted comment`, except the Merge sign-off, which TED posts once CI passes; the user answers them unless bounded Autopilot approval applies (ADR 0032, ADR 0127). Only Clarify and Design can `ted outcome advance --skip`. A Clarify round is one `round` Comment posted with `ted ask --round <file>`; Clarify’s effective Gate setting applies at every depth (ADR 0050, KRI-362). Talk it through happens in the Task Lead’s own Run chat; only `ted ask --close --summary <file>` closes a talked-through round, as `answered` with `talkedThrough`, and messages typed during a talk add no steering thread lines (ADR 0077-talk-it-through-in-the-task-lead-chat). The size check is a `question` with a `sizeCheck` field posted by `ted clarify too-big`; TED carries out the human’s choice itself, and Split it’s pieces are created only by `answerProposal` in `tasks/tasks.ts` from a `proposal` Comment (`ted task propose --file`), using `planProposal` in `packages/protocol/src/proposal.ts`, which the app’s card uses too (ADR 0082-size-check-and-split-it). A test that walks a Task to Done commits `.ted/workflow.yaml` with `order: [intake, work, merge]` or approves the Gates, since Design and Review have them by default.
- A setup Task is a Task with `setup: true`, created only by `Tasks.setUpFactory` (after cloning) or `Tasks.newSetupTask` (`POST /factories/:id/setup-task`, app only). Resolve the Workflow for a known Task with `taskWorkflow`, never `resolveWorkflow(factoryOf(task))`, so a setup Task gets `setupWorkflow` (Clarify at grilling depth, Design and Review Gates on, the default branch, `defaults/setup.md`). Its Validate runs only the branch’s Checks that match a passing Check in the approved proposal. Tests that add a Factory through `POST /factories` get `<KEY>-1` as the setup Task; a Task created while cloning is `<KEY>-2` (ADR 0086-setup-tasks-are-marked-tasks-with-a-forced-workflow).
- Starting a Task only queues it; the pump in `packages/daemon/src/tasks/tasks.ts` starts queued work when a working-Run slot is free, in the order `queueOrder` gives (`tasks/queue.ts`). New work that needs a slot (sub-agents, Planning or Automation Runs) goes through that queue and counts in its slot holders; never start it around the queue (ADR 0030). With the `adjustRunsToLoad` machine setting on, `startsNow` also holds every new start while the load per core is at or above `loadMarks.holdAt`, until it is below `loadMarks.resumeBelow` (`heldForLoad` in `tasks/queue.ts`), except the first entry when nothing holds a slot and a slot handoff; it never stops a working Run and raises no banner. `TED_LOAD_FILE` names a file holding the load ratio TED should see; `vitest.config.ts` points every test at one holding 0, and `startDaemon`’s `load` option overrides it (ADR 0101-new-work-waits-while-the-machine-is-busy).
- A Task’s rank orders the Board, the List’s Manual sort and the queue. Clients reorder only through `POST /tasks/:id/move` with the Tasks it now sits after and before; `placeBetween` in `tasks/order.ts` picks the rank and Priority. Never send or compute a rank in a client (ADR 0040).
- A sub-agent is a Run with a `parentRunId`; a Task’s Task Lead Run is its newest Run without one. Sub-agents start only through `packages/daemon/src/tasks/sub-agents.ts`, as `sub-agent` entries in the queue, and only the current Task Lead Run may start, wait for, message or stop them (ADR 0049-sub-agents-are-runs-queued-by-the-tasks-module).
- Automations fire only from `packages/daemon/src/automations/automations.ts`: it decides each firing (scheduled, made up, skipped), adds `automation` entries to the queue through `Tasks.addQueueSource`, starts and settles their Runs, and holds the idle timer while any Automation is on. An Automation Run’s ID is its firing’s ID, so `store.automations.firing(runId)` says whether a Run is one. Schedules are computed only by `packages/protocol/src/schedule.ts`; tests drive the clock with `startDaemon`’s `automations.now` and a short `checkEveryMs`. Templates must never reach real Linear or Sentry in tests (ADR 0070-automations-fire-from-the-daemon-and-queue-like-runs).
- The Coordinator screen draws one chat for all of a Factory’s Coordinator Runs, built by `Conversations.coordinatorChat` and drawn with `ChatBody` and `Composer` from `RunChat.tsx`; don’t give it its own chat components. A message TED writes to a Run is queued with `from: 'ted'` (`v2.RunMessageQueued`) and is never a `human` chat item (ADR 0094-coordinators-have-bounded-factory-authority).
- Planning chats live only in `packages/daemon/src/plans/plans.ts`: a plan’s ID is its Run’s ID, it queues as `planning`, its rounds and proposals are `store.plans` requests (not Task Comments), and its detached worktrees under `TED_HOME/plans/<id>` are removed whenever it ends. Inside a Planning Run (`TED_PLAN`), `ted ask --round` and `ted task propose` post to the plan (ADR 0083-planning-chats). Plan in chat on a size check starts a plan linked to its Task (`v1.PlanStartedFromTask`); only the Tasks module narrows that Task or tells its Task Lead, through `Tasks.planApproved` and `Tasks.planEnded`, and archiving or deleting the Task detaches the plan through `Plans.taskGone` (ADR 0087-plan-in-chat-from-a-task). **Retry** on a Failed plan (`v1.PlanRetried`) checks the repos out again and resumes the planner’s session; **Plan more from here** starts a new plan from a Finished or Stopped one and stores the old chat’s rounds, answers, proposal and created Tasks as text in `v1.PlanContinued`, so it survives the old chat’s deletion. Planning worktrees count as Worktrees in Settings → Storage (ADR 0083-planning-chats).
- `ted task create` with a Run token works only from an Automation Run, in its own Factory, and records the Task as created by that Automation. A `--source` already tracked in the Factory (open, archived without merging, or Done) is refused for every caller except the app, matched through `sourceKey` in `tasks/sources.ts`; `--follow-up <id>` creates a Follow-up that shares the source (ADR 0070-automations-fire-from-the-daemon-and-queue-like-runs).
- At Merge, a failed GitHub CI check is a `github-ci` Failure case, not a send-back: `ciFailureSteps` in `packages/daemon/src/tasks/ci-failures.ts` decides what to record, close, replace or send back from the poller’s read, and only `reconcileCi` in `tasks/tasks.ts` carries it out, from the merge watcher and from the poller’s reaction. A case is keyed by `ciFailureKey` (repo, pull request, head, attempt); never record a second open case for one key, and never start or rerun a GitHub workflow for Retry. An accepted attempt is left out of `ciState` through `acceptedCi` and nothing else: GitHub’s merge state still decides, `nextStep` waits on `required-check` while GitHub blocks, and auto-merge stays off then. Its evidence is built only by `ciFailureEvidence` in `tasks/github-activity.ts`, fenced, with no name or log for a check `trustedCheck` rejects. ### Wayfinding operations

Used by `/wayfinder`.

- **Map**: an issue in the TED project labelled `wayfinder:map`.
- **Ticket**: a sub-issue of the map (`parentId` = the map), labelled with exactly one of `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling`, `wayfinder:task`. Map and tickets carry no other labels.
- **Blocking**: Linear’s native “blocked by” relation.
- **Frontier**: open sub-issues of the map with no assignee whose blockers are all completed or canceled; lowest identifier first.
- **Claim**: assign the ticket to the dev driving the map before any work.
- **Resolve**: post the answer as a comment, move the ticket to Done, then add a line (linked title + one-line gist) to the map’s Decisions so far.
- **Out of scope**: move the ticket to Canceled and add a line to the map’s Out of scope section.

## Code review before merge

Every code change gets a review before it merges to `main`, usually from Codex (`/codex-review`). Fix or answer each confirmed finding before merging.

A change also gets a security review before merging if it touches any of these: starting agents or running shell commands, messages between processes, credentials or tokens, network requests, or reading and writing files outside the repo being worked on. Use an available security review skill or tool, or review manually when none is available.
