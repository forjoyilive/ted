# Failure acceptance does not depend on the base tip

ADR 0095 bound a human’s acceptance of a failure to a tested context whose fingerprint included each repo’s base tip, the tip of `origin/<base branch>` in Ted’s clone. On a repo whose base branch gets a commit every few minutes this made acceptance unusable: a decision captured at 06:08 could not be accepted at 06:13 because four commits had reached `main` at 06:09, with the Task’s HEAD, tree and merge-base unchanged, and an acceptance that did go through was invalidated by the next base commit.

A commit on the base branch does not change what the Task branch contains or what was tested. So consent is now bound to each repo’s identity, HEAD, merge-base and worktree tree, the resolved Check definitions and environment hash, the failed-CI bindings and the CI observation, and not to the base tip. When the Task takes the new base in, by merge or rebase, its HEAD and merge-base change and consent ends then. A base commit that changes `.ted/` changes the Check hash, which also ends it. The base tip is still recorded in every context.

Contexts are compared by those fields through `sameTested` in `tasks/failure-cases.ts`, in acceptance, in obligations and at `ted failure ask`. The stored `fingerprint` is left as it was, a hash of the whole capture, and is no longer compared. That keeps version 2: contexts already in stores, with the base tip inside their fingerprint, are compared by their stored fields, so pending decisions and standing acceptances survive the upgrade and no shipped event changes (ADR 0010). A new version with a narrower fingerprint was rejected because a stored version 2 context would still have to be compared field by field with it. `version` stays in the comparison, so a version 1 context still never matches.

What this gives up: a pull request GitHub allows to merge while behind its base can now merge with a standing acceptance made before the base moved. The code that merges is the code the human accepted, and a Task with no failure cases merges the same way; Ted still rebases and reruns the Checks when GitHub reports the pull request behind or conflicting, and that rebase ends the acceptance. Local Check coverage already compared only repo, HEAD, tree and the Check hash, and is unchanged.

The same incident showed a second trap. An assessment is bound to the `contextId` of the newest evidence, or to the original context, so a Task Lead who captures a fresh context but adds evidence without naming it asks a question bound to the old one. After a real change the human then cannot accept, and nothing told either side why. Now:

- A refused acceptance says which of three things happened: the code or Checks changed, the current state could not be read, or Ted has no verifiable record of what was tested.
- For the first and third, Ted posts a “Failure acceptance refused” note, once per decision for the same advice (a second refusal posts again only if the steps it gives have changed, for example after the source Run ended), delivered to the Task Lead through the same path as the invalidation notice, with the commands to run. The invalidation notice names them too.
- `ted failure ask` refuses to post a question bound to a context that differs from the current one when a fresh capture could be attached. It still posts when the case has no context, the snapshot can’t be taken, or no later capture could attest the source, because Fixed, No longer applicable, Retry and Fix in this Task remain valid answers there.

The app’s card keeps Fixed and No longer applicable disabled until a reason is typed, and the renderer strips Electron’s `Error invoking remote method` prefix in the one function every `window.ted` request goes through.
