# Automations and Apps

Rules for Automations, Scheduled Checks, Apps, browsers, simulators and emulators. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- Automations fire only from `packages/daemon/src/automations/automations.ts`: it decides each firing (scheduled, made up, skipped), adds `automation` entries to the queue through `Tasks.addQueueSource`, starts and settles their Runs, and holds the idle timer while any Automation is on. Its Runs wait in the working-Run queue by the Automation’s priority (see `tasks.md`). `GET /automation-runs`, closed to Run tokens, lists every Factory’s firings that are queued or started, or ended in the last day (`recentAutomationRunsMs`), for the Automation Runs screen; `POST /automation-runs/:id/stop` stops a running Run, aborts a running Scheduled Check command, ends a queued check agent through `endCheckAgent`, or drops a queued firing. The screen’s filter, sort and direction are the `automationRunsView` machine setting, read and sorted only by `packages/protocol/src/automation-runs-view.ts`. An Automation Run’s ID is its firing’s ID, so `store.automations.firing(runId)` says whether a Run is one. Schedules are computed only by `packages/protocol/src/schedule.ts`; tests drive the clock with `startDaemon`’s `automations.now` and a short `checkEveryMs`. Templates must never reach real Linear or Sentry in tests. An Automation with `checkout` on gets a fresh scratch worktree of every repo per Run, made, set up in the sandbox and removed only by `automations/checkout.ts` (through `makeCopy` and `removeCopy` in `code-copy.ts`); its Apps belong to the Run through `Tasks.setRunAppOwner` and stop when the firing ends.
- A Scheduled Check is an Automation with `check` (its own command) instead of a prompt. Its firings are decided in `automations/automations.ts` like any other but never enter the working-Run queue: `startChecks` waits while the busy hold says the computer is busy (only with `waitWhenBusy` on, only for scheduled and made-up firings, until `check.runBy` or 4 hours), then `automations/scheduled-checks.ts` takes a `CheckSlots` place, gets a checkout of the default branch from the same `Checkouts` an Automation Run uses (`automations/checkout.ts`, keyed by the firing’s ID, setup included), runs the command through `runChecks` in the sandbox (Bypass excepted, like other Checks), and releases the checkout; its output stays in `TED_HOME/logs/automation-checks/<id>/`. Until it ends it holds the idle timer and counts in `activity()` through `store.setScheduledChecks`. A failure goes to `Tasks.checkFailed`, which creates one Backlog Task per failing test file (`planCheckFailures` in `automations/check-failures.ts`) keyed by `v1.AutomationCheckTaskCreated`, or adds a Ted note to the open Task with that key. Under `TED_SANDBOX=1` this repo’s `vitest.config.ts` also points `TED_SANDBOX_BIN`, on every platform, at `test/fixtures/pass-through-sandbox.sh` because a second sandbox can’t start inside the first, and `testCacheDir` keeps test locks and logs in `$XDG_CACHE_HOME/ted`. A test that starts the real sandbox without going through `TED_SANDBOX_BIN`, or checks what the sandbox refuses, calls `skipInsideTedSandbox` from `packages/daemon/test/support/ted-sandbox.ts`; so does one the sandbox stops for another reason (a Ted-home refusal, starting or inspecting processes), passing the matching `sandboxReasons` entry.
- When a Scheduled Check ends with a setup failure and no agent step runs, its error names the command’s error through `setupErrorSummary` in `automations/check-failures.ts`: the last consecutive group of error lines, with terminal colors, npm’s log-file notice and empty npm error lines removed, limited to 300 characters. This keeps the cause visible when npm ends its output with a log path. With no error line it uses the last nonempty line left after filtering; with no summary it says “see the output”.
- A Scheduled Check’s agent step (`check.agentStep`: `on-failure`, the default for a new one, `always` or `never`; `agentRunsAfter` in `automations/check-agent.ts`) is an Automation Run with the firing’s ID. `finishCheck` records the result with `v1.AutomationCheckAgentQueued` (the tested commit) and the firing stays started; the queue launches it through `launchCheckAgent` in a checkout of that commit with the prompt from `checkAgentPrompt`, which fences and redacts the result. The agent reports only through `ted automation report` (`v1.AutomationCheckAgentReported`); `endCheckAgent` is the one place a check agent’s firing ends, and when a failed Check’s agent didn’t report (it couldn’t start, failed, was stopped or went idle) it runs Ted’s own `Tasks.checkFailed` Tasks and records `v1.AutomationCheckFallbackApplied`. Its Run token gets exactly three more actions, all checked in the daemon from the firing, never from the agent: `Tasks.automationNote` (a note on an open Task this Automation created, `v1.AutomationTaskNoted` in the Comment’s commit), `Tasks.automationStart` (only a Backlog Task this firing created, in its own Factory, not a setup Task, not in Bypass, only with `check.startTasks`, which only the app sets; it queues through `queueAndAnswer` and records `v1.TaskStartedByAutomation`) and reading its own firing’s output. `ted task create` from it refuses `--start`, `--follow-up` and Asana sources, never auto-starts, and stops at `maxTasksPerFiring`. Never let any other Run start a Task through these routes.
- Apps start, stop and restart only through `packages/daemon/src/apps/apps.ts`, which the Tasks module owns: each App runs in a detached host (`apps/host.ts`) that kills its whole process group, gets its environment from `worktreeCommandEnv`, and is checked for a free port and readiness on loopback only. An App `url` must be on localhost, and the app opens only that URL or a pull request’s hosted preview. Anything that ends a Task’s worktree stops its Apps first. A launch that throws, including a host that doesn’t write its start record within `hostStartMs` (30 seconds), records the App as failed through `failStart`; otherwise its saved entry still reads as running and `ted run-app` never starts it again. Tests use `packages/daemon/test/fixtures/stub-app.ts` and call `killAppHosts` from `test/helpers.ts` in cleanup.
- `ted app stop` lets the current Task Lead stop any App on its own Task, whoever started it; `Tasks.stopApp` checks Run callers through `taskLead` before cancelling the browser or stopping the App. Sub-agents and other Runs cannot stop it, and restart stays app-only. A stop records `v2.AppStopped` with `by` and the Task Lead’s `runId`, so the thread says “Task Lead stopped” for the Task Lead and “You stopped” for the human; old `v1.AppStopped` events keep the human wording.
- A Task can show “Starting app” while one of its Apps is `starting`, or is a running device App with an active build and no `builtAt`, whether serial builds are on or off (`TaskApp.building`, `appStarting` in `packages/protocol/src/app.ts`). On each `apps-changed` the Tasks module lists the Task’s Apps and passes the first starting one to `store.noteAppStarting`, which feeds `TaskFacts.appStarting`; the value lives in memory only, because App state is not in the store. Restored Apps emit `apps-changed` too. Higher-priority statuses and ordinary Working activity take precedence over “Starting app”; with no Run mid-turn and no earlier activity message in `taskActivity` (such as checks, a slot wait or a stopped Run), the activity line names the App as “Starting <name>”.
- An Automation Run’s headless browser is started only by `createRunBrowsers` in `packages/daemon/src/apps/run-browser.ts`, as the app’s own executable with `--ted-headless-browser` (`packages/app/src/entry.ts` loads `headless-browser.ts`), talking over the child’s stdin and stdout; never give it a port, route or credential. It serves only a live Automation Run with a checkout, on a running loopback web App or Electron App (`electron: true` on a `command` App) it started (`POST /runs/:id/browser`), and closes when that App or the Run’s Apps stop. It reaches an Electron App only through the debugging port Ted gave it in `TED_ELECTRON_ARGS`, at the address `remote-page.ts` builds from that port; `appAccess` in `apps/apps.ts` gives an `electron: true` App the `electron` sandbox access group, which widens the macOS sandbox for that App (see `platform.md`). The page code and origin lock live once in `packages/app/src/browser-page.ts` for both it and the Task browser, behind its `PageDriver` interface; `resize` and `color-scheme` are refused for a Task, and `size` (the Task browser’s preview size) is refused for an Automation Run. The chosen size is held only in `createTaskBrowsers` and applied through `preview-emulation.ts`. Screenshots are `v1.RunBrowserCaptureAdded` rows, deleted with the Automation. `TED_ELECTRON_BIN` names the Electron a daemon on plain Node starts; its test (`packages/daemon/test/run-browser.test.ts`) is in the `electron` project.
- Only `packages/daemon/src/apps/simulators.ts` runs `xcrun simctl` or opens Simulator.app. Booting a simulator leaves its viewer closed. On an explicit Show request, Ted opens Simulator.app by bundle ID (`com.apple.iphonesimulator`) and falls back to DeviceHub (`com.apple.dt.Devices`), which replaces Simulator.app in Xcode 27, with `devices://device/open?id=<UDID>`, the undocumented link DeviceHub accepts to show one device; Show returns an error when neither opens instead of doing nothing. The slot rules it shares with Android (limit, line, permission ask, shut-down choice, idle shut-down) live once in `apps/device-slots.ts`, which each platform drives with a `DeviceDriver` and which runs no platform tool. Both platforms join one `DevicePool` (`apps/device-pool.ts`), which `apps.ts` creates: it holds the combined limit, the serial queue, the first-come line, the Apps waiting for a device (`wait`/`unwait`, which `slots()` reports as `waiting` for the sidebar’s panel) and the build turn. With `buildDeviceAppsOneAtATime` on, every device App start takes the turn before it boots or launches, and `apps.ts` ends it when the App’s log shows a `TED_APP_READY` line, when the App ends, or after 15 minutes; shutting a device down ends its App’s turn. Whether or not it holds the turn, a device App’s `builtAt` is set the first time its log shows `TED_APP_READY` after launch; if the build limit passes first, `notReady` is set until the line appears. A running device App with neither `builtAt` nor `notReady` reports `building`, and counts as ready only with `builtAt`: `ted run-app` waits for it and fails with the end of the log on `notReady` or an exit, `ted app list` says `building` or `not ready`, and the Apps panel says `building` or explains that the App didn’t print `TED_APP_READY` within 15 minutes. A restarted daemon gives the turn back (`restoreTurn`) to a device App that started, has no `builtAt` and hasn’t ended, timed from its `startedAt`, before it reattaches to any App or lets a device App ask for a slot. The pool also counts the device builds running now (`beginBuild`, ended by the same `endTurn`, whether the turn is on or off), and `launch` in `apps.ts` gives a device App’s `run` `TED_APP_CPUS` from `checkCpus` over that count. It clones one device per iOS simulator App per Task, boots Ted’s devices only into a free slot (`maxRunningDevices`, shared with emulators), and never shuts one down to make room unless the human picked it: the human’s ▶ names it, a Task Run’s `ted run-app` posts a `permission` Comment with `simulator` and waits, and an Automation Run’s waits in a first-come line without asking. Devices are deleted when the Task’s Apps stop for good. It also runs Meta’s `idb`, only from `control`, so an Automation Run can drive a simulator it started with the same `ted app` input commands as Android; size there is a device type that restarts the App on a new device, and `back` is refused. Tests use `test/fixtures/stub-xcrun.ts` and `stub-idb.ts` (`TED_XCRUN_BIN`, `TED_IDB_BIN`, `TED_OPEN_BIN` in `vitest.config.ts`, state in `TED_STUB_XCRUN`) and set `simulators.supported`; never boot a real simulator or run `xcodebuild` in a test.
- A waiting device App keeps its place when looking up its Task or Workflow fails, and retries on the next poll; only a Task lookup returning 404 or a successful lookup without its App declaration confirms it is gone. Before ending a waiting instance, `waitForSlot` in `apps.ts` rereads it and checks `waitingFor`, so an older lookup cannot end a restarted App.
- A waiting device App reports `TaskApp.asking` only while its slot permission request is open. `ted run-app` says it is waiting for an answer only with `asking: true`; `waitingOn` names another App’s build, and a waiting state alone says neither. After that build turn ends, a Task Run’s CLI waits silently until Ted reports another reason or the App starts; an Automation Run still reports that it is waiting for a slot.
- Only `packages/daemon/src/apps/emulators.ts` runs the Android SDK’s `emulator`, `adb` and `avdmanager`. Its slot rules come from `apps/device-slots.ts`, the same module iOS uses. It makes one AVD per Android emulator App per Task from the system image and hardware of the AVD the App’s `device` names, boots it headless into a free slot (`maxRunningDevices`, shared with simulators) on a console port it picks, and asks for a slot the same way iOS does, through a `simulator` permission Comment whose ask has `platform: 'android'`. Show saves a snapshot and boots it again with a window, then restarts the App. AVDs are deleted when the Task’s Apps stop for good. An Automation Run drives an emulator it started with `ted app screen|tap|type|key|swipe|appearance|size|screenshot`, through `POST /runs/:id/apps/device` and `control` in `emulators.ts`; the request (`DeviceRequest` in `packages/protocol/src/device.ts`) stays kind-neutral for iOS, the screen listing is fenced as App data, and typed text is printable ASCII in one quoted argument. Tests use `test/fixtures/stub-emulator.ts`, `stub-adb.ts` and `stub-avdmanager.ts` (`TED_EMULATOR_BIN`, `TED_ADB_BIN`, `TED_AVDMANAGER_BIN` in `vitest.config.ts`, state in `TED_STUB_ANDROID`) and set `emulators.supported`; never boot a real emulator or run Gradle in a test.
- `POST /runs/:id/apps/device` also lets the current live Task Lead in Validate use `screen`, `tap` and `pair` on its own ready iOS simulator App. `Tasks.runDeviceCommand` checks the Run token, Lead and Stage, and `Apps.control` resolves the App and the Task’s simulator. `ted app pair <App>` reads a Ted Dev pairing code from stdin. The simulator adapter uses the fixed dev pairing URL and omits simctl’s output from errors because it may contain the code. Task screenshots use the Task’s screenshot route.
- `paired_preview: { desktop, relay }` belongs only to an `ios-simulator` App. Both dependencies have `preview_only: true`: the desktop is an Electron App with URL readiness in the primary repo, and the relay is a web App with URL readiness and an allocated port in the phone’s repo. Preview-only Apps start only as dependencies of a live Validate Task Lead’s paired preview; restart them by stopping and starting the phone App. `startPairedPreview` in `tasks/tasks.ts` checks these declarations, and `tasks/paired-preview.ts` owns their preparation and cleanup.
- A Validate Lead starting an iOS App with `paired_preview` starts the named local relay and preview-only Electron App before the phone. The relay uses the phone’s worktree and an allocated loopback port. The desktop uses its Task worktree if present or a detached default-branch checkout with sandboxed setup and no copied local files. Preview App repo records are only for App lookup. Task repo membership and check inputs stay intact. The preview’s `TED_HOME`, Electron profile, in-memory keyring and Wrangler state are isolated. Stop the iPhone App to stop its dependencies and remove their scratch files. Worktree removal also cleans the preview.
