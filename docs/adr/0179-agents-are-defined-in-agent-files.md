# Agents are defined in Agent files

The Coordinator and the Planner were defined only in code: their instructions were string constants in `coordinators/coordinators.ts` and `plans/prompts.ts`, and what each may do was decided by which routes it could reach. Custom Agents (TED-429) need the same things written down, so the built-in Agents and the user’s own are now defined the same way (TED-491).

**Two files per layer.** An Agent’s settings are in `agents.yaml` and its instructions in `agents/<id>.md`, in the same layers as the Workflow: TED’s defaults (`workflow/defaults/`), the Library (`TED_HOME/library/`) and `.ted/` on the default branch. `agents.yaml` maps an Agent id to `name`, `agent` (the Provider), `model`, `powers` and `based_on`. An id follows the custom Stage id rule. A new Agent needs a `name` and an instructions file in its layer or one below. Any other key is an error, not a warning as in `workflow.yaml`, because these files decide what a chat may do.

**Powers are a fixed list.** `ask` (Ask the user), `manage_tasks` (Manage Tasks), `propose_tasks` (Propose Tasks) and `read_code` (Read the code), listed in `agentPowers` in `@ted/protocol/agent-files`. A power not listed is off, and an unknown one is an error. The built-in Coordinator has `ask` and `manage_tasks`; the built-in Planner has `ask`, `propose_tasks` and `read_code`.

**Layers merge like Stages.** A higher layer’s entry overrides the keys it names, and `powers` is replaced whole. A higher layer’s instructions file replaces the one below it. `resolveAgents` in `workflow/agent-files.ts` is the one function that merges them. `resolveWorkflow` exposes the result as `workflow.agents` and `workflow.agent(id)`, each with its source layer (`ted`, `library` or `factory`). An override of an Agent’s instructions writes `based_on` as `stageFileHash` of the inherited text. `findAgentDrift` in `workflow/drift.ts` flags it once that text changes, and the count joins Stage drift in `drift-changed`.

**TED keeps its own text around the Agent’s.** Only the Agent’s role and approach move into its instructions file. The command list, the authorization and untrusted-text rules, the round and proposal formats and the writing guidance stay in TED’s code (`coordinatorInstructions`, `plannerInstructions`), so an override changes how an Agent works but can’t remove TED’s rules. A chat reads its Agent’s instructions through `Workflows.resolve` without a fetch when it starts. A chat whose Run resumes keeps its session. A chat that TED restarts from its saved history, or from a prepared Run, reads the Agent’s current instructions again, as it read TED’s built-in text before this change. Recording the Agent on the chat, so a running chat keeps the one it started with, is TED-492’s work.

**TED checks every action against the chat’s stored Agent, never against what the Run says.** A Run can claim any identity or power in its output or in a request. Whether a chat may ask the user, act on Tasks, propose Tasks or read the code is decided from the Agent recorded for that chat when it started, so editing or removing an Agent can’t change what a running chat may do. Recording the Agent on the chat and checking each route against its powers is TED-492’s work. Until then the Coordinator and planning routes stay closed to every other Run, as before.

**Repo Agents get no extra confirmation on this Mac.** Their powers arrive through `.ted/` on the default branch, reviewed in a pull request like the rest of a Factory’s settings.
