# TED

TED (“Totally Excellent Development”) is a desktop app for running software factories: agents carry development tasks through a configurable workflow, and the human steers through an inbox and comments. Vocabulary lives in `GLOSSARY.md`; use its terms.

## Code

For validation policy and Factory customization, read [Factory validation](docs/testing/factory-validation.md). The test tooling in this repo (`pnpm check`, the Vitest setup, the test locks and logs, `pnpm release`) is development tooling, not part of the app; its detail is in [This repo’s test tooling](docs/testing/test-tooling.md).

pnpm workspace on Node 24: `packages/protocol` (paths, `daemon.json`, API types, `DaemonClient`), `packages/daemon`, `packages/cli`, `packages/app` (Electron, React renderer). Node and Electron run the `.ts` files directly. Only the renderer has a build step (Vite), and the preload stays plain `.cjs` because Electron’s sandboxed preload loader doesn’t strip types (ADR 0011).

- `pnpm install`, then `pnpm typecheck`, `pnpm lint` (Biome, then Oxlint with the anti-slop rules below; `pnpm format` fixes what both can), `pnpm test` (Vitest). Run all three locally before merging to `main`: nothing runs them on GitHub, and agents never start GitHub workflows. Agents, TED’s own Runs included, run only the test files their change touches (`pnpm vitest run <files>`) and never `pnpm test`, `pnpm check` or `pnpm flaky`; with `TED_RUN` set, those and any Vitest run of more than 3 test files are refused. In this Factory TED chooses and runs a Task’s tests itself: the Affected tests Check (`pnpm check --affected`, `scripts/affected.ts`) runs every changed test file, every test file that imports a changed module and the Electron app tests named after changed app source. When that is more than `maxAffectedFiles` (60), or the test runner changed, `chooseTier` narrows it to the changed test files, the direct importers and the app tests, and then to the changed test files and the app tests; the scheduled full check covers the rest. A Run picks no test files for coverage; the Task Lead in Validate runs only the Electron app tests a sandboxed Check left out (`node_modules/.cache/ted-affected-left-out.txt`) and a single file to look into a failure (`.ted/stages/work.md`, `.ted/stages/validate.md`). `pnpm check --affected --list` prints the selection and the reason for each file without running anything. A test command can sit waiting for a test slot before it starts; let it wait. A test that passed on retry is broken: fix its timing. Keep each Electron test file to about a dozen app launches. Resolve the native test executable with `resolveElectron` from `packages/app/test/support/electron-installation.ts`, never by requiring `electron`, and launch an app in a test with `firstWindow` from `packages/app/test/first-window.ts`. To try the app from a one-off script, launch it only through `withApp` in `packages/app/scripts/with-app.ts`; never launch Electron from a script by hand or leave it running. Inside Codex’s sandbox, and on macOS inside TED’s own sandbox (`TED_SANDBOX=1`), the Electron test files are skipped and `pnpm app` refuses, unless the sandbox is an Electron App’s (`TED_SANDBOX_ELECTRON=1`), as TED Dev’s is. Read [This repo’s test tooling](docs/testing/test-tooling.md) before changing `scripts/`, `vitest.config.ts` or `packages/daemon/test/support/`: it covers the Vitest projects and worker counts, the slots and suite lock that let runs share the machine, the wait and failure logs, machine load, `pnpm flaky` and `pnpm release`.
- Code run from source is TED Dev; only the code `pnpm package` stages is the release. `edition` in `packages/protocol/src/edition.ts` says which, and `markRelease` in `packages/app/scripts/stage.ts` is the only thing that changes it. Anything machine-wide (home folder, app name and userData, keyring service, installed command, login item, update checks, simulator names) comes from `identity()` or checks `edition`, so the two never touch each other (ADR 0089-dev-and-release-run-side-by-side).
- `pnpm ted <args>` runs the `ted` CLI from source, against TED Dev’s home. It starts the daemon if needed.
- `pnpm app` builds the renderer and opens TED Dev from source. Like `ted`, it reuses a running daemon or starts one.
- `pnpm ted dev run start [--provider claude|codex] [--cwd <dir>] "<prompt>"` starts a Run in a detached host; `pnpm ted dev run show <run-id>` prints its state and Conversation. `pnpm ted dev slow` prints the daemon’s slow requests and event-loop stalls of the last minute and hour. `pnpm ted dev memory` prints the memory the daemon, Run hosts and agents use (`GET /diagnostics/memory`, `MemoryUse` in `packages/protocol/src/memory.ts`; a Run token can’t read it); Settings → Developer and the sidebar footer show the same figures with the app’s own processes added by the main process. A process’s memory is measured only by `processMemory` in `packages/daemon/src/process-memory.ts`: its footprint on macOS (what Activity Monitor shows), its resident size elsewhere (ADR 0168-process-memory-is-its-footprint).
- The human adds a Factory from the app’s Add Factory form: `POST /factories/check-repo` checks each row and `POST /factories` adds it and clones in the background, with progress as `factory-updated` events. Queued Tasks of a Factory that is still cloning wait until `v1.FactoryCloned` (ADR 0034).
- A folder with no GitHub remote can get a private GitHub repo from the Add Factory repo row (**Set up a GitHub repo…**). Only `packages/daemon/src/github/repo-setup.ts` does it, one step per app-only `POST /factories/github-setup/step` (`init`, `ignore`, `commit`, `create`, `push`), each skipped when already done; git runs there with hooks and fsmonitor off. It is the only code that writes to a folder the user chose; never give its routes `runToken` or `fileToken` (ADR 0164-ted-sets-up-a-github-repo-for-a-folder-on-request).
- `pnpm ted dev factory add <owner/repo | git URL> --key NB [--local-folder <dir>]` adds a one-repo Factory and clones it into `TED_HOME/repos/`; `pnpm ted dev factory local-folder NB <dir>` changes the folder `worktree.copy` reads from. Then `pnpm ted task create --factory NB "<title>"` and `pnpm ted task start NB-1` start a Claude Code Task Lead in the Task’s worktree. `pnpm ted help` lists every command.
- Set `TED_HOME` to use a folder other than the default: `~/.ted-dev` for TED Dev, `~/.ted` for the release. Tests always set it to a temp folder. `TED_IDLE_EXIT_MS`, `TED_CLAUDE_BIN` and `TED_CODEX_BIN` are TED Dev overrides only; release finds `claude` and `codex` through the login-shell `PATH`. Read runtime `TED_*` inputs through `tedEnv` in `packages/protocol/src/env.ts`, which classifies them and ignores test-only and unknown names in release; use `filterTedEnv` when forwarding an environment to TED processes. Classify new inputs there, with a reason for each retained release input. See `docs/environment.md` for the policy and inventory.
- Write erasable TypeScript only, and name the `.ts` file in relative imports (ADR 0008).
- Only `packages/daemon/src/store/` imports LiveStore. Events are named `v<N>.<PastTense>` and never edited once shipped; a change is a new versioned event (ADR 0010). The one exception is `store/compact.ts`, which `data.ts` runs once per home with the store closed: after a pre-update backup it drops the lines from old `v1.RunOutputRead` and `v2.RunOutputRead` events in a copy of the event log, verifies the copy against the original, renames it into place and records `outputCompaction` in `store/ted-store.json`. A second exception is `store/drop-output.ts`: when the state database is about to be rebuilt, or once per home when `outputDrop` in `store/ted-store.json` isn’t `done` and at least 1,000 events would go, and after a pre-update backup taken in that same open, `data.ts` drops every `RunOutputRead` event that a later one for the same Run replaces, renumbers the rest into one chain in a copy of the event log, verifies the copy against the original, removes every state file and renames it into place. Event sequence numbers, and the Task log and interval boundary IDs the state derives from them, can therefore change across a rebuild: use them only for ordering and never store one in an event. A third exception is `store/blank-replaced.ts`: once per home, right after the compaction and after a pre-update backup taken in that same open, `data.ts` blanks the one text field of old events a later event replaces (`v1.SubAgentRequested.prompt` once a `v4.RunStarted` or `v1.SubAgentRequestDropped` with its ID follows, and `v1.CoordinatorChanged.data`, `v1.WorkflowLayerAccepted.files` and `v2.TaskDraftSaved.draft` in all but the last per Factory or layer) in a copy of the event log, verifies the copy with the compaction’s checks plus a check that only replaced events changed, renames it into place and records `replacedText` in `store/ted-store.json`. Don’t rewrite any other event (ADR 0099-old-run-output-events-are-compacted-once, ADR 0122-replaced-run-output-events-are-dropped-before-a-state-rebuild, ADR 0158-replaced-text-in-old-events-is-blanked-once).
- Write an event only when it changes something. A Factory layer is accepted again only when its files differ from the stored copy (`choose` in `workflow/workflows.ts`); the New Task dialog sends its draft 1 second after the last change and at once on close (`taskDraftSession`); a Coordinator chat is saved only through `store.coordinators.save`, which keeps the newest 100 receipts and commits `v1.CoordinatorChatChanged` with just the changed fields and the added list items (`store/coordinator-change.ts`), or nothing; `noteTaskWait` writes no empty wait observation for a Task it hasn’t seen this session (ADR 0157-four-events-are-written-only-when-something-changed).
- Only `store/trim-changesets.ts` changes rows in the state database outside LiveStore: `data.ts` runs it with the store closed: before `openStore` when `checkStore` says `current` and no output drop is due, and right after a state rebuild, by closing the store it just opened and opening it again before services start. When LiveStore’s `__livestore_session_changeset` table takes 20 MB or more it deletes the rows and runs `VACUUM`, at every such open. Delete rows only, never drop the table, which makes LiveStore rebuild the state. It holds only because TED has no sync backend: revisit it before adding one or upgrading LiveStore (ADR 0156-livestore-changeset-rows-are-emptied-when-the-store-opens).
- Only `store/sync-head.ts` writes LiveStore’s `__livestore_sync_status` row in the event log: `openStore` calls `markEventsSynced` before LiveStore starts, with the store closed, to set `head` to the newest event’s number, so LiveStore doesn’t load every event into memory as not yet pushed. It also lowers a head that is above the newest event, which LiveStore refuses to open. It holds only because TED has no sync backend: revisit it before adding one or upgrading LiveStore. Run lists in `store/index.ts` select `runFields`, without the prompt columns, because LiveStore keeps each query’s result in memory (ADR 0163-the-event-log-is-marked-synced-before-the-store-opens).
- A commit is in memory until LiveStore’s leader writes it to the event log; `server.ts` awaits `store.persisted()` after every non-`GET` route before answering. Code outside a route that must know a write is on disk awaits it too (ADR 0053-write-routes-answer-after-the-event-log-saves).
- Every daemon route sits behind the loopback guard in `packages/daemon/src/server.ts`. Each JSON request body has one hand-written parser beside its type in `packages/protocol/src/`, with an explicit request return type and a direct all-fields test; the CLI reuses these parsers. A parser takes `Untyped` and reads it only through `@ted/protocol/parse`, as `packages/protocol/src/failure-parsers.ts` does (ADR 0175-untyped-data-is-read-through-one-parse-module). The machine `settingParsers` table stays in `routes/machine.ts`; attachment resolution and authorization stay in the daemon. A route, its token flags and its handler live in the area’s file in `packages/daemon/src/routes/` (`tasks.ts`, `factories.ts`, `machine.ts`, `integrations.ts`, `runs.ts`); routes that work before the store opens stay in `server.ts`. Clients call the daemon only through `DaemonClient` (ADR 0009). A route is closed to Run tokens unless it sets `runToken: true`, which only actions spec 2.3 allows may set (ADR 0015). Any route other than a `GET` is also closed to the token in `daemon.json` unless it sets `fileToken: true`; only requests signed with the app’s in-memory key may call it. Never mark a route that answers a request, passes a Gate, posts as the human, changes settings or credentials, adds or changes a Factory, or starts a Run outside a Task. Never write the app’s key to disk, send it in a request, or hand it to the daemon other than on its stdin (ADR 0054-the-app-holds-the-human-token-in-memory).
- The renderer reaches the daemon only through `window.ted`. A forwarded daemon call is added only to `forwardedRequests` in `packages/app/src/daemon-requests.ts`, with the same name, arguments and result as its `DaemonClient` method. Main-process actions and semantic adapters use `CustomRequests` in `custom-requests.ts` and explicit handlers in `main.ts` and `renderer/ted.ts`; the preload stays as it is (ADR 0011). The renderer imports only types from `@ted/protocol`; a value comes from its own sub-path (`@ted/protocol/run`, `@ted/protocol/task`, …), because the main entry also exports `DaemonClient` and the request parsers, which use Node modules. `packages/app/test/renderer-bundle.test.ts` fails when one gets in.
- Every renderer colour is a token in `packages/app/src/renderer/styles/tokens.css`, written as `light-dark(<light>, <dark>)` with Figma’s Theme variable name; components use a CSS Module and `var(--…)` only, and `packages/app/test/theme.test.ts` fails on any other colour. Reuse the shared components in `packages/app/src/renderer/components/` (ADR 0020). A button is `--button-height` (28px) high, or `--button-height-small` (24px) inside a dense row such as a list row, a diff header or a Board card; buttons side by side use the same one. `Button` sets both, and a hand-made bordered or filled button takes its height from the same tokens (`packages/app/test/theme.test.ts`).
- UI labels use sentence case with `GLOSSARY.md` terms capitalized, both parts of a hyphenated term included (Sign-Off, Sub-Agent, Follow-Up). A label ends with “…” only when the item needs more input before it acts: a dialog, a picker or a name.
- User-facing text calls Claude Code, Codex and Antigravity Providers (Settings → Providers, the Provider field), and names the Provider when one is known. “Agent” stays for a Run or its role (Task Lead, sub-agent, agent Run). Code identifiers, settings keys, setting IDs, events, routes and `workflow.yaml` keys keep their `agent` names (`AgentKind`, `enabledAgents`, `lead.agent`). The CLI flag is `--provider` (`ted run start`, `ted automation create`, `ted coordinator create`); `--agent` still works as an unlisted second spelling.
- Keyboard shortcuts live in `packages/app/src/renderer/keymap.ts` and run through the one `keydown` listener in `App.tsx`; don’t add another window key listener for a shortcut. A new list or card view marks its focusable items `data-nav-item` so J/K reach them (ADR 0074-keyboard-shortcuts-one-keymap-one-listener).
- In the Task thread, an open request with one answer field (not a round or a proposal) is answered from `RequestDock` at the bottom, in place of the Comment box; its card passes `answerBelow` and has no answer field. The answer controls are `RequestAnswer` in `RequestCard.tsx`; don’t draw a second copy on the card. The dock carries `data-request` and the card `data-docked`, which `requestScope` in `key-targets.ts` uses for the request shortcuts; with several open requests a shortcut acts only when focus is in the dock or on the shown request’s card.
- The first-Factory guide card’s text and button are chosen only by `guideCard` in `packages/app/src/renderer/guide.ts`; the agent writes none of it. Whether setup counts as done is decided only by `setUpDone` in `store/index.ts`, which the guide carries as `setUp`; the card never decides it from the Task. A guide starts only in `TedStore.createFactory` and ends only through `v1.FactoryGuideEnded`, committed with the Task the user creates after setup, the setup Task’s archive or delete, or `hideGuide`; the app reads live guides through `GET /guides` and `guides-changed`. Comments marked by the old `v1.CommentMarkedTutorial` are left out of every Comment list in the store (ADR 0162-a-guide-card-follows-the-first-factorys-setup).
- A Task’s status, markers and activity line are chosen only in `packages/daemon/src/tasks/status.ts` from `TaskFacts`; a new input is a new `TaskFacts` field, and the app only draws what the Task carries (ADR 0023).
- A new machine setting is a field and default in `packages/protocol/src/settings.ts` plus a parser in `settingParsers` in `packages/daemon/src/routes/machine.ts`; every change is one `v1.MachineSettingsChanged` event. A new App Settings page is a component in `packages/app/src/renderer/settings/`, listed in `settingsSections` in `sections.tsx` (ADR 0024). A new fixed row or group heading in App Settings or Factory settings gets an entry in `packages/app/src/renderer/settings-search.ts` and that id on its element (`setting` on `SettingRow` and `SettingsGroup`, `data-setting` elsewhere), or the Settings search and ⌘K can’t find it; rows that depend on data (Stages, Checks, repos, backups) stay out. Open a setting only through `openSetting` in `setting-focus.ts` (ADR 0131-settings-search-reads-one-list-in-the-renderer).
- Text the daemon logs or puts in Copy report goes through `redactSecrets` in `packages/daemon/src/redact.ts`, which removes URL passwords and token-shaped strings (ADR 0024).
- A new kind of live update is a new `DaemonEvent` variant, emitted by `TedStore` after its commit (ADR 0012), by `packages/daemon/src/data.ts` for the store’s own status, by the Tasks module for `slots-changed` (ADR 0030), by `factory-setup.ts` for `factory-updated` (ADR 0034), or by `factory-settings.ts` for `factory-settings-changed` (ADR 0123-factory-settings-open-from-the-clone-and-refresh-in-the-background).
- A machine or Factory problem shows as a banner: call `banners.raise(…)` where you detect it and `banners.clear(…)` where it resolves, through `packages/daemon/src/banners.ts`; a button that does work in the daemon registers `banners.onAction(problem, handler)`; a button that first needs a folder sets `choose: 'folder'`, and the app sends the chosen path to the handler. A stops-work problem starting is the `banner-raised` event (ADR 0021).
- `packages/daemon/src/data.ts` opens the store, takes backups and restores them; a route that needs the store gets it through `data.services()`, so it waits while the store opens and answers `503` while a data screen is up. Only `/events`, `/data-status`, `/backups`, `/shutdown`, `/command-line`, `/app/open`, `/diagnostics/slow` and `/diagnostics/profile` work before the store opens (ADR 0026). `pnpm ted backup list` and `pnpm ted backup restore <name>` work on `TED_HOME/backups/`. A pre-update or before-restore backup holds only the event log files and `store/ted-store.json`, cloned with `COPYFILE_FICLONE`, never the state database, which a restore rebuilds; backup attachment files are a clone or hard link of the originals (`shareFile` in `backups.ts`), and nothing else is ever hard-linked. Keep 5 daily, 3 pre-update and 3 before-restore. The daily check exports the event log only when it will write today’s backup, and pruning deletes only a folder whose name, `lstat` and real path check out (ADR 0156-backups-hold-only-the-event-log-and-share-attachments).
- The daemon times every route in `server.ts` and watches its own event loop in `packages/daemon/src/slow-moments.ts`: a request of 100 ms or more and a stall of 200 ms or more are counted for an hour in memory and logged, rate-limited, through `console`. A route is named only by `routePattern` (`routes/route.ts`), which works from the route’s regular expression and never from the request, so keep each capture a whole path segment and never log a URL, query string or body. A route that holds its response open on purpose (a stream, a long-poll, a wait for the app or another process) sets `waits: true` so it isn’t timed. `GET /diagnostics/slow` (`ted dev slow`) returns the figures as `SlowMoments`; a Run token can’t read it. `POST /diagnostics/profile` records a CPU profile through `cpu-profile.ts` with `node:inspector`’s in-process session, one at a time, 5 to 120 seconds, into `TED_HOME/logs/profiles/` (mode `0600`, plain folders only, newest five kept). It never sets `runToken` or `fileToken`: only the app’s key starts a profile, from Settings → Developer, and nothing opens an inspector port The daemon process also runs a watchdog worker thread (`watchStalls` in `cpu-profile.ts`): when the daemon’s thread has sent it no beat for 2 seconds it profiles that thread through `connectToMainThread` until the beats return, and a stall of 5 seconds or more is saved as `stall-<time>.cpuprofile` in the same folder (newest five kept) with a log line naming the file. Never keep the CPU profiler running outside a stall or a profile the app asked for, because it slows CPU-bound work several times over; only `main.ts` turns the watchdog on (`stallProfiles`), never a daemon started in a test, and the app’s own profile pauses it (ADR 0114-the-daemon-records-its-own-slow-moments, ADR 0124-the-daemon-saves-a-profile-of-a-long-stall).
- Anything that starts new work (a Run, App, simulator or Automation firing) checks `store.newWorkHold()` or goes through the queue, which starts nothing while the disk is full. Code that deletes files under `TED_HOME` checks the name and real path first and never follows links, like `retention.ts` and `storage.ts`. `TED_FREE_BYTES_FILE` names a file holding the free bytes TED should see; `vitest.config.ts` points every test at one with 500 GB, and `startDaemon`’s `disk` option overrides it (ADR 0039).
- Retention deletes a Run folder (`TED_HOME/runs/<id>/`) only through `pruneRunOutput` in `packages/daemon/src/retention.ts`, and only `runOutputEnd` there decides when: never while the Run is live, its Task is open (not Done, not archived), or a Coordinator, an Automation draft, or a planning chat owns it, whatever its outcome; otherwise `runOutputDays` days (machine setting, default 7) after the Task became Done or was archived, or after a Run without a Task ended. A finished sub-agent’s clock starts when it ended, even while its Task is open, unless it has a side chat or is a reviewer whose Task is still in the visit it reviewed. Anything new that reads a finished Run’s output or revives it adds its case to `runOutputEnd`. Tests drive the clock with `startDaemon`’s `retention.now` and a short `checkEveryMs` (ADR 0098-run-output-stays-while-its-task-is-open, ADR 0156-a-finished-sub-agents-output-goes-days-after-it-ended). Archived Tasks are deleted automatically only by `createArchiveCleanup` in `packages/daemon/src/tasks/archive-expiry.ts`, through `Tasks.delete`, on the same timer, when the `deleteArchivedAfterDays` machine setting is set (default `null`, never); `archivedDue` there decides which are due and which are kept: an archived Task goes with every Task under it, as one delete from the top, only when all of them are archived that long, none has an open pull request and none blocks a Task that isn’t archived; an archived Task under an archived or Done parent goes only with its parent. `GET /archive-expiry` reports both counts from it for the app’s confirm dialog, and `close()` waits for a delete in progress before the Tasks module closes.
- What a Stage does (Validate’s Checks and reviewer, Work’s hand-off, Merge, Cleanup, Clarify rounds, `--skip`, holding Stages) and where it sits relative to Work are decided only in `packages/protocol/src/stage.ts` (`@ted/protocol/stage`): code asks a trait helper such as `validates(stage)` or `stagePhase(stage, order)`, or `stageWith(trait)` for the id itself, never a Stage id comparison. An unknown id has no special work and is an ordinary working Stage. Plain checks for Done or Backlog, moves to a named Stage and event values stay as ids (ADR 0171-what-a-stage-does-is-decided-in-one-module).
- A custom Stage is any id `isCustomStageId` in `stage.ts` accepts, written by hand in `order` with a Stage file `stages/<id>.md` in that layer or one below (`checkLayer`’s `inherited`, built with `inheritedFrom`); `StageId` and `AgentStageId` take any string, and `BuiltInStageId` lists the built-ins for tables that must cover them all. Name a Stage in TED’s text with the Workflow’s `name(id)`, never by capitalizing the id. Find a Task’s next Stage only through `next` on the Workflow `taskWorkflow` returns, which `withRecorded` binds to the order recorded at the Task’s last Stage entry (`v4.TaskStageEntered`, `store.recordedStages`), so a Task whose Stage left `order` goes on to the first later Stage that still exists; pass that order to `stagePhase` and `clarifyIsOver` for a Task. The Board read (`boardStages`) is the Factory’s resolved Stage list, and `factory-stages-changed` says when it changes (ADR 0172-custom-stages-are-written-by-hand).
- What a Task is in the middle of (a transition, a hold, starting, Checks, deleting, hierarchy work, stopping for blockers, the merge watch) is recorded only in `packages/daemon/src/tasks/in-flight.ts`; new in-flight work is a new kind there, and busy checks ask it with `is` or `busy` (ADR 0072).
- Only `packages/daemon/src/tasks/` starts Tasks or changes their Stage; it owns the order of git, commit and Run steps (ADR 0016). A route open to Runs acts only on the Run’s own Task, except the Factory-scoped peer reads and plain peer notes in `tasks/peers.ts`; only a current Task Lead uses those, and only the Task Lead reports outcomes. Peer notes persist with their recipient Comment in one commit and use its delivery receipt; they reach working Leads through steering and replacement Leads through the normal Task start. A Coordinator Run reaches only the `/coordinator/tasks` routes and `/coordinator/archive|unarchive|delete`, for Tasks of its own Factory, and acts only through `Coordinators.act`, `Coordinators.create` and `Coordinators.remove` in `packages/daemon/src/coordinators/coordinators.ts`: create (`Tasks.coordinatorCreate`, recorded with `v1.TaskCreatedByCoordinator` in the Task’s own commit), start, move, tell (`Tasks.coordinatorTell`), resume (`Tasks.coordinatorResume`), done (`Tasks.markDone` with `coordinator`, only at Merge once every pull request merged) and answer (`Tasks.coordinatorAnswer`), which closes any open request on the Task the way the human’s answer would: a `question`, a Gate request or sign-off, a `round`, a `proposal`, a size check, a failure decision or a Task Lead’s archive request (with an open pull request it must say close or keep, and it can’t answer Archive when Tasks under the Task would be archived too). `mayAnswer` there decides how each kind is answered. Its `ted coordinator` commands never read a file, and its message text and round answers are capped and go through `redactSecrets` in the route. A test waits only for a condition it can check (a state TED records, an event, a request, a file written whole), never for time to pass, and gets TED’s clocks and poll intervals through the options `startDaemon` and the test harnesses already take (`retention.now`, `mergePollMs`, `checkEveryMs` and the like) instead of real delays. A wait inside a test has no budget smaller than the trip it covers: walking a Task to a sign-off goes through `toSignoff` in `test/merge-harness.ts`, not a fresh `waitUntil`. In the app, measure an element only once it exists with a nonzero box (an image only once it has loaded and decoded, a window only once the renderer reports its new size), and read a style only once the setting that changes it has reached the renderer. A stub or fixture that writes state a test reads writes a temp file and renames it into place. A test’s timeout covers its work under that load, about three times what it takes alone: a test that walks a Task through several Stages sets its own (`90_000` and up), not the default 30 seconds. A longer timeout, a sleep or a retry is never the fix for a race: find what the test raced and wait for that. Code that compares elapsed time takes its start from the same clock read as its first check, so a pause between two reads can’t use up a short budget.
- Work TED starts for a Task or Run (the Run host, Checks, worktree `setup` and `teardown`, the settings Run now, an App the human didn’t start) starts through `workCommand` in `packages/daemon/src/priority.ts` with the `lowPriorityWork` machine setting, which puts `/usr/sbin/taskpolicy -c utility` in front on macOS and `nice -n 10` elsewhere; niceness does nothing on macOS. The daemon, `git`, `gh`, the Task shell and an App the human starts stay at normal priority. Tests compare a child’s scheduler priority (`ps -o pri=`, macOS) or niceness (Linux) with their own, since they may run lowered themselves (ADR 0102-work-ted-starts-runs-at-low-priority).
- A child process the daemon starts gets its environment from `packages/daemon/src/command-env.ts`: the one `Environment` the daemon read from the login shell, through `worktreeCommandEnv` for anything a repo’s settings run, `gitEnv` for git and `ghEnv` for `gh`. Don’t build an environment inline or read the login shell again elsewhere (ADR 0071-one-daemon-environment-for-every-child-process).
- `packages/daemon/test/support/setup.ts` gives every test file `TED_TEST_RUN`, `TED_TEST_FILE` and `TED_EXIT_WITH_PID` in `process.env`. Spawn children with `{ ...process.env, … }` so they inherit them: the daemon, Run hosts and the app exit when the `TED_EXIT_WITH_PID` process dies, and after each file and after the run, Vitest kills every process whose environment carries that file’s or run’s ID, and nothing else. Close Electron apps with `closeApp` from `packages/app/test/close-app.ts`, which kills the app if `close()` hangs; when the test has failed it first saves a screenshot, the window’s text and the test home’s `logs/` and `runs/` under `node_modules/.cache/ted-test-captures/<run>/` and prints the folder. After launching the app, wait with `loadedWindow` or `appLoaded` from `packages/app/test/first-window.ts`, which wait for `data-loaded="true"` on the app’s root (the first Factories load has ended); the sidebar draws before the data arrives. Assert on what stays (the daemon’s record, a list), not on text the app shows for a moment. `expect.poll` waits up to 10 seconds (`vitest.config.ts`). A stub step that acts on the human’s answer goes in `everyMessage`, so it runs when TED delivers the answer, not before. Build the renderer in app tests only with `buildRenderer` from `packages/app/test/build-renderer.ts`, which builds once per run: a second build empties `dist/renderer` under apps other files are starting. `DaemonClient` uses `node:http`, not `fetch`: Electron’s `fetch` throws `setTypeOfService EINVAL` outside any `await` when the daemon resets a connection. The app writes uncaught exceptions to `TED_HOME/logs/app.log` and shows no dialog when launched by tests.

## Anti-slop rules

`pnpm lint` runs the [anti-slop](https://github.com/dmmulroy/anti-slop) rules through Oxlint (`oxlint.config.ts`, plugin in `tools/oxlint/anti-slop/`, ADR 0174-anti-slop-rules-guard-new-code). They reject patterns that hide what a value is: `typeof` checks instead of parsing input once at its boundary, unexplained casts, `unknown` in parameters, returns and type aliases, loose `Record<string, …>` types, and module mocking.

- Code a Task adds or rewrites must pass. Old code keeps the violations recorded per file and rule in `oxlint-suppressions.json`, and a file can’t gain more. A Task doesn’t have to clean the rest of a file it touches, but when its change removes violations, `pnpm lint` fails until it runs `pnpm exec oxlint --prune-suppressions` and commits the lower counts. Don’t follow Oxlint’s message to run `oxlint --suppress-all`: with no file named, it records every new violation in the repo.
- Remove a cast where you can. A cast that stays in source code gets a one-line `// SAFETY: <reason>` comment just before it, stating what makes it true; this is an exception to the no-comments rule. Test files and fixtures don’t need one.
- No `vi.mock`, `vi.doMock` or Jest equivalents: pass a real seam.
- No `oxlint-disable` or `eslint-disable` comments; `pnpm lint` fails on them. A violation is fixed, or its file pattern is exempted in `oxlint.config.ts` with the reason in ADR 0174.
- Untyped data (a request body, a file, Provider CLI output, YAML, an Asana, Linear or GitHub response, JSON stored in the database, a message in the app) is read only through `@ted/protocol/parse` (`packages/protocol/src/parse.ts`), the one file exempt from `no-runtime-typeof`, `no-unknown-parameters`, `no-unknown-returns`, `no-unknown-type-aliases` and `no-unsafe-dictionary-type`. Use `Json`, `JsonObject` and `JsonArray` in place of `Record<string, unknown>`; the checks (`isString`, `isObject`, `isOneOf`, `parseJson` and the like) where a bad value is skipped or collected; and `reader(fail)` where it is refused with an error naming the field. `Untyped` is only the parameter of a function that reads its input this way. `packages/protocol/src/failure-parsers.ts` is the pattern (ADR 0175-untyped-data-is-read-through-one-parse-module).

Used by `/wayfinder`.

- **Map**: an issue in the TED project labelled `wayfinder:map`.
- **Ticket**: a sub-issue of the map (`parentId` = the map), labelled with exactly one of `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling`, `wayfinder:task`. Map and tickets carry no other labels.
- **Blocking**: Linear’s native “blocked by” relation.
- **Frontier**: open sub-issues of the map with no assignee whose blockers are all completed or canceled; lowest identifier first.
- **Claim**: assign the ticket to the dev driving the map before any work.
- **Resolve**: post the answer as a comment, move the ticket to Done, then add a line (linked title + one-line gist) to the map’s Decisions so far.
- **Out of scope**: move the ticket to Canceled and add a line to the map’s Out of scope section.
