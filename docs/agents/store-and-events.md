# Store and events

Rules for the store, events, the event log and opening the data (`packages/daemon/src/store/`, `data.ts`). They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- The store is split by area so a change to one area runs only that area’s tests under the Affected tests rule. `store/index.ts` only re-exports, and `store/schema.ts` only composes `store/schema/<area>.ts` (tables, events and materializers) and lists the tables in a fixed order, because LiveStore’s state hash follows that order and a new order rebuilds the state. `openStore` (`store/open.ts`) builds the shared context with `openContext` (`store/context.ts`: LiveStore, `commit`, `persisted`, the helpers more than one area uses and the mutable `storeState`) and spreads each area’s methods (`store/<area>.ts`, `<area>Area(ctx)`) into one `TedStore`, whose interface is the union of the area interfaces (`store/types.ts`). New store code goes in its area module; a helper moves to `context.ts` only when a second area needs it. A test that covers an area imports that area’s interface and states it with one line, such as `expectTypeOf<TedStore>().toExtend<ChecksArea>()`, so a change to the area module selects it.
- Only `packages/daemon/src/store/` imports LiveStore. Events are named `v<N>.<PastTense>` and never edited once shipped; a change is a new versioned event. The one exception is `store/compact.ts`, which `data.ts` runs once per home with the store closed: after a pre-update backup it drops the lines from old `v1.RunOutputRead` and `v2.RunOutputRead` events in a copy of the event log, verifies the copy against the original, renames it into place and records `outputCompaction` in `store/ted-store.json`. A second exception is `store/drop-output.ts`: when the state database is about to be rebuilt, or once per home when `outputDrop` in `store/ted-store.json` isn’t `done` and at least 1,000 events would go, and after a pre-update backup taken in that same open, `data.ts` drops every `RunOutputRead` event that a later one for the same Run replaces, renumbers the rest into one chain in a copy of the event log, verifies the copy against the original, removes every state file and renames it into place. Event sequence numbers, and the Task log and interval boundary IDs the state derives from them, can therefore change across a rebuild: use them only for ordering and never store one in an event. A third exception is `store/blank-replaced.ts`: once per home, right after the compaction and after a pre-update backup taken in that same open, `data.ts` blanks the one text field of old events a later event replaces (`v1.SubAgentRequested.prompt` once a `v4.RunStarted` or `v1.SubAgentRequestDropped` with its ID follows, and `v1.CoordinatorChanged.data`, `v1.WorkflowLayerAccepted.files` and `v2.TaskDraftSaved.draft` in all but the last per Factory or layer) in a copy of the event log, verifies the copy with the compaction’s checks plus a check that only replaced events changed, renames it into place and records `replacedText` in `store/ted-store.json`. Don’t rewrite any other event.
- Write an event only when it changes something. A Factory layer is accepted again only when its files differ from the stored copy (`choose` in `workflow/workflows.ts`); the New Task dialog sends its draft 1 second after the last change and at once on close (`taskDraftSession`); a Coordinator chat is saved only through `store.coordinators.save`, which keeps the newest 100 receipts and commits `v1.CoordinatorChatChanged` with just the changed fields and the added list items (`store/coordinator-change.ts`), or nothing; `noteTaskWait` writes no empty wait observation for a Task it hasn’t seen this session.
- Only `store/trim-changesets.ts` changes rows in the state database outside LiveStore: `data.ts` runs it with the store closed: before `openStore` when `checkStore` says `current` and no output drop is due, and right after a state rebuild, by closing the store it just opened and opening it again before services start. When LiveStore’s `__livestore_session_changeset` table takes 20 MB or more it deletes the rows and runs `VACUUM`, at every such open. Delete rows only, never drop the table, which makes LiveStore rebuild the state. It holds only because Ted has no sync backend: revisit it before adding one or upgrading LiveStore.
- Only `store/sync-head.ts` writes LiveStore’s `__livestore_sync_status` row in the event log: `openStore` calls `markEventsSynced` before LiveStore starts, with the store closed, to set `head` to the newest event’s number, so LiveStore doesn’t load every event into memory as not yet pushed. It also lowers a head that is above the newest event, which LiveStore refuses to open. It holds only because Ted has no sync backend: revisit it before adding one or upgrading LiveStore. Run lists select `runFields` (`store/context.ts`), without the prompt columns, because LiveStore keeps each query’s result in memory.
- A commit is in memory until LiveStore’s leader writes it to the event log; `server.ts` awaits `store.persisted()` after every non-`GET` route before answering. Code outside a route that must know a write is on disk awaits it too.
- A new kind of live update is a new `DaemonEvent` variant, emitted by `TedStore` after its commit, by `packages/daemon/src/data.ts` for the store’s own status, by the Tasks module for `slots-changed`, by `factory-setup.ts` for `factory-updated`, or by `factory-settings.ts` for `factory-settings-changed`.
- `packages/daemon/src/data.ts` opens the store, takes backups and restores them; a route that needs the store gets it through `data.services()`, so it waits while the store opens and answers `503` while a data screen is up. Only `/events`, `/data-status`, `/backups`, `/shutdown`, `/command-line`, `/app/open`, `/diagnostics/slow` and `/diagnostics/profile` work before the store opens. `pnpm ted backup list` and `pnpm ted backup restore <name>` work on `TED_HOME/backups/`. A pre-update or before-restore backup holds only the event log files and `store/ted-store.json`, cloned with `COPYFILE_FICLONE`, never the state database, which a restore rebuilds; backup attachment files are a clone or hard link of the originals (`shareFile` in `backups.ts`), and nothing else is ever hard-linked. Keep 5 daily, 3 pre-update and 3 before-restore. The daily check exports the event log only when it will write today’s backup, and pruning deletes only a folder whose name, `lstat` and real path check out.
