# Automations and Apps

Rules for Automations, Scheduled Checks, Apps, browsers, simulators and emulators. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- Automations fire only from `packages/daemon/src/automations/automations.ts`: it decides each firing (scheduled, made up, skipped), adds `automation` entries to the queue through `Tasks.addQueueSource`, starts and settles their Runs, and holds the idle timer while any Automation is on. An Automation Run’s ID is its firing’s ID, so `store.automations.firing(runId)` says whether a Run is one. Schedules are computed only by `packages/protocol/src/schedule.ts`; tests drive the clock with `startDaemon`’s `automations.now` and a short `checkEveryMs`. Templates must never reach real Linear or Sentry in tests (ADR 0070-automations-fire-from-the-daemon-and-queue-like-runs). An Automation with `checkout` on gets a fresh scratch worktree of every repo per Run, made, set up in the sandbox and removed only by `automations/checkout.ts`; its Apps belong to the Run through `Tasks.setRunAppOwner` and stop when the firing ends (ADR 0146-an-automation-run-can-have-a-checkout-and-apps).
- A Scheduled Check is an Automation with `check` (its own command) instead of a prompt. Its firings are decided in `automations/automations.ts` like any other but never enter the working-Run queue: `startChecks` waits while the busy hold says the computer is busy (only with `waitWhenBusy` on, only for scheduled and made-up firings, until `check.runBy` or 4 hours), then `automations/scheduled-checks.ts` takes a `CheckSlots` place, gets a checkout of the default branch from the same `Checkouts` an Automation Run uses (`automations/checkout.ts`, keyed by the firing’s ID, setup included), runs the command through `runChecks` in the sandbox (Bypass excepted, like other Checks), and releases the checkout; its output stays in `TED_HOME/logs/automation-checks/<id>/`. Until it ends it holds the idle timer and counts in `activity()` through `store.setScheduledChecks`. A failure goes to `Tasks.checkFailed`, which creates one Backlog Task per failing test file (`planCheckFailures` in `automations/check-failures.ts`) keyed by `v1.AutomationCheckTaskCreated`, or adds a Ted note to the open Task with that key. Under `TED_SANDBOX=1` this repo’s `vitest.config.ts` also points `TED_SANDBOX_BIN`, on every platform, at `test/fixtures/pass-through-sandbox.sh` because a second sandbox can’t start inside the first, and `testCacheDir` keeps test locks and logs in `$XDG_CACHE_HOME/ted`. A test that starts the real sandbox without going through `TED_SANDBOX_BIN`, or checks what the sandbox refuses, calls `skipInsideTedSandbox` from `packages/daemon/test/support/ted-sandbox.ts`; so does one the sandbox stops for another reason (a Ted-home refusal, starting or inspecting processes), passing the matching `sandboxReasons` entry (ADR 0147-a-scheduled-check-runs-a-command-as-a-check-on-the-default-branch).
- A Scheduled Check’s agent step (`check.agentStep`: `on-failure`, the default for a new one, `always` or `never`; `agentRunsAfter` in `automations/check-agent.ts`) is an Automation Run with the firing’s ID. `finishCheck` records the result with `v1.AutomationCheckAgentQueued` (the tested commit) and the firing stays started; the queue launches it through `launchCheckAgent` in a checkout of that commit with the prompt from `checkAgentPrompt`, which fences and redacts the result. The agent reports only through `ted automation report` (`v1.AutomationCheckAgentReported`); `endCheckAgent` is the one place a check agent’s firing ends, and when a failed Check’s agent didn’t report (it couldn’t start, failed, was stopped or went idle) it runs Ted’s own `Tasks.checkFailed` Tasks and records `v1.AutomationCheckFallbackApplied`. Its Run token gets exactly three more actions, all checked in the daemon from the firing, never from the agent: `Tasks.automationNote` (a note on an open Task this Automation created, `v1.AutomationTaskNoted` in the Comment’s commit), `Tasks.automationStart` (only a Backlog Task this firing created, in its own Factory, not a setup Task, not in Bypass, only with `check.startTasks`, which only the app sets; it queues through `queueAndAnswer` and records `v1.TaskStartedByAutomation`) and reading its own firing’s output. `ted task create` from it refuses `--start`, `--follow-up` and Asana sources, never auto-starts, and stops at `maxTasksPerFiring`. Never let any other Run start a Task through these routes (ADR 0155-a-scheduled-check-can-start-an-agent-that-files-and-starts-tasks).
- Apps start, stop and restart only through `packages/daemon/src/apps/apps.ts`, which the Tasks module owns: each App runs in a detached host (`apps/host.ts`) that kills its whole process group, gets its environment from `worktreeCommandEnv`, and is checked for a free port and readiness on loopback only. An App `url` must be on localhost, and the app opens only that URL or a pull request’s hosted preview. Anything that ends a Task’s worktree stops its Apps first. Tests use `packages/daemon/test/fixtures/stub-app.ts` and call `killAppHosts` from `test/helpers.ts` in cleanup (ADR 0084-apps-run-in-detached-hosts).
- An Automation Run’s headless browser is started only by `createRunBrowsers` in `packages/daemon/src/apps/run-browser.ts`, as the app’s own executable with `--ted-headless-browser` (`packages/app/src/entry.ts` loads `headless-browser.ts`), talking over the child’s stdin and stdout; never give it a port, route or credential. It serves only a live Automation Run with a checkout, on a running loopback web App or Electron App (`electron: true` on a `command` App) it started (`POST /runs/:id/browser`), and closes when that App or the Run’s Apps stop. It reaches an Electron App only through the debugging port Ted gave it in `TED_ELECTRON_ARGS`, at the address `remote-page.ts` builds from that port; only `SandboxScope.electron` widens the macOS sandbox for Electron, and only for that App (ADR 0153-an-automation-run-drives-its-electron-apps-over-their-debugging-port). The page code and origin lock live once in `packages/app/src/browser-page.ts` for both it and the Task browser, behind its `PageDriver` interface; `resize` and `color-scheme` are refused for a Task. Screenshots are `v1.RunBrowserCaptureAdded` rows, deleted with the Automation. `TED_ELECTRON_BIN` names the Electron a daemon on plain Node starts; its test (`packages/daemon/test/run-browser.test.ts`) is in the `electron` project (ADR 0149-an-automation-run-drives-its-web-apps-in-a-headless-browser).
- Only `packages/daemon/src/apps/simulators.ts` runs `xcrun simctl` or opens Simulator.app. The slot rules it shares with Android (limit, line, permission ask, shut-down choice, idle shut-down) live once in `apps/device-slots.ts`, which each platform drives with a `DeviceDriver` and which runs no platform tool (ADR 0156-device-slot-rules-live-in-one-module). It clones one device per iOS simulator App per Task, boots Ted’s devices only into a free slot (`maxBootedSimulators`), and never shuts one down to make room unless the human picked it: the human’s ▶ names it, a Task Run’s `ted run-app` posts a `permission` Comment with `simulator` and waits, and an Automation Run’s waits in a first-come line without asking. Devices are deleted when the Task’s Apps stop for good. It also runs Meta’s `idb`, only from `control`, so an Automation Run can drive a simulator it started with the same `ted app` input commands as Android; size there is a device type that restarts the App on a new device, and `back` is refused (ADR 0152-an-automation-run-drives-its-ios-simulator-apps). Tests use `test/fixtures/stub-xcrun.ts` and `stub-idb.ts` (`TED_XCRUN_BIN`, `TED_IDB_BIN`, `TED_OPEN_BIN` in `vitest.config.ts`, state in `TED_STUB_XCRUN`) and set `simulators.supported`; never boot a real simulator or run `xcodebuild` in a test (ADR 0085-ios-simulator-apps).
- Only `packages/daemon/src/apps/emulators.ts` runs the Android SDK’s `emulator`, `adb` and `avdmanager`. Its slot rules come from `apps/device-slots.ts`, the same module iOS uses. It makes one AVD per Android emulator App per Task from the system image and hardware of the AVD the App’s `device` names, boots it headless into a free slot (`maxRunningEmulators`, counted apart from simulators) on a console port it picks, and asks for a slot the same way iOS does, through a `simulator` permission Comment whose ask has `platform: 'android'`. Show saves a snapshot and boots it again with a window, then restarts the App. AVDs are deleted when the Task’s Apps stop for good. An Automation Run drives an emulator it started with `ted app screen|tap|type|key|swipe|appearance|size|screenshot`, through `POST /runs/:id/apps/device` and `control` in `emulators.ts`; the request (`DeviceRequest` in `packages/protocol/src/device.ts`) stays kind-neutral for iOS, the screen listing is fenced as App data, and typed text is printable ASCII in one quoted argument (ADR 0151-an-automation-run-drives-its-android-emulator-apps). Tests use `test/fixtures/stub-emulator.ts`, `stub-adb.ts` and `stub-avdmanager.ts` (`TED_EMULATOR_BIN`, `TED_ADB_BIN`, `TED_AVDMANAGER_BIN` in `vitest.config.ts`, state in `TED_STUB_ANDROID`) and set `emulators.supported`; never boot a real emulator or run Gradle in a test (ADR 0147-android-emulator-apps).
