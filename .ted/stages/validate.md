# Validate

## Goal

Find out whether the work does what the Task asks, without breaking anything else. Validate runs without the human: it never asks a question. Every doubt ends as a blocking finding sent back to Work, or as a note. Pass means no blocking findings.

## Before you start

If the Factory has checks, Ted ran them as Validate’s first step, one after another, and they all passed before these instructions reached you; the results are at the end of these instructions. A failed check sends the Task back to Work instead, so you never start with one failing. A check the human accepted shows as failed and accepted, not passed; `ted failure list` and `ted failure show <id>` show it. When you assess a failure case with `ted failure assess <id> --file <json>` and another open Task in this Factory tracks the fix, add `"repairTask":"<Task ID>"` (such as `"repairTask":"TED-639"`) whenever you recommend waiting for it, or recommend Accept because it tracks the fix: the decision then offers Wait for that Task as one choice.

These testing instructions are specific to developing Ted. The Affected tests check and the three-file limit on a Run’s own test runs are this repo’s test tooling; other Factories choose their own commands and Stage instructions. See [Factory validation](../../docs/testing/factory-validation.md) when configuring those choices.

Do not run the full test suite unless asked to or unless strictly necessary.

## Steps

1. The checks already ran Docs drift, Typecheck, Lint and Affected tests, and Mobile Typecheck, Mobile Lint and Mobile Tests when the Task includes `ted-mobile`. Docs drift ran first and may have committed doc fixes; those commits are part of the change to review. Affected tests is `pnpm check --affected`: Ted runs the test files the change added or changed, the node test files that import a changed file themselves, and the Electron app tests named after changed app source. Test files that reach a changed file only through other files are left to the scheduled full check. Nothing runs on GitHub for a pull request or a push to `main`: the CI workflow runs only when the human starts it by hand, and the full suite never runs there. Agents never start GitHub workflows. Don’t pick test files for coverage and don’t run the affected tests again. `pnpm check --affected --list` prints what the check selects and why, without running anything. One exception: on macOS Ted’s sandbox can’t start Electron or a second sandbox, so a sandboxed check leaves the Electron app tests out, along with any test file in which the sandbox made a test skip itself, and lists them in `node_modules/.cache/ted-affected-left-out.txt`. On macOS, leave the listed Electron files for a desktop terminal outside the Run. Use the declared Electron App for preview evidence and report those files as left out. Never clear a sandbox marker to try a launch. When that file exists, run the other test files it lists, at most 3 per `pnpm vitest run <files>` command, once per visit, and say in your note what it left out that you didn’t run. To look into a failure you may run that one test file yourself. Never `pnpm test`, `pnpm check` or a whole test folder: this repo’s test helpers refuse a Run’s test run of more than 3 files, and `pnpm check --affected` without `--list`. A test command can sit waiting for a test slot before it starts; let it wait. When a test you ran fails, fetch the latest base branch and run the same test there. If it passes there, the fix is probably already on the base branch: send the Task back to Work with the finding “merge the latest base branch and run this test again”, not a repair. If it fails there the same way, it is outside this Task: search this Factory’s open Tasks (`ted peers`) and the base branch’s recent commits for the test file, record a note with the test name, the error and any Task already working on it, and carry on.
2. Have the reviewer review the diff with no Work context: start it with `ted run start --reviewer --prompt-file <file>`, give it only the Task, the Design brief and the diff against the base branch, and wait for its findings with `ted run wait`. Tell the reviewer in the prompt file not to run tests: you run them, and it reads the diff. Ted picks the reviewer’s agent, model and effort. A reviewer that is queued is waiting for a free Run; keep waiting with `ted run wait`, which holds no slot, however long it takes, and don’t start a second one. If `ted run start --reviewer` fails, try again after a minute, up to three times. If it still fails, review the diff yourself against the Task and the Design brief, and say in your note that Ted’s reviewer could not start and what the error was. Start one reviewer per visit: Ted refuses a second reviewer, and any other sub-agent unless the Factory’s Workflow sets `stages.validate.sub_agents: true`. Don’t commit after you start the reviewer: Ted refuses `ted outcome advance` while `HEAD` isn’t the commit the reviewer was given, and the Task then goes back to Work so the next round reviews the change. From the second round, Ted tells you which round this is and lists the earlier findings. It gives the reviewer those findings and the diff since the commit the last round reviewed, and limits it to checking that each finding is fixed and that the fixes broke nothing. Your prompt file still supplies the Task and the Design brief; it can’t widen the review. When the Task comes back only because its branch conflicted with the base branch, Ted says so and limits the reviewer to the conflict resolution: the base commit merged in, the files that conflicted and the Task’s own commits since the last review.
3. The reviewer’s review is the code review `AGENTS.md` asks for before a merge. Don’t run `/codex-review` or send the diff to any other service as well.
4. Perform a security review when the change touches starting agents or running shell commands, messages between processes, credentials or tokens, network requests, or reading and writing files outside the repo. Use an available security review skill or tool, or review manually when none is available. Include the method used and its confirmed findings in the Validate result.
5. Check the diff against `AGENTS.md` and record any rule it breaks.
6. Check the change against the Task’s description and the Design brief. Look for missing cases, broken behaviour and leftover debugging code.
7. Try the change by hand, always against this Task’s own `TED_HOME` (`node_modules/.cache/ted-home` in the worktree), never `~/.ted` or `~/.ted-dev`:
   - For a change in `packages/app`, start Ted Dev with `ted run-app "Ted Dev"`, open each changed screen in light mode, and attach a screenshot of each with `ted comment --attach`. Light-mode images alone are sufficient. Take them with Playwright against Ted Dev launched with `TED_HIDDEN_WINDOW=1`. Judge them against the Design brief and the Figma file named in `AGENTS.md`. If Figma can’t be read, judge them against the Design brief alone and say so in a note. Quit Ted Dev when the screenshots are taken.
   - For New Task visuals and keyboard behavior, use `ted run-app "Ted iPhone Fixture"`. It opens the real sheet with Sample Factory. Capture the sheet while the keyboard is visible and again after dismissing it. Use `ted app screenshot "Ted iPhone Fixture"`. Check Cancel, reopen New Task, and confirm Create shows the sample Task’s reference. The fixture keeps submissions in memory.
   - For other changed phone screens and real Task submission, start the phone app with `ted run-app "Ted Dev iPhone"`, use `ted app screen` and `ted app tap` to open each changed screen, and attach a screenshot of each with `ted app screenshot "Ted Dev iPhone"`. Judge them against the Design brief. For a screen that needs a paired Mac, follow [Paired iPhone previews](../../docs/development/paired-iphone-preview.md). For real submission, confirm the same Task reference in Ted Dev Preview. The iPhone App starts its own desktop preview and local relay. Never deploy the relay.
   - Something that can’t be checked this way, such as a native dialog, is a note saying what the human should look at, not a reason to wait.
   - For a change in `packages/daemon`, `packages/cli` or `packages/protocol`, run the changed `ted` commands with `env -u TED_RUN_CAPABILITY -u TED_RUN_TOKEN -u TED_RUN -u TED_TASK -u TED_PLAN TED_HOME="$PWD/node_modules/.cache/ted-home" pnpm ted <args>` and paste the output into your note. Keep Task-control commands such as `ted comment`, `ted checks` and `ted outcome` in the normal Run environment.
   - Before you report, stop everything you started for this: quit Ted Dev, and end the daemon you started with this `TED_HOME` (`kill $(node -p 'require("./node_modules/.cache/ted-home/daemon.json").pid')`), the local relay if you started one, and any process you left running from the worktree. Ted ends what is left when the Task’s worktree is removed, but a daemon left running keeps writing backups and holding memory until then.
8. Sort every finding as blocking (the Task isn’t done until it’s fixed) or a note (worth knowing, fine to merge). In the first round, a finding about this Task’s own change that takes a few lines to fix, such as a duplicated line, a missing sentence in a Stage file or a label that differs from the Design brief, is blocking: fixing it now costs less than a separate Task. Post a short note listing what you ran and what you found, with the notes.

## Done when

There are no blocking findings and the note is posted. Then report the outcome with what the review and the screenshots found, for the human’s confirmation row: `ted outcome advance --review pass --review-notes <n>`, adding `--visual pass --visual-notes <n>` when you judged screenshots. `<n>` is how many notes you posted, such as `--review-notes 2`, not their text. The notes go into the Review brief.

## Send back when

There is a blocking finding. Write each one, numbered, in a findings file and run `ted outcome back --to work --findings <file>`, with `--review fail` or `--visual fail` when that is where it came from. In a round where Ted says a new finding sends the Task back only if it is P1, say in the file which findings are P1 and which are earlier findings still not fixed, and add `--severity p1`, or `--severity unfixed` when the only blocking findings are earlier ones still not fixed; Ted refuses the send-back without one of them, and the other new findings go in your note. Every return to Work counts, failed checks included. From the fifth, Ted checks whether the rounds are converging and may ask the human instead; it tells you what happens.

## Never ask the human

Don’t run `ted outcome ask`, `ted ask` or `ted comment --choice` in Validate. Decide with these rules, and list each decision in your note under “Decided without the human”:

- A check fails for a reason outside this Task: a note, as in step 1.
- Fixing a finding would change what the Task delivers: send it back to Work with the smallest fix that keeps what the Task’s description promises. If no such fix exists, send it back saying Work must remove the part that causes the finding and say so in its note.
- A finding is about code this Task didn’t change, or asks for more than the Task’s description does: a note, not a blocking finding.
- From the second round, a new finding about code the fixes didn’t touch: a note, unless it is P1. P1 means the change loses or corrupts data, opens a security hole, or breaks behaviour the Task’s description asks for. When Ted says the round checks a conflict resolution, a new finding about code the resolution didn’t touch is a note unless it is P1. When Ted says the round reviews the whole change again, sort findings as in the first round. When Ted says that from this round a new finding sends the Task back only if it is P1 (the Factory’s `stages.validate.p1_only_from`), every new finding that isn’t P1 is a note, wherever it is in the change; an earlier round’s finding that is still not fixed stays blocking.
- A tool or service is unavailable (a reviewer that can’t start, Figma, a sandbox refusal): do the step another way or skip it, and say which in a note.
