# A Run’s output lives in `host.log`; the store records only how far it was read

This amends ADR 0013 and ADR 0043.

The daemon used to copy every line of every agent’s output into the store: each poll of a Run’s `host.log` committed one `v2.RunOutputRead` event holding the lines, and its materializer inserted one `conversationEntries` row per line. On one machine, after about a day, the event log was 660 MB (536 MB of it in 60,360 `v2.RunOutputRead` events), the state database was 1.33 GB, the daemon used 3.3 GB of memory and a full CPU core, and “the event log did not save in time” (ADR 0053) answered 500 to callers 45 times in six hours. Later the store stopped opening at all: copying the 1.33 GB state database into memory failed with SQLite’s out-of-memory error.

`host.log` already holds the same lines on disk, and is what the events were copied from. So the lines now stay there and nowhere else.

- **New output commits `v3.RunOutputRead { runId, toOffset, lastOutputAt }`.** `toOffset` is the byte offset in `host.log` the daemon has read up to. `lastOutputAt` is the time of the newest `out` record in the batch (the host’s `at`, or the time the daemon read it when the record has none), or `null` when the batch held no output line. The materializer sets `runs.readOffset` and, when `lastOutputAt` isn’t `null`, `runs.lastOutputAt`. The stall check reads that one column instead of sorting a table.
- **The offset and what the lines led to still move together.** `store.recordRunOutput` commits `v3.RunOutputRead` in the same LiveStore commit as the events derived from those lines (`v1.RunSessionIdentified`, `v1.RunProblemFound`, `v1.RunRetryingChanged`, `v1.RunEnded`, `v1.RunStateChanged`, `v1.RunAutoModeUnavailable`, permission Comments and their withdrawals), exactly as before. A daemon killed before the commit is saved re-reads from the old offset and derives the same events again. Lines are no longer stored, so none can be lost or stored twice: a line is in the Conversation once its byte range is below the saved offset.
- **Old events keep loading but store no lines.** `v1.RunOutputRead` and `v2.RunOutputRead` stay defined as they shipped. Their materializers now set only `runs.readOffset` and, for `v2`, `runs.lastOutputAt` from the last entry’s `at`. The `conversationEntries` table is gone from the state schema, and so are its deletes in the materializers that remove a Task’s, Automation draft’s, Coordinator’s or plan’s Runs. Dropping the table and adding the column change the state schema’s hash, so an existing home rebuilds its state database from the event log the first time this version opens it. On the store above, the rebuilt state database is 84 MB, the rebuild takes 18 seconds and later opens take 3.5 seconds.
- **The Conversation is read from `host.log`.** `RunManager.output` (`packages/daemon/src/runs/run-output.ts`) returns the `out` records below the Run’s read offset as `{ offset, line, at }`: the record’s byte offset, its line and the host’s `at`, the same values the store used to return. A record without `at`, written by a host older than ADR 0043, comes back without one; the stored copy used to carry the time the daemon read it. The reader builds the path from the Run ID the store holds, refuses an ID that isn’t a plain name under `runs/`, and opens the file without following a link.
- **A cache per Run.** The reader keeps each Run’s parsed entries and the offset it parsed up to, and reads only the bytes after that on the next call. The cache holds at most 64 Runs and 64 MB of log bytes; over either limit it drops the Runs read longest ago, never the one just read. `last` and `findLast` (the newest lines, the permission prompt lookup, the last thing an agent said) read the file backwards in 1 MB pieces when the Run isn’t cached, so they don’t load a long Run.
- **When `host.log` isn’t whole.** Retention (ADR 0039) deletes a Run’s folder 14 days after its last output and cuts a finished Run’s log over 100 MB to its tail. A missing log gives an empty Conversation. A log shorter than the read offset was cut: the reader serves the tail, with offsets counted back from the read offset so they match the original ones. Neither case throws. The Run chat then shows a “From TED” row, “Output no longer kept” or “Earlier output no longer kept”.
- **The app.** An open Run chat reloads on `run-output` through `useReloading` in `renderer/data.ts`, which already runs at most one reload and queues at most one more, so a burst of events doesn’t stack reloads. Since November 2026 a `run-output` event for new agent output carries `lines: true`, and the chat hooks reload for those at most once a second (the first after a quiet second at once); the daemon keeps what it parsed from a Run’s lines beside its cached lines (`parsedOutput`) and gives it only the new ones.

## Considered Options

- **Keep the lines in the store and add an index.** It fixes the table scans but not the size of the event log, the state database or the daemon’s memory.
- **Keep `conversationEntries` rows for old events as a fallback when `host.log` is gone.** Rejected: those rows are what made the state database too large to open.
- **Commit the offset less often than once per poll.** Rejected for now: output read but not committed would be derived again after a crash, and observers would be told twice. A `v3.RunOutputRead` event is about 110 bytes.

## Consequences

- Backups (ADR 0026) copy the store, so a backup no longer contains Run chat output. Restoring one on a machine without the `runs/` folders gives Runs with empty Conversations.
- A Run’s Conversation lasts as long as its `host.log`. Retention is unchanged here, so the chat of a Run that last wrote output more than 14 days ago is empty, where it used to be kept in the store forever.
- Existing event logs still hold their `v2.RunOutputRead` lines; nothing reads them. Removing them from the log is a separate change.
- A finished Run whose log was cut and which is then revived appends to a file shorter than its read offset, so the daemon reads nothing new from it. This was already so before this change.
- `GET /runs/:id/chat` still parses the whole Conversation on each reload (ADR 0043); only reading it got cheaper.
