# TED

TED (“Totally Excellent Development”) is a desktop app for running software factories: agents carry development tasks through a configurable workflow, and the human steers through an inbox and comments. Vocabulary lives in `GLOSSARY.md`; use its terms.

## Code

pnpm workspace on Node 24: `packages/protocol` (paths, `daemon.json`, API types, `DaemonClient`), `packages/daemon`, `packages/cli`, `packages/app` (Electron, React renderer). Node and Electron run the `.ts` files directly. Only the renderer has a build step (Vite), and the preload stays plain `.cjs` because Electron’s sandboxed preload loader doesn’t strip types (ADR 0011).

- `pnpm install`, then `pnpm typecheck`, `pnpm lint` (Biome; `pnpm format` fixes), `pnpm test` (Vitest). Run all three locally before merging to `main`; GitHub CI runs on Ubuntu every Monday on `main` and when started by hand (`gh workflow run CI --ref <branch>`). `pnpm release <version>` checks `main` is clean and pushed, runs all three locally (and GitHub CI with `--linux`), bumps the version, tags `v<version>`, pushes, builds the macOS app on this machine and installs it in `/Applications`; `pnpm release --install` installs the last build again. The GitHub release workflow runs only when started by hand.
- Code run from source is TED Dev; only the code `pnpm package` stages is the release. `edition` in `packages/protocol/src/edition.ts` says which, and `markRelease` in `packages/app/scripts/stage.ts` is the only thing that changes it. Anything machine-wide (home folder, app name and userData, keyring service, installed command, login item, update checks, simulator names) comes from `identity()` or checks `edition`, so the two never touch each other (ADR 0089-dev-and-release-run-side-by-side).
- `pnpm ted <args>` runs the `ted` CLI from source, against TED Dev’s home. It starts the daemon if needed.
- `pnpm app` builds the renderer and opens TED Dev from source. Like `ted`, it reuses a running daemon or starts one.
- `pnpm ted dev run start [--agent claude|codex] [--cwd <dir>] "<prompt>"` starts a Run in a detached host; `pnpm ted dev run show <run-id>` prints its state and Conversation.
- The human adds a Factory from the app’s Add Factory form: `POST /factories/check-repo` checks each row and `POST /factories` adds it and clones in the background, with progress as `factory-updated` events. Queued Tasks of a Factory that is still cloning wait until `v1.FactoryCloned` (ADR 0034).
- `pnpm ted dev factory add <owner/repo | git URL> --key NB [--local-folder <dir>]` adds a one-repo Factory and clones it into `TED_HOME/repos/`; `pnpm ted dev factory local-folder NB <dir>` changes the folder `worktree.copy` reads from. Then `pnpm ted task create --factory NB "<title>"` and `pnpm ted task start NB-1` start a Claude Code Task Lead in the Task’s worktree. `pnpm ted help` lists every command.
- Set `TED_HOME` to use a folder other than the default: `~/.ted-dev` for TED Dev, `~/.ted` for the release. Tests always set it to a temp folder. `TED_IDLE_EXIT_MS` shortens the idle exit of a daemon that `ted` or the app started. `TED_CLAUDE_BIN` and `TED_CODEX_BIN` name the `claude` and `codex` binaries the daemon starts.
- Write erasable TypeScript only, and name the `.ts` file in relative imports (ADR 0008).
- Only `packages/daemon/src/store/` imports LiveStore. Events are named `v<N>.<PastTense>` and never edited once shipped; a change is a new versioned event (ADR 0010).
- A commit is in memory until LiveStore’s leader writes it to the event log; `server.ts` awaits `store.persisted()` after every non-`GET` route before answering. Code outside a route that must know a write is on disk awaits it too (ADR 0053-write-routes-answer-after-the-event-log-saves).
- Every daemon route sits behind the loopback guard in `packages/daemon/src/server.ts`. A route and the parsers for its request body live in the area’s file in `packages/daemon/src/routes/` (`tasks.ts`, `factories.ts`, `machine.ts`, `integrations.ts`, `runs.ts`); routes that work before the store opens stay in `server.ts`. Clients call the daemon only through `DaemonClient` (ADR 0009). A route is closed to Run tokens unless it sets `runToken: true`, which only actions spec 2.3 allows may set (ADR 0015). Any route other than a `GET` is also closed to the token in `daemon.json` unless it sets `fileToken: true`; only requests signed with the app’s in-memory key may call it. Never mark a route that answers a request, passes a Gate, posts as the human, changes settings or credentials, adds or changes a Factory, or starts a Run outside a Task. Never write the app’s key to disk, send it in a request, or hand it to the daemon other than on its stdin (ADR 0054-the-app-holds-the-human-token-in-memory).
- The renderer reaches the daemon only through `window.ted`. A new daemon call goes in `requests` in `packages/app/src/main.ts` and in `packages/app/src/renderer/ted.ts`; the preload stays as it is (ADR 0011).
- Every renderer colour is a token in `packages/app/src/renderer/styles/tokens.css`, written as `light-dark(<light>, <dark>)` with Figma’s Theme variable name; components use a CSS Module and `var(--…)` only, and `packages/app/test/theme.test.ts` fails on any other colour. Reuse the shared components in `packages/app/src/renderer/components/` (ADR 0020).
- Keyboard shortcuts live in `packages/app/src/renderer/keymap.ts` and run through the one `keydown` listener in `App.tsx`; don’t add another window key listener for a shortcut. A new list or card view marks its focusable items `data-nav-item` so J/K reach them (ADR 0074-keyboard-shortcuts-one-keymap-one-listener).
- A Task’s status, markers and activity line are chosen only in `packages/daemon/src/tasks/status.ts` from `TaskFacts`; a new input is a new `TaskFacts` field, and the app only draws what the Task carries (ADR 0023).
- A new machine setting is a field and default in `packages/protocol/src/settings.ts` plus a parser in `settingParsers` in `packages/daemon/src/routes/machine.ts`; every change is one `v1.MachineSettingsChanged` event. A new App Settings page is a component in `packages/app/src/renderer/settings/`, listed in `settingsSections` in `sections.tsx` (ADR 0024).
- Text the daemon logs or puts in Copy report goes through `redactSecrets` in `packages/daemon/src/redact.ts`, which removes URL passwords and token-shaped strings (ADR 0024).
- A new kind of live update is a new `DaemonEvent` variant, emitted by `TedStore` after its commit (ADR 0012), by `packages/daemon/src/data.ts` for the store’s own status, by the Tasks module for `slots-changed` (ADR 0030), or by `factory-setup.ts` for `factory-updated` (ADR 0034).
- A machine or Factory problem shows as a banner: call `banners.raise(…)` where you detect it and `banners.clear(…)` where it resolves, through `packages/daemon/src/banners.ts`; a button that does work in the daemon registers `banners.onAction(problem, handler)`; a button that first needs a folder sets `choose: 'folder'`, and the app sends the chosen path to the handler. A stops-work problem starting is the `banner-raised` event (ADR 0021).
- `packages/daemon/src/data.ts` opens the store, takes backups and restores them; a route that needs the store gets it through `data.services()`, so it waits while the store opens and answers `503` while a data screen is up. Only `/events`, `/data-status`, `/backups`, `/shutdown`, `/command-line` and `/app/open` work before the store opens (ADR 0026). `pnpm ted backup list` and `pnpm ted backup restore <name>` work on `TED_HOME/backups/`.
- Anything that starts new work (a Run, App, simulator or Automation firing) checks `store.newWorkHold()` or goes through the queue, which starts nothing while the disk is full. Code that deletes files under `TED_HOME` checks the name and real path first and never follows links, like `retention.ts` and `storage.ts`. `TED_FREE_BYTES_FILE` names a file holding the free bytes TED should see; `vitest.config.ts` points every test at one with 500 GB, and `startDaemon`’s `disk` option overrides it (ADR 0039).
- Only `packages/daemon/src/tasks/` starts Tasks or changes their Stage; it owns the order of git, commit and Run steps (ADR 0016). A route open to Runs acts only on the Run’s own Task, and only the Task Lead reports outcomes.
- A Comment’s files are recorded with `v1.CommentAttachmentAdded` in the Comment’s own commit and point at bytes already in `TED_HOME/attachments`. The human’s come from `POST /attachments` (app only); a Run uploads through `POST /tasks/:id/attachments` and may attach only files it uploaded or its own Task already has. Code that deletes attachment files checks `store.filesInUse()` first (ADR 0073-attachments-in-comments).
- HTML that must run scripts (the design review’s prototype) loads from `ted-prototype://file/<hash>/<name>` in an `<iframe sandbox="allow-scripts">`, never `allow-same-origin`; the main process serves it with a CSP that blocks the network. Other HTML stays in the `srcdoc` frame with `sandbox=""`. **Open ↗** on the Figma row opens the link the main process reads from the Comment, not one the renderer passes (ADR 0081-design-reviews-carry-their-parts-and-prototypes-run-from-their-own-scheme).
- A request is a non-`note` Comment; it leaves the Inbox only through one `v1.CommentAnswered` event (answered, approved, changes requested or withdrawn). Gate requests are posted by `ted outcome advance`, never by `ted comment`, except the Merge sign-off, which TED posts once CI passes; only the human answers them (ADR 0032). Only Clarify and Design can `ted outcome advance --skip`. A Clarify round is one `round` Comment posted with `ted ask --round <file>`; at grilling depth Clarify has a Gate whatever `stages.clarify.gate` says (ADR 0050). Talk it through happens in the Task Lead’s own Run chat; only `ted ask --close --summary <file>` closes a talked-through round, as `answered` with `talkedThrough`, and messages typed during a talk add no steering thread lines (ADR 0077-talk-it-through-in-the-task-lead-chat). The size check is a `question` with a `sizeCheck` field posted by `ted clarify too-big`; TED carries out the human’s choice itself, and Split it’s pieces are created only by `answerProposal` in `tasks/tasks.ts` from a `proposal` Comment (`ted task propose --file`), using `planProposal` in `packages/protocol/src/proposal.ts`, which the app’s card uses too (ADR 0082-size-check-and-split-it). A test that walks a Task to Done commits `.ted/workflow.yaml` with `order: [intake, work, merge]` or approves the Gates, since Design and Review have them by default.
- A setup Task is a Task with `setup: true`, created only by `Tasks.setUpFactory` (after cloning) or `Tasks.newSetupTask` (`POST /factories/:id/setup-task`, app only). Resolve the Workflow for a known Task with `taskWorkflow`, never `resolveWorkflow(factoryOf(task))`, so a setup Task gets `setupWorkflow` (Clarify at grilling depth, Design and Review Gates on, the default branch, `defaults/setup.md`). Its Validate runs only the branch’s Checks that match a passing Check in the approved proposal. Tests that add a Factory through `POST /factories` get `<KEY>-1` as the setup Task; a Task created while cloning is `<KEY>-2` (ADR 0086-setup-tasks-are-marked-tasks-with-a-forced-workflow).
- Starting a Task only queues it; the pump in `packages/daemon/src/tasks/tasks.ts` starts queued work when a working-Run slot is free, in the order `queueOrder` gives (`tasks/queue.ts`). New work that needs a slot (sub-agents, Planning or Automation Runs) goes through that queue and counts in its slot holders; never start it around the queue (ADR 0030).
- A Task’s rank orders the Board, the List’s Manual sort and the queue. Clients reorder only through `POST /tasks/:id/move` with the Tasks it now sits after and before; `placeBetween` in `tasks/order.ts` picks the rank and Priority. Never send or compute a rank in a client (ADR 0040).
- A sub-agent is a Run with a `parentRunId`; a Task’s Task Lead Run is its newest Run without one. Sub-agents start only through `packages/daemon/src/tasks/sub-agents.ts`, as `sub-agent` entries in the queue, and only the current Task Lead Run may start, wait for, message or stop them (ADR 0049-sub-agents-are-runs-queued-by-the-tasks-module).
- Automations fire only from `packages/daemon/src/automations/automations.ts`: it decides each firing (scheduled, made up, skipped), adds `automation` entries to the queue through `Tasks.addQueueSource`, starts and settles their Runs, and holds the idle timer while any Automation is on. An Automation Run’s ID is its firing’s ID, so `store.automations.firing(runId)` says whether a Run is one. Schedules are computed only by `packages/protocol/src/schedule.ts`; tests drive the clock with `startDaemon`’s `automations.now` and a short `checkEveryMs`. Templates must never reach real Linear or Sentry in tests (ADR 0070-automations-fire-from-the-daemon-and-queue-like-runs).
- Planning chats live only in `packages/daemon/src/plans/plans.ts`: a plan’s ID is its Run’s ID, it queues as `planning`, its rounds and proposals are `store.plans` requests (not Task Comments), and its detached worktrees under `TED_HOME/plans/<id>` are removed whenever it ends. Inside a Planning Run (`TED_PLAN`), `ted ask --round` and `ted task propose` post to the plan (ADR 0083-planning-chats). Plan in chat on a size check starts a plan linked to its Task (`v1.PlanStartedFromTask`); only the Tasks module narrows that Task or tells its Task Lead, through `Tasks.planApproved` and `Tasks.planEnded`, and archiving or deleting the Task detaches the plan through `Plans.taskGone` (ADR 0087-plan-in-chat-from-a-task). **Retry** on a Failed plan (`v1.PlanRetried`) checks the repos out again and resumes the planner’s session; **Plan more from here** starts a new plan from a Finished or Stopped one and stores the old chat’s rounds, answers, proposal and created Tasks as text in `v1.PlanContinued`, so it survives the old chat’s deletion. Planning worktrees count as Worktrees in Settings → Storage (ADR 0083-planning-chats).
- `ted task create` with a Run token works only from an Automation Run, in its own Factory, and records the Task as created by that Automation. A `--source` already tracked in the Factory (open, archived without merging, or Done) is refused for every caller except the app, matched through `sourceKey` in `tasks/sources.ts`; `--follow-up <id>` creates a Follow-up that shares the source (ADR 0070-automations-fire-from-the-daemon-and-queue-like-runs).
- The reviewer and the loop check are sub-agents whose agent, model and effort only `reviewerFor` in `tasks/tasks.ts` picks; never let `--agent` reach a reviewer. Any send-back TED holds for the human (over `max_back`, a loop check) is a `v1.SendBackAsked` row, and `ted outcome advance` and `back` stay refused while its question is open (ADR 0055-reviewer-and-the-validate-loop-check).
- A human message to a working Run is held in the store and delivered only by `packages/daemon/src/runs/steering.ts`, at the agent’s next tool-call boundary or when the turn ends; never write it to the agent early, and never as a hook’s `additionalContext` (ADR 0052-steering-holds-queued-messages-in-the-daemon).
- The preamble and built-in Stage files are Markdown in `packages/daemon/src/workflow/defaults/`; the preamble names only `ted` commands that exist (ADR 0017).
- The Workflow is resolved only through `Workflows.resolve` in `packages/daemon/src/workflow/workflows.ts`, at each Stage entry; every Stage entry records the layers and Stage file it used. The Library lives in `TED_HOME/library/`, the Factory layer is `.ted/` on `origin/<default branch>`. `pnpm ted workflow check [<path>]` validates a layer (ADR 0019).
- A Task’s Task Lead field (`lead`: agent, model, effort) is compared with its live Task Lead Run in `tasks/`; a model or effort change goes through `RunManager.restart`, which restarts the agent inside the same host and the same Run, and only at an idle point. An agent change stops the Run and starts a fresh one. `pnpm ted task lead <id> claude|codex [--model] [--effort]` sets it (ADR 0027).
- A Task’s worktree lifecycle (copy, `setup`, `teardown`, removal) lives in `packages/daemon/src/tasks/`; every command run in a worktree gets `worktree.env` minus the reserved names in `isReservedEnvName` (`workflow/check.ts`), a resumed setup runs the command recorded when it started, and copy never reads outside the local folder or writes outside the worktree (ADR 0025).
- List a Factory’s repos only with `factoryRepos` in `packages/daemon/src/tasks/repos.ts`, and match a Task repo to its settings by owner/repo (`repoEntry`), never by `name`. A Task’s Repos field changes only through `PUT /tasks/:id/repos` (`ted task repos set|add|remove`); in a multi-repo Factory every Task Lead Run starts in the Task folder `TED_HOME/worktrees/<TASK-ID>/`. Multi-repo tests point `https://github.com/` at local bare repos with `GIT_CONFIG_*` `insteadOf` (ADR 0060-multi-repo-tasks).
- Checks run only through `runChecks` in `packages/daemon/src/tasks/checks.ts` (one after another, first failure stops, `$SHELL -lc`, `CI=1`, no `TED_APP_*`), and each run is a Check run in the store, not a Run, so it never takes a working slot. The Merge rebase rerun reuses the same runner (ADR 0044).
- Apps start, stop and restart only through `packages/daemon/src/apps/apps.ts`, which the Tasks module owns: each App runs in a detached host (`apps/host.ts`) that kills its whole process group, gets its environment from `worktreeCommandEnv`, and is checked for a free port and readiness on loopback only. An App `url` must be on localhost, and the app opens only that URL or a pull request’s hosted preview. Anything that ends a Task’s worktree stops its Apps first. Tests use `packages/daemon/test/fixtures/stub-app.ts` and call `killAppHosts` from `test/helpers.ts` in cleanup (ADR 0084-apps-run-in-detached-hosts).
- Only `packages/daemon/src/apps/simulators.ts` runs `xcrun simctl` or opens Simulator.app. It clones one device per iOS simulator App per Task, boots TED’s devices only into a free slot (`maxBootedSimulators`), and never shuts one down to make room unless the human picked it: the human’s ▶ names it, and a Run’s `ted run-app` posts a `permission` Comment with `simulator` and waits. Devices are deleted when the Task’s Apps stop for good. Tests use `test/fixtures/stub-xcrun.ts` (`TED_XCRUN_BIN`, `TED_OPEN_BIN` in `vitest.config.ts`, state in `TED_STUB_XCRUN`) and set `simulators.supported`; never boot a real simulator or run `xcodebuild` in a test (ADR 0085-ios-simulator-apps).
- Agent health lives in `packages/daemon/src/health/` and uses `cli-env.ts` and `terminal.ts` like GitHub and Git health; a fix command opens in the user’s own terminal, never TED’s. A kind that isn’t Ready is paused in the store, and a Task Lead that can’t start is held and started again when the kind is Ready; what a CLI prints for its version, login and auth errors stays in its `agents/` module (ADR 0033). Tests set a stub’s health with `TED_HOME/stub-claude.json` or `stub-codex.json` (`{"signedIn": false}`, `{"version": "2.0.0"}`).
- A usage limit, being offline or a Run using an API key under Subscription pauses an agent kind only through the agent health monitor, which composes every cause into the one reason `pauseAgent` stores; what a CLI’s output says about limits, retries, credentials, plan usage and cost stays in its `agents/` module. Billing is the `billing` machine setting; under Subscription the agent module removes the key variables. Tests never reach the network or a billing or usage API: `TED_ONLINE_FILE` (set in `vitest.config.ts`) or `startDaemon`’s `online` option decides online, and the stubs emit limit and usage lines (ADR 0057-usage-limits-offline-and-credentials-pause-an-agent-kind).
- A new thread event line is an entry in `taskLogEntries` (`store/schema.ts`) and a case in `tasks/thread.ts`; never log secrets or prompts there. The human’s Comments reach the Task Lead only through `Tasks.comment`, which records delivery, and the next Run picks up undelivered Comments and held answers (ADR 0041).
- A Task’s title and description change only through `Tasks.edit` (`PUT /tasks/:id`, app-only), which records one `v1.TaskEdited` and tells a live Task Lead the diff. Read description versions and the Original request through `TedStore.descriptionVersions`, never from `tasks.description` alone (ADR 0063-task-edits-and-description-versions).
- A Task Lead Run that ends without TED stopping it, or sends no output for `stallAfterMs` while Working, goes through `recover` in `packages/daemon/src/tasks/tasks.ts`: resume the same Run with `RunManager.revive`, else a fresh Run from the brief, else Failed with the FAILED ask. Stop a Run only through `RunManager.stop`, which records the stop so it isn’t counted as a failure; `TED_STALL_AFTER_MS` shortens the no-output clock (ADR 0051).
- To send a live Run a message, use `RunManager.send`, which appends to the Run’s `input.jsonl`; the host forwards it to the agent’s stdin (ADR 0019).
- What an agent CLI’s output lines mean for the Run chat lives in that agent’s `chat` function in `packages/daemon/src/agents/`; `runs/conversations.ts` builds the chat items, and a message typed into a Run chat goes only through `Conversations.send`, never as a Comment. Files copied or ported from agent-orchestrator say so at the top and say what TED changed (ADR 0043).
- Code that knows how a particular agent CLI starts or what its output means lives only in `packages/daemon/src/agents/` (ADR 0014). Codex runs as `codex app-server`, driven by `agents/codex-driver.ts` inside the host (ADR 0018). The host’s `launch.json` and `host.log` formats only ever gain fields, because a running host can outlive a daemon update (ADR 0013).
- Permission prompts come only from an agent module’s `permissionPromptFrom` and are answered only through `RunManager.answerPermission`, which tags the reply with the agent generation; never write a reply to `input.jsonl` another way, and never add a route that answers one with a Run token (ADR 0047-permission-prompts-become-permission-comments).
- Every GitHub request goes through the `Gh` runner in `packages/daemon/src/github/gh.ts` (`integrations.gh` in the daemon’s services): `run`, `api` and `graphql` start the user’s `gh` with prompts and the update notifier off, back off on rate limits and check GitHub health again on an auth error. Nothing runs `gh auth token` or passes the show-token flag, and `packages/daemon/test/integrations.test.ts` greps the sources for both. Git clone, fetch and push use plain `git` with the user’s own credentials (ADR 0007, ADR 0029).
- Only `packages/daemon/src/tasks/pull-requests.ts` pushes Task branches and opens, readies or closes their pull requests, called from the Tasks module at Validate entry, Validate pass and sign-off; agents never push. `pushBranch` in `git.ts` pushes from a temporary bare repo to the Factory’s stored clone URL, so the clone’s and worktree’s git config never apply; never push from the worktree. Tests that start a daemon in-process get the stub `gh` through `TED_GH_BIN`, and push only to local bare remotes (ADR 0048-ted-pushes-task-branches-and-opens-draft-pull-requests).
- Only the merge watcher in `packages/daemon/src/tasks/tasks.ts` merges pull requests, using `nextStep` and the `gh` calls in `tasks/merge.ts`; the Task Lead never merges and can’t report an outcome at Merge. A Task counts as merged only through `TedStore.isMerged` (Done and every pull request merged). Fetch from GitHub only with `fetchBranch` in `git.ts`, never a fetch inside a worktree. Merge tests use `test/merge-harness.ts`, which sets `merge` in the stub `gh` state (`TED_STUB_GH`; `merge.prs` and `pr.numbers` give each pull request its own state and number) and starts the daemon with a short `mergePollMs` and, for CI-stuck tests, `ciStuckMs` (ADR 0056-ted-merges-pull-requests-at-the-merge-stage). The merge watcher runs in every Merge mode (merge, Merge Gate, Merge off, canceled); a human Comment while the merge is pending goes only through `cancel-merge` (ADR 0062-merge-gate-merge-off-re-sign-off-and-ci-stuck). Pull requests merge in the Factory’s `repos` order, all checked before the first; Partly merged comes only from `v1.MergeStoppedPartway`, and TED never reverts a merge (ADR 0064-multi-repo-merge-and-partly-merged).
- Read a Task’s working tree (changes, diffs, uncommitted work) only with `workingChanges` in `git.ts`, which works in a scratch git directory with a fresh index; never run `git diff`, `git status` or `git add` inside a worktree, where the agent-writable config and index apply. The app shows them through `useTaskChanges` in `renderer/changes.ts` and the components in `ChangesSection.tsx`, `DiffViews.tsx` and `DiffTable.tsx`; line comments hook in through `DiffSeams` (ADR 0079-changes-read-the-worktree-through-a-scratch-index).
- Any new path that posts a human Comment, or answers a request with the human’s words, passes the Task’s line comment drafts (`drafts(taskId)` in `tasks.ts`) to `store.postComment` or `answerRequest`; Approve never does (ADR 0079-line-comments-are-drafts-the-daemon-attaches-to-the-next-comment).
- Task pull requests are polled only by the poller in `tasks/github-watch.ts`: one batched GraphQL query per host per cycle for every open pull request of a Task that isn’t archived. The merge watcher waits for its reads (`watch.next`) and never queries GitHub itself. What GitHub reports reaches the Task Lead only through `noticesFor` and `activityMessage` in `tasks/github-activity.ts`: everything copied from GitHub goes through `clean` and sits between `<<<GITHUB <nonce>>>>` lines with a fresh nonce per message, and what was sent is a `v1.GitHubActivitySent` event. Only review comments and reviews whose author is `OWNER`, `MEMBER` or `COLLABORATOR` are forwarded; others are logged as `v1.GitHubActivityHeld` and never start a Run, and CI logs are read only from the repo’s own GitHub Actions jobs. Tests set `threads`, `reviews` (an author’s `association` defaults to `COLLABORATOR`), `deployments`, `closed` and check `url`s in the stub’s `merge` state, job logs in `logs`, and `pr.numbered` for one pull request number per Task (ADR 0065-watching-github-for-ci-failures-review-comments-and-conflicts).
- Factory settings write `.ted/` only through `packages/daemon/src/factory-settings.ts`: `workflow/edit.ts` applies the panel’s edits to the YAML document, `checkLayer` must pass before anything is committed, `commitAndPush` in `git.ts` commits from a temporary bare repo, and Save and merge uses the `tasks/merge.ts` calls. The store’s Factory repos follow the default branch’s `repos` through `storedRepos` and `Factories.syncRepos` at every resolve, but a repo new to the Factory is cloned only after the human adds it (a Save from this machine, or **Add** on the `repo-in-workflow` banner); never clone a repo only because a file names it. Settings tests set `merge.updateBase` in the stub `gh` state so a merge moves the local bare remote’s `main` (ADR 0061-factory-settings-save-through-a-pull-request).
- A settings save names only the parts it changes (`stages`, `stageFiles`, `checks`, `agents`, `permissions`, `maxWorkingRuns`, `notes`) and commits every `.ted/` file that differs in one pull request. A save that turns on Bypass is refused unless the request sets `confirmBypass`, which only the Save dialog’s checkbox sends. Override writes `based_on` as `stageFileHash` of the inherited text. Run now goes only through `check-tries.ts`, in scratch worktrees under `TED_HOME/scratch/`, one Check at a time per Factory. The stub `gh` merges one pull request per state file, so a test that saves twice rewrites the state before each save (ADR 0066-factory-settings-sections-and-scratch-worktrees).
- The Library in `TED_HOME/library/` is written only by `packages/daemon/src/library-settings.ts` (app-only `POST /library/save`): `checkLayer` must pass on the whole layer first, only `workflow.yaml` and built-in `stages/<id>.md` are written, each through a temporary file and a rename, and Edit in Library writes `based_on` with `stageFileHash` like Factory Override. Outside edits reach the app as `library-changed` from `library-watch.ts`. Idle Runs restart onto a new agent version only through `runs/version-restarts.ts` and `Conversations.restart` (ADR 0067-library-settings-and-agent-version-restarts).
- Drift is found only by `findDrift` in `workflow/drift.ts` (an override’s `based_on` against `stageFileHash` of the inherited text); counts reach the app as `drift-changed`, never as a banner or Inbox item. Inside `tasks.ts`, resolve a Task’s Workflow with `taskWorkflow(task)`, not `resolveWorkflow(factory)`, so Gates forced at creation (`NewTask.forcedGates`, `v1.TaskGatesForced`) and the default-branch target of a Task that changes `.ted/` (`NewTask.changesSettings`) apply (ADR 0076-drift-and-forced-gates).
- Removing a Factory goes only through `packages/daemon/src/factory-removal.ts`, which deletes its Tasks through `Tasks.removeFactoryTasks` before `v1.FactoryRemoved`; anything new that keeps data per Factory (store tables, files, in-memory state) must be deleted there too. Clones are deleted only through `Storage.removeUnusedClones`. A repo leaves a Factory only while no open Task (not archived, not Done) has it in its Repos field or a worktree (ADR 0068-factory-order-and-removing-a-factory-or-repo).
- A Fix that runs a CLI command opens it in the user’s own terminal through `Integrations.fix`, which builds the command from a fixed list in `packages/daemon/src/integrations.ts` and never from text a client sends (ADR 0029). Tests point `TED_GH_BIN` at `packages/daemon/test/fixtures/stub-gh.ts` (set in `vitest.config.ts`, with `TED_LOGIN_SHELL=off`); `TED_STUB_GH` names a JSON file that sets what the stub answers, and `TED_FIX_LOG` makes the daemon write Fix commands to a file instead of opening a terminal.
- The Linear API key and every Linear request live only in `packages/daemon/src/linear/`: the key sits in the OS keyring (service `TED`, or `TED Dev` from source; account `linear-api-key`), or in `TED_HOME/secrets/linear-api-key` only when the human chose it because no keyring works. Never put it in `process.env`, a Run’s environment, a log line or the store. Tests set `TED_KEYRING_MODULE` to `packages/daemon/test/fixtures/stub-keyring.ts` and `TED_LINEAR_API` to `stub-linear.ts` (both in `vitest.config.ts`) and never reach the real keyring or Linear (ADR 0037).
- In the Electron main process, start work from `app.whenReady().then(...)`. Electron emits `ready` only after the ESM entry finishes evaluating, so a top-level `await` on it hangs.
- The app’s main process reaches the daemon only through `superviseDaemon` in `packages/daemon/src/launch.ts`, which restarts a crashed daemon and reports `connected`, `reconnecting` or `stopped` to the renderer. Renderer data hooks reload when the connection comes back; a new one takes `epoch` from `useConnection()` the same way. The daemon logs through `console`, which goes to `TED_HOME/logs/daemon.log` (7 rolling files of 20 MB); `TED_RESTART_DELAYS_MS` shortens restart delays in tests (ADR 0031).
- Updates belong to the app’s main process: `packages/app/src/updates.ts` holds the status, the restart sequence and every label; electron-updater’s feed is fixed to `releaseRepo` and its requests may only go over HTTPS to GitHub. Anything that stops the daemon on purpose while the app runs goes through the supervisor (`handOver`, then `resume` if it must come back), or the supervisor counts a crash. Tests never reach a real update server: they set `TED_UPDATE_FEED` to a loopback stub serving `latest.json` and read installs from `TED_UPDATE_LOG`. Raise `hostProtocol` and `oldestHostProtocol` in `runs/host-files.ts` together when a host file format change would break an older host; the daemon then replaces old hosts at their next idle point (ADR 0078-in-app-updates-hand-the-daemon-over).
- Closing the window hides it and Quit ends the daemon through `POST /shutdown`; the menus, quit decision and dialog text are plain functions in `packages/app/src/background.ts`, tested without Electron, and `main.ts` only wires them up. Anything that should keep TED running or count as waiting goes into `TedStore.activity()` (ADR 0028). Launch the app with `TED_HIDDEN_WINDOW=1` in tests and scripts: no window, tray icon, notification or quit dialog.
- Tests never register a login item or keep the machine awake. The daemon holds the machine awake only through `holdAwake`, which `main.ts` leaves out when `TED_STAY_AWAKE=off` (set in `vitest.config.ts`); the app touches login items only when packaged, and `TED_LOGIN_ITEM_LOG` (with `TED_LOGIN_ITEM_STATUS`) makes it write each change to a file instead (ADR 0038). `TED_SKIP_FIRST_LAUNCH=1` (also in `vitest.config.ts`) makes an unpackaged app skip the Set up TED screen; tests of that screen launch with it empty (ADR 0059-first-launch-and-billing-choice).
- The sidebar Inbox count, the Dock badge, the menu-bar count and the Linux window title all come from `TedStore.waiting()` (`GET /inbox/waiting`, the `inbox-changed` event), never from `Activity`. Notifications are decided only in `packages/app/src/notifications.ts`; tests set `TED_NOTIFY_LOG` (and `TED_NOTIFY_STATUS=off`) so the app writes notifications and badge changes to a file and never shows one or touches the Dock (ADR 0088-notifications-and-the-waiting-count).
- Start the daemon, a Run host or the Run’s `ted` shim only through `nodeEntry` in `packages/daemon/src/node-entry.ts`, which goes through `$APPIMAGE` inside an AppImage. `pnpm package [--mac|--linux] [--x64] [--arm64] [--dir]` stages the code as JavaScript in `packages/app/dist/stage/` and builds installers into `packages/app/dist/release/`; it signs and notarizes only when the Apple variables are set and never publishes. The release repository and the Download URL come from `packages/protocol/src/release.ts` (ADR 0036).
- On Linux, a process spawned from Electron’s main process inherits Chromium’s open descriptors. Start the daemon only through `withDaemon`, which closes them (ADR 0011); any other long-lived process spawned from the app needs the same treatment.
- Test through public seams: `TedStore`, the daemon’s HTTP API, the daemon process, the `ted` binary, the Electron app (through Playwright’s `_electron`). Tests that start Runs use the stub agents `packages/daemon/test/fixtures/stub-claude.ts` and `stub-codex.ts` and call `killRunHosts` in cleanup, because hosts outlive the daemon; a test whose daemon was started by the app or `ted` stops it and its hosts with `stopDaemonIn(home)` from `packages/daemon/test/helpers.ts`. The stub follows the `{"steps": […]}` JSON in its prompt, or on any one line of it, so a Task Lead test puts the steps in the Task’s title. Tests that start Tasks clone a local repo made by `makeOriginRepo` in `packages/daemon/test/helpers.ts`. CI runs the tests under `xvfb-run`.
- A Task shell is a PTY that only `packages/daemon/src/shells.ts` starts, through `Tasks.worktreeAccess` (the worktree and its `worktreeCommandEnv` environment, never `TED_RUN`); the app reads its output only through the app-only long-poll route. **Open in editor** starts editors only through `packages/daemon/src/editors.ts`, with paths and lines as separate arguments and never a shell string; a file must resolve inside the worktree. Tests put fake editor launchers on `PATH`, and `TED_EDITOR_APP_DIRS` (empty in `vitest.config.ts`) names the folders searched for macOS app bundles (ADR 0075-task-shell-and-open-in-editor).
- A child process the daemon starts gets its environment from `packages/daemon/src/command-env.ts`: the one `Environment` the daemon read from the login shell, through `worktreeCommandEnv` for anything a repo’s settings run, `gitEnv` for git and `ghEnv` for `gh`. Don’t build an environment inline or read the login shell again elsewhere (ADR 0071-one-daemon-environment-for-every-child-process).
- `packages/daemon/test/support/setup.ts` gives every test file `TED_TEST_RUN`, `TED_TEST_FILE` and `TED_EXIT_WITH_PID` in `process.env`. Spawn children with `{ ...process.env, … }` so they inherit them: the daemon, Run hosts and the app exit when the `TED_EXIT_WITH_PID` process dies, and after each file and after the run, Vitest kills every process whose environment carries that file’s or run’s ID, and nothing else. Close Electron apps with `closeApp` from `packages/app/test/close-app.ts`, which kills the app if `close()` hangs. `DaemonClient` uses `node:http`, not `fetch`: Electron’s `fetch` throws `setTypeOfService EINVAL` outside any `await` when the daemon resets a connection. The app writes uncaught exceptions to `TED_HOME/logs/app.log` and shows no dialog when launched by tests.

### Wayfinding operations

Used by `/wayfinder`.

- **Map**: an issue in the TED project labelled `wayfinder:map`.
- **Ticket**: a sub-issue of the map (`parentId` = the map), labelled with exactly one of `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling`, `wayfinder:task`. Map and tickets carry no other labels.
- **Blocking**: Linear’s native “blocked by” relation.
- **Frontier**: open sub-issues of the map with no assignee whose blockers are all completed or canceled; lowest identifier first.
- **Claim**: assign the ticket to the dev driving the map before any work.
- **Resolve**: post the answer as a comment, move the ticket to Done, then add a line (linked title + one-line gist) to the map’s Decisions so far.
- **Out of scope**: move the ticket to Canceled and add a line to the map’s Out of scope section.

## Code review before merge

Every code change gets a review before it merges to `main`, usually from Codex (`/codex-review`). Fix or answer each confirmed finding before merging.

A change also gets a security review (`/security-review`) before merging if it touches any of these: starting agents or running shell commands, messages between processes, credentials or tokens, network requests, or reading and writing files outside the repo being worked on.
