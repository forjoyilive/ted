# Linear status sync for Tasks from a Linear issue

Status: accepted (KRI-26)

## Context

Since ADR 0037, a Task made from a Linear issue keeps the issue as its source, but nothing flows back: the issue stays in Todo while TED works on it and after it merges, and closing the issue in Linear doesn’t tell TED. The human chose sync both ways. Intake of new issues stays with Automations (KRI-154, KRI-155).

## Decision

- **TED → Linear.** When the Task leaves Backlog, the issue moves to its team’s started state; when the Task reaches Merge (the sign-off before it), to a started state whose name has “review” in it, if the team has one; when `TedStore.isMerged` says the Task merged, to the team’s completed state. TED picks states by Linear’s state `type` and then by name (“In Progress”, “In Review”, “Done”, else the lowest `position`), reads each team’s states once per 10 minutes, and never stores or guesses a state ID. It only moves an issue forward: an issue already at or past the target stays where it is. Archiving a Task without merging leaves the issue alone. Each pull request TED opens is attached to the issue once (`attachmentCreate`).
- **Linear → TED.** When an issue that TED saw open becomes completed or canceled while its Task is open, TED archives the Task if it has no live Run and hasn’t reached Merge, with the thread line “TED archived this Task · NOTE-1 was marked Canceled in Linear” (`v3.TaskArchived` carries `why`). Otherwise TED posts one `question` from TED, “NOTE-1 was marked Done in Linear”, with **Archive** and **Keep going**; work and the merge go on while it’s open. Reopening the issue, or the Task merging, withdraws the question. The first state TED sees for an issue is only recorded, so a Task made from an already-closed issue isn’t archived.
- **Only issues the human chose.** TED writes to an issue, and acts on its closing, only when the Task’s `linearSync` is `on`: the Task was made by a request signed with the app’s key (the New Task dialog, or a Follow-up), or the human pressed **Sync with Linear** in the Task’s menu (`POST /tasks/:id/linear-sync`, app-only); both are recorded as `v1.LinearSyncAllowed`, with `by` `created` or `menu`. A Task made with the `daemon.json` token (`ted task create` in a terminal, which any local process can also do) or by an Automation Run is not consent, or the issue’s team key is in the Factory’s **Linear teams for Automations** list (`linearSyncTeams`, a machine setting by Factory ID, empty by default). Otherwise the Task is `ask`: TED only reads the issue and records what it saw. This stops a prompt-injected Automation from making TED change any issue the human’s key can reach through `ted task create --source`.
- **Asking once per team (KRI-252).** The list is easy to miss, so the first time an Automation makes a Task from a Linear team that isn’t on its Factory’s list, TED posts one `question` from TED on that Task: “Sync Notes (NOTE) issues with Linear for Automations in <Factory>?”, saying what syncing does, with **Allow** and **Not now**. The team’s key and name come from Linear with the issue, are recorded on the Comment with `v1.CommentLinearTeamAsked`, and only the daemon sets them, so a Run’s own question with the same words and choices is a plain question. TED asks only when the issue was fetched and `linearSync` is on, and never while the team is listed or declined for the Factory or an ask for that team and Factory is still open, so it is one question per team and Factory, never one per Task. The ask doesn’t count as an open request in the Task’s `TaskFacts`, because it holds no work. Answering goes through `POST /comments/:id/answer`, which only the app can call. **Allow** adds the team to `linearSyncTeams` and records `v1.LinearSyncAllowed` with `by: team` for every Task of that team in that Factory that isn’t archived and is still `ask`, Done Tasks included, in one commit with the `v1.MachineSettingsChanged`; the poller then moves their issues forward, so a merged Task’s issue catches up to Done. **Not now** adds the team to `linearSyncDeclined` (a machine setting by Factory ID, like the list) and TED doesn’t ask again. The Settings field lists declined teams under each Factory with **Allow**, which calls the app-only `POST /integrations/linear/teams` and does what the Inbox **Allow** does. Editing the list in Settings still works as before.
- **One poller.** `tasks/linear-sync.ts` reads every watched issue (a Task with a Linear source that is open, or merged and not yet synced) every 60 seconds in one batched GraphQL query (aliases, 50 issues per query), only while the `linearSync` machine setting is on and a key exists; without a key it makes no request. Requests live only in `linear/linear.ts`; the Tasks module decides archive or question in `linearIssueClosed`. Each Task is matched to its issue through its source URL, so the issue’s workspace must be the key’s.
- **Records.** What TED saw and did are events with no table, read back from the task log like GitHub activity (ADR 0065): `v1.LinearIssueSeen` (state type and name, written when they change), `v1.LinearIssueMoved` (the step and the state name, or none when TED left it), `v1.LinearPullRequestsLinked`. A failed request is logged through `redactSecrets` and tried again next cycle.
- **Text.** State names from Linear go through `clean` (as GitHub text does) and are cut to 80 characters before they reach the store, the thread or the Inbox.
- **Settings.** `linearSync` is a machine setting, on by default, shown as **Sync status with Linear** under the Linear key in Settings → Integrations once a key is stored, with one **Linear teams for Automations in <Factory>** field per Factory below it. One key serves one workspace (ADR 0037), so machine settings match it. Removing a Factory removes its entries in `linearSyncTeams` and `linearSyncDeclined`.
- **CLI.** `ted task create --source` skips the dialog lookup (`POST /integrations/linear/lookup`, closed to Run tokens) inside a Run; the daemon still fetches the issue when it creates the Task.

## Considered Options

- **Hooks in the Tasks module at start, sign-off and merge.** Immediate, but each hook needs its own retry when Linear is down. A poller that compares the Task with what it recorded retries for free and is at most a minute late.
- **Cancel the issue when the human archives a Task.** The issue belongs to the human; archiving in TED doesn’t mean the work isn’t wanted.
- **A Factory setting in `.ted/`.** Several Factories can share one workspace and key; the key is per machine, so the switch is too. A team list in `.ted/` could also be changed by an agent’s pull request.
- **Trust every Task source.** Simple, but an Automation Run reads untrusted text and can set any source.
- **Ask on every Automation-made Task.** Answers one Task at a time and fills the Inbox; the decision the human makes is about a team, so the question is about a team.
- **Turn sync on when the poller first sees a team.** The team is known earlier, from the issue TED fetches when it creates the Task, and asking at creation means the Task is `on` before its first move.
- **A comment with the pull request link.** An attachment shows in Linear’s sidebar and Linear treats a second one with the same URL as an update.

## Consequences

- A Task made before this change starts syncing at its next poll: its first read is recorded, then it moves forward to match the Task’s Stage.
- KRI-179 checks the queries and mutations against a real workspace; tests use `stub-linear.ts` only.
