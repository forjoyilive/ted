# Renderer

Rules for the app’s renderer and user-facing text (`packages/app/src/renderer/`). They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- The renderer reaches the daemon only through `window.ted`. A forwarded daemon call is added only to `forwardedRequests` in `packages/app/src/daemon-requests.ts`, with the same name, arguments and result as its `DaemonClient` method. Main-process actions and semantic adapters use `CustomRequests` in `custom-requests.ts` and explicit handlers in `main.ts` and `renderer/ted.ts`; the preload stays as it is (ADR 0011). The renderer imports only types from `@ted/protocol`; a value comes from its own sub-path (`@ted/protocol/run`, `@ted/protocol/task`, …), because the main entry also exports `DaemonClient` and the request parsers, which use Node modules. `packages/app/test/renderer-bundle.test.ts` fails when one gets in.
- Every renderer colour is a token in `packages/app/src/renderer/styles/tokens.css`, written as `light-dark(<light>, <dark>)` with Figma’s Theme variable name; components use a CSS Module and `var(--…)` only, and `packages/app/test/theme.test.ts` fails on any other colour. Reuse the shared components in `packages/app/src/renderer/components/` (ADR 0020). A button is `--button-height` (28px) high, or `--button-height-small` (24px) inside a dense row such as a list row, a diff header or a Board card; buttons side by side use the same one. `Button` sets both, and a hand-made bordered or filled button takes its height from the same tokens (`packages/app/test/theme.test.ts`).
- UI labels use sentence case with `GLOSSARY.md` terms capitalized, both parts of a hyphenated term included (Sign-Off, Sub-Agent, Follow-Up). A label ends with “…” only when the item needs more input before it acts: a dialog, a picker or a name.
- User-facing text calls Claude Code, Codex and Antigravity Providers (Settings → Providers, the Provider field), and names the Provider when one is known. “Agent” stays for a Run or its role (Task Lead, sub-agent, agent Run). Code identifiers, settings keys, setting IDs, events, routes and `workflow.yaml` keys keep their `agent` names (`AgentKind`, `enabledAgents`, `lead.agent`). The CLI flag is `--provider` (`ted run start`, `ted automation create`, `ted coordinator create`); `--agent` still works as an unlisted second spelling.
- Keyboard shortcuts live in `packages/app/src/renderer/keymap.ts` and run through the one `keydown` listener in `App.tsx`; don’t add another window key listener for a shortcut. A new list or card view marks its focusable items `data-nav-item` so J/K reach them (ADR 0074-keyboard-shortcuts-one-keymap-one-listener).
- In the Task thread, an open request with one answer field (not a round or a proposal) is answered from `RequestDock` at the bottom, in place of the Comment box; its card passes `answerBelow` and has no answer field. The answer controls are `RequestAnswer` in `RequestCard.tsx`; don’t draw a second copy on the card. The dock carries `data-request` and the card `data-docked`, which `requestScope` in `key-targets.ts` uses for the request shortcuts; with several open requests a shortcut acts only when focus is in the dock or on the shown request’s card.
- The first-Factory guide card’s text and button are chosen only by `guideCard` in `packages/app/src/renderer/guide.ts`; the agent writes none of it. Whether setup counts as done is decided only by `setUpDone` in `store/index.ts`, which the guide carries as `setUp`; the card never decides it from the Task. A guide starts only in `TedStore.createFactory` and ends only through `v1.FactoryGuideEnded`, committed with the Task the user creates after setup, the setup Task’s archive or delete, or `hideGuide`; the app reads live guides through `GET /guides` and `guides-changed`. Comments marked by the old `v1.CommentMarkedTutorial` are left out of every Comment list in the store (ADR 0162-a-guide-card-follows-the-first-factorys-setup).
- HTML that must run scripts (the design review’s prototype) loads from `ted-prototype://file/<hash>/<name>` in an `<iframe sandbox="allow-scripts">`, never `allow-same-origin`; the main process serves it with a CSP that blocks the network. Other HTML stays in the `srcdoc` frame with `sandbox=""`. **Open ↗** on the Figma row opens the link the main process reads from the Comment, not one the renderer passes (ADR 0081-design-reviews-carry-their-parts-and-prototypes-run-from-their-own-scheme).
- The Map View’s cards, links and Tasks with no blockers come only from `blockerMap` in `packages/app/src/renderer/blocker-map.ts`; `views/TaskMap.tsx` only draws them and calls `blockTask` and `unblockTask`. `linkRefusal` there is only the text shown while dragging: the daemon decides whether a blocker is added. Board, List and Map sit under the sidebar’s Tasks row, which opens the last-used of the three (`open-tasks` in `navigation.ts`) (ADR 0127-the-map-view-draws-blockers-from-the-task-list).
- The Board’s Display choices (card size, card fields, hidden columns, Hide empty columns) are one `BoardView` per Factory in the `boardViews` machine setting, deleted with the Factory in `factory-removal.ts`. Only `boardLayout` in `packages/app/src/renderer/board.ts` decides which columns are drawn and which are listed under Hidden columns; a hidden column never shows itself.
- Unsent text in a message or answer box is kept by the daemon in `messageDrafts`, one row per `MessageBox` (`packages/protocol/src/message-draft.ts`), through the app-only `GET` and `PUT /message-drafts/:kind/:id`. A box in the renderer gets its text from `useMessageDraft` in `renderer/message-drafts.ts`, never its own `useState`, and calls `clear()` when its message is sent. Rows are deleted where `TaskArchived`, `TaskDeleted`, `CommentAnswered`, `PlanRequestAnswered`, `PlanDeleted`, `FactoryRemoved` and the Run-deleting events update the state; a new kind of box adds its owner to `messageDraftOwner` in `routes/message-drafts.ts` and its deletion there. Saved files count in `store.filesInUse()` but never in `store.taskFiles` (ADR 0130-unsent-message-text-is-kept-by-the-daemon).
- Commits, Task IDs and worktree paths in a Task’s messages become links only through `references` in `packages/app/src/renderer/references.ts` and `TaskReferences` in `components/References.tsx`, set once in `TaskPanes`: a link is drawn only after the app has checked it leads somewhere (a Task it holds, a file in the Task’s file list, a commit the daemon confirmed), and `Markdown` and `EventLine` draw plain text outside it. The app-only `GET /tasks/:id/commits` and `GET /tasks/:id/commits/:hash` read commits with `findCommits` and `commitDiff` in `git.ts`, through `inScratch`; a hash must pass `isCommitId` before it reaches git. Don’t store links on a Comment or link a hash the daemon hasn’t confirmed (ADR 0128-commits-task-ids-and-paths-in-task-messages-are-links).
