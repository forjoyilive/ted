# Validate

## Goal

Find out whether the work does what the Task asks, without breaking anything else, through Checks, independent code review and security review. Resolve every blocking Finding and failure case, complete all remaining Checks, and keep failed results distinct from the human’s acceptance.

## Before you start

Ted runs Factory Checks sequentially and stops at the first failure. When the Task comes from Work, Ted ran them before it left Work, a failure there kept it in Work, and the passing results are at the end of these instructions. When it comes from another Stage, Ted runs them at Validate entry. A failure at entry keeps the Task in Validate and gives you the original output and failure case ID. Checks after it have not run. Investigation, retry and a human decision do not count as send-backs.

Use `ted failure list`, `ted failure show <id>` and `ted failure obligations` to inspect evidence, decisions and remaining Checks. Never treat an accepted failure or a not-run Check as passed.

## Steps

1. Investigate each failed Check before deciding what to do. Add concise evidence with `ted failure evidence <id> --file <json>` (`{"evidence":"…","contextId":"optional captured context ID"}`). An assessment and the decision asked from it are bound to the `contextId` of the newest evidence, or to the original context when that evidence names none. When you assess again after the code, Checks or CI changed, first capture a new context with `ted failure context` and put its ID in the evidence’s `contextId`; otherwise the decision stays bound to the old context, the human can’t accept the failure and `ted failure ask` may be refused. When a Check’s failure can no longer be tied to the current code and Checks, `ted failure ask` posts the decision without Accept and with Fixed and No longer applicable. A Check’s failure can’t take a context captured after the Check ran: run the Check again instead. Assess it with `ted failure assess <id> --file <json>` (`{"assessment":"regression|unrelated|uncertain","recommendation":"Evidence-based explanation and recommended next step"}`). Substantiate the assessment with reproduction, changed-code analysis, logs, environment evidence or a useful base-branch comparison. A base comparison is not compulsory. Say what remains uncertain; do not guess that a failure is unrelated.
2. A supported regression goes back through the existing send-back path with Findings. For unrelated or uncertain causes, run `ted failure ask <id>` and wait for the human. They can Retry, Fix in this Task, Wait for a repair Task or Accept this failure. Decisions are refused without answering the request while Checks are running; wait for execution to finish, then choose again. Acceptance covers only that execution in its verified tested context; it resumes remaining Checks, and does not approve a merge. Every later failing Check or failed retry gets its own case and decision, and replaces an older open case for the same Check (same name and repo; a changed command too when the older case is no longer tied to the current code and Checks), unless that case waits on a repair Task or has a current acceptance. After a repair in Work, an earlier failed Check can become legitimately skipped, removed or replaced. Complete all current Checks in the fresh Validate visit, retain the regression assessment or human Fix decision that authorized the repair, and use `ted failure verify <id> --file <json>` with evidence explaining why the old Check no longer applies. Ted verifies current coverage; this records Task Lead repair evidence and keeps the original execution failed. A currently failing or not-run Check cannot be closed this way.
   Wait for a repair Task lets the user select existing work or edit and approve a focused new Task in this Factory. Creation occurs only after approval; a new repair queues by default unless the user chooses Backlog. Ted writes the brief with the original failure and repair link, stops the Task Lead, keeps the Stage and worktree, and waits without a working-Run slot. The repair follows its own Workflow. After it merges, Ted queues continuation, incorporates it through Tasks and runs fresh Checks. Repeat any reported Finding’s verification and record fresh evidence. If the merged repair skips, removes or replaces a Check, complete current Checks and use `ted failure verify <id> --file <json>` to explain the change; the affected Task need not revisit Work. If the merged repair conflicts with the Task’s branch, Ted keeps the Task going and tells you which commit to merge and which files conflict: merge that commit into the Task’s branch, resolve the conflicts, commit and end your turn, without running the Checks or `ted outcome advance`. Ted then incorporates the repair and runs fresh Checks. If you can’t resolve it, say why with `ted comment` and end your turn; Ted stops the Task for the user. If uncommitted changes in the worktree hold incorporation, Ted tells you which files: commit them if they are your own work for this Task, never discard them, and otherwise say why with `ted comment`; then end your turn. If they are still there, Ted stops the Task for the user. An archived/deleted repair or a manually removed blocker does not pass validation; removing the final blocker leaves the Task Stopped until Resume. When the repair Task is archived, deleted or unblocked without merging, the failure needs a decision again, and a new failure of the same Check replaces it. Reassess or choose another repair. An old acceptance cannot cover changed work.

3. Run the project’s relevant tests and end-to-end tests beyond what Factory Checks cover, following the repo’s testing rules. Before running extra verification, capture context with `ted failure context`. Record a failing result with `ted failure record --file <json>`: `{"source":{"kind":"finding","runId":"originating Run ID","finding":"Original Finding","category":"test|review|visual"},"evidence":"What ran and what failed","contextId":"context captured before verification"}`. Set category to test, review or visual to identify the verification that failed. Omit contextId for historical or unknown evidence; it cannot be accepted without reliable execution context. Apply the same assessment and human-decision policy to extra tests, reviewer Findings and visual failures. A Retry for a reported Finding means repeat that verification and record its fresh evidence; it never marks the Finding passed automatically. When repeated verification passes, record the fresh evidence with `ted failure verify <id> --file <json>` (`{"evidence":"What repeated and why it now passes"}`). This is Task Lead reported verification, not human acceptance.
4. Have the reviewer perform code review and security review of the committed diff with no Work context: `ted run start --reviewer --prompt-file <file>`, giving only the Task, Design brief and diff against the base branch; wait with `ted run wait`. Ted chooses its Provider, model and effort. Ask it to use `code-review` when available, or review manually. Report requested behaviour against acceptance criteria, repo standards against documented rules, and security separately, with affected files, lines, evidence and effect. Assess security impact every time; for input, files, processes, network or credentials, review trust boundaries, permissions and failure cases with an available security tool or manually. State the security scope, method and confirmed Findings, or why there is no security-sensitive impact. Capture context while the reviewer’s Run is live if you will need to bind its Findings to that execution. Never borrow a capture taken after a finished reviewer Run.
   Start one reviewer per visit. Ted refuses a second reviewer, and any other sub-agent unless the Factory’s Workflow sets `stages.validate.sub_agents: true`. Don’t send the diff to any other review tool or service as well. Don’t commit after you start the reviewer: Ted refuses `ted outcome advance` while `HEAD` isn’t the commit the reviewer was given, and the Task then goes back to Work so the next round reviews the change.
   From the second round, Ted tells you which round this is and lists the earlier Findings. It gives the reviewer those Findings and the diff since the commit the last round reviewed, and limits it to checking that each Finding is fixed and that the fixes broke nothing. Your prompt file still supplies the Task and the Design brief; it can’t widen the review.
   When the Task comes back only because its branch conflicted with the base branch, Ted says so and limits the reviewer to the conflict resolution: the base commit merged in, the files that conflicted and the Task’s own commits since the last review.
5. Check the change against the description and Design brief for missing cases, broken behaviour and debugging code. For UI changes, capture changed screens unattended as the preamble describes, judge them and attach evidence. Light-mode images alone are sufficient. Continue reviewer and visual validation even after the human accepts a Check failure.
6. Confirm code and security reviews cover the committed change. Sort Findings as blocking or notes. From the second round, a new Finding about code the fixes didn’t touch is a note unless it is P1. P1 means the change loses or corrupts data, opens a security hole, or breaks behaviour the Task’s description asks for. When Ted says the round checks a conflict resolution, a new Finding about code the resolution didn’t touch is a note unless it is P1. When Ted says the round reviews the whole change again, sort Findings as in the first round. When Ted says that from this round a new Finding sends the Task back only if it is P1 (the Factory’s `stages.validate.p1_only_from`), every new Finding that isn’t P1 is a note, wherever it is in the change; an earlier round’s Finding that is still not fixed stays blocking. Record every failure that needs diagnosis and resolution, rather than hiding it as a nonblocking note. Lead the human note with pass or fail and remaining concerns, explaining their effect. Summarize relevant coverage and attach detailed test/review evidence rather than repeating its inventory. Post evidence, assessments, human decisions, security scope/method/outcome and remaining uncertainty. Write these into the Review brief, explicitly labelling accepted failures as “failed, accepted by you”.

## Done when

Every required Check ran or has an explicit legitimate no-change skip, every failure case is resolved in its tested context, reviewer and applicable visual validation are complete, and there are no unresolved blocking Findings. Check `ted failure obligations` before advancing. Post the note and write the Task brief. Then use `ted outcome advance --review pass|fail --review-notes <n>`, adding `--visual pass|fail --visual-notes <n>` when you judged screenshots. Keep failing observations factual even when accepted. An accepted reviewer Finding retains a failed Review judgment; use `--review fail`, never `--review pass`, while that accepted failure remains. An accepted visual Finding likewise retains a failed Visual judgment; use `--visual fail`. All existing sign-offs still apply.

## Send back when

Evidence supports a regression or the human chose Fix in this Task. For a regression, record its assessment, write numbered Findings and use `ted outcome back --to work --findings <file>`, with `--review fail` or `--visual fail` for their original results. In a round where Ted says a new Finding sends the Task back only if it is P1, say in the file which Findings are P1 and which are earlier Findings still not fixed, and add `--severity p1`, or `--severity unfixed` when the only blocking Findings are earlier ones still not fixed; Ted refuses the send-back without one of them unless it is for a failed Check you assessed as a regression, and the other new Findings go in your note. Ted applies the existing max_back and loop-check rules to actual send-backs. Keep full reproduction and repair evidence in Findings; summarize what remains and whether previous fixes held. At the limit Ted checks progress again unless Loop checks are disabled, and asks the human regardless of the verdict. A pending escalation is not itself another send-back. Never repair code silently inside Validate.

## Ask the human when

The cause is unrelated or uncertain, or a fix changes what the Task delivers. Use the failure decision with evidence and a recommendation. When the Workflow has no earlier Work Stage, Fix is unavailable; explain that constraint while the Task remains held for a valid decision.
