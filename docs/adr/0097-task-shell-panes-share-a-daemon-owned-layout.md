# Task shell panes share a daemon-owned layout

Task shells now support split panes (KRI-32), extending ADR 0075’s single PTY per Task and repo. The daemon owns a binary split tree and up to eight independent PTYs per Task/repo. Leaves name opaque shell IDs; branches record a direction and divider ratio. Keeping both together lets the app reconnect to the same panes and processes without guessing which shells to create. Layout mutations carry a revision, so a stale view cannot overwrite a newer arrangement.

Each pane has its own input queue, output cursor, generation, size and exit status. A split starts a new login shell at the worktree root with `Tasks.worktreeAccess`’s environment; it does not copy another process’s current directory or variables. Close and Restart confirm before ending the shell, jobs in its original OS session and descendants still connected through current parent relationships. Both confirmations warn: “Programs that detached into separate sessions may keep running.” A program that leaves the original session and becomes reparented before cleanup is outside terminal cleanup. This boundary also applies to worktree removal and daemon shutdown. The human approved this terminal scope for KRI-32; services TED owns should use managed Apps. Each PTY starts in its own OS session. Cleanup retains that session identity after the login shell exits, so HUP-resistant jobs in separate process groups remain discoverable. macOS redacts the session field in ps; a fixed system Perl invocation reads Darwin’s getsid syscall for the listed PIDs. Linux supplies session IDs through ps. Neither path reads process arguments or environments. The original leader’s start time guards against targeting a reused leader PID. Cleanup verifies the daemon-owned shell’s PID, parent and start time, freezes its groups while discovering descendants, then sends SIGKILL to the groups with the root group last. SIGHUP alone is insufficient for `nohup` jobs. Process inspection uses the daemon’s machine environment, never a repo-controlled executable or environment. An inspection or signaling failure leaves the pane, layout and revision unchanged and allows a retry; Close publishes its layout change only after cleanup succeeds. Closing the last pane leaves an empty layout; opening the view again does not silently start a shell. An exited shell retains its output until explicitly restarted or closed. The legacy Open alias also cleans its previous session before implicitly relaunching an exited shell; a cleanup failure retains the old generation for retry.

The existing shell routes remain aliases for the first surviving shell; the app uses explicit pane IDs. New workspace and pane routes stay app-only, including GETs, and every operation revalidates access to the Task/repo. Creating a pane changes the layout only after its PTY launches. Closing a pane wakes its long-poll readers, which return missing instead of creating a replacement. Each live PTY contributes an idle hold and to the machine’s running-shell count. Removing the worktree closes every pane. Daemon shutdown attempts every pane even if one cleanup fails, retains and retries failures, and waits for their cleanup before exiting. Other daemon service teardown proceeds while those retries run.

The renderer keeps live terminal panes as stable siblings and positions them from the split tree. Splitting or collapsing a branch changes geometry without disposing surviving xterm instances, preserving Find state, selection, scrollback and the ordered input queue. Selecting a pane only changes its highlight; terminal focus is requested separately for a new, restarted or surviving neighboring pane. Find fields and header buttons retain their own focus. Restart closes Find along with replacing that pane’s terminal, so reopening Find always targets the current generation.

## Considered options

- **Supervise every historical descendant.** Deferred: tracking programs that detach and become reparented requires native OS-specific supervision beyond terminal split panes. Session and current-parent inspection cannot establish historical ownership. Periodic scans can miss short-lived parents, and inherited environment markers can be removed. The confirmations make the terminal cleanup boundary explicit instead.

- **Store the arrangement only in the renderer.** Rejected: the daemon owns the shell lifetime, and a reloaded app needs an authoritative list of surviving shells. A daemon-owned tree also avoids two views assigning different arrangements to the same processes.
- **Persist the layout across daemon restarts.** Deferred: the shell processes already end with the daemon. Recreating a saved arrangement would start fresh processes that might look like continuations. As with ADR 0075, panes and their layout survive app restarts while the daemon runs; the next open after a daemon restart starts with one fresh shell.
- **Automatically reopen missing pane IDs.** Rejected: a missing ID can mean the human closed that pane. The app refreshes the layout instead and creates shells only on an explicit open or split.
