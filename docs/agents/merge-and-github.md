# Merge and GitHub

Rules for GitHub requests, pushes, pull requests, the Merge Stage, Cleanup and CI. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- At Merge, a failed GitHub CI check is a `github-ci` Failure case, not a send-back: `ciFailureSteps` in `packages/daemon/src/tasks/ci-failures.ts` decides what to record, close, replace or send back from the poller’s read, and only `reconcileCi` in `tasks/tasks.ts` carries it out, from the merge watcher and from the poller’s reaction. A case is keyed by `ciFailureKey` (repo, pull request, head, attempt); never record a second open case for one key, and never start or rerun a GitHub workflow for Retry. An accepted attempt is left out of `ciState` through `acceptedCi` and nothing else: GitHub’s merge state still decides, `nextStep` waits on `required-check` while GitHub blocks, and auto-merge stays off then. Its evidence is built only by `ciFailureEvidence` in `tasks/github-activity.ts`, fenced, with no name or log for a check `trustedCheck` rejects. A case Ted recorded at Merge is one whose source has `checkKey`; never treat another `github-ci` case as one. The check’s name in `source.check` is for the app only: every case a Run reads goes through `withoutCheckName`, and no question or Ted note carries the name. An acceptance of a CI check is compared with `sameTestedFor`, which ignores other checks changing state; don’t use it for Checks or Findings. A check without an attempt identity keeps the old send-back (ADR 0129-failed-ci-at-merge-is-diagnosed-before-any-send-back).
- Every GitHub request goes through the `Gh` runner in `packages/daemon/src/github/gh.ts` (`integrations.gh` in the daemon’s services): `run`, `api` and `graphql` start the user’s `gh` with prompts and the update notifier off, back off on rate limits and check GitHub health again on an auth error. Nothing runs `gh auth token` or passes the show-token flag, and `packages/daemon/test/integrations.test.ts` greps the sources for both. Git clone, fetch and push use plain `git` with the user’s own credentials (ADR 0007, ADR 0029).
- Only `packages/daemon/src/tasks/pull-requests.ts` pushes Task branches and opens, readies or closes their pull requests, called from the Tasks module only at Merge entry and from the merge watcher’s retry; agents never push. Nothing is pushed while a Task is in Work, Validate or Review. `publish` pushes the commit the Tasks module chose for the repo at Merge entry (`v1.MergeCommitChosen`, read with `store.chosenMergeCommit`), never a later `HEAD`, and opens the pull request without `--draft` (ADR 0048, ADR 0056). `pushBranch` in `git.ts` pushes from a temporary bare repo to the Factory’s stored clone URL, so the clone’s and worktree’s git config never apply; never push from the worktree. When a push is refused and the remote branch is no longer at the recorded push, only `pushPastRecord` there recovers: it fetches the remote tip with `fetchBranch`, goes on only if `isAncestor` says the commit `pushOne` was asked to push contains it, records `v1.TaskPushRecordReconciled` and pushes that same commit with the fetched tip as the lease; never read `HEAD` again during a push; never push without a lease on a branch Ted has pushed before, and never recover when the tip isn’t contained (ADR 0129-a-push-recovers-when-the-remote-is-ahead-and-contained). Tests that start a daemon in-process get the stub `gh` through `TED_GH_BIN`, and push only to local bare remotes (ADR 0048-ted-pushes-task-branches-and-opens-draft-pull-requests).
- Only the merge watcher in `packages/daemon/src/tasks/merge-watcher.ts`, constructed by the Tasks module, merges pull requests, using `nextStep` and the `gh` calls in `tasks/merge.ts`; the Task Lead never merges. It does the Merge Stage’s work and runs `ted outcome advance`, and the merge watcher merges only after that: `store.changeStage` commits `v1.MergeAwaitsLead` with each entry into Merge, the advance is `v1.MergeLeadAdvanced`, and `leadPending` in `merge-watcher.ts` decides whether the watcher runs in its `lead` mode (no merge, auto-merge or Merge sign-off); a Task already at Merge without `MergeAwaitsLead` merges as before (ADR 0169-merge-waits-for-the-task-leads-advance). Before advancing, the Task Lead titles the pull request with `ted task pr` (`POST /tasks/:id/pull-request-title`, `Tasks.setPullRequestTitle`, only at Merge while `leadPending` holds): `commitTitleProblem` in `packages/protocol/src/commit-title.ts` checks the Conventional Commits form, Ted adds the Task ID, renames the pull requests with `PullRequests.retitle` and records `v1.PullRequestTitleSet`; `mergeTargets` passes the latest one as `MergeTarget.message`, which `mergePullRequest` sends as `--subject` and `--body` for merge and squash. No title means GitHub’s default message, the merge never waits for one, and `stages.merge.commit_titles: false` turns it off (ADR 0170-the-task-lead-writes-the-merge-commit). It may run `ted task done` once every pull request has merged (ADR 0140). A Task counts as merged only through `TedStore.isMerged` (Done and every pull request merged). Fetch from GitHub only with `fetchBranch` in `git.ts`, never a fetch inside a worktree. A clone’s remote refs are fetched only through `fetch` in `git.ts`, which runs one fetch per clone at a time: two at once race on `refs/remotes/origin/*` and the loser fails with “cannot lock ref”. Merge rule tests call its `cycle` interface with a stored Task and poller reads; integration tests use `test/merge-harness.ts`, which sets `merge` in the stub `gh` state (`TED_STUB_GH`; `merge.prs` and `pr.numbers` give each pull request its own state and number) and starts the daemon with a short `mergePollMs` and, for CI-stuck tests, `ciStuckMs` (ADR 0056-ted-merges-pull-requests-at-the-merge-stage). The merge watcher runs in every Merge mode (lead, merge, Merge Gate, Merge off, canceled); a human Comment while the merge is pending goes only through `cancel-merge` (ADR 0062-merge-gate-merge-off-re-sign-off-and-ci-stuck). After a cancel the watcher still watches the pull requests and finishes the Task when they are merged on GitHub, and a pull request merged outside Ted is noticed before any other merge step, even while an open request holds the merge (ADR 0136-a-canceled-merge-keeps-watching-github). Pull requests merge in the Factory’s `repos` order, all checked before the first; Partly merged comes only from `v1.MergeStoppedPartway`, and Ted never reverts a merge (ADR 0064-multi-repo-merge-and-partly-merged).
- Only `markDone` in `tasks/tasks.ts` finishes a Task at Merge outside the merge watcher, and only after the poller’s fresh read shows every pull request merged; it holds the Task, waits for the merge watcher’s cycle, records `v2.TaskMarkedDone` with who asked (`human`, `lead`, `coordinator`) and the merges, and moves to Done through `move`. The human calls it through the app-only `POST /tasks/:id/mark-done`, which never gets `runToken` or `fileToken`; the current Task Lead through `POST /tasks/:id/done` (`ted task done`, `leadDone`, checked with `taskLead`); a Coordinator through its `done` action. Never let any of them move a Task with a pull request that isn’t merged (ADR 0135-the-human-can-mark-a-merged-task-done, ADR 0140-task-leads-and-coordinators-can-mark-a-merged-task-done).
- Cleanup is an optional Stage after Merge, on only when `cleanupOn` in `workflow/resolve.ts` says so (`stages.cleanup.enabled: true` and at least one step); it is never in `order`. Only `move` in `tasks/tasks.ts` sends a Task from Merge to Cleanup, so every done path reaches it; `finish` still runs only at Done. Instruction step results go only through `ted cleanup report` (`POST /tasks/:id/cleanup-steps`, current Task Lead, `v1.CleanupStepReported`), which refuses a command step. Command steps run only through `cleanupThen` in `tasks/tasks.ts` and `runCleanupCommands` in `tasks/cleanup-commands.ts` (`runTaskCommand` with `prepareCommandLaunch`, so sandboxed outside Bypass, one `CheckSlots` place per batch, no stop at a failure), before the Task Lead is told anything, and each result is one `v1.CleanupCommandRan`, which also writes the step’s `cleanupReports` row; with no instruction step left and no failed command Ted finishes Cleanup itself (ADR 0149-cleanup-command-steps-run-before-the-task-lead). Only the user answers the failure question (`cleanupFailure`, Try again or Finish anyway, `answerCleanupFailure`). A Task in Cleanup counts as merged (`taskIsMerged`) but not Done: anything that should wait for Done checks the Stage too, like tracker sync in `tasks/tracker-sync/sync.ts` (ADR 0148-cleanup-is-a-stage-after-merge).
- Task pull requests are polled only by the poller in `tasks/github-watch.ts`: one batched GraphQL query per host per cycle for every open pull request of a Task that isn’t archived. The merge watcher waits for its reads (`watch.next`) and never queries GitHub itself. What GitHub reports reaches the Task Lead only through `noticesFor` and `activityMessage` in `tasks/github-activity.ts`: everything copied from GitHub goes through `clean` and sits between `<<<GITHUB <nonce>>>>` lines with a fresh nonce per message, and what was sent is a `v1.GitHubActivitySent` event. Only review comments and reviews whose author is `OWNER`, `MEMBER` or `COLLABORATOR` are forwarded; others are logged as `v1.GitHubActivityHeld` and never start a Run, and CI logs are read only from the repo’s own GitHub Actions jobs. Tests set `threads`, `reviews` (an author’s `association` defaults to `COLLABORATOR`), `deployments`, `closed` and check `url`s in the stub’s `merge` state, job logs in `logs`, and `pr.numbered` for one pull request number per Task (ADR 0065-watching-github-for-ci-failures-review-comments-and-conflicts).
