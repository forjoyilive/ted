# Checks run before a Task leaves Work

_Superseded by ADR 0187-the-checks-run-as-validates-first-step-and-every-return-to-work-counts: the Checks now run as Validate’s first step, a failure there is a counted return to Work, and there are no hand-off Checks or three-failures question. What follows is kept as the record._

ADR 0044 ran the Factory’s Checks when a Task entered Validate, and a failure there was a counted send-back to Work. Since then a failure at Validate entry stays in Validate as a failure case for diagnosis (ADR 0095-failure-cases-preserve-results-and-bind-human-decisions, `tasks/validation.ts`), and a regression still costs a counted send-back. About 3 of 137 measured send-backs were only a failed Typecheck or Lint straight after Work reported it was finished. Each cost a Stage change, a push, a draft pull request update and a round against `max_back`, for something the Task Lead could have fixed where it was.

## Decision

When the Task Lead reports `ted outcome advance` at Work, the next Stage is Validate, Work has no Gate and the Factory has Checks that apply, TED runs the Checks before the Stage changes.

- The order on that `advance` is: obligations, the base-conflict test-merge (ADR 0110), then the Checks. A conflict refuses the outcome first, because Checks on a branch that can’t merge say little.
- The outcome request answers at once with “TED is running the Checks”; the Checks run in the background as a Check run with the trigger `hand-off` and the Stage `work`, through the same `validation.begin` and `runChecks` as every other Check run. A run in Work is not tracked as Validate coverage and records no failure case. The sandbox, Check slots, low priority, the Task’s “Running Checks” activity and the refusal of `ted outcome` and `ted checks` while Checks run all apply unchanged. `v1.ChecksStarted` already stores the trigger as a string, so there is no new event.
- **Pass.** `handOffChecks` in `tasks/tasks.ts` moves the Task to Validate and hands the finished Check run to `validation.enter`. `adoptHandOff` in `tasks/validation.ts` saves it as the Validate visit’s Check coverage (the visit’s `ValidationProgress`, with the run as its one execution), marks an earlier failure case of a Check that now passed as verified, and delivers Validate’s instructions with that run’s results; no second run starts. TED notes what the Checks cover (each repo’s `HEAD` and worktree tree, and the Check hash) before they start. If that or the Check plan differs when the Task enters Validate, the run is not adopted and the Checks run at entry. `judge` picks the same run for the confirmation row: the newest passed `hand-off` run of the Work visit just before this Validate visit, when the visit has no `validate` run of its own. The push and the draft pull request still happen at Validate entry, so nothing is pushed for a branch whose Checks fail.
- **Fail.** The Task stays in Work. The Task Lead gets “# A Check failed” with the same Findings a Validate failure carries (the failing Check’s last 200 lines through `redactSecrets`, and the log path). No `v2.TaskSentBack` is recorded and nothing counts toward `max_back` or the Loop check. No failure case is recorded either: diagnosis, Retry and Accept this failure belong to Validate, and in Work the Task Lead repairs what the Check reports.
- **Three failures.** After three failed `hand-off` runs in one Work visit, TED posts a `question` (“Checks have failed 3 times as NB-1 tried to leave Work”, with the choices **Try again** and **Diagnose in Validate**, each explained in the body) and records it with `v1.SendBackAsked` whose `from` and `to` are both `work`. That reuses the rule that `ted outcome` is refused while a send-back ask is open, and the thread words a same-Stage ask as failing Checks, not a send-back. **Try again**, or an answer in the human’s own words, goes to the Task Lead the way any answer does, and the count starts again from the answer.
- **Diagnose in Validate.** A Check can fail for a reason outside the Task: a flaky test, or one already broken on the base branch. Repairing it in Work is the wrong fix, and the diagnosis flow that can accept such a failure (ADR 0095-failure-cases-preserve-results-and-bind-human-decisions) exists only in Validate. This choice moves the Task to Validate with the Check still failing. `answerLoopAsk` in `tasks/request-answers.ts` routes it, like every other answer, and calls `leaveWorkToDiagnose` in `tasks/tasks.ts` before it records the answer. That function refuses, leaving the question open, when the Task has left Work, is stopped or Failed, has Checks running, has a Workflow that no longer goes from Work to Validate without a Gate, has open obligations, isn’t executed on this machine (`execution.local`), or conflicts with its base branch (the conflict is recorded as in ADR 0113). Then it moves the Task through `move` with no hand-off run to adopt, so `validation.enter` runs the Checks at entry; a failure there is a failure case with Retry, Fix in this Task and Accept this failure, and a pass is an ordinary Validate visit. No send-back is recorded. The Task Lead’s Validate instructions start with what the human chose and anything they added.
- **The branch moved.** TED notes each worktree’s `HEAD` before the Checks start, after `execution.local` has confirmed this machine owns the Task. If a `HEAD` differs when they pass, TED doesn’t move the Task and tells the Task Lead to report again, so the run Validate uses is always for the commit TED pushes.
- **Stopped, failed or a new Task Lead.** Stopping a Task doesn’t stop Checks that are already running. When they finish, `handOffChecks` uses the result only if the Task isn’t stopped or Failed and its Task Lead Run is still the one that reported the outcome. Otherwise the Task stays in Work whatever the result, no failure is reported or counted into a question, and the Task Lead is told to report again: at once if a Run is live, else as a held message its next Run starts with. A Task that was stopped and resumed while the Checks ran has a new Task Lead Run, so its result isn’t used either.
- **Restart.** A daemon that stops mid-run marks the Check run interrupted on start. If its trigger is `hand-off` and the Task is still in Work, TED runs the Checks again and moves the Task if they pass, as it reruns interrupted `validate` runs. It doesn’t run them again for a Task that is stopped or Failed; that Task’s Lead gets the same held message.

Validate entered any other way still runs the Checks at entry through `validation.enter`, and a failure there stays in Validate as a failure case: a send-back from Review to Validate, the merge watcher’s send-back to Validate, the human’s approval of a Work Gate, and a Workflow whose Stage before Validate isn’t Work. A send-back that follows, for a regression or the human’s Fix decision, has the cause `check`.

A setup Task’s hand-off run uses its narrowed Checks, because `validation.begin` chooses them. Overnight mode changes nothing here: Work’s Gate, when the mode turns it off, is recorded as skipped when the Task moves after the Checks pass, and the three-failures question waits for the human like any other question.

## Considered Options

- **Hold the `ted outcome advance` request open until the Checks finish.** Rejected: Checks can run for many minutes, and ADR 0044 already keeps a long Check from holding an HTTP request.
- **Require a passed `ted checks` run on the current commit before `advance`.** Rejected: it leaves the work to the Task Lead, which is what the Stage file already asked for and what the three measured send-backs skipped.
- **Move to Validate first and undo the Stage change on failure.** Rejected: the push, the draft pull request and the Stage entry would already have happened.
- **Let the Task Lead move to Validate with a failing Check** (a flag on `ted outcome advance`). Rejected: it is a new thing a Run token can do, and a Task Lead that could skip the hand-off Checks would bring back the send-backs this ADR removes.
- **Accept the failure in Work.** Rejected: failure cases, assessments and the bound human decision belong to Validate; a second copy of them in Work would be more than this needs.
- **A new event for the three-failures question.** Rejected: `v1.SendBackAsked` already blocks outcomes, shows in the thread and survives a restart; a same-Stage ask can’t be mistaken for a real one because no Stage sends back to itself.
- **Count a failed hand-off run toward `max_back`.** Rejected: nothing was reviewed and no round happened. The three-failures question is the bound.

## Consequences

- A Task Lead that reports `advance` at Work gets its answer later, in a message, not in the command’s output. The Work Stage file and `workRoundText` say so.
- A Check failure straight after Work no longer appears as a send-back. A dashboard that wants them counts `hand-off` Check runs with the outcome `failed`.
- With Checks configured, the `check` send-back cause now comes only from the other ways into Validate.
- A Check that fails for a reason outside the Task (flaky, or broken on the base branch) can’t be accepted at hand-off. The human accepts it in Validate, which such a Task reaches through **Diagnose in Validate** on the three-failures question. There is no earlier way: the Task Lead has no command for it, so an unrelated failure costs three Check runs before the human can choose. The failure message and the Work Stage file tell the Task Lead not to change unrelated code to get past the Check and to write what it found in the Task brief.
- A Coordinator may answer the three-failures question with either choice, as it may any question from TED that has choices (`mayAnswer`, ADR 0094-coordinators-have-bounded-factory-authority). That gives it nothing it didn’t have: it can already answer the failure decision in Validate, and Accept this failure stays behind that decision’s own rules.
- A Work Stage with a Gate keeps the old order: the human approves, the Task enters Validate, the Checks run there.
