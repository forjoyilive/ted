# Validate and Checks

Rules for Checks, Validate, reviewers, send-backs, base conflicts and Failure cases. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- Validation failure history in the Task brief is written by `briefFailureHistory` in `packages/daemon/src/tasks/validation-report.ts`, which `writeBrief` in `tasks/tasks.ts` adds under Current state. A failure fixed, no longer applicable or verified by a later passing run gets one line with its reference, subject and outcome, because resolved output should not fill the brief. A failure replaced by a later failed run also gets one line, naming the replacement failure case and stating that it failed again. Unresolved and accepted failures keep their findings, evidence and latest decision; accepting a failure leaves it failed.
- A Check or Run counts as killed for lack of memory only by `memoryKill` in `packages/daemon/src/memory-kills.ts` (SIGKILL Ted didn’t send, or exit 137, with the lowest reading of the one `createMemoryWatch` the daemon hands out with memory in use above `busyMarks.memory.holdAbove` while it ran). A Task Check killed that way is `v1.CheckKilledForMemory`, never a failed Check: the executor in `tasks/validation.ts` waits for `freed` and reruns it in the same Check run, and from the second kill in a Stage visit asks the user (`memoryKill` on the Comment, Try again or Count it as failed), which only the user answers. A Scheduled Check killed that way stops with no Tasks. A Run’s is `v1.RunKilledForMemory`, committed with its ending; `recover` never marks a Task Failed for it and `failureHistory` leaves it out. Don’t read memory-kill reports from the OS, and don’t kill real processes in a test: drive `startDaemon`’s `load.memoryAvailable` and a stub that kills itself.
- When a move is refused only because the Checks haven’t run on the Task’s current code, `requireCoverage` in `tasks/validation.ts` throws `StaleCoverageError`; a Check that ran and failed is a plain 409. Mark done, sign-off approvals and `ted outcome advance` catch only that error and go through `checksThen` in `tasks/tasks.ts`, which starts the Checks and runs the same action again when they pass; never refuse a human’s action with a stale-coverage message, and never rerun a failed Check because of a click. Mark done passes `mergedOnGitHub` so coverage compares code only. At Merge the watcher doesn’t wait for a click: `mergeChecks` starts a `merge` Check run whenever coverage is out of date, and why the merge is held goes in `store.setMergeHeld` (the watcher’s refused obligations, and `mergeChecks` while its run is awaited), which the app shows under “The merge is pending”; never let a held merge show only in the log.
- Before treating a failed Check or test as outside the Task, fixing it as unrelated work or filing a repair Task, check the latest base branch and search this Factory’s open Tasks (`ted peers`, then `ted peers show <Task>`) and recent base commits for the failing test file. If the base branch already fixed it, merge it and let Validate run the Check again. If an open Task covers it, wait with `ted task block --by <Task>` instead of filing another repair. A new repair Task’s description names the failing test file so other Tasks can find it. In Validate, a failed test that passes on the latest base goes back to Work to merge that base and rerun the test; a test that fails there the same way gets a note with the test name, error and any Task already working on it (TED-695).
- A Failure case’s tested contexts are compared only with `sameTested` in `packages/daemon/src/tasks/failure-cases.ts` (version, failed-CI bindings, each repo’s HEAD, tree and merge-base, the Check hash and the CI observation); a context tested before the Task had a pull request has no CI observation, and `sameTestedFor` compares a Check or Finding case against it without CI, because nothing is pushed before Merge and CI at Merge is judged through its own `github-ci` cases. For a Work failure decision, `decisionCurrent` compares the decision’s `contextId` (falling back to the case’s `contextId`) with a verified current snapshot through `sameTestedFor` and `localInputs`; missing or invalidated snapshots make the decision stale. Never compare `fingerprint`, which also covers the base tip, and never make consent depend on the base tip. A Ted note the Task Lead must receive carries a title in `failureNoticeTitles`.
- Whether a newer failure case of the same Check replaces an older open one is decided only by `replacement` in `tasks/failure-cases.ts`: the hold check (`verify`, disposition `retried`) and the record-time `replaceOlder` both use it, so what holds a Task and what is stored agree. A repair decision whose repair Task was archived, deleted or unblocked without merging counts as abandoned (`abandonedRepair`), worked out on read with no event. An abandoned repair is treated like a Retry: a later passing run closes it (`verifyPassed`) and `verifyFailure` accepts it, with `verifyRepair` counting Checks from the decision. Only for an abandoned repair may verification name the merged Task in the same Factory that brought the fix (`fixedBy`, checked by `fixingTask`), stored on the verification entry (TED-527). A Check failure Ted can’t tie to the current code and Checks gets a decision card without Accept rather than a refusal (TED-523). `request` records why on the decision (`acceptRefused`: `changed` or `unknown`), and the card’s caption names that reason and the choices left; a card from before carries no reason and gets a general caption (TED-653). An assessment may name a repair Task (`repairTask`); `assess` in `tasks/failure-cases.ts` refuses this Task, another Factory’s, an archived or a done one, and `postFailureDecision` in `store/checks.ts` alone adds “Wait for <display ID>” before Wait for a repair Task and records it on the decision. Answering it goes through the same `waitForRepair` as choosing that Task in the repair form (TED-647).
- `stages.work.lead_closes_failures` (on in `workflow/defaults/workflow.yaml`, so a Factory turns it off with `false`) lets the current Task Lead close a Failure case it recorded as a Finding outside Validate, with passing evidence through `ted failure verify`. Only `leadClosesFailures` in `tasks/failure-cases.ts` reads the setting and only `verifyFailure` in `tasks/tasks.ts` uses it; don’t widen it to Checks, CI failures or cases recorded in Validate, and never let it accept a failure. It is on by default because the user asked for few failure questions (TED-666).
- `ted failure fix <id> "<why>"` (`POST /tasks/:id/failures/:id/lead-fix`, `chooseFix` in `tasks/failure-cases.ts`) records the current Task Lead’s own choice to fix an assessed Validate failure (a Finding or a Factory Check case, in Validate, with no human decision) in this Task, as `leadFixes` on the case through `v1.FailureFixChosen`, and withdraws an open decision question. `leadFixed` (the newest entry is bound to the current assessment) lets Validate’s `ted outcome back` through the same way a regression assessment or the human’s Fix in this Task does, and `verifyFailure` lets the Task Lead close such a case after fresh verification. Ted refuses a third choice for the same failure (same Check name and repo, or same Finding text) across the Task (`leadFixesPerFailure`), so the Task Lead then has to ask. It never accepts a failure, answers a request or works at Merge.
- The resolution choices on a failure decision card come from `offeredFailureChoices` in `packages/daemon/src/tasks/failure-choices.ts`, which both `postFailureDecision` in `store/checks.ts` and `request` in `tasks/failure-cases.ts` use; a named repair Task adds its “Wait for <Task>” choice beside `repair`. A stale Work card replaced by `refreshStale` offers only `rerunFailureChoice` instead, as described below. An assessment names the one choice the Task Lead recommends (`choice`, required by `parseAssessFailureRequest`); `request` refuses it when the card wouldn’t offer that choice, and the card marks it Recommended (for `repair` with a named repair Task, the “Wait for <Task>” choice), so a card never recommends what it doesn’t offer. An assessment stored before `choice` existed posts unchecked (TED-646).
- `tasks/send-back-hold.ts` owns Validate’s hold decisions, Loop check and hold lookups. `tasks/request-answers.ts` applies the user’s answer. The reviewer and the loop check are sub-agents whose agent, model and effort only `reviewerFor` in `tasks/tasks.ts` picks; never let `--provider` (or `--agent`) reach a reviewer. Any send-back Ted holds for the human (over `max_back`, a loop check) is a `v2.SendBackAsked` row, and a Loop check a `v2.LoopCheckStarted` row; each keeps a verified `base-conflict` cause, which the send-back Ted records later carries (TED-571), and `ted outcome advance` and `back` stay refused while its question is open. Validate’s limit question offers only Keep going (record the held return as round 1 and move to Work) and Stop the Task (record the held return the same way, then stop the Task in Work through the Stop button’s path, so a resumed Task Lead starts with those Findings); any answer resets Validate’s count, and `answerLoopAsk` still accepts the old choice labels on older questions.
- A Validate reviewer’s scope is decided only by `reviewRound` in `tasks/tasks.ts`, when the reviewer is requested: `v1.ReviewScopeRecorded` holds the commits it started at, and from the second round its instructions are Ted’s, built by `scopedReviewPrompt` in `tasks/review-rounds.ts` from the earlier Findings and the diff since the last reviewed commit. The Task Lead’s prompt file goes inside a fence with a fresh nonce and never replaces Ted’s scope. Every list of file names Ted puts in a prompt or a refusal (`fileLines` in `tasks/review-rounds.ts`, `found` in `tasks/base-conflict.ts`) goes through `oneLine` and sits inside a `<<<FILES <nonce>>>>` fence that the text calls data; never put a file name anywhere else. Every git command Ted gives a reviewer is built by `reviewCommand` there, which turns off replace refs, grafts, a shallow file, the pager, external diff and textconv programs, signature checks and worktree attributes; never write a reviewer’s git command by hand. `ted outcome advance` in Validate is refused by `movedSinceReview` in `tasks/tasks.ts` while any repo’s `HEAD` differs from the commits recorded for the visit’s reviewer, for every scope; it runs after the obligations and base-conflict checks, and a visit with no reviewer advances as before. Ted writes the round number and rule into the Validate entry and send-back messages with `validateRoundText` and `workRoundText`; change that text there, not only in a Stage file.
- In Validate, `ted run start` starts only the reviewer, and one per visit: `SubAgents.request` refuses a second reviewer while the first is queued, live or has reported, and refuses every other sub-agent unless the Task’s Workflow has `stages.validate.sub_agents: true`, read through `validateSubAgents` (`taskWorkflow` without a fetch). Don’t add a flag that lets a Run lift either rule.
- `stages.validate.p1_only_from: N` makes Validate rounds N and later send back for a new Finding only if it is P1; an earlier round’s Finding that is still not fixed stays blocking. Only `p1OnlyAt` in `tasks/validate-settings.ts` decides whether a round is under the rule, and the texts Ted adds (`p1OnlyLeadRule`, `p1OnlyReviewerRule`, `p1OnlyReviewPrompt`, `p1OnlyRefusal`) live there; every round text and reviewer prompt in `tasks/review-rounds.ts`, the `conflict` scope included, takes `p1OnlyFrom` and carries the rule. In those rounds `declareSeverity` in `tasks/tasks.ts` refuses `ted outcome back` from Validate without `--severity p1` or `--severity unfixed` (an earlier Finding is still not fixed), before the Validate judgment is recorded; a Check return from Validate’s first step, the human’s Fix in this Task decision, a verified base conflict and a send-back the human asked for skip it. The round is `countedValidateSendBacks(...).length + 1`, so every counted return, failed Checks included, moves it on. The declaration is `v1.SendBackSeverityDeclared`, recorded when the report is accepted and matched to its send-back in `store.listSendBacks`; a reviewer that ran under the rule is `v1.SeverityRuleReviewRecorded`. `workflow/defaults/workflow.yaml` sets it to 2, so later rounds send back only for P1 findings unless a Factory sets `false` (TED-666); it is not a Gate: `withoutGates`, `withForcedGates` and `setupWorkflow` don’t touch it.
- A send-back’s cause (`review`, `check`, `human`, `base-conflict`) is the separate `v1.SendBackCauseRecorded` event, committed with its `v2.TaskSentBack` through `store.recordSendBack({ cause })`; a new cause is a new string there, not a change to the send-back event. The thread reads the cause from that event’s Task log entry.
- Checks run only through `runChecks` in `packages/daemon/src/tasks/checks.ts` (in `planChecks` order, first failure stops; a command Check runs with `$SHELL -lc`, `CI=1`, no `TED_APP_*`), and each run is a Check run in the store, not a Run. A command Check never starts a Run or takes a working slot; an instruction Check starts one sub-agent, as the next rule says. The Merge rebase rerun reuses the same runner. A Check run’s trigger says why it ran: `validate` (Validate’s first step), `agent` (`ted checks`) or `merge`. `hand-off` (before leaving Work) is no longer started and stays readable in history. A Check run or a settings Run now first takes a place from the daemon’s one `CheckSlots` (`tasks/check-slots.ts`), which lets `maxChecksAtOnce` run at once and keeps the rest in a first-come line; a waiting Check run leaves the line when its Task is stopped, archived or deleted. What waits is in memory only (`store.setChecksWaiting`), and `Activity.checksRunning` counts only Checks that are running. Every Check command (a Task’s, a Scheduled Check’s, Run now) gets `TED_CHECK_CPUS`, the logical cores it may use: `checkCpus` in `tasks/check-slots.ts` gives the `checkCpuPercent` machine setting’s share of the cores (a multiple of 10 from 10 to 100, `checkCpuLimits`, default 50) divided by the Check runs holding a place when the command starts, never under 1, and callers get it from the daemon’s one `CheckSlots` (`cpus()`). A Scheduled Check gets the undivided share (`soloCpus()`), and only while the `limitScheduledCheckCpus` machine setting is on (the default): its command reads the value once, so a split taken at its start would last the whole run, and a nightly full run with 1 test worker hit its 2-hour timeout. It still holds a place, so Task Checks that start meanwhile count it. It goes into the environment in `runChecks` and `check-tries.ts`, never into `checkEnv`, whose hash is part of a Failure case’s tested context. Ted doesn’t enforce it: a Check’s command passes it to its test runner, and this repo’s `pnpm check` does through `workersWithin` in `scripts/machine-load.ts` (2 CPUs per Vitest worker). Don’t fix a Check that fills the computer by changing `busyMarks` or the CPU reading. `runChecks` in `tasks/tasks.ts` refuses `ted checks` while the Task is in Work (`handsOff`), whatever its options; don’t add an exception for a named Check.
- Before requesting an instruction Check’s sub-agent, `createInstructionChecks` calls `SubAgents.checkHold`: a Pi choice refused by `agentStartHold` (disabled, waiting for the sandbox switch, or without a model) produces a `missing` result and a report naming the reason, without starting a Run.
- An instruction Check (`{ name, instruction, fix?, timeout?, agent?, model?, effort? }`, refused by `checkChecks` in `workflow/check.ts` with `run`, `repo` or neither) runs only inside a Check run: `planChecks` puts `fix: true` Checks first, then the commands and the Ted settings Check, then the other instruction Checks, and `runChecks` hands each to `runInstruction`, which `beginChecks` in `tasks/validation.ts` wires to `runInstructionCheck` in `tasks/tasks.ts` and `createInstructionChecks` in `tasks/instruction-checks.ts`. Start its agent only with `SubAgents.requestForCheck` (purpose `instruction-check`, or `run-now-check` for Run now; `isCheckAgent` in `tasks/sub-agents.ts` accepts both, parent the latest Task Lead Run even if ended, choice from `reviewerFor` with the Check’s own fields); never with `request` or `requestForTed`, never as Validate’s reviewer, and never while holding the Check slot. Its prompt is only `instructionCheckPrompt`, with the instruction in a nonce fence; the result is only `reportResult` on the final message’s last line (`Result: pass` or `Result: fail`). Ted compares each repo’s `HEAD`, tree and uncommitted files before and after: a report-only Check that changed anything fails, a fixing one fails on uncommitted changes, and Ted never reverts. A Check may fix only when `beginChecks`’s `mayFix` holds (a `validate` Check run in Validate); Merge, `ted checks` and Run now run it report-only. No result line, a crash, a stop or a timeout is no report: `store.checkReportMissing`, then the `check-report` question from `checkReportMissing` in `tasks/tasks.ts` (Try again or Count it as failed), which only the user answers; never count it passed or retry on Ted’s own. The question and its unfinished Check run outlive a restart: Ted’s start leaves an open `check-report` question open while `awaitsReport` in `tasks/validation.ts` finds its Check run waiting, and `recover` waits for the answer there (`answerAfterRestart`) instead of resuming the Checks; when the stop came between `store.checkReportMissing` and the question, `recover` posts the question then. `store.awaitedReport` counts a missing report only while no new agent has started for that Check (no `start` boundary at its position). `beginChecks` runs the fixing Checks one at a time; after one changed code, `replanAfter` plans the rest of the Check run again from the current code (commands per changed repo, the Ted settings Check, change keys) and stores it with `store.replanChecks` (`v1.ChecksReplanned`) and in the progress, then `refreshCoverage` records coverage and context again, both before the next Check runs; never run the rest on the plan made before the fix. For a Check run containing a fixing instruction Check (`fixesFirst`), `record` in `tasks/failure-cases.ts` may take Ted’s generated context captured after the run started and no later than its finish (`capturedFor`), and `sourceContext` accepts that context by the same rule when matching the failure, including after a restart. Other Check runs still require a context captured before execution; an agent cannot supply a later context to `record`. A pass stores `changeKey` (`git patch-id --stable` per repo plus the Check’s fields) with `store.recordCheckChangeKey`; `planChecks` marks a Check `notRerun` only when `store.passedChangeKey` matches, and no key is stored while a worktree has uncommitted changes. Run now on a Task goes only through `check-tries.ts` and the `instructionTries` runner in `tasks/tasks.ts`, report-only, with no failure case; it passes `runNow: true` so its sub-agent is recorded as `run-now-check`, and `runNowAgents` in `tasks/thread.ts` keeps exactly those out of the Task’s thread. Only `instruction-check` agents recorded before that purpose existed fall back to the guess by start time and Check name.
- A Task Lead’s `ted outcome advance` at Work, Validate or Review is refused while `baseConflict` in `tasks/tasks.ts` finds that the base branch tip conflicts with the worktree’s `HEAD`. It fetches with `fetchBranch` and test-merges with `mergeConflicts` in `git.ts`, in a scratch bare repo; never test-merge inside a worktree, and let the outcome through when the check itself fails. A git read that decides a review’s scope, ancestry or a test-merge (`isAncestor`, `ownCommits`, `mergeConflicts`) goes through `inScratch` in `git.ts`: a scratch bare repo that reads the clone’s objects through alternates with replace refs off, so the clone’s `refs/replace`, `info/grafts` and `shallow` don’t apply and nothing is written to the clone. A send-back’s cause is `base-conflict` only when Ted set it (the merge watcher) or verified it with the same test-merge (`ted outcome back --cause base-conflict` from Validate or Review; from Validate it counts toward `max_back` and the Loop check like every return to Work); never record a cause on the agent’s word alone. A verified `base-conflict` send-back from Validate goes through even while a failure case is open and unassessed. The messages are in `tasks/base-conflict.ts`.
- Every conflict that test-merge finds is one `v1.BaseConflictFound` event: `store.recordBaseConflict` when `advance` is refused, or `store.recordSendBack({ conflict })` in the send-back’s own commit, which sets `sendBackId`. File names and the base name go through `clean` first, at most 50 names. Rows are deleted with the Task; read them with `store.baseConflicts` or `GET /tasks/:id/base-conflicts`.
- When every send-back since the last finished review has the cause `base-conflict`, `reviewRound` scopes the reviewer to the conflict resolution (`scope: 'conflict'`, `conflictReviewPrompt` and `conflictRoundText` in `tasks/review-rounds.ts`). It reads the Task’s own commits since the reviewed commit with `ownCommits` in `git.ts` (the first-parent chain) and trusts a merge commit only when its second parent is an ancestor of a base tip Ted fetched itself (`v1.BaseConflictFound`, or `baseTips` in memory); anything else is a full review. A `fixes` round with such merges gives the reviewer `git log -p --reverse --first-parent --remerge-diff`, not `git diff`. Never tell a reviewer to use `--remerge-diff` across a merge Ted hasn’t verified, because it hides what the merge brought in.
- `ted outcome advance` at Work checks the obligations, then `baseConflict`, then moves the Task to Validate; there are no hand-off Checks. `validation.enter` runs the Checks as Validate’s first step for every way into Validate, and delivers Validate’s instructions only after they all pass, so a failed Check starts no Validate Task Lead Run. A failure records its failure case, then goes through `sendBack` to Work with cause `check`, the Check run and the failing output as Findings, counted toward `max_back` and the Loop check; `sendBack`’s hold for the limit or the Loop check applies, with the Task waiting in Validate. A `factory-check` case that caused the Task’s latest return is decided from Work only with Accept this failure, in `resolveValidationFailure` in `tasks/validation.ts`: it is refused unless the context the decision is bound to still matches the code (`decisionCurrent` in `tasks/failure-cases.ts`), then moves the Task to Validate with no send-back and no count, and `beginChecks` resumes the saved `ValidationProgress` after the accepted Check. Keep that the only way a Task enters Validate past a failing Check, and don’t add a route that lets the Task Lead choose it. When the code changes after the Task Lead asked (it merged the base branch, Ted merged it or brought in a repair), `refreshStale` in `tasks/failure-cases.ts` withdraws the card and posts one for the same failure that offers only “Run the checks again on the new code” (`rerunFailureChoice`, decision `rerun: true`); an unreadable snapshot counts as changed. Ted calls it when a Task Lead’s turn or Run ends, when a Task enters Work, after a repair is brought in, and before any answer to a failure card in Work, so the user never gets an Accept that is refused for stale code. That choice moves the Task to Validate through `leaveWork(task, 'rerun')`, which, like Accept, doesn’t stop for Work’s Gate, so the Checks run on the current code (TED-761). `hand-off` Check runs and the three-failures question exist only in history: on start an unfinished `hand-off` run is marked interrupted and not run again, and the Task Lead is told to report again; `answerLoopAsk` still answers an open three-failures question (Try again, Diagnose in Validate). Tasks from TED-539’s version: an unfinished `hand-off` run of a Task in Validate is marked interrupted and `validation.enter` runs again at start; an open limit question with TED-539’s Diagnose in Validate goes to `diagnoseInValidate`, and while the `diagnosing` option in `tasks/validation.ts` sees that answer in the current Validate visit, a failed Check stays in Validate as a failure case instead of returning to Work. `baseConflict`, `reviewRound` and `movedSinceReview` call `execution.local` before they read a worktree, and `SubAgents.request` calls `prepareExecution` before `planReview`, so they act only on a Task this machine owns.
- The Ted settings Check (`builtIn: 'ted-settings'`, planned by `planChecks` when a change touches `.ted/`) runs only through `checkSettings` in `packages/daemon/src/tasks/settings-check.ts`. It always runs the installed checker (`checkWorkflowPath`) in the daemon. When the primary worktree is Ted’s own source (root `package.json` named `ted` and `packages/daemon/src/workflow/check-entry.ts` present, `isTedSource`), it also runs that branch’s entry file sandboxed like a command Check with no access groups, so a branch that adds a Workflow setting or sandbox access group can use it in `.ted/workflow.yaml`. The branch’s result decides pass or fail. When the branch’s checker reports no errors, the installed checker’s errors become warnings saying the Factory uses its last valid settings until the new build is installed. With no readable result, the installed checker decides and the output says why. Branch code never sees the Library’s contents: Ted hands it only the Library’s names (`libraryNames` in `workflow/check-path.ts`: Stage file ids, `order`, Agent ids and socket names, never text or socket paths) in a file under a fresh folder in the worktree’s `node_modules/.cache/`, which it removes afterwards. The installed daemon runs newer branches' entry files, so keep its contract fixed: `node packages/daemon/src/workflow/check-entry.ts --target <dir> --library-names <file> --out <file>`, the names file being `null` or `{ stageFiles, order?, agentsDefined, agentsInstructed, sockets }` read only by `parseLibraryNames`, writing `{ "problems": [{ severity, file, line, column, message, path }] }` with `path` relative to the current folder, read only by `parseSettingsResult`.
