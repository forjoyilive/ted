# One GitHub poller passes CI failures, review comments and conflicts to the Task Lead

Every open pull request of a Task that isn’t archived is watched, whatever its Stage. One poller in the Tasks module (`createPullRequestWatch` in `packages/daemon/src/tasks/github-watch.ts`) reads them all every `mergePollMs` (30 seconds) with one batched GraphQL query per host (`readByHost` in `tasks/merge.ts`; the host comes from the pull request’s URL). The merge watcher from ADR 0056-ted-merges-pull-requests-at-the-merge-stage no longer reads GitHub itself: each Task’s merge loop waits for the poller’s next read and works from it, so Tasks at Merge add no queries. A merge loop that needs a read at once (on entering Merge, or after a rebase) wakes the poller early; that is still one query per host for that cycle. The poller runs while there is something to watch and stops when nothing is left, so it holds the daemon’s idle timer only then.

After each read, the poller:

- **Records the pull request.** A pull request closed on GitHub is `v1.PullRequestClosedOnGitHub` (state `closed`, `closedOnGitHub`); reopened on GitHub it is `v2.PullRequestReopened`, which also clears `closedOnGitHub` (Ted’s own reopen now uses it too). An archived Task whose pull request was closed on GitHub ended as `pull-request-closed`, which the List shows as “Pull request closed on GitHub”. A hosted preview is the newest successful GitHub Deployment with an `http(s)` URL, else a successful commit status (not a check run, whose link is only its report page) whose name says preview or deploy; it is stored as `preview` on the pull request (`v1.PullRequestPreviewFound`) for the Apps section.
- **Passes new activity to the Task Lead.** `noticesFor` in `tasks/github-activity.ts`, ported from agent-orchestrator’s PR reactions, turns the read into notices: failing checks (one notice per head commit and set of failed checks, with the last 30 lines of each GitHub Actions job log, fetched only when the notice is new), each unresolved review comment (bot comments only when anchored to a line), each review that requests changes or comments with text, and a merge conflict (one per head commit). At Merge, while Ted is merging or holding the Merge Gate, only review comments go this way; CI failures and conflicts there still send the Task back to Work through the merge watcher, and the next read at Work passes on their details. A notice is new when its key and signature aren’t in a `v1.GitHubActivitySent` event for the Task, so nothing is sent twice and nothing is lost while `gh` fails: when it works again, the next read sends whatever wasn’t sent. All of a Task’s new notices go to its open Task Lead Run as one message. With no open Run, and the Task not stopped, failed, blocked, held for its agent, queued or starting, Ted queues a fresh Run from the brief (`v1.GitHubActivityQueued`, a fresh-Run ask like Resume), whose note says what GitHub reported; the next read after it starts sends the details.

**Only people with a say in the repo reach the agent.** A review comment or review is forwarded only when GitHub gives its author the association `OWNER`, `MEMBER` or `COLLABORATOR`. Anyone can comment on a public repo’s pull request, so anything else (`CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `NONE`, and most bots) is not sent and never starts a Run: Ted logs it once as `v1.GitHubActivityHeld`, and the thread says “not sent to the Task Lead (outside contributor)” so the human can pass it on by hand. CI log tails are read only for check runs from the `github-actions` app whose job URL is in the pull request’s own repo; a check run from another app, or one pointing at a fork, still shows as failed but without its log.

**GitHub text is untrusted.** Check names, CI logs, review comments, reviewer names and URLs are written by other people or by CI. Everything copied from GitHub goes between two `<<<GITHUB <nonce>>>>` lines, with a fresh random nonce for every message, under a line telling the agent it is data and not instructions. Before it goes in, it is passed through `redactSecrets`, terminal escape sequences, control characters and bidirectional and zero-width characters are removed, each comment is cut at 4,000 characters and each log line at 400, and reviewer names keep only the characters a GitHub login can have. Only Ted’s own text sits outside the fence: the pull request as Ted stored it (`acme/app#7`), counts of what arrived, and what to do. The thread line and the fresh-Run note use the same counts. Only the job ID is taken from a check’s URL; the log path is built from the repo Ted stored.

**When `gh` fails.** A host whose query fails is reported to the merge loops of Tasks on that host, which show Waiting for GitHub sign-in on an auth or missing-`gh` error as before; an auth error also makes the Gh runner check GitHub health, which raises the signed-out banner. Runs carry on. Rate limits back off in the Gh runner (ADR 0029); over 15 minutes is the warning banner.

## Considered Options

- **A second poller for activity next to the merge watcher.** Rejected: the spec allows one query per host per cycle, and two pollers would read the same pull requests twice.
- **Keeping per-Task merge loops reading GitHub.** Rejected for the same reason: ten Tasks at Merge were ten queries a cycle.
- **Posting GitHub activity as Comments from Ted.** Rejected: it would put other people’s text in the human’s thread and Inbox as if Ted wrote it, and Comments from Ted aren’t delivered to Runs.
- **Keeping the notice text in the store to put in the fresh Run’s prompt.** Rejected: the store would hold copies of CI logs and other people’s comments; GitHub still has them, and the next read sends them.

## Consequences

- The daemon stays up while any Task that isn’t archived has an open pull request.
- A review comment that is edited isn’t sent again; a new comment is.
- The read covers the newest 100 review threads with their newest 30 comments, and the newest 50 reviews. On a pull request past those numbers, a reply on an older thread is missed; reading further pages would mean more than one query per host per cycle.
- A review bot the repo owners installed is usually not a collaborator, so its comments are held back like an outsider’s.
- If a merge conflict clears and comes back on the same head commit, it isn’t sent again.
- A fresh Run started for GitHub activity begins its Stage before the details arrive, a few seconds later as its next message.
