# Platform

Rules for the sandbox, caches, child processes and their environment, disk and retention, banners, diagnostics and remote execution. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- `pnpm ted dev run show <run-id>` prints a Run’s state and Conversation. `pnpm ted dev slow` prints the daemon’s slow requests and event-loop stalls of the last minute and hour. `pnpm ted dev memory` prints the memory the daemon, Run hosts and agents use (`GET /diagnostics/memory`, `MemoryUse` in `packages/protocol/src/memory.ts`; a Run token can’t read it); Settings → Developer and the sidebar footer’s memory breakdown show the same figures with the app’s own processes added by the main process. The sidebar footer’s line shows the whole machine’s CPU and memory in use, using the same resource readers as the busy hold: `GET /diagnostics/usage` adds it as `machine` from the daemon’s one `Busy` (`reading()` in `packages/daemon/src/busy.ts`). The footer and busy strip can show samples taken at different times. A process’s memory is measured only by `processMemory` in `packages/daemon/src/process-memory.ts`: its footprint on macOS (what Activity Monitor shows), its resident size elsewhere. `GET /diagnostics/memory` and `GET /diagnostics/usage` share one process reading through `currentUsage` in `packages/daemon/src/diagnostics.ts`, reused for 10 s after it finishes, because `footprint` over many processes takes seconds under memory pressure; `GET /diagnostics` reads fresh. The `machine` figures are read separately through `Busy.reading()` on each usage request.
- A machine or Factory problem shows as a banner: call `banners.raise(…)` where you detect it and `banners.clear(…)` where it resolves, through `packages/daemon/src/banners.ts`; a button that does work in the daemon registers `banners.onAction(problem, handler)`; a button that first needs a folder sets `choose: 'folder'`, and the app sends the chosen path to the handler. A stops-work problem starting is the `banner-raised` event. Dismissing a warning hides it for 24 hours, except a problem for which `dismissClears` (`packages/protocol/src/banner.ts`) returns true, which is cleared for good because nothing raises it again; `repo-added` is one, raised only when the repo is added.
- The daemon times every route in `server.ts` and watches its own event loop in `packages/daemon/src/slow-moments.ts`: a request of 100 ms or more and a stall of 200 ms or more are counted for an hour in memory and logged, rate-limited, through `console`. A route is named only by `routePattern` (`routes/route.ts`), which works from the route’s regular expression and never from the request, so keep each capture a whole path segment and never log a URL, query string or body. A route that holds its response open on purpose (a stream, a long-poll, a wait for the app or another process) sets `waits: true` so it isn’t timed. `GET /diagnostics/slow` (`ted dev slow`) returns the figures as `SlowMoments`; a Run token can’t read it. `POST /diagnostics/profile` records a CPU profile through `cpu-profile.ts` with `node:inspector`’s in-process session, one at a time, 5 to 120 seconds, into `TED_HOME/logs/profiles/` (mode `0600`, plain folders only, newest five kept). It never sets `runToken` or `fileToken`: only the app’s key starts a profile, from Settings → Developer, and nothing opens an inspector port The daemon process also runs a watchdog worker thread (`watchStalls` in `cpu-profile.ts`): when the daemon’s thread has sent it no beat for 2 seconds it profiles that thread through `connectToMainThread` until the beats return, and a stall of 5 seconds or more is saved as `stall-<time>.cpuprofile` in the same folder (newest five kept) with a log line naming the file. Never keep the CPU profiler running outside a stall or a profile the app asked for, because it slows CPU-bound work several times over; only `main.ts` turns the watchdog on (`stallProfiles`), never a daemon started in a test, and the app’s own profile pauses it.
- Anything that starts new work (a Run, App, simulator or Automation firing) checks `store.newWorkHold()` or goes through the queue, which starts nothing while the disk is full. Code that deletes files under `TED_HOME` checks the name and real path first and never follows links, like `retention.ts` and `storage.ts`. `TED_FREE_BYTES_FILE` names a file holding the free bytes Ted should see; `vitest.config.ts` points every test at one with 500 GB, and `startDaemon`’s `disk` option overrides it.
- Retention deletes a Run folder (`TED_HOME/runs/<id>/`) only through `pruneRunOutput` in `packages/daemon/src/retention.ts`, and only `runOutputEnd` there decides when: never while the Run is live, its Task is open (not Done, not archived), or a Coordinator, an Automation draft, or a planning chat owns it, whatever its outcome; otherwise `runOutputDays` days (machine setting, default 7) after the Task became Done or was archived, or after a Run without a Task ended. A finished sub-agent’s clock starts when it ended, even while its Task is open, unless it has a side chat or is a reviewer whose Task is still in the visit it reviewed. Anything new that reads a finished Run’s output or revives it adds its case to `runOutputEnd`. Tests drive the clock with `startDaemon`’s `retention.now` and a short `checkEveryMs`. Archived Tasks are deleted automatically only by `createArchiveCleanup` in `packages/daemon/src/tasks/archive-expiry.ts`, through `Tasks.delete`, on the same timer, when the `deleteArchivedAfterDays` machine setting is set (default `null`, never); `archivedDue` there decides which are due and which are kept: an archived Task goes with every Task under it, as one delete from the top, only when all of them are archived that long, none has an open pull request and none blocks a Task that isn’t archived; an archived Task under an archived or Done parent goes only with its parent. `GET /archive-expiry` reports both counts from it for the app’s confirm dialog, and `close()` waits for a delete in progress before the Tasks module closes.
- Shelved: remote execution is on hold. Its code is kept but hidden behind `TED_REMOTE_EXECUTION=on` (`remoteExecutionOn` in `packages/protocol/src/env.ts`), which only Ted Dev reads; without it Settings → Machines, the worker window and `ted execution` are refused and the daemon opens no execution port. Don’t build new work on it or treat it as required, and Validate doesn’t need the two-Mac lab. The rule below still holds for the code that is kept. Execution commands for a paired Mac are issued only by `createExecutionCommands` in `packages/daemon/src/execution/commands.ts`: `issue` saves the intent with the Task’s assignment and awaits `store.persisted()` before the command can be sent, a final report is confirmed to the execution Mac only after it is saved, and no report is applied and no command sent before the connection’s inventory is reconciled. On the execution Mac only `execution/operations.ts` runs operations, from the journal in `execution/journal.ts`, which is written and synced before anything is reported; it records `start` before a launch, starts nothing while disconnected, and never runs an `uncertain` operation again. Never delete or shorten a journaled result, never add a timeout that releases an operation or an assignment, and never add a route, CLI command or button that issues an operation: only the harness reaches `issue`, through `DaemonOptions.execution.ready`. The message types, parsers and `executionLimits` are in `packages/protocol/src/execution-commands.ts`; a new operation kind adds its start-evidence check beside its runner. `TED_EXECUTION_CRASH_AT` is test-only.
- Outside Bypass, every Task worktree setup and teardown, every Check of a Task and every App an agent or Ted starts runs in the OS sandbox from `packages/daemon/src/sandbox.ts` (`sandbox-exec` on macOS, `bwrap` on Linux): it writes only the Task’s worktrees, its own temp folder and the Task’s caches, both under `TED_HOME/sandbox/<TASK-ID>/`, and reads nothing else in `TED_HOME` but the Task’s clones. On macOS, a command whose sandbox has the `ios-xcode` access group (below) also writes what Xcode makes in the per-user temp folder (`getconf DARWIN_USER_TEMP_DIR`) whatever `TMPDIR` says: `TemporaryItems/NSIRD_(xcodebuild|SWBBuildService|XCBBuildService|actool|ibtool|ibtoold|swift-build|swift-run|swift-test)_*` (`ibtoold` saves the PNGs it renders through `NSIRD_ibtool_`), SwiftPM’s `TemporaryDirectory.` plus exactly six letters or digits, Swift Build’s `swbuild.tmp.` plus exactly eight, and what `actool` and its helpers need to compile an asset catalog or an Icon Composer `.icon`: an `actool-sprite-atlas-scratch-<UUID>` folder; a `<UUID>` folder holding only `assets.uicatalog` (and `-journal`), `<name>.icon.xcassets` and rendered icons, because other programs make `<UUID>` folders there too; `ibtoold-<pid>/IB/<UUID>.HostToRemote` and `.RemoteToHost` FIFOs; CoreData’s `Untitled-` plus eight letters or digits `.uicatalog` (and `-journal`); and rendered icons named `<name>_<UUID>-<pid>-<16 hex>.png` with ImageIO’s `.<name>….png-<6 characters>` temp file. Those `actool` items may only be folders, plain files or, under `ibtoold-<pid>`, FIFOs; never links, because `ibtoold-<pid>` names are guessable and stay behind, and a planted link there would redirect the user’s own `actool`. It can’t list `ibtoold-<pid>` or its `IB` folder. To compile a storyboard, `ibtoold` also writes a `<UUID>.storyboard` plain file in the per-user temp folder. It creates, re-modes, touches and deletes that file, and the user’s own `ibtoold` makes its copies with the same mode, so the rule can’t be narrower than any plain file of that name; the user’s copies are safe only because each name is a random UUID, lives for one compile and can’t be listed. Sandboxed commands can’t open POSIX shared memory whose name starts with `ib`: that is `ibtool`’s registry of idle `ibtoold` servers, and through it a sandboxed `ibtool` hands its job to the user’s own unsandboxed `ibtoold`, which then writes wherever the job names. Without the registry, `ibtool` runs `ibtoold` itself inside the sandbox, so the `ib…-IBTOOLD-IN` (and `-OUT`, `-ERROR`, `-CONTROL`) FIFOs it would otherwise make in the per-user temp folder stay refused. The sandbox matches these names without regard to case, so the check that keeps a `TED_HOME` inside one of them from getting these rules ignores case too. A sandboxed command can read other processes’ arguments (`sysctl` `KERN_PROCARGS2`; no Seatbelt rule hides them short of denying `sysctl-read`), and the user’s own `AssetCatalogAgent-AssetRuntime` passes its FIFO paths there. When the per-user temp rules are available and the daemon’s umask does not mask others-execute, sandboxed commands run under `/bin/sh` with the daemon’s umask plus others-execute masked, and in `ibtoold-<pid>` they may create new folders and FIFOs but change only those with exactly the mode that umask gives `0777` (`0754` under a daemon umask of `022`). The user’s own (`rwxr-xr-x` under umask `022`, `rwx------` under `077`) have another mode, so a sandboxed command can’t write, replace, remove or re-mode them; only a user process whose umask is exactly the sandbox’s (`023`) would make matching ones. When the daemon’s umask already masks others-execute, the two can’t be told apart, so the `ibtoold-<pid>` rules are left out and `actool` doesn’t work in the sandbox. Reading the user’s FIFOs stays possible, as before. `xcrun_db` stays refused even though `xcrun` warns it can’t write it: the user’s own `xcrun` trusts that cache. Nothing else there is writable, because every process of the user shares that folder; a failed xcodebuild’s default `ResultBundle_<time>.xcresult` stays refused, because a predictable name there would let a sandboxed command plant links for the user’s own builds, so builds pass `-resultBundlePath` inside `$TMPDIR`. Xcode’s package resolution writes `<package>.dia` to `~/Library/Caches/org.swift.swiftpm/manifests/ManifestLoading` whatever its cache options say, so Ted makes that folder before each sandboxed command with `ios-xcode` and opens only plain `.dia` files in it, never links or folders, and only while the folder isn’t itself a link; the rest of SwiftPM’s caches stays closed, because the user’s own builds trust them. macOS mounts each iOS Simulator runtime at `/private/var/run/com.apple.security.cryptexd/mnt/com.apple.iPhoneOS.SimulatorRuntime-<version>.<random>`; without a read there, CoreSimulator reports the runtime and every device on it “unavailable, runtime profile not found” and `xcodebuild -destination` finds no device. So `ios-xcode` reads (never writes) folders under that `mnt` folder whose names start with `com.apple.iPhoneOS.SimulatorRuntime-`, and their contents. It still can’t list `mnt` itself, which CoreSimulator doesn’t need, or read the watchOS, tvOS and visionOS runtimes there. Tools that let Ted move their caches get a folder in the Task’s cache from `buildCacheEnv` instead (`CP_HOME_DIR` for CocoaPods, alongside the Xcode and Gradle ones). The JVM on macOS takes `java.io.tmpdir` from the system, not `TMPDIR`, so every sandboxed command gets `-Djava.io.tmpdir="<its temp folder>"` in `JAVA_TOOL_OPTIONS`, and Gradle and other JVM tools need no workaround. Callers merge the sandbox’s environment into their own with `withSandboxEnv`, which puts a `JAVA_TOOL_OPTIONS` already set first; the JVM takes the last value of a property, so the sandbox’s folder wins, and a command that sets its own `JAVA_TOOL_OPTIONS` inside the sandbox still wins over both. macOS refuses a sandbox inside another, so SwiftPM’s own manifest sandbox can’t start in Ted’s: `swift build`, `run` and `test` need `--disable-sandbox`, and xcodebuild needs `-IDEPackageSupportDisableManifestSandbox=1`; no environment variable does it. Swift macros run in `swift-plugin-server` under the compiler’s own sandbox, so code that uses them needs `swiftc -disable-sandbox`, the build setting `SWIFTC_DISABLE_SANDBOX=YES` in xcodebuild. Expo’s ExpoModulesJSI build phase runs a second xcodebuild under `env -i`, which drops those flags and `TMPDIR` but keeps `PATH`, so an Expo App’s `run` command builds that framework first with an `xcodebuild` wrapper on `PATH` that adds `-IDEPackageSupportDisableManifestSandbox=1` and `-IDEDisablePackageManifestCaching=1` and restores `TMPDIR` (`packages/daemon/src/workflow/defaults/setup.md`); a user-wide `defaults write` or a Ted-wide wrapper was rejected, because it would weaken the user’s own builds or still miss Xcode’s script phases, which put Xcode’s own tools first on `PATH`. It also can’t list the per-user temp folder or its `TemporaryItems` folder (`file-read-data` denied on those two paths only), so it can’t find a folder the user’s own Xcode is using and write into it; it reaches its own folders there by name. The worktrees, temp folder and cache folders Ted prepares for the sandbox must be plain folders inside `TED_HOME`, checked without following links, and never inside another writable one. Anything new that lets a Run make Ted run repo code goes through it too. When the sandbox is missing, refuse and raise `sandbox-unavailable`; never run unsandboxed. The one exception is a Pi Run outside Bypass after the human turned on `piUnsandboxedAllowed` in Settings → Providers: Pi is a Provider the human chose and its Runs are the work they asked for, so on a machine without a working sandbox the choice is theirs, made in the app with the reason in front of them; until then Pi work waits (`docs/agents/runs-and-providers.md`). A Pi Run outside Bypass otherwise runs in this sandbox, wrapped by its Run host. Only an App start signed with the app’s key (▶, Restart, the sign-off Preview row) runs outside it, never because of a request field, and it restarts a sandboxed instance; the app confirms first while the App carries `confirmOutsideSandbox`, until the human ticks Always, stored in the `appsOutsideSandbox` machine setting (per Factory ID, deleted with the Factory). Each approval holds the repo, the App name and a SHA-256 of what runs (`outsideSandboxApproval` in `packages/daemon/src/apps/apps.ts`: repo, name, kind, run command, the App’s `env`, the repo’s worktree env and `electron`), which the daemon sends with the App and the app saves unchanged. An approval counts only while that fingerprint matches, so a merged change to the command asks again instead of running unsandboxed unseen. The daemon checks again when the App starts: a human start or restart in a sandboxed Task needs a saved approval for the current fingerprint or the `declaration` the human just confirmed in the request, and is refused with 409 otherwise, because the app’s list can be older than the Workflow. The App’s instance record keeps the declaration a human launch ran with, and Ted’s own restarts of that App (a simulator size change, an emulator reboot) pass it as the confirmation, so a changed App is refused there too. A human-started device App waiting for a slot or another App’s build keeps the declaration it was confirmed for in its waiting record and is checked again before it launches; if it no longer matches, it fails with the same message. Approvals saved as bare App names are dropped when settings are read, so each such App asks once more. It connects only to Unix sockets in those folders and the sockets its own `sandbox_access` asks for by name (`socket:<name>`, below); on Linux, `wrap` returns the folders as descriptors for `bwrap --bind-fd`, which a caller passes in `stdio` from fd 3 and closes after the spawn. `TED_SANDBOX_BIN` names the sandbox program, and a test Check or App writes only inside its worktree (`stub-*` files). On macOS it also refuses reads and writes of the personal folders in `protectedFolders` (`packages/daemon/src/protected-folders.ts`), denied before its own folders are allowed so a `TED_HOME` inside one still works; add a folder there, never in one place only. On macOS it reads file contents (`file-read-data`, `file-read-xattr`) only in its own folders and a base read set, so a Check or App can’t read `~/.ssh`, `~/.aws`, `~/.npmrc` or tokens under `~/.config`; metadata reads stay open so paths resolve and `getcwd` works, but it can’t list a folder outside the set. The base set is `baseReads` in `sandbox.ts`: system folders (`/usr`, `/bin`, `/sbin`, `/System`, `/Library`, `/Applications`, `/opt`, `/nix`, `/private/etc`, `/private/var/db`, `/private/var/select`, `/private/var/run/resolv.conf` (DNS settings, where `/etc/resolv.conf` leads; Ruby’s `net/http` reads it when it loads), `/dev`), each `PATH` folder (and, outside HOME, the folder above a `bin`), `DEVELOPER_DIR`, `JAVA_HOME`, `COREPACK_HOME`, the per-user temp folder’s `xcrun_db`, and known paths in HOME: Git’s settings (`.gitconfig`, and `config`, `ignore` and `attributes` in `.config/git`, never its `credentials` store; Git stops when it can’t read them) and toolchain folders (`.nvm`, `.fnm`, `.local/share/fnm`, `.volta`, `.local/share/mise`, `.asdf`, `.rbenv`, `.pyenv`, `.gem/ruby` (not `.gem`, which holds RubyGems’ `credentials`), `.rustup`, `.cargo/bin`, `.bun/bin`, `Library/pnpm`, `Library/Developer`). `~/Library/Developer/CoreSimulator` is refused (a `deny` after the base allow) unless the command has the `ios-simulator` group, and the Android SDK (`~/Library/Android/sdk`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, real paths) is read only with the `android-emulator` group and refused otherwise, even where a `PATH` folder or `sandbox_reads` entry lies inside it. The `PATH` and toolchain environment entries may also add folders under HOME. `baseReads` resolves existing paths and drops HOME itself, its ancestors and `/`; the profile separately allows reading `/` itself. The per-user temp items it may write are readable too, and `/private/tmp` only with the `shared-tmp` access group (below). A Factory adds files or folders with `sandbox_reads` in `.ted/workflow.yaml` (absolute, `~/…` or a whole `$NAME`, the later layer’s list winning), for example `~/.npmrc` for a private registry; callers running a Factory’s commands pass it through `sandboxGrants`. Pi Runs use their own scope from `runs/pi-sandbox.ts` and do not receive `sandbox_reads` or `sandbox_sockets`. A listed path inside `TED_HOME` or a personal folder stays refused, because those denies come after the allows. `sandbox_reads` remains per Factory; an App’s `sandbox_access` does not narrow that read set. On Linux, bwrap mounts no host root (the Android SDK is mounted only with `android-emulator`, and a candidate inside it is dropped otherwise, though an SDK under a mounted system folder such as `/opt` stays visible): the sandbox sees only its own folders and, read-only, the same base set and `sandbox_reads`, so files elsewhere in HOME don’t exist inside it. The candidates come from `readCandidates`, which both platforms share apart from the system folders; Linux’s are `/usr`, `/bin`, `/sbin`, `/lib`, `/lib32`, `/lib64`, `/libx32`, `/etc`, `/opt`, `/nix`, `/snap`, `/sys`, `/etc/resolv.conf` and `/run/systemd/resolve` (DNS on systemd-resolved hosts), with bwrap’s own `/dev` and `/proc`. `linuxReads` mounts each one where it really is, and makes an entry reached through a link, such as a merged-usr `/bin`, a link straight to that real path, never a second mount, so a chain of links still resolves and the `TED_HOME` and personal-folder tmpfs mounts cover everything it reaches. It leaves out anything already visible through a mounted parent, and any entry whose real path is inside a personal folder or `TED_HOME`, so a link can’t open either. Toolchains that read data outside the set, such as `/var/lib` or `sssd` sockets, need `sandbox_reads`.
- Sandbox access groups widen the sandbox for one command. They are named groups defined only in `packages/protocol/src/sandbox-groups.ts`, never paths from a repo, and `ted sandbox groups` lists them. The Factory’s Workflow lists them under `sandbox_access` on an App, a command Check, or a repo’s `worktree.setup` or `worktree.teardown`; `ted workflow check` rejects an unknown name. `electron` holds `macElectronServices` (below) and sets `TED_SANDBOX_ELECTRON=1`; an App with `electron: true` gets it through `appAccess` in `apps/apps.ts` without listing it, and a Check that runs Electron lists it. On Linux it sets the same environment flag but opens no extra services. `ios-xcode` holds every Xcode rule above: the per-user temp folder items, the ManifestLoading `.dia` files, the iOS Simulator runtime reads and the tighter umask. It is shared access on the user’s Mac: every process of the user uses those folders, and the user’s own Xcode trusts what is there, so give it only to the App, Check or setup that builds with Xcode. A command without it runs with the daemon’s own umask and gets only the runtime reads if it has `ios-simulator`. `ios-simulator` holds `macSimulatorServices` (names starting `com.apple.CoreSimulator.`), reads of `~/Library/Developer/CoreSimulator`, where Ted’s per-Task devices live because `apps/simulators.ts` uses the default device set, and the iOS Simulator runtime reads it shares with `ios-xcode`; on Linux it opens nothing. `android-emulator` allows, at `localhost` and `outbound` on macOS, localhost TCP 5037 (the adb server) and 5554–5585 (the console and adb ports `apps/emulators.ts` picks from), which the macOS profile otherwise denies one port at a time at every network level, `outbound` included, because Seatbelt matches one port or all of them. The group also reads the Android SDK. At `none` on macOS, loopback stays closed even with this group. On Linux it keeps host networking, because bwrap can’t open one host port alone, so such a command can also reach outside hosts. `~/.android`, which holds adb’s keys, stays closed: the daemon starts the adb server outside the sandbox, and sandboxed `adb` and Gradle only talk to it. An App with `kind: ios-simulator` or `kind: android-emulator` gets the group of its kind through `appAccess` without listing it, because Ted boots its device for it; any other App, a Check (an `xcodebuild test` on a simulator, a Gradle build that reads the SDK) or a setup lists the group. The two are separate from `ios-xcode`, so an App or Check that builds with Xcode and also uses the simulator lists both. `shared-tmp` lets a command on macOS read and write `/private/tmp` (`/tmp`). Every process of the user shares that folder, so a command with it can plant files or links there for the user’s own tools or other Tasks; give it only to an App, Check or setup whose tool writes there whatever `TMPDIR` says, and a refused `/tmp` or `/private/tmp` path in its log gets the hint below. On Linux it changes nothing and a refused `/tmp` path gets no hint, because `bwrap` mounts the command’s own temp folder at `/tmp`. Except for the approved setup Task entries below, groups are read only from the Workflow on the base branch, so a Task’s branch can’t grant itself access before the user merges: Apps, Validate Checks and teardown take their entry’s groups; setup takes the repo’s setup groups only while its recorded command is still the one the base branch declares; Automation checkouts, cache seeding and a Chat’s checkout run the repo’s setup with its groups. Chat commands, Cleanup commands and Scheduled Checks get no group. A command Check tried from Settings (`savedCheckAccess` in `packages/daemon/src/check-tries.ts`) gets the `sandbox_access` of the base branch’s command Check of the same name only when its `run` is identical, character for character, and it resolves to the same repo (the request parser trims spaces and line breaks around `run` first, and the trimmed command is what runs); otherwise it gets none, because its command comes from the request and an unsaved edit must not grant itself access. Its scratch worktree’s setup takes the repo’s setup groups from the base branch, like an Automation checkout. The try records `sandboxAccess`, or `withheldAccess` when the saved Check has access the try didn’t get, and its output and Settings say which. A setup Task’s proposal carries each App’s and Check’s groups (`sandboxAccess`) and any repo’s worktree setup/teardown groups (`worktree`), and the approval card lists them under Sandbox access. Until merge, a setup Task’s Apps and Checks get only the groups the user approved on their row (`approvedApps` and `approvedChecks` in `packages/daemon/src/tasks/setup-access.ts`), and its branch is refused at hand-off when a repo’s setup or teardown asks for other groups than the approved ones; repo setup groups take effect only after merge, because a setup Task runs no repo setup. When an App, Check or worktree setup/teardown lacks a group and its log shows a refusal that group would address, Ted appends one line naming the group and the App, Check or setup (`packages/daemon/src/sandbox-hints.ts`): path refusals for `ios-xcode` and `shared-tmp` (macOS only), service refusals for `electron`, a lost CoreSimulator connection or a refused `Library/Developer/CoreSimulator` path for `ios-simulator` (macOS only), adb unable to reach its server, a refused connect to port 5037 or 5554–5585, or a refused Android SDK path for `android-emulator`, and other connection or DNS lookup failures for `network`. Agents propose the group in `.ted/workflow.yaml` (`sandbox_access`), so the user grants it by merging or approving; they never work around a refusal by moving a tool’s files, turning off its checks or running it some other way. The user sees and changes groups in Factory settings (each App, command Check and worktree setup/teardown). The Sandbox section lists current access by command and group; the save dialog and the Review and Merge sign-offs list who gains or loses which group. They describe changes with `sandboxAccessChanges` in `packages/protocol/src/sandbox-access.ts`; the sign-offs store the comparison of `sandbox_access` between the branch’s `.ted/workflow.yaml` and its merge base with the base branch (`workflow/access.ts`) as the gate’s `sandboxAccess`, or set `sandboxAccessUnknown` when Ted can’t read either file, so a failed comparison never looks like no change.
- Unix sockets outside a command’s own folders are granted per command, never Factory-wide. The user names each socket in the Library only (`TED_HOME/library/workflow.yaml`, `sandbox_sockets: { docker: /var/run/docker.sock }`, a path absolute, `~/…` or a whole `$NAME`), and an App, command Check or worktree setup/teardown asks for one with `socket:<name>` in its `sandbox_access`. A raw path in a repo would let a branch open any socket on the user’s machine, so `ted workflow check` refuses `sandbox_sockets` in a Factory’s `.ted/workflow.yaml`; the repo only names what the user’s own Library opens, and the base-branch and approval rules above apply to `socket:` entries like any group. The old list form grants nothing in either layer and `ted workflow check` warns with the steps to move each path. A `socket:` name the Library doesn’t define is a warning, because another user’s Library may define it; at run time `wrap` returns it in `missingSockets` and `appendRefusalHints` adds a line naming the missing Library entry. Commands with no `sandbox_access` of their own (chats, Cleanup, Scheduled Checks, a Check tried from Settings that doesn’t match its saved Check) get no sockets.
- Network has three levels: `none`, `localhost` (the default) and `outbound`. `sandbox_network` in `.ted/workflow.yaml` sets the Factory’s level for every sandboxed command (the later layer wins). The `network` access group gives one App, command Check, worktree setup or worktree teardown `outbound`. Ted’s own Factory sets `sandbox_network: outbound`, so every sandboxed command in it gets outbound access. Per-host grants aren’t offered: Seatbelt can’t filter by hostname, so they would need a filtering proxy. On macOS, `localhost` allows `(remote ip "localhost:*")` and denies every other IP destination, and `none` denies loopback too. Seatbelt’s `localhost` also matches this machine’s own addresses, so a command at `localhost` can reach a service the user runs on the Mac’s LAN address; traffic still never leaves the machine. Tests check the denial against TEST-NET `192.0.2.1`, never the machine’s own address. Below `outbound` the profile also leaves `mDNSResponder` off its socket list: `localhost` still resolves, but no lookup can carry data out through DNS. On Linux, `none` and `localhost` run the command without `android-emulator` with `--unshare-net`, in its own network namespace with only its own loopback; `outbound` keeps host networking. An App at `localhost` on Linux (`serves` in the scope) also keeps host networking, because the user’s browser and Ted must reach its port and bwrap can’t share host loopback alone. So on Linux such an App can still reach outside hosts, until Ted forwards App ports into a namespace of its own. Pi Runs always get `outbound`, because they must reach their model provider. Commands that get no group (chat commands, Cleanup commands, Scheduled Checks) still get the Factory’s level.
- On macOS the sandbox denies every `mach-lookup` and allows only `macServices` in `sandbox.ts`, so a sandboxed command can’t reach the keychain (`com.apple.SecurityServer`), the pasteboard, Launch Services, CoreServices or any other system service off the list. Each entry was kept because a toolchain fails or loses a feature without it, tried by running node, git, `swift build`, `xcodebuild`, `actool`, `simctl` and Ted Dev under a deny-all profile and adding one service at a time:
  - `com.apple.system.opendirectoryd.libinfo` and `.membership`: user and group lookups (`getpwuid`); without them `id -un`, node’s `os.userInfo()` and `simctl` fail.
  - `com.apple.bsd.dirhelper`: `confstr` for `DARWIN_USER_TEMP_DIR` and `DARWIN_USER_CACHE_DIR`, which xcodebuild and `getconf` use.
  - `com.apple.system.notification_center`: `notify(3)`, which libc and Foundation use for time zone, DNS and network changes.
  - `com.apple.system.logger` and `com.apple.logd`: logging (`asl`, `os_log`).
  - `com.apple.SystemConfiguration.configd` and `.DNSConfiguration`: DNS servers, search domains and proxy settings for name resolution. They stay open at every network level: they only report settings, and below `outbound` lookups already fail because `mDNSResponder` is off the socket list.
  - `com.apple.trustd` and `com.apple.trustd.agent`: certificate trust for TLS and for loading provisioning profiles, which xcodebuild does at every build.
  - `com.apple.lsd.mapdb`: Launch Services’ read-only file type database; without it xcodebuild can’t tell a `Package.swift` folder is a package. The rest of Launch Services stays closed, so a command can’t open apps.
  - `com.apple.FSEvents`: file watching, for xcodebuild, Metro, Vite and `fs.watch`.
  - A command with the `ios-simulator` access group (every `kind: ios-simulator` App has it) also gets `macSimulatorServices`: names starting `com.apple.CoreSimulator.`, through which `simctl`, xcodebuild and `actool` reach the simulator.
  - Names ending `.MachPortRendezvousServer.<pid>`: Chromium’s child processes (Electron, Playwright’s Chrome) fetch their ports from this service, which their own parent registers; without it every child process dies at start.
  - A command with the `electron` access group (every `electron: true` App has it) also gets `macElectronServices`: `com.apple.coreservices.launchservicesd`, because Electron aborts at launch unless it can check in, and `com.apple.windowserver.active`, without which no window opens.
  - `cfprefsd` stays closed: through it a command could read any app’s preferences, which the base read set keeps it from reading as files. None of the toolchains above needed it. Writing preferences is denied separately (`user-preference-write`).
- A Task’s cache folder (`TED_HOME/sandbox/<TASK-ID>/cache`) starts as a copy-on-write clone of its Factory’s seed in `TED_HOME/seeds/<factory-id>/seed`, made only by `startCache` in `packages/daemon/src/tasks/cache-seeds.ts`, which `prepareLaunch` in `tasks/local-lifecycle.ts` and `sandboxScope` in `tasks/tasks.ts` call before a sandboxed command; only that module writes `seeds/`. It fills a seed in the background, never making a Task wait: a `CheckSlots` place, `store.newWorkHold()`, scratch worktrees of `origin/<base>` and each repo’s `setup` in the sandbox with a cache of its own, then a clone of that cache swapped in under the per-Factory lock that clones take; the key is the setup command, `worktree.env`, `worktree.copy`, base branch and the lockfile blob IDs. Never give a sandbox a seed as its cache or a folder holding one, never clone a seed where the file system can’t clone (`filesClone`), and keep Bypass Factories out. Removing a Factory deletes its seed through `Tasks.removeFactorySeed`; seeds and Task caches count as Sandbox caches in Storage.
- A copy of a Factory’s code outside a Task (chats, Automation Runs and Scheduled Checks, the seed cache, the settings Run now) is made only through `makeCopy` in `packages/daemon/src/code-copy.ts`, the one caller of `git.addScratchWorktree`; if a step fails it removes the worktrees it added. The same module removes copies, and both ways first end every process left in the copy and its sandbox folder (`endProcessesInside`, matched against folders `taskFolder` builds), because anything still running there would keep files open or keep working in a deleted folder: `discardCopy` also refuses a folder that isn’t plain (chats), `removeCopy` removes the worktrees and then the folder through `removeInside` (the others; an Automation Run passes its `TED_HOME/sandbox/<runId>/` folder as `sandbox`). The differences between callers (cloning a missing repo, fetching, ignoring a failed file copy) are `makeCopy` options, kept so the move changed no behaviour.
- A Fix that runs a CLI command opens it in the user’s own terminal through `Integrations.fix`, which builds the command from a fixed list in `packages/daemon/src/integrations.ts` and never from text a client sends. Tests point `TED_GH_BIN` at `packages/daemon/test/fixtures/stub-gh.ts` (set in `vitest.config.ts`, with `TED_LOGIN_SHELL=off`); `TED_STUB_GH` names a JSON file that sets what the stub answers, and `TED_FIX_LOG` makes the daemon write Fix commands to a file instead of opening a terminal.
- Work Ted starts for a Task or Run (the Run host, Checks, worktree `setup` and `teardown`, the settings Run now, an App the human didn’t start) starts through `workCommand` in `packages/daemon/src/priority.ts` with the `lowPriorityWork` machine setting, which puts `/usr/sbin/taskpolicy -c utility` in front on macOS and `nice -n 10` elsewhere; niceness does nothing on macOS. The daemon, `git`, `gh`, the Task shell and an App the human starts stay at normal priority. Tests compare a child’s scheduler priority (`ps -o pri=`, macOS) or niceness (Linux) with their own, since they may run lowered themselves.
- Every Run gets its own temp folder, `TED_HOME/runs/<run-id>/tmp` (mode `0700`, a plain folder checked without following links), made by `writeLaunch` before each launch of its host. `runEnv` in `packages/daemon/src/runs/run-manager.ts` points `TMPDIR`, `TMP`, `TEMP` and `CLAUDE_CODE_TMPDIR` at it, after the owner’s environment so nothing overrides them; Claude Code builds the `TMPDIR` its sandboxed commands see from `CLAUDE_CODE_TMPDIR`. Without it every Claude Code Run on the machine shared `/tmp/claude-<uid>`, and one Task Lead’s `$TMPDIR/brief.md` was saved as another Task’s brief. The preamble and the sub-agent preamble also tell agents to name temp files with `mktemp`, for a tool that ignores `TMPDIR`. The folder goes with the Run folder.
- Process inspection with `ps` can be refused by the sandbox before a child starts. `ownProcessGroup` in `packages/daemon/src/launch.ts` and `parentOf` in `packages/daemon/src/runs/run-manager.ts` return `undefined` for both a synchronous launch failure and a failed command, so reset cleanup and idle sleep can continue. Idle sleep directly kills an agent only when its parent is confirmed to be the Run host.
- A child process the daemon starts gets its environment from `packages/daemon/src/command-env.ts`: the one `Environment` the daemon read from the login shell, through `worktreeCommandEnv` for anything a repo’s settings run, `gitEnv` for git and `ghEnv` for `gh`. Don’t build an environment inline or read the login shell again elsewhere.
- TLS certificate checks stay on: never set `rejectUnauthorized: false`. To trust a certificate Ted made itself, such as the remote execution controller’s, pass it as `ca`; HTTPS Apps are checked against Node’s and the system’s certificates (`systemCertificates` in `packages/daemon/src/apps/apps.ts`). A child process reads the system ones, because Node crashes with SIGSEGV reading the keychain when a sandbox refuses `com.apple.SecurityServer`, as it does when tests run the daemon inside Ted’s sandbox; if the child fails, Apps get Node’s certificates only.
