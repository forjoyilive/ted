# Factories and settings

Rules for adding, changing or removing a Factory, machine settings, Configuration, the Library, permission mode and drift. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- The human adds a Factory from the app’s Add Factory form: `POST /factories/check-repo` checks each row and `POST /factories` adds it and clones in the background, with progress as `factory-updated` events. Queued Tasks of a Factory that is still cloning wait until `v1.FactoryCloned`.
- A folder with no GitHub remote can get a private GitHub repo from the Add Factory repo row (**Set up a GitHub repo…**). Only `packages/daemon/src/github/repo-setup.ts` does it, one step per app-only `POST /factories/github-setup/step` (`init`, `ignore`, `commit`, `create`, `push`), each skipped when already done; git runs there with hooks and fsmonitor off. It is the only code that writes to a folder the user chose; never give its routes `runToken` or `fileToken`.
- No CLI command asks a running daemon to add a Factory: a Factory’s `.ted/workflow.yaml` names commands that daemon would run with its own access, so an agent must not add a Factory to the user’s Ted. `pnpm ted dev factory add <folder> --key <KEY>` (`packages/daemon/src/dev/local-factory.ts`, Ted Dev only) is the one way to add a Factory from a terminal or a Run, into a `TED_HOME` such as the worktree’s `node_modules/.cache/ted-home`: it resolves links and compares paths without regard to case, refuses the user’s home, either Ted home (`~/.ted` and `~/.ted-dev`) and any folder containing one of them, and allows a home inside a Ted home only beneath its `worktrees/`, `runs/` or `sandbox/` folder. It refuses a home whose daemon is running, then starts its own daemon in its own process, so that daemon has only the caller’s sandbox. The source must be the repo’s top folder with at least one commit and a branch checked out; its resolved folder name uses only ASCII letters, digits, “.”, “_” and “-”. It bare-clones the folder’s committed branches into `TED_HOME/origins/local/<name>.git`, adds the Factory `local/<name>` from that `file://` URL through the app-only `POST /dev/factories` with the in-process app key, and stops the daemon; adding clones and reads the Workflow but runs no repo command and calls no `gh`. Inside a Claude Code Run’s Bash sandbox with `TED_HOME` in the worktree, the daemon’s clone into `TED_HOME/repos/` fails with “Operation not permitted” on a `.git/hooks` or `.git/config` path: Claude Code always refuses writes to those paths in its working folder (its “Protected paths”), and only `sandbox.filesystem.disabled`, which turns off all filesystem isolation, lifts that, so Ted doesn’t set it for Runs. Run that one command with the Bash sandbox off; under Ted’s own Check sandbox it works as it is. Run again with the same folder and key, it refreshes that copy; it refuses a same-named repo from another folder (the copy records its source as `ted.source`) and a second key for the same repo, before fetching. Uncommitted changes aren’t copied, and pull requests and merging don’t work for such a Factory. For a Ted Dev with demo Factories, run `pnpm ted dev seed` from a terminal (it refuses inside a Run); `packages/app/scripts/demo-screenshots.ts` seeds that demo and captures screenshots, and `withApp` in `packages/app/scripts/with-app.ts` drives the app from a script (see `docs/development/demo.md`). `pnpm ted dev ask question|permission|sign-off` (`packages/daemon/src/dev/ask.ts`) also refuses inside a Run and requires an open, complete demo; it never starts a daemon. It gives an idle demo Task Lead with no open request a script to post a fresh Inbox request; `--task` picks the Task, and a sign-off requires Intake, Clarify or Design with its sign-off on. In a Factory that exists, `pnpm ted task create --factory <key> "<title>"` and `pnpm ted task start <task>` start a Task Lead in the Task’s worktree. `pnpm ted help` lists every command.
- A new machine setting is a field and default in `packages/protocol/src/settings.ts` plus a parser in `settingParsers` in `packages/daemon/src/routes/machine.ts`; every change is one `v1.MachineSettingsChanged` event. A new App Settings page is a component in `packages/app/src/renderer/settings/`, listed in `settingsSections` in `sections.tsx`. A new fixed row or group heading in App Settings or Configuration gets an entry in `packages/app/src/renderer/settings-search.ts` and that id on its element (`setting` on `SettingRow`, `SettingsGroup` and `SectionHeading`, `data-setting` elsewhere), or the Settings search and ⌘K can’t find it; rows that depend on data (Stages, Checks, repos, backups) stay out. In Configuration, read each fixed setting’s name, help and detail from `settingEntry(id)` so the view and search show the same wording. Open a setting only through `openSetting` in `setting-focus.ts`.
- Edits in Configuration write `.ted/` only through `packages/daemon/src/factory-settings.ts`: `workflow/edit.ts` applies the panel’s edits to the YAML document, `checkLayer` must pass before anything is committed, `commitAndPush` in `git.ts` commits from a temporary bare repo, and Save and merge uses the `tasks/merge.ts` calls. The store’s Factory repos follow the default branch’s `repos` through `storedRepos` and `Factories.syncRepos` at every resolve, but a repo new to the Factory is cloned only after the human adds it (a Save from this machine, or **Add** on the `repo-in-workflow` banner); never clone a repo only because a file names it. The settings view (`GET /factories/:id/settings`) answers from the clone and never waits for a fetch: `Workflows.refresh` fetches afterwards, at most once a minute per clone, and `factory-settings-changed` tells the page when `origin/<default branch>` moved; Save, Save and merge, `mergeInherited` and Run now fetch first through `Workflows.source` or `resolve` with `fetch: true`, and every fetch `Workflows` makes goes through `workflow/fetches.ts`, one per clone at a time. A test that pushes to the remote reads the view with `?refresh=first`. Settings tests set `merge.updateBase` in the stub `gh` state so a merge moves the local bare remote’s `main`.
- A settings save names only the parts it changes (`stages`, `stageFiles`, `checks`, `instructionChecks`, `agents`, `maxWorkingRuns`, `notes`) and commits every `.ted/` file that differs in one pull request; a save that names `checks` without `instructionChecks` keeps the instruction Checks as they are, and the YAML lists command Checks before instruction Checks. Settings edits write `sandbox_access` on Apps, command Checks and worktree setup and teardown from their `sandboxAccess`: a list sets it, an empty list removes it, and a missing field keeps what the file has, including when a command no longer has a timeout; converting a command Check to an instruction Check removes `sandbox_access`, because instruction Checks run no sandboxed command. Override writes `based_on` as `stageFileHash` of the inherited text. Run now goes only through `check-tries.ts`, one Check at a time per Factory: a command Check in a scratch worktree under `TED_HOME/scratch/`, its repo’s `setup` and the Check both in the sandbox (writable: the scratch worktree; cache and temp folders under `scratch/<factory-id>/sandbox/`; no sandbox for a Bypass Factory; with no sandbox it raises `sandbox-unavailable` and refuses, like Validate), an instruction Check report-only in the worktree of a Task the user picks from `GET /factories/:id/checks/try/tasks`. The stub `gh` merges one pull request per state file, so a test that saves twice rewrites the state before each save.
- Permission mode is machine-local per Factory, default Auto, and only the app’s confirmed `PUT /factories/:id/permissions` enables Bypass. `permissions.ts` owns the lookup; `Workflows.resolve` puts the local mode in the resolved Workflow and treats the repo value as advisory. RunManager rechecks at launch, restart and recovery; hosts consume each prepared launch once. Planning, Automation and Coordinator Runs stay in Auto. Factory removal clears consent.
- Provider defaults are resolved by `resolveAgentChoices` in `workflow/agent-choices.ts`. An unset choice prefers an enabled, installed Provider other than Pi; when none is installed, it prefers Pi if Pi is enabled, installed and not paused, before falling back to an enabled Provider. The default reviewer prefers a different installed Provider other than Pi, so installing Pi alone never makes it the second reviewer. Explicit choices stay as set and pass the start checks.
- The Library in `TED_HOME/library/` is written only by `packages/daemon/src/library-settings.ts` (app-only `POST /library/save`): `checkLayer` must pass on the whole layer first, only `workflow.yaml` and `stages/<id>.md` for a built-in or custom Stage id (`stageFileId` in `stage.ts`) are written, each through a temporary file and a rename, and Edit in Library writes `based_on` with `stageFileHash` like Factory Override. Outside edits reach the app as `library-changed` from `library-watch.ts`. If starting the watcher throws or it emits an error (including exhausted file handles), close it and poll for edits until shutdown, so outside edits still refresh inherited Workflows without restarting the daemon. Refreshes run one at a time and mark a version seen only after `Workflows.inherited` succeeds, so a failed refresh can retry; `saw` keeps an in-flight refresh from publishing a version older than an app save. Idle Runs restart onto a new agent version only through `runs/version-restarts.ts` and `Conversations.restart`.
- Drift is found only by `findDrift` and `findAgentDrift` in `workflow/drift.ts` (an override’s `based_on` against `stageFileHash` of the inherited text); counts reach the app as `drift-changed`, never as a banner or Inbox item. Inside `tasks.ts`, resolve a Task’s Workflow with `taskWorkflow(task)`, not `resolveWorkflow(factory)`, so Gates forced at creation (`NewTask.forcedGates`, `v1.TaskGatesForced`) and the default-branch target of a Task that changes `.ted/` (`NewTask.changesSettings`) apply.
- The sidebar’s Factory order and Factory groups are one `FactoryLayout`, saved only as `v1.FactoryLayoutSaved` through the app-only `PUT /factories/layout`, or `PUT /factories/order`, which keeps the groups (`orderedLayout`), whose materializer also rewrites `factoryOrder`, so `Factory.position` and ⌘1 to ⌘9 follow the sidebar. Every change to the layout in the app is a pure function in `packages/app/src/renderer/factory-layout.ts`.
- Removing a Factory goes only through `packages/daemon/src/factory-removal.ts`, which deletes its Tasks through `Tasks.removeFactoryTasks` before `v1.FactoryRemoved`; anything new that keeps data per Factory (store tables, files, in-memory state) must be deleted there too. Clones are deleted only through `Storage.removeUnusedClones`. A repo leaves a Factory only while no open Task (not archived, not Done) has it in its Repos field or a worktree.
- Automatic Backlog starts are one machine setting, `backlogStarts`, changed only through the app-only `PUT /backlog-starts`; `PATCH /settings` refuses it. Whether a Factory takes part is decided only by `backlogStartFactories` in `packages/protocol/src/backlog-starts.ts` against the current Factory layout. A layout save that drops a chosen group chooses its Factories one by one (`withoutGroups`), and `factory-removal.ts` drops a removed Factory. Until it is first saved, the store derives it from the Factories’ old `autoStartBacklog` flags. Its `includeAgentFiled` switch also starts Tasks a Task Lead filed, and its separate `includeGitHubIssues` switch Tasks an Automation made from a GitHub issue, whose text can come from outsiders; saved values without them read as off. Why a Backlog Task in a taking-part Factory won’t start is decided only by `backlogWait` in `tasks/tasks.ts`, which shares `filedWait`’s rules for who filed the Task with `backlogEligible`, and reaches the app as `Task.backlogWait` through the store’s queue activity, because failed auto-starts and clone state live only in the Tasks module.
- Configuration → Sandbox lists everything that widens the sandbox for a Factory or runs something outside it: Bypass, Apps in `appsOutsideSandbox`, Pi’s `piUnsandboxedAllowed` (in Auto Factories), sockets the Library names in `sandbox_sockets`, Apps with `electron: true` or `kind: ios-simulator` or `kind: android-emulator`, `sandbox_network: outbound`, and each `sandbox_access` group an App, command Check or worktree setup/teardown has, `network` included. Its rows and summary come only from `sandboxOpenings` and `sandboxSummary` in `packages/protocol/src/sandbox-openings.ts`, so the user sees all access in one place. Anything new that widens the sandbox adds a row kind there, with its text and off control in `packages/app/src/renderer/views/SandboxSection.tsx`.
