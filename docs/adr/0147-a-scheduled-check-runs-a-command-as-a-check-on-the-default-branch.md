# A scheduled Check runs a command as a Check on the default branch

TED’s Runs run only the test files they touch, and nothing ran the whole suite until a release. On 2026-11-13 about 100 tests had broken across about 100 merges, and the 0.1.17 release attempt was the first full run to find them (KRI-397). The human wants a full run every night inside TED, not as a terminal or launchd job.

**An Automation can be a Scheduled Check.** It has its own command (`check.command`), a time limit (`check.timeout`, default `2h`) and an optional time to run by on a busy computer (`check.runBy`, `HH:MM`). It is chosen when the Automation is created (the **Scheduled Check** card in the New Automation dialog, or `check` in `POST /automations`) and can’t be turned into an agent Automation or back. It has no prompt; it keeps the usual schedule, On switch, Run now and history, and Retry for a firing TED couldn’t run (a Check that ran and failed is rerun with Run now; the human chose to keep Retry that way). `v1.AutomationCheckSet` holds the command in the Automation’s own commit, in three columns of the `automations` row beside the `checkout` setting of ADR 0146, and `v1.AutomationCheckFinished` holds each firing’s result in the commit of its `v1.AutomationRunEnded`.

**Firing stays in `automations/automations.ts`; running is a Check run.** The Automation’s firings are decided as before (ADR 0070), but a Scheduled Check’s firing never enters the working-Run queue and never takes a working slot. `startChecks` hands it to `automations/scheduled-checks.ts`, which takes a place from the daemon’s one `CheckSlots` (`maxChecksAtOnce`, ADR 0103), gets a fresh checkout of the default branch (the clone’s `origin/HEAD`, even when the Workflow gives the repo another `base_branch`) from the `Checkouts` an Automation Run with a checkout uses (`automations/checkout.ts`, ADR 0146), keyed by the firing’s ID under `TED_HOME/automation-runs/<firing>/`, with the repos’ `copy` files and sandboxed `setup`, and runs the command through `runChecks` (ADR 0044) in the primary repo. The checkout is released after every firing, so TED never runs git inside a tree a sandboxed command has written. The output stays in `TED_HOME/logs/automation-checks/<id>/` (the newest 30 files); `GET /automation-runs/:id/output` reads it, redacted, and the Automation’s history shows each firing’s outcome, time and an **Output** button. From the firing until it ends, a Scheduled Check holds the daemon’s idle timer and counts in `TedStore.activity()` (`setScheduledChecks`: waiting while it waits for a quiet computer or a Check slot, running after), so the machine stays awake for it and Quit warns about it. Deleting the Automation or removing its Factory deletes its logs, and `Checkouts.forget` deletes its cache under `TED_HOME/sandbox/automation-<id>/`.

**It stays in the sandbox (ADR 0091).** The setup runs sandboxed as `Checkouts` runs it for every Automation Run. The command runs in `sandbox.ts` with the checkout’s scope (its worktrees writable, its clones readable, the Automation’s cache), unless the Factory runs in Bypass, exactly like the Factory’s other Checks. A missing sandbox raises `sandbox-unavailable` and the firing fails; it never runs unsandboxed.

**It follows Start fewer Runs when this computer is busy.** With `adjustRunsToLoad` on, a scheduled or made-up firing waits while `heldForLoad` (`tasks/queue.ts`, `loadMarks`) says the computer is busy, and runs once it is quiet. At `runBy` in the app-wide time zone (or 4 hours after the firing when there is no `runBy`) it runs anyway, and its result says it ran while the computer was busy. Run now and Retry never wait. A firing checks `newWorkHold` before it waits for a Check slot and again once it has one.

**No agent unless it fails.** A pass is a quiet history row. A failure or a time-out goes to `Tasks.checkFailed` in `tasks/tasks.ts`: `failingTestFiles` in `automations/check-failures.ts` reads the vitest or jest `FAIL` lines from the output, and `planCheckFailures` makes one Task per failing test file, or one Task for the whole Check when no file is named or more than 10 are. Each Task starts in Backlog with the command, the failing files, the output’s last 200 lines and the log’s path. `v1.AutomationCheckTaskCreated`, in the Task’s own commit, keys it by file; while that Task is open (not Done, not archived), the same key failing again adds a TED note to it instead of making another Task. The key is deleted with the Task and kept when the Task is reset, since a reset Task still answers the same failure. A firing that couldn’t set up its worktree is a failed firing with Retry, not a Check failure, and makes no Task.

**A sandboxed command can tell it is sandboxed.** The sandbox already sets `TED_SANDBOX=1` on every command it wraps (added on `main` to keep Electron from starting there). A line of the form `TED_SANDBOX_SKIPPED: <what>` in a Scheduled Check’s output is shown in its result as “Skipped <what>”.

## What was checked before building

Both by running this repo’s tests under the profile `sandbox.ts` generates, on macOS 27.

- **Electron can’t start in the sandbox.** It aborts (SIGABRT) while checking in with Launch Services. Allowing the `com.apple.coreservices.launchservicesd` lookup makes it start, but that service is what `open` uses to hand work to processes outside the sandbox, which the profile denies on purpose (ADR 0091). So the allowance isn’t narrow, and we took the issue’s fallback, which `main` had also taken: with `TED_SANDBOX=1` on macOS, `vitest.config.ts` skips the Electron test files (as it does in Codex’s sandbox). This change adds `passWithNoTests` there, so the empty Electron project doesn’t fail `pnpm check`, and a `TED_SANDBOX_SKIPPED: the Electron app tests` line beside the existing warning.
- **The suite’s shared files.** The sandbox can’t write `~/.cache/ted`. With `TED_SANDBOX=1`, on every platform, `testCacheDir` in `packages/daemon/test/support/suite-lock.ts` uses `$XDG_CACHE_HOME/ted`, which the sandbox points at the command’s cache folder, for the suite lock, the slots, `test-waits.jsonl` and the failure log. A sandboxed run therefore doesn’t see a full run the human starts by hand; the busy hold is what keeps them apart. A human’s run is unchanged even with `XDG_CACHE_HOME` set.
- **`ps` can’t start in the sandbox.** macOS refuses to start a setuid program in a sandboxed process, and `ps` is setuid. Every test file’s cleanup lists processes with it, so every file failed. `psProcesses` in `packages/daemon/test/support/processes.ts` now treats `EPERM` as no processes; the daemon and Run hosts still exit with their `TED_EXIT_WITH_PID` process. (On this macOS `ps eww` no longer shows other processes’ environments anyway.)
- **TED can’t sandbox inside its own sandbox.** `sandbox-exec` can’t apply a profile in an already sandboxed process, so daemon tests that run Checks, worktree setup or Apps failed inside a Scheduled Check. The human chose a pass-through: with `TED_SANDBOX=1`, `vitest.config.ts` sets `TED_SANDBOX_BIN` to `packages/daemon/test/fixtures/pass-through-sandbox.sh`, which drops the sandbox’s options and runs the command in the outer sandbox, and tests that pick their own program (`local-lifecycle.test.ts`, the restart test in `checks.test.ts`) take it from `TED_SANDBOX_BIN`. A test that needs the real sandbox, or checks what it refuses, calls `skipInsideTedSandbox` from `packages/daemon/test/support/ted-sandbox.ts` and is skipped with that reason. `low-priority.test.ts` skips its priority tests on macOS there too, because it reads priorities with `ps`, and the socket tests in `sandbox.test.ts` skip when the sandbox’s deep temp folder makes a Unix socket path too long.

## Considered Options

- **A Factory Check in `.ted/workflow.yaml`.** Rejected by the human: the Factory has no Check for the full suite, and Checks run on Task branches.
- **An agent Run that runs the command.** Rejected: `pnpm check` refuses under `TED_RUN`, and an agent isn’t needed until something fails.
- **Allow Launch Services or setuid `ps` in the profile.** Rejected for Launch Services as above. `ps` was handled in the test tooling instead, so the profile didn’t change.
- **Reuse the Run now scratch worktree in `check-tries.ts`.** Rejected: Run now keeps its worktree and runs `git reset` inside it, which is safe only because Run now isn’t sandboxed code writing it; and Run now and a Scheduled Check would fight over one worktree.

## Consequences

- A Scheduled Check of this repo’s `pnpm check` runs typecheck, lint and the node tests, without the Electron tests, and the human still runs the Electron tests by hand or at release.
- Inside a Scheduled Check, the tests of the sandbox itself (what it opens and refuses, and the Bypass and restart rules that depend on it) are skipped, so the nightly run doesn’t cover them; they still run in every `pnpm check` the human starts. A new test that checks what the sandbox refuses calls `skipInsideTedSandbox`.
- Linux (`bwrap`) wasn’t tried. The cache redirect and the pass-through apply there too, since `bwrap` inside `bwrap` is likely refused the same way and the pass-through runs the command in the outer sandbox either way; the Electron files are skipped only on macOS, as `main` has it.
