# A Scheduled Check can start an agent that files and starts Tasks

A Scheduled Check (ADR 0147) turns each failing test file into its own Task. Ten failing files with one cause become ten Tasks, and a flaky test becomes a Task like a real break (KRI-400). On 2026-11-14 the human decided that an agent should read the result and do better: each Automation chooses when the agent runs, the agent creates the Tasks, TED’s own Tasks are the fallback, and the agent may start the Tasks it creates.

**The agent step is a setting of the Check.** `check.agentStep` is `on-failure` (the default for a new Scheduled Check), `always` or `never`, and `check.startTasks` is the **Start the Tasks it creates** checkbox, off by default. Both are `v1.AutomationCheckAgentSet`, committed with `v1.AutomationCheckSet`; a Scheduled Check created before this change has no such event and reads as `never`, so it keeps its old behaviour until the human turns the step on. The Automation’s `prompt`, empty for a Scheduled Check until now, holds the agent’s instructions; the dialog fills it with `scheduledCheckPrompt` from `packages/protocol/src/automation.ts`, and an empty prompt means that default. Create and edit stay app-only (no `fileToken`, and `refuseRun` refuses a Run token), so only the app sets the checkbox.

**The agent is an Automation Run with the firing’s ID.** After the Check, `finishCheck` in `automations/automations.ts` asks `agentRunsAfter` (`automations/check-agent.ts`). If the agent runs, it commits `v1.AutomationCheckFinished` with `v1.AutomationCheckAgentQueued` (holding the commit the Check tested) and leaves the firing started; `agentPhase` on the firing makes it an `automation` queue entry, so it starts through the pump like every Automation Run (ADR 0070). `launchCheckAgent` makes a new checkout with `Checkouts.make({ commit })`, which checks the primary repo out at that commit instead of `origin/<base>`, with the usual `copy` files and sandboxed setup (ADR 0146). The Check’s own checkout is still released after the command, as ADR 0147 requires, so the agent never sees a tree the Check’s command wrote. The prompt comes from `checkAgentPrompt`: the command, outcome, exit code, duration, the busy flag, skipped parts, failing files and the output’s last lines sit between `<<<CHECK-RESULT nonce>>>` and `<<<CHECK-OUTPUT nonce>>>` fences with a fresh nonce, redacted, and the prompt calls them data. The full log is read with `ted automation output`, whose route a Run token may call only for its own firing. The agent runs at most 3 test files per Vitest run and never `pnpm check`; the existing `TED_RUN` refusals enforce that.

**The agent reports with `ted automation report "<summary>"`.** That is the only signal TED trusts: `v1.AutomationCheckAgentReported` stores the redacted summary, and its first line is the history row’s message. `endCheckAgent` is the one place a check agent’s firing ends. When the Check failed and no report was recorded, it runs TED’s usual `Tasks.checkFailed` Tasks (one per failing file, keyed as before, or a note on the open Task with that key) and records `v1.AutomationCheckFallbackApplied` with the reason and the Tasks it noted. That covers an agent that can’t start (agent paused or off, a full disk, a failed checkout or launch, checked when the agent is queued and again at launch), a Run that fails after its one resume, a Run the human stops, and a Run that goes idle without reporting. A passed Check needs no fallback. The firing then ends as finished, or stopped when the human stopped it and no fallback ran.

**Starting a Task is a narrow new Run-token authority.** Three routes in `routes/automations.ts` set `runToken: true`, and the Tasks module checks each from the store, never from what the agent says:

- `POST /automation-runs/tasks/:task/start` (`ted automation start`, `Tasks.automationStart`): the caller must be a live Run whose ID is a started firing of a Scheduled Check whose `startTasks` is on; the Task must be in that Automation’s Factory, recorded by `v1.AutomationTaskCreated` as created by this same firing, not a setup Task, not archived, still in Backlog and not already asked to start, and the Factory must not run in Bypass (Tasks an Automation makes there wait for the human, as before). It starts through `queueAndAnswer`, which only queues, so slots, Factory caps, the busy hold and `newWorkHold` still apply, then records `v1.TaskStartedByAutomation` with the Automation’s name, which the thread shows as “The Automation “…” started this Task”.
- `POST /automation-runs/tasks/:task/note` (`ted automation note`, `Tasks.automationNote`): the Task must be open, in the same Factory, and created by this Automation in any firing, by its agent or by TED. The note is a TED note headed with the Automation’s name, redacted and capped at 20,000 characters, and `v1.AutomationTaskNoted` is committed with it.
- `POST /automation-runs/report`, above.

`ted task create` from a Scheduled Check’s agent refuses `--start`, `--follow-up` and Asana sources (a Follow-up and a Workflow without Backlog would otherwise start a Task without the checkbox), never starts a Task by itself, and refuses an eleventh Task in one firing (`maxTasksPerFiring`). Notes and starts are rows of `automationTaskActions`, deleted with the Task and with the Automation and kept through a reset, and the history row shows them beside the Tasks the firing created.

## Considered Options

- **Any Task created or noted counts as a report.** Rejected: an agent that finds only flaky tests creates nothing and would trigger the fallback, and an agent that crashes after filing one of three Tasks would count as done.
- **Keep the Check’s checkout for the agent.** It would save a second setup, but ADR 0147 releases the checkout so TED never runs git in a tree a sandboxed command wrote.
- **Let `--start` on `ted task create` honour the checkbox.** Two paths to the same authority are two things to secure; starting has one route.
- **Every Scheduled Check may start Tasks.** Rejected by the human: starting is behind a per-Automation checkbox, off by default.

## Consequences

- The first firing of a failing Check with the agent step on costs a second checkout and setup, and an agent Run, before any Task appears.
- Existing Scheduled Checks don’t run the agent until the human chooses an agent step in Edit.
- An agent may create duplicates if it crashes after filing some Tasks and the fallback then files TED’s own; losing a failure would be worse.
