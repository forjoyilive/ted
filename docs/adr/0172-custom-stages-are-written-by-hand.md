# Custom Stages are written by hand in workflow.yaml

Users want to shape their Factory’s Workflow (TED-439). ADR 0171 moved what each Stage does into `packages/protocol/src/stage.ts`, where an unknown id is an ordinary working Stage. The rest of TED still assumed the nine built-in ids: `checkLayer` refused any other id, `next` ranked Stages by their built-in position, and texts named a Stage by capitalizing its id (TED-441).

A Factory’s `.ted/` or the Library can now add a custom Stage: an id in `order`, a Stage file `stages/<id>.md` and optional settings under `stages.<id>`. There is no app control for adding one yet.

- **The id.** `isCustomStageId` accepts lowercase letters, digits and hyphens, up to 40 characters, that aren’t a built-in id. `StageId` and `AgentStageId` take any string; `BuiltInStageId` and `BuiltInAgentStageId` list the built-ins for tables that must cover them all. Shipped events already held Stage ids as strings and are unchanged.
- **The layer check.** A custom id may go anywhere between Intake and Merge in `order`, once. It takes only `name` (one line, at most 60 characters), `gate`, `max_back`, `effort`, `enabled` and `based_on`; built-in Stages can’t take `name`. Each custom Stage in a layer’s `order` needs a Stage file in that layer or a layer below it, so `checkLayer` takes `inherited` (the lower layers’ Stage file ids and `order`, from `inheritedFrom`). A missing file is an error at the `order` item, and the layer’s last valid version stays in use. A custom Stage file no `order` lists is a warning in a Factory layer. `Workflows`, Factory settings, the setup proposal check and `ted workflow check` pass `inherited`.
- **Resolving.** Custom Stages default to no Sign-off, `max_back: 3` and the inherited effort. The resolved Workflow carries their display names (`names`, `name(id)`). If a lower layer later loses a file a stored Factory layer needs, the Stage is left out (`missing`) instead of starting a Task Lead with no instructions. `withTaskGates`, `withoutGates`, `withForcedGates` and `setupWorkflow` walk `order`, so per-Task choices, Autopilot and forced Sign-offs cover custom Stages. They insert only built-in Stages, by rank, and leave custom Stages where `order` puts them.
- **The next Stage.** `v4.TaskStageEntered` adds each custom Stage’s display name to the order every Stage entry already recorded. `withRecorded` binds a Task’s Workflow to its last recorded order. When the Task’s current Stage is no longer in the Workflow, `next` walks that record to the first later Stage that still exists. `checkBack` compares positions the same way. TED never moves a Task because the Workflow changed: the Task finishes the Stage it is in first.
- **No special work.** A custom Stage has every trait off. The Task Lead may change code, start sub-agents and ask questions, ends with `ted outcome advance` or `ted outcome back` to an earlier working Stage, and can’t `--skip`. TED runs no Checks, reviewer or pull request step there. A custom Stage after Validate may change code: the existing stale-coverage rule (ADR 0139) reruns the Checks before Review passes or the merge, and the reviewer doesn’t run again. Before Work it counts as planning and after Work as work in progress, because `stagePhase` places it after the built-in Stage before it in the recorded order.
- **Names and clients.** TED’s text about a Stage (messages to the Task Lead, send-back questions, sign-off names, thread lines) uses the display name: from the Workflow, or from the names in `v4.TaskStageEntered` for the thread. The Board read (`boardStages`) is each Factory’s resolved Stage list with `name` and `custom`, and the new `factory-stages-changed` event says when it changes. Request parsers, List filters and Board Display choices accept any Stage id; the daemon checks it against the Task’s Workflow.

## Considered Options

- **Register custom Stages in a list separate from `order`.** Rejected: a second list could disagree with `order`, and the file name already says which Stage a file belongs to.
- **Rank a removed Stage by the current `order` alone.** Rejected: a custom Stage that leaves `order` has no place there, and the Task would jump to Done or back to Intake.
- **A new column for display names in the Stage entry table.** Rejected: a new column means a state rebuild. The names are merged into the `order` JSON the table already holds.

## Consequences

- A Stage file in a repo can now make the Task Lead do more in a step of its own. This adds no power: the same repo’s built-in Stage files could already say anything. Display names are one line and short, and are only ever shown as a name.
- Settings pages don’t list custom Stages yet (TED-443), and the app draws them with its own capitalized id until it uses the Stage list (TED-442).
- A new kind of Stage work is still a trait in `stage.ts`. A custom Stage gets one only when a later Task decides to give custom Stages special work.
