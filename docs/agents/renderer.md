# Renderer

Rules for the app’s renderer and user-facing text (`packages/app/src/renderer/`). They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- The renderer reaches the daemon only through `window.ted`. A forwarded daemon call is added only to `forwardedRequests` in `packages/app/src/daemon-requests.ts`, with the same name, arguments and result as its `DaemonClient` method. Main-process actions and semantic adapters use `CustomRequests` in `custom-requests.ts` and explicit handlers in `main.ts` and `renderer/ted.ts`; the preload stays as it is. The renderer imports only types from `@ted/protocol`; a value comes from its own sub-path (`@ted/protocol/run`, `@ted/protocol/task`, …), because the main entry also exports `DaemonClient` and the request parsers, which use Node modules. `packages/app/test/renderer-bundle.test.ts` fails when one gets in.
- Archiving selected Tasks in `components/SelectionBar.tsx` sends bounded batches through `window.ted`, waiting for each batch before starting the next, so hundreds of Tasks can be archived with one confirmation without flooding the bridge. Keep the whole selection under one pending action until every batch finishes; an individual archive failure is reported and leaves the remaining Tasks to be attempted.
- The stopped background-process notice uses `StoppedConnectionNotice` in `packages/app/src/renderer/ConnectionNotice.tsx`. Its dismissal stays in the mounted component’s state, keyed by the latest crash time, because the daemon is unavailable. Keep the Restart menu visible after dismissal so the user can restart the background process or copy its report. Daemon banner dismissals follow `docs/agents/platform.md`.
- Problem notices sit beside the navigation sidebar, including in Settings, so they keep the same placement across the app. `BannerStack` and the notification prompt fill the available pane width with 20px side margins. `SettingsShell` receives the notices through `problems` above its scrolling page; keep them outside `components/Offline.tsx` so recovery actions remain usable while the settings controls are disabled.
- At viewport heights of 640px or less, the sidebar’s Usage card hides its Provider summary rows and reduces its padding to leave more room for Factory navigation. At the same height, `components/Sidebar.module.css` reduces the sidebar’s outer padding, top-level row padding and section spacing so more Factory navigation stays visible. Keep the Usage button and its popover available at every height; `components/PlanUsage.module.css` owns the Usage card’s layout change.
- In Settings → Phones, Ted Dev’s Copy code in `packages/app/src/renderer/settings/PhonesPage.tsx` confirms “Code copied” through an accessible status only after `ted.copyText` succeeds. Disable the button while copying; on failure, show “Couldn’t copy code.” as an alert and allow another attempt, keeping the pairing link and clipboard error out of the message. Keep this feedback with the current pairing by keying `PairDialog` with `pairingId`, so a new code starts without the old result.
- Every renderer colour is a token in `packages/app/src/renderer/styles/tokens.css`, written as `light-dark(<light>, <dark>)` with Figma’s Theme variable name; components use a CSS Module and `var(--…)` only, and `packages/app/test/theme.test.ts` fails on any other colour. Reuse the shared components in `packages/app/src/renderer/components/`. A button is `--button-height` (28px) high, or `--button-height-small` (24px) inside a dense row such as a list row, a diff header or a Board card; buttons side by side use the same one. `Button` sets both, and a hand-made bordered or filled button takes its height from the same tokens (`packages/app/test/theme.test.ts`).
- UI labels use sentence case with `GLOSSARY.md` terms capitalized, except the common words the glossary marks as written in lowercase (check, comment, finding, gate, sign-off, follow-up, sub-agent and others), which take a capital only at the start of a label or sentence: “Running checks”, “Follow-up…”, “Review sign-off”. The same goes for Ted’s messages, CLI output and the instructions it gives agents. A label ends with “…” only when the item needs more input before it acts: a dialog, a picker or a name.
- User-facing text calls Claude Code, Codex, Antigravity and Pi Providers (Settings → Providers, the Provider field), and names the Provider when one is known. “Agent” stays for a Run or its role (Task Lead, sub-agent, agent Run). Code identifiers, settings keys, setting IDs, events, routes and `workflow.yaml` keys keep their `agent` names (`AgentKind`, `enabledAgents`, `lead.agent`). The CLI flag is `--provider` (`ted run start`, `ted automation create`, `ted coordinator create`); `--agent` still works as an unlisted second spelling.
- The List’s optional Provider column shows the Task’s saved Task Lead choice (`task.lead.agent`), using `agentLabels` in `task-fields.ts`; an unset choice reads “Default”, so the column does not guess which Provider the Workflow will resolve. It starts hidden and can be shown in Display for All Tasks or a Factory’s List, with the choice saved separately for each scope. Display’s Columns section scrolls within the window so every choice stays reachable.
- Pi model pickers use `ModelSelect` and the shared list in `packages/app/src/renderer/pi-models.ts`, so every picker follows the same models. `usePiModels` loads the list when Pi is chosen; `refreshPiModels` refreshes it on picker focus or mouse down and after Settings → Providers finishes Check again, sharing any request already in progress. An open `Select` follows option changes and keeps the active option by value, so a refreshed list cannot select a different model by its old position.
- Task Lead fields in New Task and Automation dialogs share `LeadFields` in `views/NewTaskDialog.tsx` and wrap within the dialog, so Provider, Model and Effort stay usable with long model names in a narrow window. Keep the model picker able to shrink and the Automation fieldset’s minimum width at zero; the collapsed New Task More summary truncates with an ellipsis.
- New Task focuses and enables Title as soon as the dialog opens, while the saved draft loads. Title edits made during loading replace the saved title and keep the rest of the restored draft; without an edit, the saved title returns. The other draft fields and Create wait for loading to finish. Closing after an early title edit waits for the draft to load and save, so the user's typing is kept.
- Before changing Dashboard periods, comparisons or charts, read `docs/features/dashboard-stages.md` for the date boundaries and comparison rules. Overview, Stages and Cost share one `DashboardRange`, including custom dates, through `DashboardRangePicker`; keep custom dates as calendar dates when saving them or sending them to the daemon, which decides their time boundaries. When restoring Dashboard state, `rememberedDashboard` resets a custom range whose End is after today in the renderer’s local calendar to Last 30 days, keeping the remembered tab and Factory filter; this prevents a saved range from sending dates the API refuses. The range picker separates presets from custom dates with one `--border-subtle` divider, before the selected custom dates when present or before “Custom range…” otherwise. Request a divider in the shared `Select` with `data-divider-before` on the option that starts the group. Date fields use Ted’s shared `packages/app/src/renderer/components/Calendar.tsx` so the calendar follows the app’s theme.
- Keyboard shortcuts live in `packages/app/src/renderer/keymap.ts` and run through the one `keydown` listener in `App.tsx`; don’t add another window key listener for a shortcut. A new list or card view marks its focusable items `data-nav-item` so J/K reach them.
- `TaskStatusChips` hides the ordinary Working pill while a `test-activity` marker has `phase: running`, because the marker already describes the work. A Working status carrying `app` is labelled “Starting app” and stays visible beside a running-test marker.
- “Starts automatically” uses the shared `TaskStatusChips` pill in Board, List, Map and the Task thread, with hover text explaining that Backlog starts will start the Task when there’s room. Each surface gets eligibility through `useStartsOnItsOwn` in `components/BacklogStarts.tsx`, under the app’s `StartsAutomaticallyProvider`, so changes to Backlog starts or the Factory layout reach every View. The pill appears only when the Task has no status or markers; it describes automatic Backlog starts rather than adding a stored Task status.
- Task Views read `useTaskList` in `data.ts` and pass its `loaded` state to Board, List and Map, so their empty states appear only after Tasks finish loading. The waiting Inbox uses `loaded` from both `useTaskList` and `useInbox` before showing its empty state or New Task action. Until then, these Views show `Loading` or `Skeleton` from `components/Loading.tsx`; an initial empty array does not mean there are no Tasks or requests. A failed Task list load is tried again every 2 seconds, as the Factory list is, and so is a failed load of the Inbox’s waiting or Answered requests (`retryEveryMs` on `useEventValue`), so a daemon too busy to answer once doesn’t leave these Views on the placeholder. The no-Factory screen waits for both Factories and Tasks to finish loading.
- The Task’s Apps tab reads `useTaskAppsState` in `data.ts` so an unanswered request stays distinct from an empty list. Until Apps arrive, `AppsSection` shows `Loading`, or `LoadingError` with Try again when the request fails; “No Apps for this Task” appears only after a successful empty result with no hosted previews.
- The Apps tab’s status mark comes only from `appsTabMark` in `packages/app/src/renderer/apps.ts`: failed Apps take precedence (red dot), then starting or running Apps (the working-Run dot), then waiting Apps (empty circle). Stopped and exited Apps show no mark. `DetailsTabs` gives the mark an accessible description so the status is available without its colour.
- The Task thread’s title row wraps its status pills and actions together below the title when space is tight, so the controls don’t squeeze the title into a few characters per line. Keep those controls together in `titleControls` in `views/TaskThread.tsx`; the title and controls can each wrap within their available width.
- The Task thread’s status row wraps in a narrow pane so metadata does not push the Stage and activity out of view. Keep the Stage track, Stage name, activity and Run icons together in `stageGroup` in `views/TaskThread.tsx`; metadata can wrap between items, while `metaItem` keeps a Task ID, Back to Work count or follow-up or split label with its link together.
- In the Task thread, an open request with one answer field (not a round or a proposal) is answered from `RequestDock` at the bottom, in place of the Comment box; its card passes `answerBelow` and has no answer field. The answer controls are `RequestAnswer` in `RequestCard.tsx`; don’t draw a second copy on the card. The dock carries `data-request` and the card `data-docked`, which `requestScope` in `key-targets.ts` uses for the request shortcuts; with several open requests a shortcut acts only when focus is in the dock or on the shown request’s card.
- A failure decision’s named repair choice shows the repair Task’s recorded title and current Stage beside “Wait for <display ID>”, so the user can identify the repair before selecting it. `useNamedRepair` in `RequestCard.tsx` reads the title from the decision and the Stage’s display name from the repair Task’s Factory; an archived Task shows Archived, and an unavailable Task keeps its title without a Stage. These details are display text; the answer stays “Wait for <display ID>”.
- Run chat headers in `packages/app/src/renderer/components/RunChat.tsx` keep the chevron and label visible while long titles, group summaries and metadata truncate with an ellipsis within the row. Titles, tool descriptions shown as metadata and command metadata have hover text so the user can read what was clipped. Keep the shrinking columns in `RunChat.module.css`; long tool or command text must fit within the chat pane.
- Comment boxes and Run chat composers share `useAttachFiles` and `AttachButton` in `components/AttachFiles.tsx` for uploads, file picking and paste. The chat’s `Composer` keeps files with its text through `useMessageDraft`, accepts file-only messages and waits for uploads before sending; `ChatSection` routes dropped files to its live composer. Show pending files with `AttachmentTiles` and sent files with `CommentFiles`. The Coordinator’s opening composer sets `attach={false}` because files can be attached only after that chat starts.
- Long blocking findings in Ted’s Task notes start collapsed through `packages/app/src/renderer/components/Collapsible.tsx`, with Show more and Show less controls only when the content overflows. Fenced output in Task notes and every Markdown code block longer than 10 lines show only their last 10 lines through `useLastLines` in `packages/app/src/renderer/components/LastLines.tsx`, because errors and summaries sit at the end; Copy still copies the whole block. A sign-off’s changed-file lists show 10 files before Show more. `noteParts` in `packages/app/src/renderer/note-parts.ts` separates those notes’ prose from fenced blocks; keep each block’s line breaks and its surrounding prose in order.
- The first-Factory guide card’s text and button are chosen only by `guideCard` in `packages/app/src/renderer/guide.ts`; the agent writes none of it. Whether setup counts as done is decided only by `setUpDone` in `store/context.ts`, which the guide carries as `setUp`; the card never decides it from the Task. A guide starts only in `TedStore.createFactory` and ends only through `v1.FactoryGuideEnded`, committed with the Task the user creates after setup, the setup Task’s archive or delete, or `hideGuide`; the app reads live guides through `GET /guides` and `guides-changed`. Comments marked by the old `v1.CommentMarkedTutorial` are left out of every Comment list in the store.
- HTML that must run scripts (the design review’s prototype) loads from `ted-prototype://file/<hash>/<name>` in an `<iframe sandbox="allow-scripts">`, never `allow-same-origin`; the main process serves it with a CSP that blocks the network. Other HTML stays in the `srcdoc` frame with `sandbox=""`. **Open ↗** on the Figma row opens the link the main process reads from the Comment, not one the renderer passes.
- The Map View’s cards, links and Tasks with no blockers come only from `blockerMap` in `packages/app/src/renderer/blocker-map.ts`; `views/TaskMap.tsx` only draws them and calls `blockTask` and `unblockTask`. `linkRefusal` there is only the text shown while dragging: the daemon decides whether a blocker is added. Board, List and Map sit under the sidebar’s Tasks row, which opens the last-used of the three (`open-tasks` in `navigation.ts`).
- The Board’s Display choices (card size, card fields, hidden columns, Hide empty columns) are one `BoardView` per Factory in the `boardViews` machine setting, deleted with the Factory in `factory-removal.ts`. Only `boardLayout` in `packages/app/src/renderer/board.ts` decides which columns are drawn and which are listed under Hidden columns; a hidden column never shows itself.
- Bulk Archive and Archive all in Done close their confirmation dialogs when the user confirms, so New Task stays usable while archiving finishes. Track the archive through keyed `usePendingAction` in `packages/app/src/renderer/pending-action.ts` (the sorted Task IDs for a bulk archive, the Factory ID for Done), so closing and reopening the controls cannot submit the same archive again while it is pending. The app-level Task context menu owns the failure alert so it survives a selection or View change.
- Unsent text in a message or answer box is kept by the daemon in `messageDrafts`, one row per `MessageBox` (`packages/protocol/src/message-draft.ts`), through the app-only `GET` and `PUT /message-drafts/:kind/:id`. A box in the renderer gets its text from `useMessageDraft` in `renderer/message-drafts.ts`, never its own `useState`, and calls `clear()` when its message is sent. Rows are deleted where `TaskArchived`, `TaskDeleted`, `CommentAnswered`, `PlanRequestAnswered`, `PlanDeleted`, `FactoryRemoved` and the Run-deleting events update the state; a new kind of box adds its owner to `messageDraftOwner` in `routes/message-drafts.ts` and its deletion there. Saved files count in `store.filesInUse()` but never in `store.taskFiles`.
- Commits, Task IDs and worktree paths in a Task’s messages become links only through `references` in `packages/app/src/renderer/references.ts` and `TaskReferences` in `components/References.tsx`, set once in `TaskPanes`: a link is drawn only after the app has checked it leads somewhere (a Task it holds, a file in the Task’s file list, a commit the daemon confirmed), and `Markdown` and `EventLine` draw plain text outside it. The app-only `GET /tasks/:id/commits` and `GET /tasks/:id/commits/:hash` read commits with `findCommits` and `commitDiff` in `git.ts`, through `inScratch`; a hash must pass `isCommitId` before it reaches git. Don’t store links on a Comment or link a hash the daemon hasn’t confirmed. A 6-character code links only when it starts exactly one of the Task’s Failure case or Run IDs. A linked commit, Failure case or Run gets its kind as plain text before the link, from `kindLabel`. A tracker key the app doesn’t hold as a Task is confirmed through the app-only `GET /integrations/linear/issue-links` before it links.
