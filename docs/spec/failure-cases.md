# Failure cases

A Failure case records one failure independently of factual Check runs and original Findings. It belongs to a Task, survives daemon restart and a fresh Task Lead Run, and keeps the source, bounded evidence, tested context, assessments, recommendations, human requests, resolutions and observed invalidations.

Validate now creates cases for failed Factory Checks and provides explicit operations for reviewer, visual and extra-test Findings. Merge creates cases for failed post-rebase Checks and failed GitHub CI checks (see the last two sections). A Task with no cases takes its existing advancement and merge paths without additional context capture or GitHub work.

## Short references

TED displays the first six characters of Failure case, Run and tested-context IDs in new generated text and UI labels. Existing text stays as written. Structured CLI results and daemon responses retain full IDs; failure CLI results also include `reference`, `runReference`, `recordedByReference` and `contextReference` alongside the corresponding canonical fields where present.

Failure commands, Run commands and failure request-file `source.runId` and `contextId` fields accept an exact full ID or a unique prefix of at least six characters. An ambiguous prefix returns an error asking for more characters or the full ID. Lookup uses the existing authorized scope: Failure cases and contexts belong to the selected Task, and a Task Lead can steer only its own sub-agents. Resolution happens before existing validation and persistence; events and associations always retain full IDs. Check run IDs and other identifier types are unchanged.

## Operations and authorization

All paths start with `/tasks/:id`. DaemonClient exports matching typed operations.

| Method and suffix | Caller | Purpose |
| --- | --- | --- |
| GET /failures | App, file token, or own-Task Run | Read every case and its history |
| GET /validation-obligations | App, file token, or own-Task Run | Verify context, durably invalidate stale consent, return independent blockers |
| GET /failure-contexts/:contextId | App, file token, or own-Task Run | Inspect the referenced tested revision and hashes |
| POST /failure-contexts | Current Task Lead | Capture context before executing or observing the result |
| POST /failures | Current Task Lead | Record source, evidence and optional contextId |
| POST /failures/:caseId/evidence | Current Task Lead | Append evidence and optional new tested context |
| POST /failures/:caseId/assessments | Current Task Lead | Append regression, unrelated or uncertain assessment and recommendation |
| POST /failures/:caseId/decision | Current Task Lead | Ask the human about the latest assessment and its context |
| POST /failures/:caseId/resolve | App only | Resolve the linked requestId as accepted, fixed or no-longer-applicable |

App and file tokens cannot impersonate the Task Lead. A sub-agent, previous Task Lead or another Task’s Run cannot mutate a case. Resolution routes have neither runToken nor fileToken permission. The existing app-only `POST /comments/:id/answer` uses the same resolver with the exact choices **Accept this failure**, **Fixed**, and **No longer applicable**. Fixed and No longer applicable require a reason. On the app’s failure card every choice can be picked straight away, and nothing is sent until the button is pressed (or Enter in the box). Picking Fixed or No longer applicable labels the box with the question the reason answers and says a reason is required; the button, named for the picked choice (**Confirm Fixed**), stays disabled until the box has text. A textual reply posts a human Comment, including line-comment drafts, and leaves the decision open; on the card it is the choice **Send a message to the Task Lead**, which says the failure stays open and whose button is **Send message**. Text typed with no choice picked is not sent. A Coordinator acting on the human’s direction may answer through its bounded `/coordinator/tasks/:id/answer` route (ADR 0094), using the same resolver and preserving the Coordinator attribution. That path leaves the human’s line-comment drafts unsent; it grants no access to the direct resolution or comment-answer routes.

New assessments record `evidenceCount`, the append position of the evidence they cover. New decision requests and pending resolutions require that position to match the case’s additions; timestamps do not establish freshness. Earlier assessments without this optional field remain usable when no evidence was added. If additions exist, a legacy pending decision needs a fresh assessment and request because its evidence binding is unverified. Already recorded resolutions and immutable history are retained. The existing JSON event payload gains an optional field; shipped event schemas do not change.

A source identifies a Factory Check or post-rebase Check by checkRunId and zero-based position; a Finding by originating runId and original text; or GitHub CI by repo, pull request number, head and attempt. Check references must belong to this Task, identify failed or timed-out execution and match the trigger. The saved snapshot comes from the store. Finding and CI evidence is explicitly Task Lead reported, with recordedBy provenance; TED does not claim to have independently verified it. CheckRun.outcome, CheckResult.state and ValidateJudged are never changed by these operations.

Recording, assessment and human acceptance are separate writes. A decision requires an assessment, is linked atomically to one question Comment, and binds that exact case, assessment and context. Resolution and one CommentAnswered are committed together, with the human’s line-comment drafts. Duplicate, stale, withdrawn and already answered requests return 409. Evidence and recommendation validation precedes withdrawal, so rejected input leaves the pending question intact. Decision Comments show original evidence, appended evidence, source identity and original/decision context references, with each evidence item bounded and redacted. A newer assessment or evidence withdraws the previous question; withdrawal does not close the case. New acceptance following invalidation requires a fresh assessment and request. Fixed and No longer applicable close this case explicitly; a later failure is a new case.

## Tested context

Contexts are generated by the daemon, versioned and referenced by ID. They bind every active Task repo’s identity, HEAD, merge-base and complete scratch-index worktree tree, including tracked edits, deletions, binary files and nonignored untracked files. Each repo’s base tip (the tip of `origin/<base branch>` in TED’s clone) is recorded with the context for history and display, and is not part of what consent is bound to (ADR 0115). They use workingChanges and never trust the worktree’s index or diff output. Ignored dependencies, build artifacts and other normally ignored paths are outside this boundary. Git tree identity covers submodule references rather than files inside a submodule.

Version 2 contexts additionally retain hashes of each observed failed CI execution’s repo, PR number, head and full poller attempt identity. No raw attempt identifiers are added to context. CI sources with a context must match one of those hashes; a different head, attempt or nonfailing execution is rejected with 409. Omit contextId to retain historical or unverified evidence without acceptance eligibility. Earlier context versions without these bindings cannot authorize CI acceptance.

The context also hashes resolved Check definitions (commands, timeouts and repo selection) and applicable Check environment, including repo settings and the inherited command environment. Raw environment values and diffs are never persisted in context. Resolved Workflow settings come from the Library and Factory default branch, as usual; editing a worktree’s .ted files changes its tree identity before those settings become active. HEAD and merge-base identities invalidate consent after rebases and after the Task merges its base in, even when file content stays identical.

A commit on the base branch alone changes neither what the Task branch contains nor what was tested, so it neither blocks acceptance nor invalidates it. When the Task takes the new base in, by merge or rebase, its HEAD and merge-base change and consent ends then. A base commit that changes the Factory’s `.ted/` settings changes the resolved Check definitions, which still ends consent. The Merge Stage’s own rules are unchanged: TED rebases a pull request GitHub reports as behind or conflicting and reruns the Checks, and a pull request GitHub allows to merge while behind its base merges as it would for a Task with no failure cases.

Two contexts are compared by the fields that say what was tested: `version`, `ciFailures`, each repo’s `repo`, `head`, `tree` and `mergeBase` in order, `checks` and `ci`. `sameTested` in `tasks/failure-cases.ts` is the only comparison; acceptance, obligations and `ted failure ask` all use it. The stored `fingerprint` still hashes the whole capture, base tip included, and is no longer compared, so version 2 contexts captured before this rule keep working without a new version or a rewritten event. A version 1 context never equals a current one, as before.

Where pull requests exist, the existing GitHub poller supplies the current head and every Check/status identity, attempt timestamps and state. Same-SHA reruns and pending replacement attempts change context. An explicitly null status rollup is a known empty Check list and permits capture for repositories without CI. Missing identity, missing rollup data, unavailable reads or truncated Check lists cannot establish current consent. Merged pull requests remain polled until Done where explicit cases need their context. Decision and merge boundaries refresh through watch.next; there is no second GitHub client or poller. A snapshot waits for GitHub first, resolves Workflow and Check inputs, then reads local scratch-index trees last. No external wait follows the local verification before the snapshot is returned for consent, obligations or movement authorization.

An assessment, and the decision asked from it, are bound to the `contextId` of the newest evidence addition, or to the original context when that addition names none. A context captured later and attached to nothing changes no binding. `ted failure ask` is refused with 409 when the assessment’s context differs from a verified current snapshot and a newly captured context could attest the source (a Finding whose originating Run is still live, or a CI failure still observed); the refusal names the commands: `ted failure context`, `ted failure evidence` with that `contextId`, `ted failure assess`, `ted failure ask`. The ask is still posted when the assessment has no context, when the snapshot can’t be taken or verified, and when no later capture could attest the source (a Check, or a Finding whose Run ended), because the human can still close such a case, or Retry or Fix it in Validate.

Acceptance is refused with 409 in three ways, each with its own message: the decision’s context differs from the current snapshot (the Task’s code or Checks changed; ask the Task Lead to assess again), the current snapshot could not be taken or was superseded (try again), or the original or decision context is missing or does not attest the source (record the failure again). For the first and third, TED also posts one “Failure acceptance refused” note per decision, delivered to the Task Lead like an invalidation notice. It says whether a fresh context can be attached to this case, with the commands, or whether the verification has to run again as a new case. The invalidation notice carries the same steps. The question stays open in both cases.

The question’s text is short: what failed (the Finding, the Check or the CI run), the Task Lead’s assessment in plain words, its recommendation, one line on what the choices do, and the failure’s ID. It carries no evidence or context IDs; those stay on the case. The app’s card shows the same three things first, under **What failed**, **Task Lead’s assessment** and **Recommendation**, and folds the evidence, the case ID and the tested context under **Show history**, for cases recorded in any Stage. The IDs show their first six characters, with the full ID as a tooltip.

When the Task Lead asks for a decision and acceptance can’t succeed on it, the question is posted without **Accept this failure**: a case recorded outside Validate offers **Fixed** and **No longer applicable**, a Validate case offers **Retry** and **Fix in this Task**, and the body says why. That is the case when the decision’s context already differs from the current snapshot with no fresh context attachable (the Run that found the failure has ended), or when the original or decision context is missing or does not attest the source. An answer with a choice the question doesn’t carry is refused with 400. A question posted while acceptance was still possible keeps its choice; if the code changes afterwards, the refusal names the choices that work.

Callers capture context before execution and supply that ID with the result. A Check’s context cannot have been captured after execution began. A Finding’s capture must fall within the originating Run’s recorded lifetime: at or after its start and no later than its end. A capture after a finished Run is rejected; omit contextId to preserve that historical Finding. These source bindings must hold for both the original capture and the decision’s capture, and are rechecked when resolving and verifying acceptance, including previously recorded cases. Appended evidence cannot bind an old CI failure to a replacement attempt; record that execution as its own case. This explicit capture is a caller’s assertion of which execution used the context; legacy Check runs have no independent execution-to-context attestation. Without a reliable capture, omit contextId. Unknown-context cases hold and cannot be accepted, even if later evidence names a context that cannot attest the original execution; the human may close them with a reason. Evidence additions may reference a new explicit capture, followed by a new assessment and decision. They do not change the original source or original Check snapshot.

Evidence, Findings, recommendations and reasons pass through redactSecrets and are bounded to 16,000 characters. Credential-bearing HTTP links and links containing credential query parameters are refused. Submit a concise redacted explanation and stable source reference, never full logs, credentials or environment dumps.

## Obligations and holds

validationObligations returns satisfied, cases (each with disposition and context state), blocker IDs, and factual checkRuns with their unchanged passed, failed or interrupted outcomes (an unfinished run has no outcome). The satisfied flag covers the explicitly recorded case obligations. Unresolved and invalidated cases block. Accepted means a human decision remains effective in current context; it never means passed. Fixed and No longer applicable are explicit closures. Consumers must continue to check factual execution and all existing Workflow and merge prerequisites.

An observed context mismatch or read failure appends a durable invalidation, including observations made by the context-capture operation before it acknowledges or reports a capture failure, and the final snapshot when accepting a different case. Verification applies synchronously before that acceptance is committed or refused; persistence, hold actions and notices follow. A matching decision may resolve its own case while other cases remain invalidated. Returning to a previously accepted context never revives consent. For each GitHub read, the poller synchronously compares the CI projection with existing accepted contexts for every active Task before awaiting any activity delivery, local snapshot or hold action. Changed or unavailable CI commits invalidation immediately, even while a Task operation or remote merge is busy. Persistence, auto-merge cancellation and notice delivery follow independently, so a slow hold action cannot block the poller needed by another snapshot. These later effects do not reapply the old observation to newer consent. Full background context checks and merge authorization obtain fresh reads under the Task boundary rather than reusing a read from before a wait. The poller observes changes while watching GitHub; decisions and movement verify again. Once a Task reaches Done, obligations reads expose historical context and retain the recorded dispositions without recapturing deleted worktrees or excluded merged PRs. Background polling and merge observation skip completed-Task revalidation. This does not revive previously invalidated consent. Each in-flight context collection binds the Task’s CI observation generation when it captures CI, before Workflow and local tree reads. Every changed or unavailable CI projection supersedes older collections, including A→B→A transitions; identical polls do not. Context consumers check that binding synchronously before capture, consent or movement can be authorized, after local verification and without another external wait. Superseded collections are treated as unverified and require a fresh attempt; they cannot acknowledge consent and invalidate it later. The binding is transient: no pending collection survives restart, while any committed invalidations and decisions replay unchanged. Changes that occur and are reverted entirely between observations cannot be detected.

Tasks serializes repo membership changes with capture, decisions, obligations and movement; concurrent repo edits return 409 and can be retried after the active operation. Repo changes verify and persist any resulting invalidation before releasing that boundary, including when a repo operation fails partway. Tasks serializes mutations and decisions with movement, guards forward advancement, skip, Sign-off approval, move-anyway, no-Merge completion and Done, and checks again before each remote merge or enable-auto-merge action. A busy Task lock retries the merge cycle; it is not a failed remote merge and does not mark the Task Partly merged. Repair, discussion and send-back remain available. Each case resolves independently.

Opening a case or invalidating consent disables auto-merge that TED previously enabled. If GitHub refuses, the hold remains saved, the API reports the failure, a durable Task note warns that GitHub may still merge, and polling retries. External merges remain factual and are never reverted. A human or GitHub can complete a remote merge already issued before a new failure arrived; TED cannot retract that race, but it still holds forward completion. Multi-repo merge rechecks obligations between repos and retains existing partly-merged behavior. A failure hold records Partly merged when an external merge leaves some repos open, before returning or attempting auto-merge cancellation.

## Storage

Versioned FailureContextCaptured, FailureCaseRecorded, FailureEvidenceAdded, FailureAssessed, FailureDecisionRequested, FailureResolved and FailureAcceptanceInvalidated events materialize contexts and cases. Each case snapshot retains append-only history; request and resolution linkage is committed with its Comment event. The area’s routes parse requests, Tasks owns authorization and lifecycle, and only store/ imports LiveStore. Task removal deletes both materialized tables through the existing removal path. Store replay rebuilds the same decisions and holds.

Invalidation and its TED notice are committed atomically. Notices use the existing Comment delivery marker and pending-Comment path, including saved-session recovery after agent-health suspension and daemon restart. Delivery preserves the TED author, records acknowledgement durably, and pending notices are excluded from duplicate fresh-Run recap.

## Validate diagnosis and continuation

Validate adopts Failure cases for automated Factory Checks and Task Lead reported Findings. Check execution captures context before starting and records a failed result with redacted evidence instead of sending it back immediately. The Task Lead must substantiate regression, unrelated or uncertain; no compulsory base-branch comparison is required. A supported regression uses the existing send-back path. Unrelated and uncertain failures ask the human, with the assessment, original and added evidence, tested context and recommendation in the question and thread.

Validate decisions offer Retry, Fix in this Task and Accept this failure. These actions are available through the app-only resolver, the ordinary app-only question answer path, or the bounded Coordinator answer path described above. Existing Fixed/No longer applicable API resolutions remain compatible for legacy cases. Modern Validate cases reject those values before answering or closing the decision; use Retry for fresh verification, Fix in this Task for repair, or Accept this failure for context-bound acceptance. Retry and Fix are recorded decisions, not closures or proof of success. Investigation, retry and the decision itself do not increment send-back counts. Fix delegates to the same sendBack implementation as a regression, preserving max_back, the loop check and their existing human escalation. A Workflow without an earlier Work Stage refuses Fix.

`v1.ValidationProgressed` stores the ordered plan, Validate visit, tested context, next outstanding position and links to factual Check runs in a per-Task materialized table. A continuation creates a new Check run for the outstanding suffix, with the same sequential stop-at-first-failure runner. Acceptance skips only its identified failure; Retry repeats that position before continuing the suffix. Old Check runs are never rewritten: their failed and not-run entries remain factual. A new failing execution creates a new case, requiring its own assessment and resolution. A passing execution records `v1.FailureVerified`; a failed retry links the older obligation to its replacement case without claiming it passed. Both histories remain visible. Before advancement, the current Check plan and tested context must still match completed coverage. Code, repo environment or plan changes make coverage outstanding again without rewriting historical results; a newly required Check must run even if the previous plan was empty. Legitimate recorded no-change skips remain skips. Forward validation is held while any required Check remains outstanding or any failure remains unresolved. Repair may return through earlier Stages into Validate for verification, while unrelated explicit case holds remain enforced.

When the Task comes from Work, the Checks already ran before it left Work (ADR 0111-checks-run-before-a-task-leaves-work). A failure there keeps the Task in Work and creates no Failure case. A pass moves the Task, and that `hand-off` Check run is saved as the Validate visit’s progress with its plan and the worktree it tested, so Validate starts no second run; an earlier case of a Check that passed in it is recorded as verified. If the plan or the worktree no longer matches the run, the Checks run at entry instead.

Extra tests, reviewer and visual Findings use `ted failure context`, `record`, `evidence`, `assess` and `ask`, with JSON files for structured input. `ted failure list`, `show` and `obligations` show the durable state. A Finding Retry tells the Task Lead to repeat the identified verification, rather than running an arbitrary client-supplied shell command. After a Retry or repair, the current Task Lead can record fresh successful verification evidence through `POST /failures/:caseId/verification` (`ted failure verify`); reported Validate Findings qualify. An earlier Factory Check also qualifies after a Work repair and a fresh Validate visit, once all current Checks have passed, have legitimate skips or have their own current human acceptance and the original Check is skipped, removed or replaced. The Task Lead supplies evidence explaining that repair; stale, failed or not-run current coverage holds it. Original failures and skips remain factual. This is explicit Task Lead reported evidence, not independent Check execution or human acceptance.

With `stages.work.lead_closes_failures: true` in the Task’s Workflow, the current Task Lead can also use `ted failure verify` on a case whose source is a Finding and that was recorded outside Validate, in any Stage and without a Retry or Fix decision first. The case becomes verified, its open question is withdrawn and the thread gets a “Failure repair verified” Comment. With the setting off, the default, TED refuses with 409 and names the setting; the human closes the case with Fixed or No longer applicable (ADR 0118).

The app uses normal question/Inbox behavior, window.ted, shared components and theme tokens. Check results and output retain the failed glyph and “failed, accepted by you” wording alongside evidence, assessment and the human’s choice. Review confirmation and the saved brief carry the same distinction. Reviewer and visual validation and existing sign-offs remain required; acceptance never grants merge approval. Context-bound acceptance retains the foundation’s stale-consent safeguards.

Local Check coverage records the execution inputs independently of the remote CI observations used for failure acceptance. Code, plan and repo-environment changes still invalidate it; CI progress or unavailable CI alone does not. It compares each repo’s identity, HEAD and tree with the Check hash, and never included the base tip or the merge-base. Full Check reruns after Validate, including post-rebase Merge Checks, refresh the recorded local coverage without changing historical results. A partial named rerun does not stand in for the outstanding full plan.

Passing positions reconcile eligible older factory-Check obligations as they finish. Recovery also reconciles durable passing positions before resuming an interrupted suffix, including an old acceptance invalidated by changed context. A current acceptance remains a human decision in history; it is not rewritten as a passing execution. Historical request cards show the assessment and resolution linked to that request, rather than a later request’s answer.


Automatically collected Check evidence is sanitized before recording: unsafe or invalid links are replaced by an explicit omission marker, with the full log reference retained. Stored Check metadata uses the same safe display text; matching executions uses the authoritative Check run source, so redaction cannot change verification identity. User and Task Lead evidence still reject unsafe links. Completed Tasks retain saved coverage and execution links when cleaned-up worktrees can no longer be read.


An active Validate entry without saved progress is unverified, including after restart. Reconstruct its current Check plan; a later forward boundary also holds missing coverage until a full current rerun. Recovery starts a new visit instead of resuming the previous visit’s failed execution. Legitimate empty plans and no-change skips remain explicit.

Fix in this Task is refused while Checks are running, before its request is answered. The human can choose it again after execution finishes; refusal does not create a send-back or a deferred Fix. Starting agent-requested Checks is also refused during a Task transition. Accepted reviewer Findings retain a failing Review judgment in history and the Review confirmation; omitting judgment flags cannot infer a pass, and an explicit passing judgment is refused while that accepted reviewer failure remains. Clean reviews keep the existing default inference.

Validate decisions reserve the Check execution boundary before asynchronous resolution. Retry, Fix and Accept return 409 while Checks run, leaving the question open. Accepted Findings can carry a structured source category (`test`, `review` or `visual`); accepted visual and reviewer failures retain failed judgments and refuse contradictory passing flags. Legacy reviewer sources are recognized by their recorded reviewer Run.

A passed Validate judgment records its Check plan/execution links and failure evidence/decision histories in `v2.ValidateJudged`. Historical Review confirmations and their Check-output dialogs use that immutable snapshot; later visits, repairs, evidence, decisions or invalidations do not change an earlier approval. `v1.ValidateJudged` remains readable: a legacy historical confirmation shows its recorded Check run and judgments without substituting live progress or current acceptance details. Current Review cards continue showing current obligations. These presentation snapshots never authorize advancement or replace the daemon’s live coverage/context checks.

## Local Checks after Merge rebase

After an automatic rebase, the existing merge watcher asks the shared validation module to establish current local Check coverage. Progress is bound to the latest rebase in the Merge visit as well as the local code and Check inputs. A historical passing Check run is not sufficient. Each required position must pass, remain a legitimate skip, or identify its own current human acceptance. The original Check run, including failed and not-run results, is retained unchanged.

A failed post-rebase execution records a `post-rebase-check` Failure case with its pre-execution tested context. The Task stays in Merge while the Task Lead diagnoses it. The existing failure decision UI offers Retry, Fix in this Task, Accept this failure and Wait for a repair Task. Retry repeats the failed position; acceptance continues the remaining positions. Another failure creates a separate case. A supported regression assessment or the user’s Fix decision sends the Task through the existing Work, Validate and Review re-sign-off path, including send-back limits and human escalation. Investigation and Retry do not count as send-backs.

The shared progress and execution links recover across restart, including an execution interrupted before its case was recorded. Polling a held failure neither runs it again nor posts another question. A new rebase or changed local code, environment or Check plan requires fresh coverage; an old acceptance cannot cover a new execution. Existing tested-context rules continue to invalidate acceptance when relevant CI observations change. Passing fresh verification or a replacement failing execution reconciles the earlier obligation without changing its original evidence.

Tasks retains authority over decisions, repair incorporation and send-back. Incorporated repairs require a fresh plan, even if their commits were already present locally.

When bringing a merged repair into a Task’s branch conflicts as its Task Lead starts (after the repair merges, or on Resume), TED doesn’t stop the Task. It posts a note naming the repair, the base branch and the conflicting files, and starts the Task Lead with a message naming the base commit to merge, with the file names fenced as data. The Task Lead merges it, resolves the conflicts and commits in the same Stage, without running the Checks or advancing. When that turn ends, TED tries again: a branch that now contains the base tip counts as incorporated and fresh validation runs; a conflict that remains, or an unfinished merge, stops the Task with a notice that names the files and tells the user to merge the base branch into the Task’s branch, commit, then Resume. Resume runs the same step, so a conflict that remains goes to the Task Lead again. Uncommitted changes in the worktree, a base branch that doesn’t yet contain the repair and a Task blocked again still stop the Task for the user; the uncommitted-changes notice names the files. The original failure stays unresolved until fresh validation passes. The existing watcher resumes Merge Checks after incorporation; repair resumption creates no second Merge controller. The Task Lead may record assessments but cannot advance, merge or approve. Merge sign-off, Merge off, cancellation, expected-head checks, all-repos-before-first-merge ordering, Partly merged handling and GitHub branch protection still apply. Local acceptance never authorizes a branch-protection bypass.

## GitHub CI at Merge

At Merge, a failed GitHub CI check no longer sends the Task back on its own (ADR 0129). `ciState` in `tasks/merge.ts` reports failed CI only once no check that counts is still pending; until then the Task waits on CI and the CI-stuck timer applies. The checks that count are unchanged: the required ones when the repo has any, otherwise all of them.

For each read from the poller, `reconcileCi` in `tasks/tasks.ts` runs the pure `ciFailureSteps` (`tasks/ci-failures.ts`) over the Task’s cases and pull requests, from the merge watcher at the start of a cycle and from the poller’s reaction while an open question holds the watcher:

- **Record.** One `github-ci` case per failed check that counts, keyed by `ciFailureKey` (repo, pull request, head, attempt). An open case with the same key is never recorded again, so repeated polls and restarts add nothing. TED records it with the tested context taken from the same read, marks it `validation`, and posts the “CI failed at Merge” note, which reaches the Task Lead like any failure notice. The source also carries `checkKey` (a hash of the check’s kind, app and name, used to find later attempts), `required`, and `check`, the cleaned name, only for a check TED trusts (`trustedCheck`). Only TED sets `checkKey` (the request parser drops it), and it is what marks a case as one TED recorded at Merge: a `github-ci` case the Task Lead records itself, in Validate or anywhere else, is never closed, replaced or sent back by these steps. The name in `check` is for the app’s card. `withoutCheckName` removes it from every case a Run token reads, and the question and TED’s notes are written without it, so the name reaches an agent only inside the fenced evidence. Nothing is recorded while any of the Task’s pull requests is missing from the read, has a truncated check list or has a check without an attempt identity.
- **Evidence.** `ciFailureEvidence` in `tasks/github-activity.ts` builds it from the read: commit, whether GitHub requires the check, and, inside a `<<<GITHUB <nonce>>>>` fence, the cleaned name, result, details link, attempt and log tail. Log tails come from `ciTails`, which reads only the repo’s own Actions jobs through the `Gh` runner. For an outside app the evidence has the pull request link and no name or log.
- **Close.** A later attempt of the same check that passed closes the case (“Passed on a later attempt”) and withdraws its open question. A pull request that moved to another commit, or a Task that left Merge, closes the case “without a pass”; CI on the new commit is looked at afresh when the Task is at Merge again. These closures are verifications written by TED, shown as “closed by TED”.
- **Replace.** A later attempt that failed is a new case; the old one links to it with `replacedBy`.
- **Send back.** A current regression assessment, or the user’s Fix in this Task, goes through `applyValidationFix` and the existing Merge send-back, with its limits and re-sign-off.

Decisions use the Validate resolver. **Retry** records the decision and nothing else: TED never starts a GitHub workflow, the pull request shows “Waiting for a CI rerun on GitHub”, and the next attempt closes or replaces the case. **Wait for a repair Task** uses the existing repair wait; after the repair is incorporated the case waits for a new attempt or a new commit like a Retry. **Accept this failure** leaves that attempt out of `ciState` (`acceptedCi`), so GitHub’s own merge state decides: TED merges when GitHub allows it, and otherwise `nextStep` waits on `required-check`, the Task shows “Waiting: GitHub requires a failed check”, auto-merge stays off and TED posts one “GitHub still blocks this merge” note per accepted set. Acceptance never bypasses a GitHub requirement and never counts as a pass or a merge approval.

An acceptance of a CI check is compared with `sameTestedFor`: each repo’s head, tree and merge-base and the Check hash must match, and the accepted attempt must still be among the failed attempts. Other checks on the pull request changing state doesn’t end it. Acceptances of Checks and Findings keep `sameTested`, which also compares the whole CI observation. The poller’s own observation doesn’t invalidate a CI case TED recorded at Merge, because the same read closes or replaces it.

When any check on the Task’s pull requests has no attempt identity, or the check list is incomplete, a decision can’t be tied to one attempt, and a failed check is sent back to Work as before.
