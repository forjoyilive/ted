# Checks run in the daemon as Check runs, not Runs

_When Checks run changed in ADR 0111, and again in ADR 0188-the-checks-run-as-validates-first-step-and-every-return-to-work-counts: Validate runs them as its first step however the Task enters it, and a failure records a failure case and is a counted return to Work. Ted no longer starts Check runs with the trigger `hand-off`; old ones stay readable. The round in “round 2 of 5” now counts every return, and Validate’s default limit is 8. The rest of this ADR stands._

When a Task enters Validate, or an agent runs `ted checks`, the daemon runs the Factory’s Checks itself through one runner, `runChecks` in `packages/daemon/src/tasks/checks.ts`. Each set of results is a **Check run** in the store (`v1.ChecksStarted`, `v1.CheckStarted`, `v1.CheckFinished`, `v1.ChecksFinished`), with one row per Check. A Check run is not a Run: it has no agent and never takes a working slot, but the Task shows Working with “Running Checks · Tests (2 of 3)” while one is unfinished.

The runner runs Checks one after another from the repo root in the Task’s worktree, through `$SHELL -lc`, with stdin closed. Spec §8.1 asks for the user’s login shell so a Check sees the same tools on `PATH` as in a terminal. The environment comes from `worktreeCommandEnv` (`packages/daemon/src/command-env.ts`), which setup and teardown also use: the daemon’s environment without any `TED_` name (so no `TED_APP_*`, `TED_HOME` or other daemon internals), `ELECTRON_RUN_AS_NODE` or agent credential (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CODEX_API_KEY`, `OPENAI_API_KEY`), then the repo’s `worktree.env`, then `CI=1` and `TED_TASK`. Check commands and the code they run may have been edited by the agent; outside Bypass they run in an OS sandbox that can write only the Task’s worktrees, a temp folder and the Task’s own caches, and can’t read the rest of `TED_HOME` (ADR 0091-agent-started-checks-and-apps-run-sandboxed). It reuses the setup runner’s process-group kill and timeout. The first failure or timeout stops it; later Checks become “not run”. A repo whose diff against the merge-base is empty, with untracked files counted, has its Checks skipped. When the Task’s changes touch `.ted/`, the runner adds the built-in Ted settings Check, which validates the worktree’s `.ted/` in the daemon instead of shelling out to `ted`.

A failed Validate Check run sends the Task back to Work through the same send-back path as `ted outcome back`, so it counts toward Validate’s `max_back`. `v2.TaskSentBack` adds the round, the limit and the Check run to the send-back, so the thread can say “round 2 of 5” and show the Blocking findings box beside the ✓ row. The Findings hold the last 200 lines of the failing Check’s output, passed through `redactSecrets`, and the path to the full log under `logs/checks/<Task>/<Check run>/`.

While a Task’s Checks run, `ted outcome` is refused, so the Task Lead can’t move the Task past them. A daemon that stops mid-run leaves the Check run unfinished; on start it marks it interrupted and, if the Task is still in Validate, runs the Checks again from the start. `ted checks` starts a Check run and polls it, so a long Check never holds an HTTP request open.

The thread draws Check runs from `GET /tasks/:id/check-runs` and the `check-run-updated` event. Send-backs come through the thread events of ADR 0041: `v2.TaskSentBack` reads “Validate sent this back to Work (round 2 of 5)”, carries the Check run’s id, and the thread puts that run’s ✓ row above its Blocking findings box instead of a separate Check run line. `GET /tasks/:id/send-backs` and the `sent-back` event stay for other readers. The Merge rebase rerun (KRI-130) calls the same runner.
