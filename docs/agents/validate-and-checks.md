# Validate and Checks

Rules for Checks, Validate, reviewers, send-backs, base conflicts and Failure cases. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- A Check or Run counts as killed for lack of memory only by `memoryKill` in `packages/daemon/src/memory-kills.ts` (SIGKILL Ted didn’t send, or exit 137, with the lowest reading of the one `createMemoryWatch` the daemon hands out under `busyMarks.memory.holdBelow` while it ran). A Task Check killed that way is `v1.CheckKilledForMemory`, never a failed Check: the executor in `tasks/validation.ts` waits for `freed` and reruns it in the same Check run, and from the second kill in a Stage visit asks the user (`memoryKill` on the Comment, Try again or Count it as failed), which only the user answers. A Scheduled Check killed that way stops with no Tasks. A Run’s is `v1.RunKilledForMemory`, committed with its ending; `recover` never marks a Task Failed for it and `failureHistory` leaves it out. Don’t read memory-kill reports from the OS, and don’t kill real processes in a test: drive `startDaemon`’s `load.memoryAvailable` and a stub that kills itself (ADR 0167-a-memory-kill-is-not-a-failure).
- When a move is refused only because the Checks haven’t run on the Task’s current code, `requireCoverage` in `tasks/validation.ts` throws `StaleCoverageError`; a Check that ran and failed is a plain 409. Mark done, sign-off approvals and `ted outcome advance` catch only that error and go through `checksThen` in `tasks/tasks.ts`, which starts the Checks and runs the same action again when they pass; never refuse a human’s action with a stale-coverage message, and never rerun a failed Check because of a click. Mark done passes `mergedOnGitHub` so coverage compares code only (ADR 0139-out-of-date-checks-run-before-a-move).
- A Failure case’s tested contexts are compared only with `sameTested` in `packages/daemon/src/tasks/failure-cases.ts` (version, failed-CI bindings, each repo’s HEAD, tree and merge-base, the Check hash and the CI observation); never compare `fingerprint`, which also covers the base tip, and never make consent depend on the base tip. A Ted note the Task Lead must receive carries a title in `failureNoticeTitles` (ADR 0095-failure-cases-preserve-results-and-bind-human-decisions, ADR 0115-failure-acceptance-does-not-depend-on-the-base-tip).
- Whether a newer failure case of the same Check replaces an older open one is decided only by `replacement` in `tasks/failure-cases.ts`: the hold check (`verify`, disposition `retried`) and the record-time `replaceOlder` both use it, so what holds a Task and what is stored agree. A repair decision whose repair Task was archived, deleted or unblocked without merging counts as abandoned (`abandonedRepair`), worked out on read with no event. A Check failure Ted can’t tie to the current code and Checks gets a decision card without Accept rather than a refusal (TED-523).
- `stages.work.lead_closes_failures: true` lets the current Task Lead close a Failure case it recorded as a Finding outside Validate, with passing evidence through `ted failure verify`. Only `leadClosesFailures` in `tasks/failure-cases.ts` reads the setting and only `verifyFailure` in `tasks/tasks.ts` uses it; don’t widen it to Checks, CI failures or cases recorded in Validate, and never let it accept a failure. It stays off in `workflow/defaults/workflow.yaml` (ADR 0119-a-setting-lets-the-task-lead-close-its-own-fixed-failures).
- The reviewer and the loop check are sub-agents whose agent, model and effort only `reviewerFor` in `tasks/tasks.ts` picks; never let `--provider` (or `--agent`) reach a reviewer. Any send-back Ted holds for the human (over `max_back`, a loop check) is a `v1.SendBackAsked` row, and `ted outcome advance` and `back` stay refused while its question is open (ADR 0055-reviewer-and-the-validate-loop-check).
- A Validate reviewer’s scope is decided only by `reviewRound` in `tasks/tasks.ts`, when the reviewer is requested: `v1.ReviewScopeRecorded` holds the commits it started at, and from the second round its instructions are Ted’s, built by `scopedReviewPrompt` in `tasks/review-rounds.ts` from the earlier Findings and the diff since the last reviewed commit. The Task Lead’s prompt file goes inside a fence with a fresh nonce and never replaces Ted’s scope. Every list of file names Ted puts in a prompt or a refusal (`fileLines` in `tasks/review-rounds.ts`, `found` in `tasks/base-conflict.ts`) goes through `oneLine` and sits inside a `<<<FILES <nonce>>>>` fence that the text calls data; never put a file name anywhere else. Every git command Ted gives a reviewer is built by `reviewCommand` there, which turns off replace refs, grafts, a shallow file, the pager, external diff and textconv programs, signature checks and worktree attributes; never write a reviewer’s git command by hand. `ted outcome advance` in Validate is refused by `movedSinceReview` in `tasks/tasks.ts` while any repo’s `HEAD` differs from the commits recorded for the visit’s reviewer, for every scope; it runs after the obligations and base-conflict checks, and a visit with no reviewer advances as before. Ted writes the round number and rule into the Validate entry and send-back messages with `validateRoundText` and `workRoundText`; change that text there, not only in a Stage file (ADR 0107-ted-scopes-the-reviewer-from-round-two).
- In Validate, `ted run start` starts only the reviewer, and one per visit: `SubAgents.request` refuses a second reviewer while the first is queued, live or has reported, and refuses every other sub-agent unless the Task’s Workflow has `stages.validate.sub_agents: true`, read through `validateSubAgents` (`taskWorkflow` without a fetch). Don’t add a flag that lets a Run lift either rule (ADR 0108-one-reviewer-per-validate-visit, ADR 0117-a-setting-allows-other-sub-agents-in-validate).
- `stages.validate.p1_only_from: N` makes Validate rounds N and later send back for a new Finding only if it is P1; an earlier round’s Finding that is still not fixed stays blocking. Only `p1OnlyAt` in `tasks/validate-settings.ts` decides whether a round is under the rule, and the texts Ted adds (`p1OnlyLeadRule`, `p1OnlyReviewerRule`, `p1OnlyReviewPrompt`, `p1OnlyRefusal`) live there; every round text and reviewer prompt in `tasks/review-rounds.ts`, the `conflict` scope included, takes `p1OnlyFrom` and carries the rule. In those rounds `declareSeverity` in `tasks/tasks.ts` refuses `ted outcome back` from Validate without `--severity p1` or `--severity unfixed` (an earlier Finding is still not fixed), before the Validate judgment is recorded; a send-back for a failed Check the Task Lead assessed as a regression (with no failed review or visual result), the human’s Fix in this Task decision, a verified base conflict and a send-back the human asked for skip it, and the hand-off Checks failing at Work are not a send-back at all. The declaration is `v1.SendBackSeverityDeclared`, recorded when the report is accepted and matched to its send-back in `store.listSendBacks`; a reviewer that ran under the rule is `v1.SeverityRuleReviewRecorded`. The setting stays off in `workflow/defaults/workflow.yaml` and in this repo’s `.ted/workflow.yaml`, and it is not a Gate: `withoutGates`, `withForcedGates` and `setupWorkflow` don’t touch it (ADR 0116-a-setting-sends-back-only-p1-findings-from-a-round).
- A send-back’s cause (`review`, `check`, `human`, `base-conflict`) is the separate `v1.SendBackCauseRecorded` event, committed with its `v2.TaskSentBack` through `store.recordSendBack({ cause })`; a new cause is a new string there, not a change to the send-back event. The thread reads the cause from that event’s Task log entry (ADR 0109-send-backs-record-a-cause).
- Checks run only through `runChecks` in `packages/daemon/src/tasks/checks.ts` (one after another, first failure stops, `$SHELL -lc`, `CI=1`, no `TED_APP_*`), and each run is a Check run in the store, not a Run, so it never takes a working slot. The Merge rebase rerun reuses the same runner (ADR 0044). A Check run’s trigger says why it ran: `hand-off` (before leaving Work), `validate` (at Validate entry), `agent` (`ted checks`) or `merge` (ADR 0111-checks-run-before-a-task-leaves-work). A Check run or a settings Run now first takes a place from the daemon’s one `CheckSlots` (`tasks/check-slots.ts`), which lets `maxChecksAtOnce` run at once and keeps the rest in a first-come line; a waiting Check run leaves the line when its Task is stopped, archived or deleted. What waits is in memory only (`store.setChecksWaiting`), and `Activity.checksRunning` counts only Checks that are running (ADR 0103-a-machine-limit-on-checks-running-at-once). Every Check command (a Task’s, a Scheduled Check’s, Run now) gets `TED_CHECK_CPUS`, the logical cores it may use: `checkCpus` in `tasks/check-slots.ts` gives the `checkCpuPercent` machine setting’s share of the cores (a multiple of 10 from 10 to 100, `checkCpuLimits`, default 50) divided by the Check runs holding a place when the command starts, never under 1, and callers get it from the daemon’s one `CheckSlots` (`cpus()`). A Scheduled Check gets it only while the `limitScheduledCheckCpus` machine setting is on (the default). It goes into the environment in `runChecks` and `check-tries.ts`, never into `checkEnv`, whose hash is part of a Failure case’s tested context. Ted doesn’t enforce it: a Check’s command passes it to its test runner, and this repo’s `pnpm check` does through `workersWithin` in `scripts/machine-load.ts` (2 CPUs per Vitest worker). Don’t fix a Check that fills the computer by changing `busyMarks` or the load reading (ADR 0171-ted-tells-a-check-how-many-cpus-it-may-use).
- A Task Lead’s `ted outcome advance` at Work, Validate or Review is refused while `baseConflict` in `tasks/tasks.ts` finds that the base branch tip conflicts with the worktree’s `HEAD`. It fetches with `fetchBranch` and test-merges with `mergeConflicts` in `git.ts`, in a scratch bare repo; never test-merge inside a worktree, and let the outcome through when the check itself fails. A git read that decides a review’s scope, ancestry or a test-merge (`isAncestor`, `ownCommits`, `mergeConflicts`) goes through `inScratch` in `git.ts`: a scratch bare repo that reads the clone’s objects through alternates with replace refs off, so the clone’s `refs/replace`, `info/grafts` and `shallow` don’t apply and nothing is written to the clone. A send-back’s cause is `base-conflict` only when Ted set it (the merge watcher) or verified it with the same test-merge (`ted outcome back --cause base-conflict` from Validate or Review, which then doesn’t count toward `max_back`); never record a cause on the agent’s word alone. A verified `base-conflict` send-back from Validate goes through even while a failure case is open and unassessed. The messages are in `tasks/base-conflict.ts` (ADR 0110-base-conflicts-are-checked-at-hand-off-and-recorded-as-a-cause).
- Every conflict that test-merge finds is one `v1.BaseConflictFound` event: `store.recordBaseConflict` when `advance` is refused, or `store.recordSendBack({ conflict })` in the send-back’s own commit, which sets `sendBackId`. File names and the base name go through `clean` first, at most 50 names. Rows are deleted with the Task; read them with `store.baseConflicts` or `GET /tasks/:id/base-conflicts` (ADR 0113-base-conflicts-found-at-hand-off-are-recorded).
- When every send-back since the last finished review has the cause `base-conflict`, `reviewRound` scopes the reviewer to the conflict resolution (`scope: 'conflict'`, `conflictReviewPrompt` and `conflictRoundText` in `tasks/review-rounds.ts`). It reads the Task’s own commits since the reviewed commit with `ownCommits` in `git.ts` (the first-parent chain) and trusts a merge commit only when its second parent is an ancestor of a base tip Ted fetched itself (`v1.BaseConflictFound`, or `baseTips` in memory); anything else is a full review. A `fixes` round with such merges gives the reviewer `git log -p --reverse --first-parent --remerge-diff`, not `git diff`. Never tell a reviewer to use `--remerge-diff` across a merge Ted hasn’t verified, because it hides what the merge brought in (ADR 0112-after-a-base-conflict-validate-reviews-the-resolution).
- On `ted outcome advance` at Work, when Validate is next, Work has no Gate and Checks apply, `handOffChecks` in `tasks/tasks.ts` runs them before the Stage changes, as a Check run with the trigger `hand-off`, after the base-conflict check. A pass moves the Task and passes the Check run to `validation.enter` through `move`’s `checked` option; `adoptHandOff` in `tasks/validation.ts` saves it as the Validate visit’s Check coverage when the Check plan and the worktree are still what Ted noted before the Checks started, so Validate runs no second one and `judge` picks it up; otherwise the Checks run at entry. A failure keeps the Task in Work with no send-back and no failure case; the third failure in a Work visit is a question recorded as `v1.SendBackAsked` with `from` and `to` both `work`, with two choices. **Try again** keeps the Task in Work. **Diagnose in Validate** is answered in `answerLoopAsk` (`tasks/request-answers.ts`) through `leaveWorkToDiagnose` in `tasks/tasks.ts`, which refuses for a stopped or Failed Task, running Checks, a Workflow that no longer goes from Work to Validate without a Gate, open obligations or a base conflict, then moves the Task with `move` and no `checked` run, so the Checks run at Validate entry and a failure becomes a failure case; keep it the only way a Task leaves Work with failing Checks, and don’t add a route that lets the Task Lead choose it. Ted doesn’t move the Task if a worktree’s `HEAD` changed while the Checks ran, or if the Task is stopped or Failed or has a different Task Lead Run when they finish (`handOffHalted`): the result isn’t used and `handOffUnused` tells the Task Lead to report again; a restart doesn’t rerun an interrupted hand-off for such a Task. Any other way into Validate still runs the Checks at entry through `validation.enter`, where a failure stays in Validate as a failure case; don’t route those through the hand-off path. `handOffChecks`, `baseConflict`, `reviewRound` and `movedSinceReview` call `execution.local` before they read a worktree, and `SubAgents.request` calls `prepareExecution` before `planReview`, so they act only on a Task this machine owns (ADR 0111-checks-run-before-a-task-leaves-work).
