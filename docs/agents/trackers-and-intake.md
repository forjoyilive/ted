# Trackers and intake

Rules for Linear, Asana and GitHub issues: keys, sync, imports and intake. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- The Linear API key and every Linear request live only in `packages/daemon/src/linear/`: the key sits in the OS keyring (service `TED`, or `TED Dev` from source; account `linear-api-key`), or in `TED_HOME/secrets/linear-api-key` only when the human chose it because no keyring works. Never put it in `process.env`, a Run’s environment, a log line or the store. Tests set `TED_KEYRING_MODULE` to `packages/daemon/test/fixtures/stub-keyring.ts` and `TED_LINEAR_API` to `stub-linear.ts` (both in `vitest.config.ts`) and never reach the real keyring or Linear.
- Tracker sync (Linear, Asana and GitHub issues) runs only through `packages/daemon/src/tasks/tracker-sync/`: `createTrackerSync` owns the cycle, the global switch check, the order per item (record what was read, stop unless the Task’s sync is `on`, handle a closing, move forward, link new pull requests once), and closed-outside handling (first read is a baseline; open to closed archives a Task with no live Run, not at Merge and with nothing unarchived under it, parent or not, and notes it on the parent, through the Tasks module’s callbacks, and otherwise asks Archive or Keep going, withdrawn on reopen or finish); `createTrackerConsent` owns per-Task permission and the one Allow or Not now question per group and Factory. A tracker adds a `TrackerConnector` (source, bounded reads, move, link, texts; requests stay in its own folder) and uses `trackerRecords`, whose `v1.Tracker*` events, `tracker-closed` and `tracker-group` purposes and `trackerSyncGroups`/`trackerSyncDeclined` settings are keyed by tracker ID; never change Linear’s connector to add one, and leave any new question kind out of what holds a merge or a nudge (`isTrackerClosedQuestion`, `isTrackerGroupAsk`).
- Linear is the first connector, in `packages/daemon/src/tasks/linear-sync.ts` (`linearConnector`, `linearRecords`): one batched read per cycle, only while the `linearSync` machine setting is on and a key exists; it moves the issue forward by state type (started, review, completed), attaches each pull request once, and an issue closed in Linear archives an unstarted Task or asks. Its records stay on the shipped `v1.Linear*` events. It writes, or acts on a closing, only for a Task whose `linearSync` is `on` (made through the app’s key, allowed with the app-only `POST /tasks/:id/linear-sync`, or its team in `linearSyncTeams` for the Factory, never from `createdBy`); a Task made with the `daemon.json` token or by an Automation is `ask` until then. The first Automation-made Task from a team not listed or declined for its Factory gets one question from Ted (`linearTeam` on the Comment, set only by the daemon), one per team and Factory; only the app answers it: **Allow** goes through `allowLinearTeam` in `tasks/tasks.ts` (also the app-only `POST /integrations/linear/teams`), which lists the team and records `v1.LinearTeamSyncAllowed` on its `ask` Tasks (Done ones included), matched only by the team Linear reported in `v1.LinearIssueSeen`, never by the URL’s identifier; **Not now** adds it to `linearSyncDeclined`. Linear state names go through `clean`; tests start the daemon with `linearSyncMs` and the stub’s `states`.
- Asana is the second connector (Task Sync), in `packages/daemon/src/tasks/asana-sync.ts` (`asanaConnector`, `asanaRecords` over `trackerRecords(store, 'asana')`), while the `asanaSync` machine setting is on and Asana is connected. Its only writes are `comment` and `complete` in `asana/asana.ts` (fixed `/tasks/<digits>` paths, JSON, redirects refused, size-capped, `Retry-After` kept as `retryAfterMs` (seconds or a date, limited to a day), refused when the token’s account isn’t the one the write names); a cycle sends at most 100 requests and a `TrackerWait` stops it. Permission is `v1.TrackerSyncAllowed` with the connected account’s gid: `importAsana` records it in the `createTaskTree` commit only for the app’s imports, and the app-only `POST /tasks/:id/asana-sync` records it otherwise; it counts only while that account is connected. An app import with `taskSync: false` (the import dialog’s checkbox) records `v1.TrackerSyncDeclined` instead, which also overrides project allowances until the Task menu allows it; Retry and Add them as Tasks copy the question’s Task. The store holds the connection (`setAsanaConnection`, also from every Asana settings route’s status) and the open items under a parent (`setAsanaOpenChildren`) in memory and puts `asanaSync` (`asanaSyncOf` in `packages/protocol/src/asana-sync.ts`) on each Asana Task. Before a comment Ted reads the item’s comments for the pull request’s URL, so a lost reply or a restart never posts it twice; it checks the switch and the Task’s state again just before each write, completes an item only after every pull request merged and no Asana subtask is open, and never for an archived unmerged Task. A Factory can also allow Asana projects, through the shared group lists keyed `asana` and only the app’s `POST /integrations/asana/projects` and `…/remove`, which read the project with the connected account first; the machine settings route refuses the `asana` entries and `trackerSyncGroupAccounts`. A Task counts as allowed through projects only by its item’s own last-read projects (`v1.TrackerItemGroupsSeen`, from the cycle’s `memberships.project.gid` read and the import), only for the account recorded in `trackerSyncGroupAccounts`, and an Automation’s import asks about one unlisted project per Factory through `askGroups`. A merged parent whose item still has unfinished items under it goes through `readSubtree`, `planUnfinished` and `parentStep` in `tasks/asana-unfinished.ts`: items with a Ted Task make it wait, and anything else is one `asanaUnfinished` question (`v1.CommentAsanaUnfinishedAsked`) that only the user answers; Add them as Tasks is the one import that creates children under a Done parent (`doneParent` in `planAsanaImport`), and nothing completes an item under the parent.
- GitHub is the third connector (`packages/daemon/src/tasks/github-sync.ts`, `githubConnector` and `githubRecords` over `trackerRecords(store, 'github')`), with every GitHub call in `packages/daemon/src/github/issue-sync.ts` through the `Gh` runner. The `githubIssueSync` machine setting, off by default, is its only consent: a Task syncs when its source has `TaskSource.github`; never add a per-Task or per-repo permission. It writes only fixed text, never an agent’s words and never naming Ted or AI: “Work on this has started.” once past Design, “Fixes” or “Part of” the issue in pull request descriptions (`issueLine` and `withIssueLine` in `tasks/pull-requests.ts`; `pullRequestBody` asks `PullRequestTask.issue` just before each write, and an issue with open or unknown sub-issues gets “Part of”), “Fixed in <links>.” once every pull request merged, then a close as completed unless a sub-issue is open, which gets one Ted note instead. Before a comment it reads up to 500 of the issue’s comments for the same text by the signed-in user and posts nothing when there are more; it checks the switch and the Task again just before each write, and a link it didn’t write throws `TrackerWait` so it isn’t recorded. The first read of a finished Task records it as done without writing. A close whose `closer` is one of the Task’s pull requests isn’t closed outside.
- Asana tasks are read only through `read` in `packages/daemon/src/asana/asana.ts` (the connected account’s token, redirects refused, size-capped) and imported only by `importAsana` in `tasks/tasks.ts`: `readAsanaTree` (`asana/tree.ts`) reads the whole tree and downloads files first, `planAsanaImport` (`tasks/asana-import.ts`) decides each item’s place, and `store.createTaskTree` creates every Task, link, note and question in one commit. Never create an imported Task before the read finishes. New Task fills Title from the selected Asana task when it is empty or still matches the last title Ted filled, preserving a title the user entered. `AsanaImportRequest.title` names only the selected root Task; a missing or blank title falls back to its Asana name, and child Tasks keep their Asana names. This lets the user name the parent without renaming its imported children. Files are downloaded only by `fetchAsanaFiles` (`asana/files.ts`), from Asana-hosted `download_url`s over HTTPS to a named host, without the token. An Asana source is matched by task ID (`sourceKey` gives `asana:<gid>`). Unreadable items and conflicts are one `asanaMissing` question on the nearest imported parent, which holds it through a blocker link of kind `asana` until the app answers Retry or Go ahead; Autopilot and the Coordinator never answer it. `addToTree` is app only. Tests use `stub-asana.ts`’s `setTasks`.
- What an Automation may bring in from Linear, GitHub or Asana is decided only in `packages/daemon/src/tasks/intake.ts`: `automationIntake` for `ted task create` (the Follow-up and `--start` refusals when it is made, then `judgeGitHub`, `verify`, `unchanged` and `refuseTrackedParent` where `create` calls them), `refuseAsanaRoot` for Asana imports, `intakeHold` (with its wrappers `asanaIntakeHold`, `linearIntakeHold` and `githubIntakeHold`) and `scopeHold` for reading a tracker’s intake setting, refusing when it is missing, and stopping when it changed during the check or the Factory is being removed or gone, and `intakeLines` for the Automation prompt’s intake text. A new intake rule, its refusal text and its prompt line go there together, with a case in `packages/daemon/test/intake.test.ts`; the tracker reads stay in `tasks.ts` and the tracker folders, and the module commits nothing.
- A bulk intake run (`ted asana intake`, `ted github intake`, `ted linear intake`) goes through `createBulkIntake` in `packages/daemon/src/tasks/bulk-intake.ts`, which owns everything the three share: one run at a time per tracker and Factory, the per-run cap, the loop that counts each item as tracked, left, imported, skipped or stopped, and the summary log line. The cap counts the Tasks each import created: for an Automation Run, every Task its firing created with that tracker’s source URL (`createdInFiring` in `tasks.ts`); for the app, the Tasks this run created. An import that doesn’t fit throws `IntakeBudgetError`; with `overBudget: 'stop'` (Asana) every later item is left, with `'next'` (GitHub, Linear) later smaller items are still tried. A failed import skips that item unless the hold’s `unchanged` now throws, which stops the run. Each tracker supplies its listing, tracked check and one-item import from `tasks.ts`, so the module reads no tracker and commits nothing itself; its loop is tested with a fake tracker in `packages/daemon/test/bulk-intake.test.ts`.
- Asana intake imports only through `Tasks.asanaIntake` (`POST /asana-intake`, `ted asana intake`, which the `asana` Automation template runs on its schedule) from the Factory’s `asanaIntakeScopes` entry, which only the app-only `PUT /factories/:id/asana-intake` sets after `confirmAsanaScope` (`asana/intake.ts`) checks it with Asana; the Asana group on the Factory settings Intake page (`views/AsanaIntakeSection.tsx`) picks it from the app-only, one-page-at-a-time `GET /integrations/asana/workspaces`, `…/workspaces/:gid/projects` and `…/projects/:gid/sections` (`listAsanaChoices`) and marks a stale saved choice from `GET /factories/:id/asana-intake/check` (`checkAsanaScope`); the machine settings route refuses the key and `factory-removal.ts` deletes it. A root is decided only by `checkAsanaRoot` on Ted’s own read (incomplete, assigned to the connected user, a member of the saved project and section) and is skipped when it or an ancestor is already tracked in the Factory; never trust a name or membership a Run sends. Every Automation Asana import (`asana-import`, its preview, `ted task create --source <Asana URL>`) passes the same check through `requireIntakeRoot` in `tasks/tasks.ts`, which reads Asana and leaves the verdict to `refuseAsanaRoot` in `tasks/intake.ts`, and an Automation can’t make a Follow-up of Asana work. The scope read at the start is compared again before each commit; a run creates at most `maxAsanaIntakeTasks` Tasks, counted for an Automation Run across all its Asana imports (`asanaAllowance` for a single import, `createBulkIntake` for `ted asana intake`), and every Asana read retries through `retryingRead`, which waits for a 429’s `Retry-After`. Tests use `stub-asana.ts`’s `setWorkspaces`, `setProjects` and task `memberships` and `parent`, and check its `requests` for writes.
- Linear intake imports only through `Tasks.linearIntake` (`POST /linear-intake`, `ted linear intake`, which the `linear-intake` Automation template runs), from the Factory’s saved Team or Project in `linearIntakeScopes`; `linearIntakeHold` in `tasks/intake.ts` refuses an Unscoped Factory. Ted lists the issues itself through `Linear.intakeIssues` in `linear/linear.ts` (assigned to the connected user, state type in `linearIntakeStateTypes`, at most 1,000 read), skips one already tracked in the Factory (`sourceClash`) and creates each other one through the same `createTask` as `ted task create --source`, so every one-issue rule applies. A run creates at most `maxLinearIntakeTasks`, counted for an Automation Run across its firing, and stops when the scope changes. Tests use `stub-linear.ts`’s `assignedToMe` and `startDaemon`’s `linear.intakeLimit`.
- A Linear issue’s images and uploaded files are downloaded only by `fetchLinearFiles` in `packages/daemon/src/linear/files.ts`, inside `issueFor`, with the key sent only to `uploads.linear.app` or the Linear API URL’s origin and no redirect elsewhere; at most 20 files, each under the attachment cap and typed by its first bytes. `Tasks.create` makes them the Task’s attachments, rewrites their links in the stored Linear description to the file paths, and posts one Ted note for any it couldn’t fetch; it never fails for them. Tests serve files with the stub’s `uploads` and `uploadUrl`.
- A GitHub issue source is imported only by `githubIssue` in `tasks/tasks.ts`, through `readGitHubIssue` in `packages/daemon/src/github/issues.ts` (one GraphQL query through `Gh`; never the token), and only when its owner/repo, and the `nameWithOwner` GitHub reports, match a Factory repo; anything else stays a link. The copy goes through `clean`, every part gets a Ted heading with its author and `maintainer` (`OWNER`, `MEMBER`, `COLLABORATOR`) or `outsider`, every line an author wrote starts with `> `, and it lives only in `TaskSource.github.context` (`v1.TaskSourceGitHubSet`), never the Task description, which reaches the Task Lead unfenced; `sourceContext` fences it with a fresh nonce, and `promptTitle` in `workflow/workflow.ts` keeps an imported title out of the unfenced prompt until the user edits it. Membership comes from `factoryRepos`. `outsiderText` records whether an outsider wrote any of it. Files come only from `packages/daemon/src/github/files.ts`: GitHub’s upload hosts, the signed link from the rendered HTML, no `Authorization` header or cookie, redirects only to those hosts, at most 20. A read or file failure is a Ted note and never fails creation. Open sub-issues in Factory repos become child Tasks only through `readSubIssueTree` in `github/sub-issues.ts`, read whole before `store.createTask` creates the parent, its `children` and every note in one commit; any unreadable part leaves the parent with no children. Tests set `issues` in the stub `gh` state and `startDaemon`’s `github.uploadOrigins`. An Automation’s GitHub-issue import also passes `judgeGitHub` in `tasks/intake.ts` (open, in a Factory repo, the Factory’s `githubIntakeScopes` label when set, no tracked parent issue), on Ted’s own read, and creates the Task in Backlog; automatic Backlog starts may then start it when `backlogStarts.includeGitHubIssues` is on and its Factory takes part. That switch is separate from `includeAgentFiled` because an issue’s text can come from outsiders (see `factories-and-settings.md`); only the app-only `PUT /factories/:id/github-intake` sets the label. `ted github intake` (`POST /github-intake`, `Tasks.githubIntake`, Automation Runs only) imports every open issue with that label in the Factory’s repos: `listIntakeIssues` in `github/intake.ts` lists them, `planGitHubIntake` and `githubIntakeHold` in `tasks/intake.ts` leave out tracked issues and refuse without a label, and each issue goes through `createTask` like a one-issue create, at most `maxGitHubIntakeTasks` per run.
