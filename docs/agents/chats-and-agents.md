# Chats and Agents

Rules for Coordinator chats, planning chats, Agent files and their powers. They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- Each Coordinator chat is a `coordinatorChats` row keyed by its own ID, and a Factory can have any number open at once; it is written only through `store.coordinators` (`v1.CoordinatorChatChanged`, `v1.CoordinatorChatArchived`, `v1.CoordinatorChatContinued` (Unarchive), `v1.CoordinatorChatDeleted`, and `v1.CoordinatorChatRenamed`, which sets the row’s own `title` column so a save never undoes a rename). A chat’s title is that column, else `planTitle` of its opening message; planning chats rename through `v1.PlanRenamed`. The app (`PATCH /coordinator-chats/:id`, `PATCH /plans/:id`) and paired phones acting as the user can rename a chat. The old Factory-keyed events stay as they are and their materializers map them into that table: the chat open at the update keeps the Factory’s ID and every saved conversation is an archived chat (`endedAt` set). Everything in `Coordinators` is keyed by chat ID except its Task actions, which keep one queue per Factory (`serial`); two chats acting on one Task meet only the existing stale-action checks. The app’s routes take the chat ID (`/factories/:id/coordinator-chats` to list and start, `/coordinator-chats/:id…` for the rest), and a Coordinator Run finds its chat through `store.coordinators.forRun`. Starting a chat never touches the others; only `Coordinators.archiveChat` archives a chat (stopping its Runs and canceling its open confirmation cards), only `unarchiveChat` brings one back and only `deleteChat` deletes one, open or archived, and the app and paired phones acting as the user call them. Messages to an archived chat are refused. Anything that treats a Run as a Coordinator Run by `forRun` decides whether an archived chat’s Run counts too (`endedForRun`). The Agents screen (`views/Agents.tsx`) lists every Coordinator chat and planning chat of a Factory in one list built by `agentChatRows` in `renderer/agent-chats.ts`, with archived chats split off by `splitArchived` into a collapsed Archived section, and draws a Coordinator chat with `Conversations.coordinatorChat`, `ChatBody` and `Composer` from `RunChat.tsx`; don’t give it its own chat components. Every open chat, Coordinator, planning or another Agent’s, is drawn by `AgentChat` and `AgentChatDetails` in `components/AgentChat.tsx` (header, top banner, details pane); `CoordinatorChat` and `PlanChat` only load their data and pass it in. The app’s chat actions come only from `chatActions` in `agent-chats.ts`, which the header’s ⋯, a right-click on the header and the chat list’s row menu all draw. The app and phone share `coordinatorRetryable` and `planMenuResumable` in `packages/protocol/src/agent-chat-view.ts` to decide whether to offer Retry or Resume; the phone’s `actions` list is built in `packages/daemon/src/phones/chats.ts`. New chat opens `AgentPicker` (`views/AgentPicker.tsx`), one card per Agent from `GET /factories/:id/agents` and a last New Agent card that opens the Factory’s Agent files; picking the Planner opens the new planning chat form and any other Agent opens `CoordinatorStart`. Both forms show the Agent with `AgentHeading` and a “← All agents” link back to the picker, and there is no Agent menu after the pick; `Agents.tsx` moves the typed message to the next Agent picked after going back. A card’s text is `agentDescription` in `packages/protocol/src/agent-chat-view.ts`: the Agent’s optional one-line `description` from `agents.yaml`, falling back to Ted’s own line for the built-in Agents; a chat’s title is edited with `TitleEditor` from `components/AgentChat.tsx`. An Inbox request from a chat names the Agent and the chat’s title (`chatTitle`, `planTitle` on the waiting item) and opens the chat on the Agents screen; the Inbox’s automatic move to the next request stops before a chat’s request. A message Ted writes to a Run is queued with `from: 'ted'` (`v2.RunMessageQueued`) and is never a `human` chat item. A Coordinator chat’s questions, rounds and proposals are `chatRequests` rows (`v1.ChatRequestPosted`, `v1.ChatRequestAnswered`, through `store.chats`), one open at a time per chat, posted only by the chat’s current Run through `Coordinators.ask`; they join `waiting()` as `source: 'coordinator'` with `requestKind`, can be snoozed with the chat as owner, and are answered only by the app (`POST /coordinator-chats/:id/requests/:rid/answer`, never `runToken` or `fileToken`), never by the Coordinator’s `answer` action or Autopilot; archiving the chat withdraws them, and the rows go with the chat and the Factory. An approved chat proposal creates Tasks with `coordinatorOperation` (so `v1.TaskCreatedByCoordinator`), under one parent when it has several rows, and leaves the chat open. A chat whose Agent has Read the code works in a checkout under `TED_HOME/chat-code/<chatId>/`, made only by `checkOut` in `chats/checkout.ts` (through `makeCopy` in `code-copy.ts`) when its first Run starts and stored on the chat; it is removed on archive (made again after Unarchive), delete and Factory removal, and at start Ted removes every checkout whose chat isn’t open. It counts as Worktrees in Settings → Storage.
- Every Coordinator action on a Task keeps its receipt only through `coordinatorReceipts` in `packages/daemon/src/coordinators/coordinator-receipts.ts`. It owns the per-Factory queue (`serial`), the repeat check and the “operation ID already used” refusal for single and grouped (`<operation>:<taskId>`) receipts, the “Action interrupted” placeholder saved to disk before the action, the result saved after it with the Task’s state before and after, redaction of every receipt text, and the chat’s last 100 Tasks. A new action calls `record` (or `append` for a receipt with nothing to interrupt) and keeps only its own checks, its call into `Tasks` and its wording. Receipt IDs and fingerprints never change, so chats saved earlier still replay.
- Planning chats live only in `packages/daemon/src/plans/plans.ts`: a plan’s ID is its Run’s ID, it goes through the pump as `planning` (a chat, outside the slot limit), its rounds and proposals are `store.plans` requests (not Task Comments), and its detached worktrees under `TED_HOME/plans/<id>` (made with `checkOut` from `chats/checkout.ts`, only when its stored Agent has Read the code) are removed whenever it ends. Inside a Planning Run (`TED_PLAN`), `ted ask --round` and `ted task propose` post to the plan, and `Plans.post` refuses a round without Ask the user and a proposal without Propose Tasks on the plan’s stored Agent. Plan in chat on a size check starts a plan linked to its Task (`v1.PlanStartedFromTask`); only the Tasks module narrows that Task or tells its Task Lead, through `Tasks.planApproved` and `Tasks.planEnded`, and archiving or deleting the Task detaches the plan through `Plans.taskGone`. A plan stays open until the user archives it: **Resume** on a Stopped plan and **Retry** on a Failed one (`POST /plans/:id/resume`, `v1.PlanRetried`) check the repos out again and resume the planner’s session, only when `canResume`; stopping keeps open requests of a plan that can resume, and answering one or sending a message resumes it, Finished plans included, through the Run’s queued messages. If a Run ends with a message still queued, Ted resumes the planner’s session under the bounded recovery rule in `runs-and-providers.md`; a stopped Run stays stopped. If resuming after an answer fails, the answer stays saved and `resumeAfterAnswer` throws `AnswerSavedError` (`packages/daemon/src/errors.ts`, HTTP 409). The phone answer handler returns `refused` with that error’s secret-redacted message before checking whether the request is gone, so the user learns that the answer was saved; a later attempt to answer the closed request returns `gone`. The app and paired phones acting as the user archive (`Plans.archive`, `POST /plans/:id/archive`: stops a live Run, tells a linked Task, then one `v1.PlanArchived` withdraws every open request) and unarchives (`v1.PlanUnarchived`); an archived plan neither resumes nor takes answers, and approving a proposal archives the plan through `v1.PlanEnded` with `finished`. Archived chats of both kinds are deleted automatically only by `createChatArchiveCleanup` in `packages/daemon/src/chat-expiry.ts`, on the archived-Task timer, when the `deleteArchivedChatsAfterDays` machine setting is set (default `null`); `GET /chat-archive-expiry` gives the due count. **Plan more from here** starts a new plan from one that has ended (Finished, Stopped or Failed), archived or not, and stores the old chat’s rounds, answers, proposal and created Tasks as text in `v1.PlanContinued`, so it survives the old chat’s deletion. Planning worktrees count as Worktrees in Settings → Storage.
- The rules for posting and answering a chat request live once in `packages/daemon/src/chats/requests.ts`, for both chat kinds, so a fix reaches both: one open request per chat (a planning chat’s notes never count), `--supersedes` only of an unanswered request of the same kind (404 when the chat has no such request), round numbers, proposal row defaults, the refusal for a closed request, the round-answer message and chat titles. A new proposal over an open one is refused until the agent passes `--supersedes`, in both kinds. `Plans` and `Coordinators` keep their own storage, events, power checks and what an approval does.
- An Agent (the Coordinator, the Planner or one a layer adds) is defined in `agents.yaml` and `agents/<id>.md` in each Workflow layer, checked by `checkAgentFiles` and merged only by `resolveAgents` in `workflow/agent-files.ts`; read one through `workflow.agent(id)`. Powers are the fixed `agentPowers` list in `@ted/protocol/agent-files`. Only the Agent’s role text lives in its file: Ted’s command lists and safety rules stay in `coordinatorInstructions` and `plannerInstructions`. Ted checks every action against the chat’s stored Agent, never against what the Run says. A chat’s Agent is chosen only by `pickAgent` in `chats/agents.ts` (the Planner only in a planning chat, every other Agent only in a Coordinator chat; `manage_tasks` on `planner` is a `ted workflow check` error and `resolveAgents` drops it) and stored once, as `v1.ChatAgentRecorded` in the same commit as the chat’s first `v1.CoordinatorChatChanged` or `v1.PlanStarted`, in `chatAgents`; its rows are deleted by `v1.CoordinatorChatDeleted`, `v1.CoordinatorRemoved`, `v1.PlanDeleted` and `v1.FactoryRemoved`, and anything new that deletes a chat deletes its row too. Read it only through `store.chats.agent(chatId)`, falling back to the built-in Agent read from Ted’s own default files for a chat without a row; never read the Agent files again for a running chat, at a restart or for a replacement Run. Powers are checked only by `requirePower` and `hasPower` in `chats/powers.ts`, on the stored Agent of the chat found from the Run token (`store.coordinators.forRun`, or the plan whose ID is the Run’s ID): `actor` and `admit` in `coordinators.ts` (Manage Tasks, every `ted coordinator` route), `Coordinators.ask` (`POST /coordinator/requests`) and `Plans.post` (Ask the user for a question or round, Propose Tasks for a proposal), and the checkout (Read the code). Never take a chat or Agent ID from a request body or from `TED_CHAT`, which only tells the CLI where to send `ted ask` and `ted task propose`. The preamble pieces for each power live in `chats/powers.ts`, and `coordinatorInstructions` and `plannerInstructions` add only the granted ones. Read the code is a soft limit (Ted makes no checkout, but a Provider’s file tools may still read under `TED_HOME`); Ask the user, Manage Tasks and Propose Tasks are enforced in the daemon. A chat whose Agent left the Factory’s Agent files stays readable, archivable and deletable, and `removedRefusal` refuses its messages and answers. `GET /factories/:id/agents` lists resolved Agents without instructions or path.
- The Manage Agents power (`manage_agents`, the built-in Coordinator’s, never the Planner’s) lets a Coordinator chat read the Factory’s Agents (`GET /coordinator/agents`) and post an Agent draft, a chat request of kind `agent` (`v1.ChatAgentDraftPosted` in the request’s commit), checked and redacted by `planDraft` in `chats/agent-drafts.ts`. No Run writes Agent files: only the app’s `POST /coordinator-chats/:id/requests/:rid/agent` (`Coordinators.answerAgentDraft`, never `runToken` or `fileToken`) saves one, through `saveDraft`, which calls `LibrarySettings.save` or `FactorySettings.save` in pull-request mode. The card may narrow a draft (edit text, untick powers) but never add a power (`chosenDraft`), and `draftStillFits` refuses when the Agent changed since the draft.
- An Agent’s named commands (`commands` in `agents.yaml`) run only through `createChatCommands` in `packages/daemon/src/chats/commands.ts`, for a chat whose stored Agent has Run commands in the copy (`run_commands`, which needs `read_code`): `ted agent run <name>` (`POST /chat-commands`, `GET /chat-commands/:id`) sends only the name, and Ted finds the chat from the Run token through `Coordinators.runCommand` or `Plans.runCommand` and the command text from `store.chats.agent` (stored with `v1.ChatAgentCommandsRecorded`), never from the request. It runs like a Check (one per chat at a time, `newWorkHold`, a `CheckSlots` place, `TED_CHECK_CPUS`, `$SHELL -lc`), always in the sandbox, writing only the chat’s worktrees and `TED_HOME/sandbox/chat-<chatId>/`; with no sandbox it raises `sandbox-unavailable` and refuses. Each repo’s `setup` runs once per copy through `runScratchSetup` in `tasks/scratch-setup.ts`. Output goes back through `redactSecrets` inside a fresh-nonce fence, and each run is one `v1.ChatCommandRan` row shown as a `command` chat item. `discard` in `chats/checkout.ts` (through `discardCopy` in `code-copy.ts`) ends processes left in the checkout and the chat’s sandbox folder before removing both.
- An Agent’s outside commands (`outside_commands` in `agents.yaml`) let a Coordinator ask Ted to run a named command outside the sandbox; only `createOutsideCommands` in `packages/daemon/src/chats/outside-commands.ts` runs them, for a Coordinator chat whose stored Agent has Run outside commands (`run_outside`, never on `planner`) and whose current Agent files still list the same text (`stillListed`). A command is plain words with at most one `<slot>`, checked only by `outsideCommandWords` in `packages/protocol/src/outside-command.ts`; `ted agent run-outside <name> [argument]` (`POST /chat-outside-commands`) sends a name and one plain-word argument, which `outsideArgv` puts in the slot as its own argument, and Ted spawns the words with no shell, in the real path of the repo’s local folder, with the login environment minus Ted’s Run variables, at normal priority, one per Factory. The first time it is a chat request of kind `outside-command`; only the app’s `POST /coordinator-chats/:id/requests/:rid/outside-command` runs it or ticks Always allow, and that route, the stop route and the allowance routes never set `runToken` or `fileToken`; the Coordinator’s `answer`, Autopilot and the Agent draft card (`planDraft`) never grant it. An approval is one `outsideCommandAllowances` row keyed by Factory, Agent, name, exact text, repo and folder, deleted by `v1.FactoryRemoved`; any difference brings the card back. Output reaches the chat line live and the Run as a fenced, redacted message from Ted when it ends. Tests stub `pnpm` on `PATH` and never run real signing. Before running, Ted checks the local folder with `checkFolder` in `chats/local-folder.ts`, which fetches only Ted’s clone and runs only read-only git in the folder; `localFolderAction` in `packages/protocol/src/local-folder.ts` decides whether to run, fast-forward first (`updateFolder`, the only code that changes the user’s folder, and only by `merge --ff-only`) or hold the command, even an Always-allowed one, on a card. Never commit, stash, check out or install in the user’s folder.
- An idle Coordinator or planning chat Run sleeps like an idle Task Lead: `runs/idle-sleep.ts` asks `Coordinators.mayRest` or `Plans.mayRest`, and a wake after a daemon restart takes the chat’s environment from `Coordinators.runEnv` or `Plans.runEnv`. Anything new a chat waits for without a working turn that a restarted agent would lose makes its `mayRest` false while it lasts. Messages still reach a chat only through `RunManager` (`send`, `dispatch`), which wakes it.
- A paired phone can send a message, start, stop, retry or resume, rename, archive, unarchive and delete a Coordinator or planning chat through the relay, as the user. It uses the same `Coordinators` and `Plans` calls as the Mac (`phones/chat-actions.ts`, rules in `platform.md`). Sending a message resumes an ended planning chat when `canResume` is true, including a Failed one. The phone answers only the planning chat requests the phone Inbox routes allow.
