# Coordinators have bounded Factory authority

A Factory has one ongoing Coordinator conversation. It helps the human compare Tasks and choose next work without taking over any Task Lead’s responsibilities. It acts only when messaged, and only requests in that conversation authorize creating Tasks, starting Backlog Tasks, reordering waiting Tasks, resuming stopped Tasks, sending a message to a Task’s Task Lead (tell) or answering a Task’s open requests (answer). Advice and ambiguous references require a chat reply.

`coordinators/coordinators.ts` owns its lifecycle and registers a QueueSource with Tasks. Each idle-to-working turn takes a slot at the Planning tier, under machine and Factory caps, agent health and disk holds. The Coordinator uses its own managed folder, never a repo checkout. Existing Run Conversation storage retains messages and agent output; additive Coordinator events persist identity, Run associations, phase, referenced Tasks and action receipts. Concurrent first messages share the Factory’s unique row. Replacement association includes its launch prompt and pending input in the same persisted Coordinator event, so a restart before host creation can resume that request. Stop archives undispatched messages with their removal from the dispatch queue in one store commit; they remain visible as Not sent and are never replayed by a later message.

The stored Run association supplies authority, rather than a request’s Factory ID or an environment variable. The server restricts these Runs to Coordinator tools, caller discovery and their own boundary operation. Ordinary Run routes cannot bypass that restriction. App-only routes create conversations, send human messages, Stop and Retry. The daemon shares one steering service between Conversations and Coordinator. Coordinator owns idle-turn admission; steering owns every queued message delivery through its serialized chain, including delivery after admission. An idle admission dispatches one pending message; later messages stay in the daemon for a working tool boundary or a subsequent admission after settlement. This avoids queuing unseen agent turns behind a healthy response while waiting for their acknowledgments. A Coordinator message stays queued until the agent acknowledges it. RunManager dispatch writes and syncs a generation-tagged input record carrying the message’s stable delivery ID and the host-output offset. Initial launch and session revival also sync their prompt’s message identities and output checkpoint before recording RunStarted or RunRevived. If preparation leaves a managed Run folder without a Run row, Retry persists a fresh identity with the original input before attempting another launch; the abandoned identity stays registered for checked Factory cleanup. Recovery reconciles acknowledged prompt input before choosing a new turn and removes redundant initial queue rows already represented by the saved prompt; it recognizes an already written or accepted delivery instead of appending it again. Cancellation checks these durable records, including after restart, and succeeds only before dispatch; dispatch rechecks each selected message immediately before writing. These are additive fields in the existing generation envelope, which older hosts already unwrap. Steering retains admission until an in-flight dispatch completes, including settlement during persistence; a delivery failure stops its live Run while retaining the slot, and live Working/Waiting Runs remain slot holders even if stopping fails; Stop, removal and shutdown close its dispatch gate. Steering’s boundary flag and hook handle working responses, while its observers cannot deliver an idle Coordinator follow-up around the queue. Canceling the last queued message returns the conversation to Ready without taking a slot. Replacement Run association retains the admitted Working phase until the response settles. Failed session resumption can replace the Run while preserving earlier history and receipts. Old Runs have no action authority.

Reads return fresh facts with bounded pages and nonce-delimited untrusted Task context. Actions require current target and neighbour versions. Starts delegate to `Tasks.start`; moves delegate to `Tasks.move`, using neighbour IDs rather than client ranks. The daemon validates Factory and waiting-group membership and rejects reversed or equal neighbour bounds using TED’s Priority and rank order. Per-action operation IDs and fingerprints are persisted before dispatch; an interrupted dispatch returns an uncertain receipt rather than replaying the action. Receipts preserve the actual result and before/after state, including Priority changes. Multi-Task actions are independent, never atomic.

Startup restores steering flags after Coordinator admission state is available. Health recovery drains launch and steering before checking for pending input, persists a continuation when needed, and only then stops and requeues the interrupted response. Retry reuses pending input before adding a continuation. Shutdown closes admission and drains launches, steering, action chains and health recovery before the store closes. Factory removal blocks Coordinator creation from its start through final cleanup and rechecks first-message creation after defaults resolve. It waits for launches and actions, stops Coordinator hosts and removes saved rows, pending messages, Conversation history and checked managed folders before FactoryRemoved. This is an explicit, narrow Factory-scoped exception to ordinary Task Run authority. It grants no power over Task edits, credentials or settings, and none over Stages beyond the effect of an answer; “Every request on a Task, and resume” below says which requests it may answer.

## Tell and answer

The first version could only read, start and reorder. With many Tasks waiting on the same kind of question (22 at once, most of them “my reviewer is queued, what should I do?”), the human had to answer each one by hand. The human chose to let the Coordinator act on those Tasks when told to in its chat, and accepted that this changes “only the human answers a request” (ADR 0032) for one kind of request.

- **Tell** posts a Comment on the Task through `Tasks.coordinatorTell`, which stores it as the human’s Comment and delivers it as `humanComment` does: to a live Task Lead through steering, or to the next Run otherwise. The same guards apply: an archived Task and a pending merge refuse it. The Coordinator adds its own: the Task must be in its Factory, not archived and not Done.
- **Answer** closes one open request through `Tasks.coordinatorAnswer`, which runs the same code as `Tasks.answer` with `{ action: 'answer' }`. The request must be on the target Task, open and of kind `question`. A question a Run asked takes a choice, a message or both. A question TED asked is allowed only when it has `choices` and the Coordinator passes one of them; see “TED’s questions” below. The Coordinator never answers a Gate request or sign-off, a `permission` or `simulator` ask, a `round`, a `proposal`, a size check, the Linear team ask or a failure decision.
- Every Comment body and answer text the Coordinator sends starts with the fixed line `coordinatorLine` (“Sent through the Coordinator on the human’s instruction.”), so the thread and the Task Lead see where it came from. The Comment’s author is still the human, because the human asked for it; the line is the only mark.
- Both follow the same rules as start and move: a current Task version, an operation ID, a receipt saved before dispatch, and one Task per action. The fingerprint adds a hash of the message, the request ID and the choice, so an operation ID reused with different input is refused.
- Neither sends the Task’s line comment drafts. Those are the human’s unfinished review notes, and every other path that posts the human’s words attaches them (ADR 0079). That is why tell and answer have their own entry points in the Tasks module instead of calling `Tasks.comment` and `Tasks.answer`: the drafts stay unsent until the human sends them.
- The message is text the Coordinator writes: `--message "<text>"`, or stdin when it is left out. The commands never open a file. An earlier draft took `--message-file`, which would have let a Coordinator misled by Task text post any file the user can read (an SSH key, a token file) into a Task thread. The route trims the message, refuses more than 8,000 characters with a 400, and runs it through `redactSecrets` before it is stored. TED has no general cap on a Comment’s body, so 8,000 is this route’s own limit.
- The daemon cannot check that the human asked. It trusts the Coordinator’s instructions for that, as it already does for start and move; the hard limits above are what the daemon enforces.

## TED’s questions

The first version of answer refused every question TED asked, because some of their choices start a Run, archive the Task or move its Stage. The human then asked for them: most Tasks stuck overnight were waiting on exactly these, and one chat message should clear them. So the Coordinator may answer a question TED asked when it has choices and the Coordinator gives one. What each choice does is unchanged, because the answer runs the same code as the human’s:

- **A send-back over `max_back`** from a Stage other than Validate (“Send it back to Design”, “Keep it in Work”): resets the Stage’s send-back count and tells the Task Lead the answer. The Task Lead then moves the Task or not.
- **Validate at its limit, or a loop check that found a loop** (“Try again”, “Back to Design”, “Move to Review anyway”): TED moves the Task back to the Stage Validate named, back to Design, or on to the next Stage with the Findings still open.
- **The FAILED ask** (“Retry”): starts a fresh Task Lead Run.
- **CI stuck at Merge** (“Send to Task Lead”, “Keep waiting”, “Merge anyway”): sends the Task back to Work, waits again, or merges without waiting for the checks.
- **The idle Task Lead** (“Nudge again”): sends the Task Lead the nudge.
Two of these choices skip a check: “Merge anyway” merges without waiting for CI, and “Move to … anyway” leaves Validate with Findings open. The Coordinator reads untrusted Task text, so the daemon refuses both from it (`Tasks.humanOnlyChoices`) and shows them as `humanOnlyChoices` in what it reads. Only the human gives them.

- **Model unavailable** (“Use the default model”, “Change setting”): restarts the Run on the CLI’s default model, or only closes the question.
- **Closed in Linear** (“Archive”, “Keep going”): archives the Task, or only closes the question.

Still refused, whoever asked: the Linear team ask, which changes a machine setting and which only the app may answer (ADR 0090); and failure decisions, whose choices (“Accept this failure”, “Fixed”, “No longer applicable”) waive a failed Check or Finding for the Task’s validation, which is a judgement on evidence and not a way to unstick a Task. A free-text answer to one of TED’s questions is refused too: for the FAILED ask and CI stuck it would only post a Comment and leave the Task stuck, and a required choice makes the Coordinator name exactly what it did.

Three things keep this bounded. The Coordinator’s instructions allow these answers only when the human’s message names the Tasks or a clear group and says which choice to give, and tell it to quote each question and choice in its reply. The receipt names the question, the choice and the Task’s Stage and status before and after, and the stored before and after snapshots show a Stage change or an archive. The after state is read as soon as the answer returns, so work the answer starts in the background (a Run starting, a merge) may show only on the next read. And the daemon still cannot check what the human said; that rests on the instructions, as for every other action.

So the Coordinator can now move a Stage or start a Task Lead Run, but only as the effect of a choice on a question TED asked. There is still no action that names a Stage to move to.

## Every request on a Task, and resume

Tell and answer still left most of the Inbox to the human. A Task waiting at a Merge sign-off could only be told something, and a Comment at a Gate counts as a request for changes, so the Task went back to review. The human asked for the Coordinator to do what they can do for the Tasks of its Factory, when asked in its chat, and to work in batches: “answer the open questions and clarifications”, “approve what is ready”, “resume the stopped Tasks”. This replaces the limits in “Tell and answer” and “TED’s questions” above where they differ.

- **Answer** now closes any open request on the Task except three. `mayAnswer` gives the way to answer each kind, and the Coordinator reads it as `coordinatorMayAnswer`: a question takes a choice, a message or both; a question TED asked that has choices, a size check and a failure decision take one of their choices; a Gate request, a sign-off and a proposal take approve or request changes; a Clarify round takes one answer per question, or every recommended answer. The round’s questions are in what the Coordinator reads.
- **Still refused:** `permission` and `simulator` asks, which let an agent run a command outside its allowed set or shut down a simulator and are answered only through the app (ADR 0047, ADR 0085), and the Linear team ask, which changes a machine setting (ADR 0090). These are about the machine, not the Task.
- **“Merge anyway” and “Move to … anyway”** are no longer the human’s alone. `Tasks.humanOnlyChoices` is gone.
- **Resume** is a new action. It goes through `Tasks.coordinatorResume`, which is the human’s Resume without the drafts: a stopped or failed Task goes back into the queue and starts when a slot is free, so resuming more Tasks than there are slots needs nothing extra.
- Every answer runs the same code as the human’s (`answerAs`), so a Gate approval still checks the Task’s obligations, binds to the signed-off commit (ADR 0100) and starts the merge at Merge. None of them sends the line comment drafts; a request for changes at a Gate used to attach them always and now does so only for the human.
- The mark stays. Approvals, requests for changes and answers carry `coordinatorLine` at the start of their text. A round’s answers have no text of their own, so the line is stored as the answer’s `text` and put at the top of what the Task Lead is told.
- Round answers are capped like a message: 50 answers, 8,000 characters in all, each through `redactSecrets`.

**Judgement.** The first versions told the Coordinator never to choose an answer. A batch request only works if it can, so the human’s request now sets the kind of action and the Tasks, and may leave each answer to the Coordinator, which decides it from the Task’s description, brief and Comments and what the human said. It skips a request the facts don’t settle and reports it. It gives the answers that pass a check (a Gate or sign-off approval, “Merge anyway”, “Move to … anyway”, a failure decision) only when the request covers approvals, merging or failures.

**What this costs.** The daemon cannot check that the human asked, and the Coordinator reads Task text that agents and GitHub wrote. Before this, a Coordinator misled by that text could not approve a Gate or merge: the daemon refused. Now only its instructions stand between misleading Task text and an approval or a merge the human did not ask for. The human accepted that for the sake of batch work. What the daemon still enforces: the Coordinator’s own Factory, a current Task version, one receipt per action with the before and after state, the three refused kinds, the fixed mark, and no path to the human’s drafts, files, settings or credentials.

## Starting over

A conversation could only be stopped, and the Run that replaces a stopped one is handed the earlier conversation as history. There was no way to drop a conversation that had gone wrong or to start one that carries nothing from before. **New conversation** (`POST /factories/:id/coordinator/reset`, app only) does what Factory removal does to the Coordinator and nothing else: `Coordinators.reset` holds saves and launches the way removal does while still answering reads, waits for launches and actions, stops the Run, and deletes the saved row, pending messages, Conversation history and managed folders. The Factory and its Tasks are untouched, and the receipts go with the conversation; what the Coordinator did stays in each Task’s thread. The next message creates a new conversation. A message sent while the reset runs is refused.

## What the Coordinator reads

To group stuck Tasks it needs each Task’s open requests. `ted coordinator tasks` now returns, per Task, up to 5 open requests (ID, kind, who asked, Stage, title, the first 1,000 characters of the text, choices, when it was asked, and whether the Coordinator may answer it), a count of any more, and the current time, so it can tell how long each has waited. `ted coordinator task` returns up to 20 the same way, whatever page of Comments is asked for. Both stay inside the nonce-delimited untrusted context.

The list read every Task, Done and archived ones included, 30 to a page, so in a Factory with history the Coordinator paged through finished work to find open Tasks (TED-269). `ted coordinator tasks` now leaves out Done and archived Tasks unless it passes `--all`, holds 100 Tasks to a page, and takes `--stage` and `--status` (each repeatable), `--waiting` (Tasks with open requests) and `--search` (title text or a Task ID); filters combine. Each answer adds `matching`, the count of Tasks that match, and `stageCounts`, the Factory’s Tasks per Stage whatever the filters (with `--all`, Done too and an `archived` count). The query has one parser, `parseCoordinatorTaskQuery`, which the route and the CLI share; unknown or repeated single filters are refused.

## One conversation in the Run chat

The Coordinator screen first drew each Run in its own chat, with earlier Runs folded away under “Earlier conversation”, and had its own composer. Stop and a paused agent both end the Run, so the next message started a new Run and the conversation looked gone (KRI-278).

- `GET /factories/:id/coordinator/chat` returns one `RunChat` built by `Conversations.coordinatorChat`: every Run’s items in order, the instructions of the first Run only, a “From TED” row titled “New Run” where a replacement Run starts, and messages Stop canceled as `human` items with `unsent`. The summary is the newest started Run’s. The app draws it with `ChatBody` and the Run chat’s `Composer`, set to look like a Task’s thread: the human’s messages as Comment rows labelled “to the Coordinator” (`humanAs`, `audience`), TED’s rows and the Task receipts as event lines (`tedAs`), and one scroll position per Factory (`spot`), so a new Run doesn’t move it. Send goes to `POST …/coordinator/messages` and ■ to `…/coordinator/stop`. **Interrupt and send** and **Send now** are hidden, because a Coordinator message always waits for its queued turn.
- `GET /coordinators` lists each Factory’s Coordinator status for the sidebar, which reloads it on `coordinator-changed` and `agent-health-changed`.
- A message TED writes for the Coordinator (the continuation after a pause, and after Retry) is queued with `v2.RunMessageQueued { from: 'ted' }` and read back as `RunMessage.from`. It is never a `human` chat item: it shows as a “From TED” row once the agent has it, and not at all while it waits. In a prompt it sits under `## Message from TED`, which `chatItems` splits off the human’s text. Stop does not add it to the unsent messages. Coordinators saved before `from` existed may hold TED’s continuation among their unsent messages; `coordinatorChat` leaves out an unsent or queued message whose text is one of TED’s continuations, and shows a delivered one as a “From TED” row.
- Several pending messages can reach the agent as one turn, and each still shows as its own item with its own author. For an opening prompt, the Coordinator saves where each message sits in the prompt (`prompts[runId]`: message ID, time, author, start and end offsets) in its own row before the Run starts, and `chatItems` cuts the prompt at those offsets. For a resumed session, the turn is `coordinatorTurn(messages)`; `chatItems` rebuilds that text from consecutive delivered `RunMessage`s and accepts only an exact match. A Run started before this has no saved offsets and falls back to the headings.

## Creating Tasks

The Coordinator could reorganise Tasks but not add one, so “make a Task for this” or “break this into five Tasks” still went through the human. The human asked for the Coordinator to create Tasks the way they can, since its job is to make managing Tasks easier.

- `ted coordinator create` (`POST /coordinator/tasks`, `runToken: true`, Coordinator Runs only) makes one Task in the Coordinator’s own Factory. It may set the title, description, parent, blockers, source URL, Priority, Clarify depth, Task Lead and a place between neighbours, and start the Task with `--start`. Without `--start` the Task stays in Backlog. Attachments, repos, a Sentry ID and Autopilot are not offered: the first would need files, and only the app sets Autopilot.
- The title (up to 300 characters) and description (up to 8,000) are text the Coordinator writes, inline or on stdin; the command never opens a file. Both go through `redactSecrets` in the route.
- `Tasks.coordinatorCreate` runs `Tasks.create` for the Coordinator’s Factory as a non-app caller, so a source the Factory already tracks is refused and the Task’s Linear sync stays `ask`. Parent, blockers and neighbours must be Tasks of the same Factory. The parent is set with `Tasks.setParent` and the place with `Tasks.move` after the Task exists; if either fails the Task is kept and the receipt says what didn’t happen.
- Like every other action, create has an operation ID, a fingerprint and a receipt saved before dispatch, and one action makes one Task; several Tasks are several actions. `v1.TaskCreatedByCoordinator` (Task, Factory, operation) is committed with the Task itself and makes its `createdBy` `coordinator`. A retry of an operation whose receipt was saved before the Task finds the Task by that operation and finishes the receipt, so an interrupted create never makes a second Task. The receipt’s `taskId` is unset until the Task exists.
- The description carries no `coordinatorLine`; the creator kind shows where the Task came from, and the receipt in the Coordinator chat opens it.

## Drafting Automations

The user wanted to describe an Automation in a chat, such as “every morning, pull my new Linear issues”, and not fill in the Automations form by hand (TED-432). An Automation runs unattended, with its own prompt, Provider and schedule, so a misled Coordinator that could save one would act long after the conversation ends. The Coordinator therefore drafts Automations and never saves them.

- A new power, Manage Automations (`manage_automations`), gives a chat `ted coordinator automations`, `ted coordinator automation show`, `draft`, `change` and `delete`. The built-in Coordinator has it, a layer can give it to its own Agents, and the Planner can’t have it, like Manage Tasks. TED checks it with `requirePower` on the chat’s stored Agent for every route (`GET /coordinator/automations`, `GET /coordinator/automations/:id`, `POST /coordinator/automation-drafts`).
- A chat reads and drafts only for its own Factory. A draft carries the same settings as the Automations form, a Scheduled Check’s command included, and is read by `parseAutomationDraftRequest`, which refuses a Factory, `runNow` and `check.startTasks: true` and caps the name (120), prompt (8,000) and model (100). Every text field goes through `redactSecrets` before it is stored. The commands never read a file; the JSON comes from `--fields` or stdin.
- A draft saves only an `AutomationCard` on the chat row (`automationCards`, through `store.coordinators.save` and `v1.CoordinatorChatChanged`; no new event). The card shows in the chat and as a `source: 'coordinator'` Inbox request, with every setting for a new Automation, only the changed settings for a change, and the schedule’s next firings. `coordinators/automation-cards.ts` builds and carries out cards.
- Only the app-only `POST /coordinator-chats/:id/automation-cards/:cardId` (no `runToken`, no `fileToken`) answers a card. **Create**, **Save** and **Delete** call `Automations.create`, `edit` and `delete` with the app as caller, the same code the Automations screen uses; **Cancel** changes nothing. The existing `/automations` write routes still refuse every Run (`refuseRun`).
- A change or delete card holds a fingerprint of the Automation’s settings when it is drafted. If the Automation changed or is gone when the user answers, TED refuses the card, records why on it and changes nothing.
- **Start the Tasks it creates** is only the user’s: a draft can’t turn it on, a change may turn it off, and the card offers the checkbox for a Scheduled Check whose agent step isn’t `never`.
- Autopilot, the Coordinator’s `answer` action and the `daemon.json` token never answer a card. Archiving the chat cancels its open cards.
