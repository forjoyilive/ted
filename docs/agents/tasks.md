# Tasks

Rules for Tasks, Stages, requests, the queue, the Workflow, worktrees and the Task Lead (`packages/daemon/src/tasks/`, `workflow/`). They are part of `AGENTS.md` and bind the same way. Paths are from the repo root.

- A Task’s status, markers and activity line are chosen only in `packages/daemon/src/tasks/status.ts` from `TaskFacts`; a new input is a new `TaskFacts` field, and the app only draws what the Task carries.
- What a Stage does (Validate’s Checks and reviewer, Work’s hand-off, Merge, Cleanup, Clarify rounds, `--skip`, holding Stages) and where it sits relative to Work are decided only in `packages/protocol/src/stage.ts` (`@ted/protocol/stage`): code asks a trait helper such as `validates(stage)` or `stagePhase(stage, order)`, or `stageWith(trait)` for the id itself, never a Stage id comparison. An unknown id has no special work and is an ordinary working Stage. Plain checks for Done or Backlog, moves to a named Stage and event values stay as ids.
- A custom Stage is any id `isCustomStageId` in `stage.ts` accepts, written by hand in `order` with a Stage file `stages/<id>.md` in that layer or one below (`checkLayer`’s `inherited`, built with `inheritedFrom`); `StageId` and `AgentStageId` take any string, and `BuiltInStageId` lists the built-ins for tables that must cover them all. Name a Stage in Ted’s text with the Workflow’s `name(id)`, never by capitalizing the id. Find a Task’s next Stage only through `next` on the Workflow `taskWorkflow` returns, which `withRecorded` binds to the order recorded at the Task’s last Stage entry (`v4.TaskStageEntered`, `store.recordedStages`), so a Task whose Stage left `order` goes on to the first later Stage that still exists; pass that order to `stagePhase` and `clarifyIsOver` for a Task. The Board read (`boardStages`) is the Factory’s resolved Stage list, and `factory-stages-changed` says when it changes.
- What a Task is in the middle of (a transition, a hold, starting, Checks, deleting, hierarchy work, stopping for blockers, the merge watch) is recorded only in `packages/daemon/src/tasks/in-flight.ts`; new in-flight work is a new kind there, and busy checks ask it with `is` or `busy`.
- Only `packages/daemon/src/tasks/` starts Tasks or changes their Stage; it owns the order of git, commit and Run steps. A route open to Runs acts only on the Run’s own Task, except the Factory-scoped peer reads and plain peer notes in `tasks/peers.ts`; only a current Task Lead uses those, and only the Task Lead reports outcomes. Peer notes persist with their recipient Comment in one commit and use its delivery receipt; they reach working Leads through steering and replacement Leads through the normal Task start. A Coordinator Run reaches only the `/coordinator/tasks` routes, `/coordinator/requests`, `GET /coordinator/agents`, `/coordinator/automations`, `/coordinator/automation-drafts` and `/coordinator/archive|unarchive|delete|transfer` (the allow list in `server.ts`), for Tasks of its own Factory, and acts only through `Coordinators.act`, `Coordinators.create`, `Coordinators.remove` and `Coordinators.transfer` in `packages/daemon/src/coordinators/coordinators.ts`: create (`Tasks.coordinatorCreate`, recorded with `v1.TaskCreatedByCoordinator` in the Task’s own commit), start, move, tell (`Tasks.coordinatorTell`), resume (`Tasks.coordinatorResume`), done (`Tasks.markDone` with `coordinator`, only at Merge once every pull request merged) and answer (`Tasks.coordinatorAnswer`), which closes any open request on the Task the way the human’s answer would: a `question`, a Gate request or sign-off, a `round`, a `proposal`, a size check, a failure decision or a Task Lead’s archive request (with an open pull request it must say close or keep, and it can’t answer Archive when Tasks under the Task would be archived too). `mayAnswer` there decides how each kind is answered. Its `ted coordinator` commands never read a file, and its message text and round answers are capped and go through `redactSecrets` in the route. It never answers a `permission` or `simulator` ask, the Linear team ask or a move request, and it changes a Stage only as the effect of an answer or of done; what it posts starts with `coordinatorLine`, and a round it answers carries that line as the answer’s `text`. `Coordinators.remove` unarchives, and archives a Task with nothing to warn about, at once; a delete, or an archive of a Task with an open pull request, Tasks under it, Tasks it blocks or a working Task Lead, only saves a `CoordinatorConfirmation`, which shows as a card in the Coordinator chat and a `source: 'coordinator'` Inbox request. Only the app’s `POST /coordinator-chats/:id/confirmations/:id` (`Coordinators.answerConfirmation`, never `runToken` or `fileToken`) carries it out, through `Tasks.archive` and `Tasks.delete`, after refusing each Task that changed since the card was shown. `Coordinators.transfer` (`ted coordinator transfer`, with a reason) never moves a Task itself: it posts the same move request a Task Lead posts, through `Tasks.coordinatorAskMove`, and records a receipt; `transfer` confirmations saved before that still show and can be answered. With Manage Automations a chat reads its own Factory’s Automations and drafts new ones, changes and deletes (`/coordinator/automations`, `/coordinator/automation-drafts`); a draft is only an `AutomationCard` on the chat row, built and carried out by `coordinators/automation-cards.ts`, and only the app’s `POST /coordinator-chats/:id/automation-cards/:id` (never `runToken` or `fileToken`) carries it out through `Automations.create`, `edit` and `delete`, refusing a change or delete whose Automation changed since the card was shown. A draft never turns on `check.startTasks` or runs the Automation; the `/automations` write routes keep refusing Runs.
- A Comment’s files are recorded with `v1.CommentAttachmentAdded` in the Comment’s own commit and point at bytes already in `TED_HOME/attachments`. The human’s come from `POST /attachments` (the app, or the terminal with the `daemon.json` token); a Run uploads through `POST /tasks/:id/attachments` and may attach only files it uploaded or its own Task already has. An Automation Run uploads through `POST /attachments` (`Tasks.uploadForCreate`), and `POST /tasks` takes from a Run only files it uploaded itself. Code that deletes attachment files checks `store.filesInUse()` first.
- A request is a non-`note` Comment; it leaves the Inbox only through one `v1.CommentAnswered` event (answered, approved, changes requested or withdrawn). Gate requests are posted by `ted outcome advance`, never by `ted comment`, except the Merge sign-off, which Ted posts once CI passes; the user answers them unless bounded Autopilot approval applies. Only Clarify and Design can `ted outcome advance --skip`. A Clarify round is one `round` Comment posted with `ted ask --round <file>`; Clarify’s effective Gate setting applies at every depth (KRI-362). Talk it through happens in the Task Lead’s own Run chat; only `ted ask --close --summary <file>` closes a talked-through round, as `answered` with `talkedThrough`, and messages typed during a talk add no steering thread lines. The size check is a `question` with a `sizeCheck` field posted by `ted clarify too-big`; Ted carries out the human’s choice itself, and Split it’s pieces are created only by `answerProposal` in `tasks/tasks.ts` from a `proposal` Comment (`ted task propose --file`), using `planProposal` in `packages/protocol/src/proposal.ts`, which the app’s card uses too. Split it and a plan’s Create Tasks make every row a child Task of one parent; only `finishParent` in `tasks/tasks.ts` moves that parent to Done without a pull request, once a child has merged and none is left unmerged, and only for a Task with a `v1.ChildTasksCreated` record and no changes of its own. `createProposalTasks` creates every piece without a start request: a blocked piece starts after its blockers merge only through the Factory’s automatic Backlog start. A test that walks a Task to Done commits `.ted/workflow.yaml` with `order: [intake, work, merge]` or approves the Gates, since Design and Review have them by default.
- A request a working Run asks for (not a `note` or `permission`) is held until its turn ends: `v1.RequestHeld` in the Comment’s commit, then `v1.RequestReleased`, which moves its `createdAt` to the release time, from `tasks/held-requests.ts` when the Run’s turn ends (`turnEnded`, not `settled`: a queued message can start the next turn before the Run is ever seen idle) or it ends, or after 5 minutes. While held it stays out of `waiting()`, `listOpenRequests`, Task facts, `GET /tasks/:id/comments` and Comment events; anything new that shows or answers requests for the human leaves out `held` Comments too. Never reorder the thread instead. `vitest.config.ts` sets `TED_HOLD_REQUESTS_MS` to `0`, so tests release held requests at once; a test about holding passes `startDaemon`’s `heldRequests: { maxMs: holdAtMostMs }`.
- A Task Lead asks to archive its own Task only through `ted task archive` (`POST /tasks/:id/archive-request`, `requestArchive` in `tasks/tasks.ts`, current Task Lead only), which posts an `archive` question with Archive and Keep it and the reason and pull request recommendation in `v1.CommentArchiveAsked`. Archive is carried out in `tasks/request-answers.ts` through `archiveAsked`: the hierarchy check, then the answer, then the app’s archive with the answer’s options, so the request reads as answered. Autopilot approves it with the recommendation unless Tasks under it would be archived, and reaching Done withdraws it.
- A Task Lead asks to move its own Task to another Factory only through `ted task move` (`POST /tasks/:id/move-request`, `requestMove` in `tasks/tasks.ts`, current Task Lead only), and a Coordinator through `ted coordinator transfer`; both post one `question` with Move and Keep it and a `move` field (`v1.CommentMoveAsked`). Only the user answers it: never Autopilot, `ted autopilot answer` or a Coordinator. Move is carried out in `answerMove` in `tasks/request-answers.ts`: check the plan key the card sent, record the answer, then `Tasks.moveToFactory`, so the request reads as answered. The plan for an answer leaves out only the request being answered (`GET /tasks/:id/move-plan?request=`); a move that withdraws a Coordinator’s open move request tells its chat. `ted factories` (`GET /factories/others`) lists the other Factories for a Task Lead.
- A snoozed Inbox request is a `requestSnoozes` row (`v1.RequestSnoozed`, `v1.RequestSnoozeCleared`), one table for Task Comments, Planning requests and Automation questions. `TedStore.waiting()` leaves snoozed requests out and `TedStore.snoozed()` lists them; `inbox-changed` carries both. The answer events’ materializers delete the row, so a new way to answer or delete a request needs no extra step. A request returns only through a commit (`store.returnDueRequests`, called by the snooze timer in `tasks/tasks.ts` and at start), never by comparing the clock in a read. Only the app snoozes (`PUT /requests/:id/snooze`, no `runToken` or `fileToken`); the Coordinator can’t. A Task whose open requests are all snoozed gets `requestsSnoozedUntil` in `TaskFacts`. Preset times come from `requestSnoozePresets` in `packages/protocol/src/time.ts`. Tests drive the clock with `startDaemon`’s `snoozes.now`.
- A setup Task is a Task with `setup: true`, created only by `Tasks.setUpFactory` (after cloning) or `Tasks.newSetupTask` (`POST /factories/:id/setup-task`, app only). Resolve the Workflow for a known Task with `taskWorkflow`, never `resolveWorkflow(factoryOf(task))`, so a setup Task gets `setupWorkflow` (Clarify at grilling depth, Design and Review Gates on, the default branch, `defaults/setup.md`). Its Validate runs only the branch’s Checks that match a passing Check in the approved proposal. Its branch may hold only the Agents the approved proposal suggested, minus those the user removed with the approval (`removedAgents` on the answer): `requireSetupAgents` in `tasks/tasks.ts`, through `setupAgentDifferences` in `tasks/setup-agents.ts`, refuses `ted outcome advance` from Work or Review and the Review approval while the Agent files differ, or while an approved Agent’s id is one Ted’s defaults or the Library already define (their settings would fill in what the branch leaves out). Tests that add a Factory through `POST /factories` get `<KEY>-1` as the setup Task; a Task created while cloning is `<KEY>-2`.
- A start the user didn’t click (the automatic Backlog start, `wakeTask`, the Coordinator, an Automation) passes a `StartCause` to `queueStart`, which `store.queueTask` and `store.startAfterPlanning` commit as `v1.TaskStartCause` with the start; the thread shows the cause in place of “Task started”. A new automatic start passes one too.
- Starting a Task only queues it; the pump in `packages/daemon/src/tasks/tasks.ts` starts queued work when a working-Run slot is free, in the order `queueOrder` gives (`tasks/queue.ts`). New work that needs a slot (sub-agents, Automation Runs) goes through that queue and counts in its slot holders; never start it around the queue. Runs that wait in the queue outside a Task (Planning chats, Automation Runs, Automation drafts, Coordinators, Side chats) start once through `startGuard` in `tasks/queued-runs.ts`; Plans, Automations and drafts also build their queue entry with `queuedRuns` and track usage limits and failed sign-ins with `runLimits` there, and Plans and Automations decide resume-once with `afterProcessEnded`. An owner whose queue reads its start guard creates it with `startGuard` and passes it to `queuedRuns`, because registering the queue entry pumps at once. A new kind of such Run uses these, never its own copy. Chats (`chatKinds` in `packages/protocol/src/slots.ts`: Coordinator, side chat, planning chat) also go through the pump, which holds them only for a full disk or a paused agent kind: `startsNow` starts them past the limit, Factory caps and the busy hold, and neither it nor `slotUse` counts them as working. With the `waitWhenBusy` machine setting on (the default), `startsNow` also holds every new start while the computer is busy, except the first entry when nothing holds a slot, a slot handoff, a Task Lead continuation after Checks or an answer (`skipsBusy`, from the `after` a held Task Lead message records; continuations held in the last 10 minutes go first), and a Task whose Stage skips the hold, as a continuation or a queued Task. Each working Stage sets two keys in `workflow.yaml`: `stages.<id>.priority`, a whole number, 0 or more, and `stages.<id>.skip_busy_hold`, `true` or `false`; Backlog and Done take neither, because no Task waits in the queue there. Unset, Cleanup ranks 2 and skips the hold, Merge ranks 1 and every other Stage 0, from `defaultStagePriority` and `skipsBusyHoldByDefault` in `stage.ts`, so a merged Task finishes and frees its worktree and Apps before new work starts. Rank never lets a Task past the busy hold, the limit, Factory caps, the disk hold or agent pauses. Among Tasks, `queueOrder` sorts by the Stage’s rank first (higher first), then continuations before new starts, then recent continuations, then Task Priority, then rank; setup Tasks, sub-agents, chats and Automations keep their place ahead of Tasks. Held and revived Task Leads sort as continuations in the same order, so a Task in Work waiting to relaunch doesn’t take the last slot from one in Merge. The rank and the skip come only from `stageQueue` in `tasks/queue.ts`; the pump reads each Factory’s Stage settings from the cache `remember` fills beside its cap (the pump is synchronous and the Workflow resolves asynchronously; until a Factory’s Workflow first loads, the defaults apply), and publishes `skipsBusy` in `taskPlaces`, which the store passes to `TaskFacts` so comment delivery and the Task’s wait reasons know whether the busy hold stops it. A queued Task keeps its place (“Queued · 2nd”) while the busy hold stops it, so the user can still see the order Tasks will start in; disk and Provider holds still replace the place with their reason. The busy hold shows once, as the sidebar strip above usage, and never stops a working Run. Busy is decided only by `nextBusy` in `packages/daemon/src/busy.ts`, through the one `createBusyHold` the daemon hands to the queue, Scheduled Checks and device slots. It reads the share of CPU in use since the last reading (from `os.cpus()` times, not the load average, which lags by a minute) and the share of memory in use, against `busyMarks`: a CPU hold starts after two readings above 90% at least one check (`busyCheckEveryMs`, 15 seconds) apart, so a short spike doesn’t hold, and lifts below 75%; a memory hold starts at one reading above 90% in use, because running out of memory kills processes, and lifts below 80%. While work waits the pump reads every check, and a first high CPU reading holds new starts until the next one decides. Other queue events may check sooner; `createBusyHold` reuses readings less than a second old. `createCpuReader` needs a baseline: on its first reading, or after a gap over 60 seconds, it takes a second sample one second later and reports the share between the two, so the first Task queued after a quiet spell is held like the rest; checks made during that second share the one sample. An unknown resource never holds work. `nextBusy` starts CPU confirmation over after a gap longer than the greater of 60 seconds and four checks, so separated spikes don’t confirm a hold. The hold carries both readings, which resources hold, `since` and `checkedAt`, and the sidebar strip shows them in `BusyCard` on hover or focus; an agent’s simulator or emulator boot waits in the first-come line while busy, a human’s ▶ doesn’t. `TED_LOAD_FILE` and `TED_MEMORY_FILE` name files holding the CPU share in use and memory figures Ted should see; `vitest.config.ts` points every test at fixtures that never hold, and `startDaemon`’s `load` option overrides them. With no stored `maxWorkingRuns`, the store’s default is `defaultWorkingRuns` of total memory.
- A Task’s rank orders the Board and the List’s Manual sort after Priority; in the queue it breaks ties after Stage priority, continuation order and Task Priority. Clients reorder only through `POST /tasks/:id/move` with the Tasks it now sits after and before; `placeBetween` in `tasks/order.ts` picks the rank and Priority. Never send or compute a rank in a client.
- A sub-agent is a Run with a `parentRunId`; a Task’s Task Lead Run is its newest Run without one. Sub-agents start only through `packages/daemon/src/tasks/sub-agents.ts`, as `sub-agent` entries in the queue, and only the current Task Lead Run may start, wait for, message or stop them.
- `ted task create` with a Run token works only from an Automation Run, in its own Factory, and records the Task as created by that Automation, or from the current Task Lead of an open Task (`leadCreator` in `tasks/tasks.ts`): its own Factory, initially in Backlog (`backlogEligible`), no `--start` or blockers, the caller checked again before the save, at most `maxTasksPerLead` (10) per Task, with a reminder in the output past `suggestedTasksPerLead` (3), an Asana or GitHub source without its subtree, recorded with `v1.TaskCreatedByTaskLead` and `v1.TaskLeadCreatedTask` in the new Task’s commit; `--child` makes it a child that the creating Task waits for through `shouldStopForBlockers`, and `createTask` queues that child at once (`queueAndAnswer`, start cause `task-lead-child`), so a repair the Task Lead files for a failure starts without the user; other Tasks a Task Lead creates stay in Backlog. The child stays in Backlog too, with a note on the creating Task, when `runsInBypass` holds (starting an unsandboxed agent needs a person) or when the creating Task was itself created by a Task Lead (so children can’t start each other without end). A `--source` already tracked in the Factory (open, archived without merging, or Done) is refused for every caller except the app, matched through `sourceKey` in `tasks/sources.ts`; `--follow-up <id>` creates a Follow-up that shares the source.
- The preamble and built-in Stage files are Markdown in `packages/daemon/src/workflow/defaults/`; the preamble names only `ted` commands that exist.
- The Workflow is resolved only through `Workflows.resolve` in `packages/daemon/src/workflow/workflows.ts`, at each Stage entry; every Stage entry records the layers and Stage file it used. The Library lives in `TED_HOME/library/`, the Factory layer is `.ted/` on `origin/<default branch>`. `pnpm ted workflow check [<path>]` validates a layer.
- A Task’s Task Lead field (`lead`: agent, model, effort) is compared with its live Task Lead Run in `tasks/`. A saved change applies only when the human clicks **Restart now to apply changes** (`POST /tasks/:id/lead/restart`, `restartNow` in `tasks/lead-lifecycle.ts`, which interrupts a working turn first), when the Task enters a new Stage (`move` sets `leadRestartPending`), when the model is unavailable, or when a new Task Lead Run starts; never at an ordinary idle point. A model or effort change goes through `RunManager.restart`, which restarts the agent inside the same host and the same Run. An agent change stops the Run and starts a fresh one whose prompt carries the Task brief and a plain-text copy of the old conversation (`conversationText` in `tasks/carry-over.ts`, which cuts the middle of a long one and has Ted post a note saying so). `pnpm ted task lead <id> claude|codex [--model] [--effort]` sets it.
- A Task’s worktree lifecycle (copy, `setup`, `teardown`, removal) lives in `packages/daemon/src/tasks/`; every command run in a worktree gets `worktree.env` minus the reserved names in `isReservedEnvName` (`workflow/check.ts`), a resumed setup runs the command recorded when it started, and copy never reads outside the local folder or writes outside the worktree. Before a start makes a worktree, `clear` in `tasks/local-lifecycle.ts` looks at its path: it removes a leftover only when it is a worktree of the repo’s clone at exactly that path with nothing uncommitted (read with `workingChanges`) and no commits beyond the base, and stops the start for anything else that is there; never delete a leftover that holds work, and a start that fails removes the worktree and branch it made.
- Before a Task’s worktree is removed (`finish` in `tasks/tasks.ts`, `cleanFolders` in `tasks/local-lifecycle.ts`), Ted ends every process whose working folder or executable is inside `TED_HOME/worktrees/<TASK-ID>/` or `TED_HOME/sandbox/<TASK-ID>/`: SIGTERM, then SIGKILL after 5 seconds to those that still match. Processes are found only by `processPaths` and matched only by `processesInside` in `packages/daemon/src/leftover-processes.ts`, against a folder `taskFolder` built from the root’s real path without following links; never match by command line or open file, and never by a path outside those two roots. Every `lsof` call (here and in `lockHolders` in `lock.ts`) goes through `openPaths`, with `-b` and no file names, so Ted’s own work never touches an attached drive and makes macOS ask about removable volumes. At start, `sweepLeftovers` in `tasks/leftovers.ts` does the same for every Task-ID-shaped folder under those roots that belongs to no Task or to a Done or archived Task whose worktrees are removed, and never for an open Task or `TED_HOME/plans/`.
- List a Factory’s repos only with `factoryRepos` in `packages/daemon/src/tasks/repos.ts`, and match a Task repo to its settings by owner/repo (`repoEntry`), never by `name`. A Task’s Repos field changes only through `PUT /tasks/:id/repos` (`ted task repos set|add|remove`); in a multi-repo Factory every Task Lead Run starts in the Task folder `TED_HOME/worktrees/<TASK-ID>/`. Multi-repo tests point `https://github.com/` at local bare repos with `GIT_CONFIG_*` `insteadOf`.
- A new thread event line is an entry in `taskLogEntries` (`store/schema.ts`) and a case in `tasks/thread.ts`; never log secrets or prompts there. The human’s Comments reach the Task Lead only through `Tasks.comment`, which records delivery, and the next Run picks up undelivered Comments and held answers. The label under an undelivered Comment comes from the Task’s `commentDelivery`, chosen in `tasks/status.ts`.
- A Task’s title and description change only through `Tasks.edit` (`PUT /tasks/:id`, app-only), which records one `v1.TaskEdited` and tells a live Task Lead the diff. Read description versions and the Original request through `TedStore.descriptionVersions`, never from `tasks.description` alone.
- A Task Lead Run that ends without Ted stopping it, or sends no output for `stallAfterMs` while Working, goes through `recover` in `packages/daemon/src/tasks/lead-lifecycle.ts`: resume the same Run with `RunManager.revive`, else a fresh Run from the brief, else Failed with the FAILED ask. Stop a Run only through `RunManager.stop`, which records the stop so it isn’t counted as a failure; `TED_STALL_AFTER_MS` shortens the no-output clock.
- When Ted stops a working Task Lead as it goes down, the Tasks module records `v1.TaskStoppedByTed`: `Tasks.stoppingForQuit` before `runs.stopAll()` in the `/shutdown` route, or `RunManager`’s `stoppedOutside` observer for a host that was ended without the daemon asking. `store.tedStops()` is the offer the app’s `RestartStoppedDialog` shows, and only the app-only `POST /ted-stops/answer` (`Tasks.answerTedStops`, `v1.TedStopAnswered`) restarts those Tasks, through `store.resumeTask` and the pump. Never restart them automatically, under Autopilot either, and never mark that route `runToken` or `fileToken`. The one exception is an answer: any answer to one of the Task’s requests (the human’s, Autopilot’s or the Coordinator’s) resumes a Task that `interrupted` in `tasks/tasks.ts` allows, through `resumeAfterAnswer` after `answerAs` (at Merge, only an answer to the Task Lead’s own request, `leadAskedAtMerge` in `tasks/status.ts`), never a Task the human stopped. The human’s own Comment does the same through `resumeAfterComment` when `taskWakesOnComment` in `tasks/status.ts` allows it, even with a request open; the Coordinator’s `coordinatorTell` never wakes a Task.
- Read a Task’s working tree (changes, diffs, uncommitted work) only with `workingChanges` in `git.ts`, which works in a scratch git directory with a fresh index, or with `workingTree` there when only the tested context (`HEAD`, base tip, tree and merge-base) is needed, which runs the same reads without the diffs; never run `git diff`, `git status` or `git add` inside a worktree, where the agent-writable config and index apply. The app shows them through `useTaskChanges` in `renderer/changes.ts` and the components in `ChangesSection.tsx`, `DiffViews.tsx` and `DiffTable.tsx`; line comments hook in through `DiffSeams`. Code in `tasks/` that needs the same worktree more than once in one operation (a move, `ted outcome advance`, the start of a hand-off, Validate entry, an obligations read) makes one `worktreeReads()` from `tasks/worktree-reads.ts` and passes it down as `reads`: it keeps one `workingChanges` result per worktree and base, and reads again when `HEAD` or the base tip has moved. It doesn’t see an uncommitted edit made after its read, so never keep one past its operation or across anything that can change the worktree (a Check run, a commit, a rebase, `adoptLatestBase`), and call its `forget()` after a wait on GitHub (`baseConflict`’s fetch, a failure snapshot’s pull request read). A failure snapshot (`failureSnapshot`, the tested context `sameTested` compares) never takes one: it reads the worktree itself with `workingTree`, after its GitHub read. The coverage noted before hand-off Checks, `adoptHandOff`, `bindApproval`, `guardAutopilotAnswer` and the merge watcher each read on their own too.
- Any new path that posts a human Comment, or answers a request with the human’s words, passes the Task’s line comment drafts (`drafts(taskId)` in `tasks.ts`) to `store.postComment` or `answerRequest`; Approve never does, and neither do the Coordinator’s `Tasks.coordinatorTell`, `Tasks.coordinatorAnswer` and `Tasks.coordinatorResume`, which must never send the human’s drafts.
- The first time a Task enters Work, `adoptLatestBase` in `tasks/tasks.ts` moves each worktree to the tip of its base branch: `move` calls it before the Stage changes when `firstWorkEntry` (`tasks/latest-base.ts`) finds no earlier Work entry, and `launchQueued` calls it for a Task held before Work by preparation (`store.heldBeforeWork`), when it really starts. Never on a send-back or a later entry. It moves a repo only as a fast-forward (`baseStep`): `HEAD` is an ancestor of the tip `fetchBranch` read, and the clone’s `origin/<base>` contains that tip, because the Changes view and `touchesSettings` diff against that ref; then `moveBranchTo`, whose `reset --keep` refuses to overwrite local changes. It never blocks the move: every failure is logged with `redactSecrets` and the Task enters Work as it was. Each repo that moved is one `v1.BaseBranchAdopted` event and a thread line, and the Task Lead is told through `latestBaseNote`, added to the Work entry message or, with no live Run, to the next Task Lead prompt; the note names no file.
- Effective Autopilot uses the Task’s `on` or `off` choice, or the `overnightMode` machine setting for `inherit`. While effective Autopilot is on, ordinary Gates set by the Workflow or a Task’s own overrides count as off. Only `taskWorkflow` applies it (`withoutGates`, before forced Gates and `setupWorkflow`), and every Gate check goes through `gateOn` in `tasks/tasks.ts`; never read `stages[…].gate` of a Task’s Workflow elsewhere to decide a Gate. Forced Gates and a setup Task’s Gates stay on. Posted routine requests may be answered by Autopilot through the normal request transition; protected requests stay manual. A skipped Gate is one `v1.GateSkippedOvernight` event, which also keeps a merge started overnight going after the mode is turned off. A Task whose primary-repo changes touch `.ted/` (`touchesSettings` in `tasks/checks.ts`, read with `workingChanges`; unreadable counts as touching) keeps its saved Gates and gets the Review Gate forced on while the mode is on: any code that decides a Gate or moves a Task forward resolves the Workflow with `gateWorkflow`, not `taskWorkflow`, and a Gate kept this way is one `v1.GateKeptOvernight` event. With the `reviewUnvettedTasks` machine setting on (the default), a Task an Automation created or whose GitHub issue has outsider text keeps its Gates the same way, decided only by `unvettedReason` in `tasks/autopilot.ts` before the `.ted/` check. At Merge such a Task merges only on an approval bound to the signed-off commit (`v1.GateApprovalBound`, recorded by `bindApproval` when a Review or Merge Gate is approved); never cache that decision across a change of the worktree’s HEAD, the signed-off commit or the worktree’s `.ted/` folder, and turn GitHub auto-merge off before waiting for a Merge sign-off. Reads (`GET /tasks/:id/gates`, Factory settings, Library, Board) keep the saved values and add `overnight: true`. Only the app sets a Task’s Autopilot choice. Autopilot accepts recommended round answers and approves routine sign-offs; only the current Task Lead may use the own-Task ordinary-question answer route, with a recorded explanation. Automatic answers recheck effective mode and eligibility under the request lock and record Autopilot attribution with the answer. Setup questions, rounds and sign-offs, talked-through rounds, permissions, failure decisions, size checks, split proposals and missing-access requests remain manual. Talked-through rounds close only through the summary-close command described above.
- A Task is reset only through `Tasks.reset` (`POST /tasks/:id/reset`, app only, never `runToken` or `fileToken`), for a Task `resetRefusal` in `packages/protocol/src/task.ts` allows: started, and not Done, archived or holding a merged pull request. It refuses while the Task’s Checks run, stops the Task, closes its pull requests and refuses if one stays open, removes its worktrees with the same `clearing` path Archive uses, deletes its branch on GitHub and in the clones (a missing branch is fine, any other failure stops the reset before anything in the store is cleared), and then commits one `v1.TaskReset`, whose materializer deletes the Task’s thread and code rows and sets the Task row back to Backlog with the first description version; the Task then rejoins the queue at its old rank. It keeps the `v1.Linear*` and `v1.Tracker*` Task log rows (`trackerSyncLog`), because the Task’s tracker sync consent is read from them, and the thread draws nothing from before the last `v1.TaskReset`. Anything new that stores data per Task must be cleared in `v1.TaskReset` as well as `v1.TaskDeleted`, unless a reset Task should keep it.
- A Task moves to another Factory only through `Tasks.moveToFactory` (`POST /tasks/:id/move-to-factory`, app only, never `runToken` or `fileToken`; or the user’s Move on a move request), for a Task `moveRefusal` in `packages/protocol/src/task-move.ts` allows, with every Task under it. `planMove` in `tasks/tasks.ts` builds the one plan that both `GET /tasks/:id/move-plan` and the move use. A started Task is discarded the way Reset does (`discardForMove`), then one commit from `store.moveTask` holds `v1.TaskMovedToFactory` for each Task, the removed blocker links, the parent link, the withdrawn requests and Ted’s notes. The Task keeps its UUID and gets the new Factory’s number; the old Factory and number stay in `taskMoves`, which numbering counts and `taskRowByDisplayId` falls back to. The materializer keeps the thread, Runs, Task brief, description versions and attachments, and clears the code rows and the `trackerSyncLog` Task log rows, so tracker sync asks again. Anything new that stores data per Task about its code or Factory must be cleared in `v1.TaskMovedToFactory` too. A moved started Task’s first Task Lead gets the old conversation through `movedPickUp`.
- A Task shell is a PTY that only `packages/daemon/src/shells.ts` starts, through `Tasks.worktreeAccess` (the worktree and its `worktreeCommandEnv` environment, never `TED_RUN`); the app reads its output only through the app-only long-poll route. **Open in editor** starts editors only through `packages/daemon/src/editors.ts`, with paths and lines as separate arguments and never a shell string; a file must resolve inside the worktree. Tests put fake editor launchers on `PATH`, and `TED_EDITOR_APP_DIRS` (empty in `vitest.config.ts`) names the folders searched for macOS app bundles.
